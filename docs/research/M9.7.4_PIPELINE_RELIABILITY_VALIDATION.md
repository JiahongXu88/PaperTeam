## 1. Root Cause（五条链路，审计确认）

1. **P0-1**：`project.language` 是「死路」字段——前端可填、后端可存，但
   workflow / Researcher / Writer / Reviewer prompt / skill 路由**零消费**
   （`resolveSkillIds` 只看 role+contextScope）。语言实际由「idea 文本中的
   偶然措辞 + 中文系统 prompt 反向拉力 + zh skill 无条件注入」博弈决定
   （M9.7.3：A 臂 4/4 中文稿、B 臂 3/3 英文稿、英文稿 × 中文 style skill
   → review 7/7 协议失败）。
2. **P0-2**：`riskScore` / `scores` 是仅有的两个「缺失即抛
   AgentRunFailedError」的 mode 专属字段；抛错 → transient → **整个
   review.run stage 原样重跑**（三路 fan-out 全部重来、prompt 逐字节相同、
   validator error 从不反馈模型）→ maxAttempts（2）耗尽 → run failed。
   几十分钟 run 因单字段缺失死亡。
3. **P0-3**：DOI-only 查询（`importDoi` → `resolveMetadata({doi})`，无
   title）下 `scoreCandidate` 对 provider 回显 DOI 即采信（tier=doi），
   `compareFields` 因 `query.title === undefined` 跳过 title 比对 →
   OpenAlex 对 arXiv DOI 的索引错配被标成 `match`；且 `resolveMetadata`
   的 mismatch 分支仍返回 record → `importDoi` 无条件 `Object.assign`
   写库（错误论文 title 以 resolved 水位线毒化）。全链路无
   `10.48550/arxiv.X ↔ arXiv:X` 交叉校验。
4. **P1-1**：Discovery 候选停 `pending_review` 是 D-0033/D-0035 红线设计
   （promote 只能用户手动，全仓唯一调用方 = HTTP 端点），**不是 bug**；
   缺的是 workflow 在写作前从未把「32 条候选待审 vs verified 证据只覆盖
   3 篇」呈现给用户——两个既有 HITL 都不携带该事实，coverage 天花板
   3/20≈15% 的杠杆（用户 promote）从未被触达。
5. **P1-2**：research.json 的 bibliography 每轮**整字段 REPLACE**（代码不
   累积）；20→30→36 的膨胀主因 = research 会话 transcript 跨 run 保留 →
   模型每轮「复述上轮 + 再补新的」，prompt 无旧清单约束、无数量纪律；
   B 臂终态 36 条经逐条核对全部是真实不同文献（非重复入库）。次因 =
   canonical 合并的 title/year 判等口径过弱（variant 成对存活，机制
   存在、本轮数据未触发）。

`backend/src/project/language.ts`（`normalizeManuscriptLanguage` →

     润色链是 zh 专用设计：zh skill + 中文 invariant 哨兵词表；en 静默

**English 下 style review 的准确行为**（任务书 §2.2 要求记录）：
- skill 层：`review/style` 会话不注入 `academic-style-zh`（skill 集为空，

- prompt 层：style modeSpec 切换为英文版检查项（vague summaries /
  repetitive phrasing / mechanical parallelism / … 与中文版逐项对应，
  riskScore JSON 契约不变）；fact / academic 指令保持中文（M9.7.3 实测
  对英文稿工作正常），仅要求 finding 文本跟随稿件语言。

## 3. Reviewer Output Repair（P0-2）

`ReviewerService.reviewMode` 改为**有界 error-feedback 修复循环**：

- 首次输出 → `extractJsonObject` + `parseModeReview`；
- 结构化违约 → `StructuredOutputError`（`outputParsing.ts` 新增子类，
  `kind: json_parse | missing_field | wrong_type | invalid_enum |
  invalid_value` + `field`，向后兼容 `AgentRunFailedError`）→ 构造
  repair prompt（**具体校验错误清单 + 上一轮输出原样注入 + 「保留审稿
  内容、只补字段、不重做审稿」**）→ 同会话再调用；
- 上限 `REVIEW_REPAIR_MAX_ATTEMPTS = 2`（original + 2 = 3 次/model），
  耗尽后如实抛错（错误信息含修复历史）；
- 修复成功 → `result.repair = { attempts, errors }` 随
  `reviews/review-r*-*.json` 落盘（诊断留档）；
- **任务失败（status != completed，模型/网络层）不进 repair**——直接抛出
  交给 Stage transient retry（两层重试语义不混淆）；
- **禁止伪造默认分数**：riskScore / scores 只能由模型补齐，代码零兜底
  （`reviewerVerdict.test.ts:79` 的「不兜底」红线语义保持）。

是否仍有字段缺失就杀 run 的路径：**有——且是有意的**。repair 耗尽
（3 次模型输出全部违约）后 stage 仍按 transient 失败重跑
（maxAttempts=2 → 全链路最多 2×(1+2)=6 次模型调用/mode）后 run failed。
这与「几十分钟 run 不该死于单次字段缺失」的目标一致：单次/两次偶发
违约被 repair 吸收；系统性违约（如修复前的英文稿 × zh skill 环境）仍
失败——但该环境本身已被 P0-1 消除。

## 4. Metadata Identity Hardening（P0-3）

三层防线（全部确定性，`METADATA_VERIFICATION_VERSION` v3 → v4）：

1. **arXiv DOI ↔ arXiv ID 互转**（`sources/identity.ts` `arxivIdFromDoi`）：
   `10.48550/arxiv.2210.03629` → `2210.03629`（老式编号同样覆盖）；
   `compareFields` 新增 arxivId 交叉校验——candidate 声称的 arXiv ID 与
   DOI 推导不一致 → mismatch。
2. **DOI-only query 的 arXiv 权威交叉验证**（`ScholarlyResolver.resolve`）：
   query 无 title 且 DOI 可推导 arXiv ID 且 provider 判 match 时，用
   ArxivLookupProvider（arXiv 官方 API 实体查询）取权威 title 比对：
   - title 相似度 < 0.92 → **mismatch**（attempts 记 `arxiv-authority`）；
   - arXiv 权威源不可用 / 查无此 ID → **unresolved**（保守：宁可
     unresolved，不给 wrong match）；
   - 一致 → match（attempts 记交叉验证通过）。
3. **mismatch 不再写库**：`resolveMetadata` 的 mismatch 分支不再返回
   record——`importDoi` / `enrichMetadata` 的 `Object.assign` 路径天然
   跳过，错误论文字段无法以 resolved 水位线入库（旧行为「mismatch 仍
   可用于元数据补全」正是毒化通道；行为变更见 §8 测试更新）。

**修复的潜伏缺陷**（审计中发现）：`scoreCandidate` 无 arXiv ID 精确命中
tier——无 title 的 arXiv-only query 全部 reject（M9.7.1「arXiv enrich
未定论」的根源之一）。现 arXiv ID 精确命中与 DOI 同级（tier=doi）。

**如实边界**：普通 DOI（非 10.48550/arxiv.*）的 DOI-only query 保持现状
（无独立权威源可交叉验证，实体查询错配风险低；未在本轮扩大到双源
确认——S2 限流环境下 unresolved 率会不可控上升）。

## 6. Bibliography Lifecycle Fix（P1-2）

三层治理（replace 语义保持不变——它本身不是 bug）：

1. **prompt 侧（治主因）**：重跑时 `buildResearchPrompt` 注入上一轮
   bibliography 清单（title | year，≤30 条）+ 总量纪律（「只列与课题最
   相关的文献，总量 ≤30；以上一轮为基础，仅补充真实新发现；同文献不得
   以不同 key / 年份形态重复」）——直接抑制「会话记忆复述 + 每轮扩充」。
2. **同轮去重**：`readBibliography` 在 key 去重之外增加
   `compactTitle|year` 精确判等折叠（先出现者保留 = LLM 相关性序）；
   year 一方缺失不折叠（年份未知不构成同一性）。
3. **canonical 层**：`mergeArtifactBibliography` 增强——库内条目比对从
   「compactTitle+year 全等」扩展到「titleSimilarity ≥0.92 且年份兼容
   （相等或一方缺失）」（title variant 不再与库内成对存活；库内
   authoritative 胜出）；**artifact 条目有界**
   （`MAX_ARTIFACT_BIBLIOGRAPHY_ENTRIES = 40`，超出按 LLM 输出序裁尾；
   source-library 条目永不因上限被裁）。40 = prompt 纪律上限（30）之上
   的失控兜底。

修后是否还会无限膨胀：单轮 LLM 输出被 prompt 纪律（≤30）+ canonical
硬上限（artifact ≤40）双重 bound；跨轮无累积（replace 语义）；同文献
跨形态折叠（同轮 + canonical 两层）。极端情况（模型完全无视指令）的
上界 = 40 条 recalled + 全部 promoted 文献。

## 9. Remaining Limitations

1. Language：fact / academic reviewer 指令仍为中文（M9.7.3 实测对英文稿
   工作）；legacy 项目（无 language）保持中文默认（现状不变）；style
   polish 链在 en 项目静默跳过（zh 专用设计，en 无成熟润色链——如实
   记录而非硬造）。
2. Metadata：普通 DOI 的 DOI-only query 无交叉验证（无独立权威源；
   双源确认因 S2 限流环境未实施）；arXiv 正式发表版 title 与 arXiv 版
   差异大（<0.92）时会被保守判 mismatch（宁可不 enrich，不写错数据）。
3. Evidence Supply：本轮只打通「提示 + HITL 决策点」，候选 promote →
   全文 → 重跑 research 的完整闭环量化（coverage 从 15% 提升多少）属
   M9.7.5；evidence_supply 出现条件（pending ≥3）是提示阈值不是质量
   判定。
4. Bibliography：prompt 纪律（≤30）依赖模型遵循；canonical 上限（40）
   只作用于 artifact 条目——promoted 文献无上限（by design，事实数据
   不裁）。
5. mismatch 不再写库的行为变更：PDF OCR 坏标题 + DOI 正确的场景失去
   「resolver 自动纠正」（保留 inferred，用户手动 PATCH）——保守方向
   的有意取舍（错误 metadata 比缺失更糟）。
