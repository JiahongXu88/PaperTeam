## 1. Language Contract：language 是「死路」字段

链路逐环核查（✅ 已接入 / ❌ 未接入）：

| 环节 | 状态 | 证据 |
| --- | --- | --- |
| Project 定义 + 存储 | ✅ 仅定义/存储 | `ProjectMetadata.language?: string`（ProjectStore.ts:91）；自由字符串，无 enum、无默认值，仅长度 ≤50 |
| API 入参/回显 | ✅ 仅透传 | httpServer.ts:2670（readResearchMeta 白名单）；前端 NewProjectPage 可填写 |
| Workflow context | ❌ | WorkflowState / StageRunContext / createRun request 全部无 language；stages 只传 targetProfile/documentType |
| Researcher prompt | ❌ | buildResearchPrompt 项目信息块（ResearcherService.ts:586-592）列 6 个字段，唯独无 language |
| Outline / Writer prompt | ❌ 且硬编码中文 | buildOutlinePrompt（WriterService.ts:983）、buildSectionPrompt 无 language；buildStylePolishPrompt:584「中文学术表达」、legacy buildWriterPrompt:1043 强制 ctexart；摘要字数「100–200 字」是中文口径 |
| Reviewer prompt | ❌ 且 style lens 硬编码中文 | buildReviewPrompt（ReviewerService.ts:411-481）无 language；style modeSpec:440-442「中文学术表达质量」「正常的中文学术段落应当零或极少 issue」 |
| Skill selection | ❌ | resolveSkillIds(role, scope)（routing.ts:134-158）只看 role+contextScope 前缀，无 language 维度 |

zh-only skill 清单（共 2 个）：

| skill id | 路由 | 中文证据 |
| --- | --- | --- |
| `academic-style-zh` | reviewer + `review/style`；writer + `writing/style-polish` | seed purpose「中文学术表达原则」（上游 Humanizer-zh） |
| `academic-writing-zh` | writer 默认 + `writing/{outline,sections,revision,improvement-plan,style-polish}` | seed purpose「Writer 撰写/修订中文工科论文」 |

**P0-1 root cause**：`project.language` 前端可填、后端可存，但 Pipeline 零消费。
语言实际由「researchIdea 文本中偶发的 "Write the paper in English" + 中文系统
prompt 的反向拉力 + zh skill 注入」三方博弈决定——M9.7.3 中 A 臂 4/4 中文稿、
B 臂 3/3 英文稿即此偶然性的直接证据。English 项目下
`writing/outline` → `academic-writing-zh`、`review/style` → `academic-style-zh`
无条件注入（PiRuntimeAdapter roleSkills → SkillRegistry → resolveSkillIds 全链
无 language 感知），英文稿件 × 中文 style skill → Reviewer 结构化输出 7/7 失败。

Legacy（无 language）：读取侧静默丢弃，行为与显式 language 完全一致（都走
中文 prompt + zh skill）——即现状默认中文。

## 2. Reviewer Output Contract：两个「缺失即抛错」字段 + 无 repair 的 stage 级重跑

- 无 zod / JSON Schema / provider structured output；schema = 共享
  `ModeReviewResult` 接口（ReviewerService.ts:81-93）+ 手写校验
  `parseModeReview`（:259-301）。
- `riskScore`（style）与 `scores`（academic）是仅有的两个「缺失/非法即抛
  AgentRunFailedError」的 mode 专属语义字段（:286、:297-299）；
  `issues` 缺失已放宽为空数组、`summary` 缺失确定性兜底、verdict 有别名归一
  ——两者至今无任何兜底（reviewerVerdict.test.ts:79 钉死「不兜底」语义）。
- 失败冒泡路径：parseModeReview 抛错 → reviewMode/reviewAll 无 catch →
  `Promise.all` 一路失败拖垮三路 fan-out（另外两路已产出的合法结果与费用
  全部丢弃）→ WorkflowOrchestrator classifyBusinessError：
  `AGENT_RUN_FAILED → "transient"`（WorkflowOrchestrator.ts:940-962）→
  stage retryable 命中 → **整个 stage 重跑**（execute 全量：digest 重建 +
  三路 reviewer 全部重跑，prompt 逐字节相同，validator error 从不反馈给
  模型）→ maxAttempts（默认 2，config WORKFLOW_STAGE_MAX_ATTEMPTS）耗尽 →
  finalizeFailed → run failed。M9.7.3 B 臂 3/3 run 死于此
  （style×5 缺 riskScore + academic×2 缺 scores）。
- 系统内唯一 repair 先例是 LaTeX 编译修复（repairSection），Reviewer 无。
- 对比：existing_paper 分章审阅有 per-section 有界重试（3 次、退避 5s/20s），
  失败只丢该节——review.run 的三路 fan-out 没有等价的 per-mode 隔离。

**P0-2 root cause**：可修复的结构化输出违约（缺一个数字字段）被归类为
transient 并以「原样重跑整个 stage」应对——无 error feedback、无 repair、
无 mode 隔离；几十分钟的 run 因单字段缺失死亡。

## 3. Metadata Identity：DOI-only 查询 + 回显即采信 + mismatch 仍写库

三层 provider 实现中，M9.7.3 案例落在 ScholarlyResolver（层 A）：

- match 判据不在各 provider，集中在共享裁决：
  `scoreCandidate`（candidateScoring.ts:37-75）→ `pickFromSearch`
  （scholarly.ts:400-422）→ `verdictFor`/`compareFields`。
- `10.48550/arxiv.2210.03629` 被判 match 的精确路径：
  1. `SourceImportService.importDoi`（:188-221）→ `resolveMetadata({ doi })`
     ——query **只有 DOI，无 title**；
  2. OpenAlex `works/https://doi.org/<doi>` 返回 200 + 错误论文
     （本环境 OpenAlex 对 arXiv DOI 索引错配，数据侧问题）；
  3. `scoreCandidate`：candidate.doi（OpenAlex 回显）=== query.doi →
     `tier="doi"`——**只信回显 DOI，标题无参照也不比**；
  4. `compareFields`（candidateScoring.ts:97-113）：`query.title === undefined`
     → title 比对跳过；DOI 相等 → 无 mismatch → **match**；
  5. **附加缺陷**：`resolveMetadata` 的 mismatch 分支（SourceImportService.ts
     附近，注释自述「记录仍可用于元数据补全」）仍返回 record，
     importDoi 无条件 `Object.assign(metadata, …)` + provenance="resolved"
     ——即使 resolver 判了 mismatch，错误字段照样入库。
- 全链路无 `10.48550/arxiv.X` ↔ `arXiv:X` 互转校验；`identityKey` 的 DOI 与
  arXiv 键是两个身份（D-0034 红线，不自动合并），互相不校对。
- 后续防线：EvidenceGroundingService Stage 2（:235-263）query 带
  sourceMeta.title → compareFields 有参照 → 能拦截（M9.7.3 实测拦了 6/6）；
  但若 title 已被第 5 步毒化（错 vs 错），该防线失效——防线不能依赖入库前
  数据恰好干净。

**P0-3 root cause**：DOI-only query 的身份判定只依赖「provider 对查询 DOI 的
回显」，没有任何独立参照（query title / arXiv 权威源 / 第二源）交叉验证；
mismatch 结论又不阻断写库。

## 4. Evidence Supply：候选停 pending_review 是设计使然，但 Workflow 无承接点

系统存在两套互不相通的 "candidate"：

| | Discovery Candidate（文献候选） | Evidence Candidate（证据候选） |
| --- | --- | --- |
| 模型 | CandidateSource（CandidateStore.ts:38-61） | EvidenceCandidate（evidence/candidates.ts） |
| 状态机 | pending_review → accepted/rejected | pending → verified/mismatch/rejected/unverifiable |
| 晋级 | **只能用户手动 promote**（全仓唯一调用方 = httpServer.ts:993） | evidence.ground 三段核验（workflow 自动） |

- `promoteCandidate` 无任何自动调用方——「32/20 条全 pending_review /
  0 采纳」**不是断链 bug，是 D-0033/D-0035 红线**（Retrieved ≠ Verified，
  候选必经用户 promote）。
- 但 idea_to_paper 前段 `research.idea → evidence.ground →
  research.feasibility → hitl.feasibility_confirm → outline.plan →
  hitl.outline_confirm → writing.sections` **直通**：无 candidate-review
  HITL；evidence.ground 的 DoD 只看 Evidence candidate 队列，对 Discovery
  candidate 完全无感知；两个既有 HITL 都不呈现「候选待审 / 证据池只有 3 篇」
  的事实——用户除非主动翻 Discovery 页，否则永远不会被提醒。
- Candidate Review UI/API **齐全**：DiscoveryPanel CandidateSection
  （批量 Promote/Reject/角色选择），promote 后 fire-and-forget 全文解析、
  chunk 自动重建；verified evidence 的产生需要重跑 research
  （retrieve_library 检索新 chunk → 锚定 → evidence.ground 转正）。
- Workflow HITL 机制成熟（StageSpec.hitl 声明式 + resume 契约），
  但没有 evidence-supply 类型的 HITL 节点。

**P1-1 root cause**：HITL 边界本身正确；缺失的是「在写作前把
pending 候选数量 vs verified 证据覆盖」作为 HITL 决策点呈现给用户——
coverage 天花板 3/20≈15% 的杠杆在用户 promote，而用户从未被问到。

## 5. Bibliography Lifecycle：replace 语义 + 会话记忆复述 → 单调膨胀

- 存储：research.json 的 `bibliography` 字段（LLM 引用意图，无 identity 字段）；
  canonical 派生视图 = `buildBibliographyFromSources(sources)` ∪
  `mergeArtifactBibliography(artifact)`（bibliography.ts:198-289，不落盘）；
  references.bib = canonical 中实际被 \cite 的子集（syncReferencesBib）。
- **每次 research run 是整字段 REPLACE**（ResearcherService.ts:184，
  `bibliography: readBibliography(parsed)`）——代码层不做跨轮 append/merge；
  `readBibliography` 仅本轮内按 LLM 自造 key 去重（:718-726），既不查文献库
  也不查上一轮。
- **20→30→36 的机制**：research retry = stage 重跑（transient），同一项目
  research 会话 sessionKey 稳定 + in-memory transcript **跨 run 保留**
  （PiRuntimeAdapter ManagedSession，32 次 run / 预算 / 空闲才 rotation）→
  模型每轮看到自己上一轮的完整输出，倾向「复述旧的 + 再补新的」；prompt
  又不带旧清单、无数量指引 → 每轮输出更长。B 臂终态 36 条经逐条核对
  **全部是真实不同文献**（非重复条目）——膨胀是「每轮列得更多」，
  不是「同一篇反复入库」。
- 次级机制：canonical 合并查重口径弱——同 DOI 精确 或
  `compactTitle+year` 全等（year 缺失记 "?" 永不匹配）；「同论文不同形态」
  （年份 variant / 标题 variant / 缺 DOI / 缺作者）不命中 → 库内条目与
  artifact 条目成对存活（B 臂数据未实际出现，机制存在）。arXiv 与 DOI 双
  身份不合并是 D-0034 红线（preprint/正式版两个身份），非 bug。
- 来源区分：canonical `origin: source-library | artifact`、BibTeX
  `sourceId` 追溯字段、SourceStore 六值 origin 已存在——bounded 控制可以
  只作用于 artifact 条目而不动 promoted literature。

**P1-2 root cause**：膨胀主因 = 会话记忆复述 × 无跨轮清单约束 × canonical
全量并入 × Writer 全部引用；次因 = 合并查重的 title/year 口径过弱。

## 6. 修复方向（概要；详见实现）

1. **P0-1**：language 归一化（zh/en/legacy）→ Researcher/Outline/Writer/
   Reviewer prompt 注入 Target Language；skill 路由按 language 过滤 zh-only
   skill（English 下 style lens 不注入 academic-style-zh，style prompt 文案
   语言化，review 仍执行、riskScore 契约不变）；legacy 保持现状默认。
2. **P0-2**：ReviewerService 层 error-feedback repair——结构化校验失败时
   携带具体 validation errors + 上一轮输出做有界（≤2 次）修复调用；
   repair 失败才冒泡；禁止伪造默认分数（不违反「不兜底」红线）。
3. **P0-3**：arXiv DOI（10.48550/arxiv.*）→ arXiv ID 互转 + arXiv 权威源
   交叉验证（DOI-only query 的 match 必须经 arXiv 官方 API 的 title 确认）；
   mismatch 不再作为元数据写库依据。
4. **P1-1**：新增 `hitl.evidence_supply` HITL（写作前呈现 pending 候选数 vs
   verified 证据覆盖，用户 continue / cancel；不自动 promote、不 FAIL、
   每 run 至多一次）。
5. **P1-2**：research prompt 注入上一轮 bibliography 清单 + 数量纪律；
   canonical 合并查重增强（标题相似度 + 年份容忍）；artifact 条目有界
   （source-library 永不裁）。
