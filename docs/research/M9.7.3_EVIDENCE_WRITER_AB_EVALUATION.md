### 1.1 环境事故与输入侧决策（如实记录）

评估准备阶段发现本环境学术元数据链存在**系统性毒化**，两次试点后确立最终输入形态：

1. **arXiv 元数据 resolver 损坏**（M9.7.1 §12-8 同款）：arXiv import 的 enrich
   3/3 未定论，title/year 留空；显式 enrich 重试同样无效。
2. **OpenAlex 对 arXiv DOI 索引错配**（本评估新发现）：以 DOI
   `10.48550/arxiv.2210.03629` 导入时，OpenAlex 返回 `outcome=match` 但标题为
   *Distributing Accountability, Not Capability: Phase Separation…*（错误论文）；
   带DOI的种子做 evidence.ground 时，metadata 核验阶段 6/6 mismatch
   （mismatch(title)/mismatch(doi)）——**注入错误元数据比缺失更糟，该路径被否决**。
3. **最终输入形态**：BibTeX 导入（仅 title/authors/year/booktitle，题录取自
   已下载权威 PDF 首页逐字题录——M9.7.1 §13-6 建议的输入侧兜底）+ 官方
   手动全文挂载端点（M9.3 设计的人工 fallback）。刻意**不带 doi/eprint**：
   使 evidence.ground 的 metadata 核验按 title 走 benign 路径（match 或
   not_found），避开 OpenAlex 毒化。两臂完全一致应用。
4. 两次试点（titleless-arXiv 项目 `p-be23582385a7`、bibtex-v1 项目
   `p-d9ecbfced20f`）在发现问题后取消，保留为记录（`e2e/.tmp/m973/`
   下 `a-pilot-*`），其成本不计入实验（pilot 合计 $0.91）。

该决策使产品内 Evidence→citation-key 解析链（sourceId 精确匹配）**首次在真实
run 中完整接通**：M9.7.1 历史 run 因 title 缺失，该链全程返回 null（gate
coverage 显示 0/17，报告的 17.6% 系评估者人工追溯口径）。

## 6. Analysis

### 6.1 Evidence-backed Writer 是否有效？

**Writer 层面：部分有效；Pipeline 层面：净负面。**

- **有效的部分（机制确实改变了 Writer 行为）**：A/B 分组白名单使引用质量
  向证据倾斜——首轮写作种子 key 实例 54%→58%、每种子引用数 ×1.5、唯一 key
  22→20（引用面略收敛）；三轮写作 missing/hallucinated 全零、无孤儿文件，
  稿件结构纪律更好（A 的 11 个 missing 出现在**修订轮**，B 未及修订，该对比
  严格说不成立，但 B 写作时点三轮均零缺失）。
- **无效的部分（核心指标不达标）**：Evidence Coverage 15.0%，**未超过
  M9.7.1 基线的 17.6%**（本轮基线复测 13.6%——同数量级）。原因见 6.2。
- **净负面**：B 臂 3/3 run 全部失败于 review.run（英文稿件 × 中文 reviewer
  技能 → 协议输出违规 7/7），完整 Pipeline 产出（review/gate/revision/PDF）
  为零；基线 1/2 run 完成。**在 GLM-5.3 + 当前 reviewer 栈下，M9.7.2 使
  端到端产出能力倒退。**

### 6.2 提升来自哪里？为什么 Coverage 不动？

Writer 引用**强度**的改善来自分组白名单的注意力引导（A组 key 排面更显著 +
规则 3 的强制性措辞）。但 Coverage 是**唯一 key 集合口径**，其天花板由上游决定：

1. **证据池只有 3 篇种子论文**（15 条 formal evidence 全部锚定 S001-S003）。
   bibliography 却有 20-36 个 key（LLM 回忆条目）——3/N 在 N=20 时上限即 15%，
   低于 M9.7.1 的 17.6% 纯粹因为当年 N=17。
2. **B组 keys 仍被全部引用**（B 终态 36 keys 全部出现在正文）——M9.7.2 的
   「B组仅限背景陈述」是软约束，GLM 给每个回忆 key 都安排了"背景"用法。
   分组改变的是引用密度分布，不是引用集合。
3. **bibliography 随 research 轮数膨胀**（20→30→36）：无去重上限的 LLM 回忆
   条目持续累积，进一步稀释 coverage 分母。
4. 32/20 条 search 候选全部 pending_review **0 采纳**——若经 HITL 采纳并
   全文化，A组本可扩大。**真正的杠杆在证据池扩充（上游），不在 Writer 政策（下游）**。

### 6.3 是否引入副作用？

1. **语言漂移 → review 链路系统性阻断（严重）**：B 3/3 英文大纲/稿件 vs
   A 4/4 中文；诊断 D-1 证实同环境中文稿件可通过 review。因果链
   （M9.7.2 prompt → 语言选择）为观察性关联（p≈0.03，n 小），但**操作层面
   结论确定**：M9.7.2 条件下端到端 0/3 完成。
2. **引用密度翻倍**：136 vs 62-77 处实例——每论断的引用堆积更多（A组 key
   单 key 最高 23 次），存在过度引用倾向。
3. 无证据 key 的引用面未收缩（36/36 全被引）——「不得新增 B组引用」的修订
   特则未获检验（B 未进入修订），写作期 B组 使用未受有效约束。

### 6.4 下一步优化方向

1. **P0 — Reviewer 协议鲁棒性**（两臂共同的失效模式，B 被完全阻断）：
   style/academic 输出校验失败时，将校验错误回注重试（error-feedback retry）
   而非整 stage 弃败；或输出 schema 收紧为 tool-call/JSON mode；
2. **P0 — 语言钉扎**：`project.language` 当前为死字段（backend 不消费）——
   接入 outline/writer prompt 显式钉扎输出语言，阻断语言漂移这一阻断链；
3. **P1 — 证据池扩充闭环**：pending 候选（本轮 32/20 条闲置）→ 采纳 →
   批量全文 → grounding，把 A组 从 3 keys 扩到 ~10+ keys，coverage 才有
