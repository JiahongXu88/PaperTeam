## 0. Executive Summary

1. **缺的不是管线，是文件**。PDF→解析→chunk→Evidence 管线全部就绪且经评估验证
   （M6.8/M6.9）；断点只有一个：discovery 候选 promote 后是 `metadata_only`
   （无原始文件），SourceChunker 红线跳过 → 无 chunkId 锚点 → 无法 propose
   evidence。M7.2 = 把 OA 全文**自动挂到既有条目上**，下游管线零改动自动接管。
2. **挂接点结论（Phase 0 三问的答案，详 §1）**：
   - FullText 挂 **Literature Library 条目生命周期层**（SourceStore 补
     `attachFile`；SourceImportService 补 `tryResolveFullText`），不挂
     Retrieval / Evidence（它们是下游派生与消费层）；
   - resolver 三实现按 ADR §12 冻结形状放 `backend/src/search/fullText.ts`，
     复用 ProviderHttpClient（唯一基建增量 = `fetchBytes` 二进制方法）；
   - 不破坏 verification / supportStrength / citation 的保证 =
     **同 sourceId 原地补挂**（不建新条目），chunkId 锚点链与 Evidence
     三段核验零改动（§1.3）。
3. **两个 Phase 0 新发现（实现必须处理，文档此前未记录）**：
   - **F-1 chunker 类型开关**：`SourceChunker.chunkSource` 按 `sourceType`
     switch——`doi/arxiv/url` 类型即使有 `fileName` 也走 default 分支 skip
     （`SourceChunker.ts:78-91`）。⇒ attach 时必须把 `sourceType` 更新为
     文件类型（`pdf`），否则全文挂上了 chunker 照样跳过；
   - **F-2 检索自动刷新已存在**：`RetrievalService.ensureState` 每次检索对比
     文献库签名（`sourceId:contentHash:updatedAt`，`RetrievalService.ts:653`），
     变化即增量刷新。⇒ attach 后检索层**无需新接线**即可感知；主动
     `rebuildSource` 只是把时机从「下次检索」提前到「resolve 完成时」。
4. **验收对齐 SCOPE_FREEZE §M7.2 五条**（§7），红线（§3.10）：不新增 Agent /
   不动 Workflow / 不引入 ProviderHttpClient 之外 HTTP 基建 / chunker 与
   Evidence 核验零改动 / 无爬虫兜底（无 DOI/arXiv 的 Web 候选永远
   metadata_only——这是定位不是缺陷）。

## 1. Phase 0 架构分析

### 1.1 Literature Library（问题 1：FullText 挂在哪一层）

**模型**（`sources/SourceStore.ts:93-124`）：`SourceItem` = sourceId（`S\d{3,}`）
+ fileName（metadata-only 为空）+ sourceType（pdf/bibtex/text/markdown/image/
doi/arxiv/url/metadata）+ sourceRole + **origin**（USER_ADDED / DOI_IMPORT /
ARXIV_IMPORT / URL_IMPORT / BIBTEX_IMPORT / AGENT_RETRIEVED）+ **status**
（`metadata_only → pending → available/partial/failed` + rejected）+
metadata（title/authors/year/doi/arxivId/url/venue/abstract）+ identity +
contentHash + analysis/analysisHash + workKey/versionType/relatedSourceIds。

**存储**（D-0013 文件优先）：`sources/papers/<sourceId>-<安全名>`（原始文件）、
`sources/parsed/<id>.json`（PdfAnalysis）、`sources/index.json`（原子重写）、
`sources/candidates.json`（Discovery 候选，非 authoritative）、
`sources/chunks/<id>.jsonl(+.vectors.json)`（派生）。

**当前导入流程**（`sources/SourceImportService.ts`）：五路径——PDF 上传
（contentHash 判重）/ DOI / arXiv / URL / BibTeX（后四者 metadata-only 入库，
DOI/arXiv 可选 ScholarlyResolver enrich）+ `promoteCandidate`（候选→正式，
幂等，`origin=AGENT_RETRIEVED`，无全文 → `metadata_only`）+ enrichMetadata +
linkSources + removeSource（Evidence 引用保护 409）。

**架构预留证据（设计意图早已埋好）**：
- `SourceStatus` 的 `metadata_only` 语义注释：「有元数据、无全文（DOI/URL/
  BibTeX 导入）」——本里程碑的目标状态机迁移就是它的出口；
- `SourceStore.filePath` 对无文件条目的报错文案：「可先通过 DOI / arXiv / URL
  获取全文后上传」；
- `SourceImportService.importUrl` 注释：「不抓取正文——**ContentFetcher 属
  后续节点**」；
- `VerificationLevel` 早已含 `fulltext`（`EvidenceStore.ts:34`）。

**回答：FullText 挂 Literature Library 条目生命周期层。** 理由：
- 全文文件是 Source 的 authoritative 属性（与 papers/ 目录同一所有权），
  SourceStore 是唯一写方（现状：add/addRecord/setAnalysis）；
- 编排（何时解析、下载、重试）是入库路径编排语义——SourceImportService
  的既有职责（五路径 + promote 都是它）；
- resolver 的「DOI/arXiv → OA URL」映射是检索域能力（与 provider 同族），
  按 ADR §12 放 search/，经 serviceStack 注入——sources 域不感知 HTTP 细节；
- **不挂** Retrieval（chunk 是 Derived State，attach 后自动/显式重建即可）、
  **不挂** Evidence（Retrieved ≠ Verified 红线；全文只创造锚点前提，不触碰核验）。

### 1.2 PDF / Parser / Chunk 流程（问题 2：如何复用现有流程）

**现状（文件型条目的既有管线，全部可复用）**：

```text
POST /sources（上传）→ sources.add（contentHash 判重，status=pending，落文件）
  → BuiltinPdfAnalyzer.analyzeFile（httpServer.ts:850-861 自动触发）
  → sources.setAnalysis（contentHash 防失效守卫；status → available/partial/failed）
  →（检索时）RetrievalService.ensureState：签名变化 → SourceChunker.chunkSource
      → pdf：PyMuPdfParser（blocks+页码+TOC 章节）优先，不可用回退 builtin 文本层
      → ChunkStore.writeChunks（<id>.jsonl）+ manifest + 可选向量旁车
      → lexical/dense hybrid 检索（retrieve_library 工具同源）
```

**F-1（关键约束）**：`SourceChunker.chunkSource` 的输入判定是
`sourceType ?? inferFromName`，switch 命中 `doi/arxiv/url/metadata` 一律
`skipped(full_text_unavailable)`（`SourceChunker.ts:75-91`）——**与是否已有
fileName 无关**。因此 attach 必须同步 `sourceType: "pdf"`（导入类型由
`origin` + fullText provenance 保留审计），chunker 零改动即正确工作。

**F-2（关键便利）**：`librarySignature = sourceId:contentHash:updatedAt`
（`RetrievalService.ts:653-656`），`ensureState` 每次检索对比签名增量刷新
（新 source 补建 / stale 重生成 / 孤儿清理，`RetrievalService.ts:433-448`）。
attach 改写 contentHash + updatedAt ⇒ **检索层自动感知，无新接线**。
主动 `rebuildSource`（`RetrievalService.ts:340`）把 chunk 生成提前到 resolve
完成时——架构评审 N-3 指出「M7.2 FullTextResolver 落地后需在此接线」即此；
`SourceNotIndexableError`（扫描件文本层过薄等）如实记录不失败。

**回答：复用方式 = attachFile 落文件（走 add 同一套安全化/大小上限/contentHash
语义）→ BuiltinPdfAnalyzer.analyzeFile + setAnalysis（与上传路径逐字节同一
代码路径）→ chunk 交给既有管线（签名自动刷新 + 主动 rebuildSource 兜底）。**

### 1.3 Evidence 链路（问题 3：如何保证 Candidate/Literature → FullText → Evidence 不破坏既有语义）

**现状**：EvidenceCandidate（propose 校验 chunkId 格式 + ChunkAccess 回取
锚点真实存在）→ 三段核验（quote 逐字 / metadata 权威 / 语义 judge）→
EvidenceRecord（`verificationStatus=verified`、`supportStrength=direct/partial`、
`verificationLevel=fulltext`、`location.chunk=chunkId`、source 引用带
doi/title 供 `matchBibliographyKey` 反查 bib key）。正式证据 =
`isFormalEvidence`（verified + sourceId + chunk 锚点三件套）。

**不破坏的保证（三条，全部源于「同 sourceId 原地补挂」这一决定）**：
1. **追溯链完整**：chunkId 形状 `<sourceId>:<sectionId>:<序号>:<hash10>`
   （D-0036）内嵌 sourceId。若全文另建新条目（上传路径现状），chunk 锚点指向
   新 sourceId，验收链「verified ← chunk ← library ← promote ← candidate」
   在 library 处断成两条（架构评审 N-1，M7.1b 用前端 link 编排绕过）。
   attach 到 promote 产生的同一 sourceId ⇒ 链路单线闭合，且 N-1 在自动
   路径上根除（手动上传补挂端点仍留待后续，见 §8）。
2. **核验语义零改动**：三段核验消费的是 chunk 原文（ChunkAccess 按落盘
   jsonl 回取，内容 hash 自校验）与 SourceMetadata（doi/title/author/year）。
   attach 只新增文件与 provenance，不改 metadata 判等字段；metadata enrich
   若发生走既有 `applyMetadataMerge`（user > resolved > inferred）。quote
   逐字校验、judge、supportStrength 判定代码一行不动。
3. **citation / bibliography 兼容**：`matchBibliographyKey` 匹配
   `EvidenceRecord.source.doi/title`（grounding 转正时已从 canonical 记录
   回填）——与全文无关，不受影响。删除保护（SOURCE_IN_USE 409）按
   sourceId 查询，同样不受影响。

## 3. 设计方案

### 3.1 分层总览（增量全部落在冻结分层的空位内）

```text
search/fullText.ts（新）                ProviderHttpClient（+fetchBytes）
  FullTextResolver 接口（ADR §12 冻结）    └─ 二进制下载（重试/熔断/健康同源）
  UnpaywallResolver（DOI）                    ↑
  ArxivPdfResolver（arxivId）                 │ 复用
  OpenAlexOaResolver（DOI/openalexId）        │
  downloadPdf（SSRF 护栏 + 大小帽 + magic 校验 + 逐跳重定向校验）
        ↑ 类型注入（无运行时环）
SourceImportService.tryResolveFullText（编排：resolve → download → attach
  → analyze → provenance → rebuildSource；promote 后台单次尝试）
        ↓
SourceStore.attachFile（既有条目原地补挂：fileName/contentHash/bytes/
  status=pending/sourceType=pdf）+ setFullTextProvenance
        ↓ 既有管线（零改动）
BuiltinPdfAnalyzer → setAnalysis → RetrievalService（签名自动刷新 +
  主动 rebuildSource）→ retrieve_library → propose_evidence → 三段核验
```

### 3.2 FullTextResolver 接口与三实现（`backend/src/search/fullText.ts`）

接口 = ADR §12 冻结稿原样（identity 用已落地的 `sources/identity.ts`
SourceIdentity，为 ADR 草案的超集，向后兼容）：

```ts
export interface FullTextResolver {
  readonly name: string;             // "unpaywall" | "arxiv" | "openalex-oa"
  resolve(identity: SourceIdentity): Promise<
    | { kind: "found"; url: string; source: string; license?: string }
    | { kind: "not_found" }
    | { kind: "error"; note: string }
  >;
}
```

| 实现 | 身份键 | 机制 | license |
|---|---|---|---|
| `UnpaywallResolver` | doi | `GET api.unpaywall.org/v2/{doi}?email=`；取 `best_oa_location.url_for_pdf`（**只认 PDF 直链**，landing page URL 不算 found——下载层只能消费 PDF 字节） | `best_oa_location.license` 原样透传（如 `cc-by`） |
| `OpenAlexOaResolver` | doi（`works/doi:{doi}`）或 openalexId（`works/W…`） | 同族 API + mailto 礼貌参数；取 `best_oa_location.pdf_url` | 同上（常为 CC URI） |
| `ArxivPdfResolver` | arxivId | 确定性 `https://arxiv.org/pdf/{去版本号id}`，无需 API（存在性由下载层 404 如实报告） | undefined（arXiv 逐篇 license 不一，不臆造） |

**链构建（确定性顺序）**：`buildFullTextResolverChain(identity)`：
- 有 doi → `[unpaywall?, openalex-oa]`；有 openalexId 无 doi → `[openalex-oa]`；
- 有 arxivId → 追加 `[arxiv]`（预发表版兜底：正式版 OA 优先）；
- 都没有 → 空链 = **不可解析**（Web 候选定位，`FULLTEXT_NOT_RESOLVABLE`）。

**配置**：Unpaywall 强制 email——复用 `PAPERTEAM_OPENALEX_MAILTO`，回退
`CITATION_CONTACT_EMAIL`（与 OpenAlex 礼貌池同一配置，零新 env）；两者皆无 →
Unpaywall 不注册（启动日志如实记录，openalex/arxiv 不受影响，同 AMiner 无
key 纪律）。

### 3.3 ProviderHttpClient.fetchBytes（唯一 HTTP 基建增量）

```ts
async fetchBytes(provider: ProviderProfile, url: string,
  init?: ProviderFetchInit & { maxBytes?: number },
): Promise<{ bytes: Buffer; contentType: string | null }>
```

- 与 fetchJson/fetchText 同一重试/熔断/健康骨架（临时失败重试、429 冷却、
  类型化错误）——实现上把 `fetchOnce` 泛化出二进制分支，文本路径行为不变；
- **不跟随重定向**（`redirect: "manual"`）：逐跳校验是调用方（downloadPdf）
  的 SSRF 纪律，3xx 原样返回（`location` header 可读）；
- `maxBytes`：content-length 预检 + **流式读取累计截断**（reader 循环，超帽
  cancel + 报错——服务端隐藏 content-length 也不会缓冲超限字节）。

### 3.4 下载护栏（`downloadPdf` helper，search/fullText.ts）

agent-search SSRF 逐跳校验教训（M6.1 ADR §6 输入）落到实现：

1. **URL 校验（每跳执行）**：仅 https；拒绝 userinfo；端口必须 443/缺省；
   拒绝 localhost / `*.localhost` / 私网与保留 IP 字面量（127/8、10/8、
   172.16/12、192.168/16、169.254/16、0/8、::1、fc00::/7、fe80::/10）；
   IPv6 方括号形式解析后同判；
2. **重定向**：手动逐跳跟随，≤5 跳，每跳重新过 1 的校验（arxiv.org →
   export.arxiv.org 这类合法跳转放行；跳内网直接拒绝）；
3. **大小帽**：`MAX_SOURCE_BYTES`（20MB，与 SourceStore 同一常量）；
4. **magic 校验**：`%PDF-` 头（前 5 字节）——HTML 付费墙 / landing page
   误当 PDF 的情况在此确定性拦截，不臆造；
5. 产出：`{ bytes, fileName(建议名), license?, resolverName, url }`。

### 3.5 SourceStore 增量：attachFile + fullText provenance

```ts
export interface SourceFullTextProvenance {
  status: "resolved" | "not_found" | "failed";
  resolver?: string;      // 命中实现（unpaywall / openalex-oa / arxiv）
  url?: string;           // 实际下载 URL（审计）
  license?: string;       // 透传，不解释
  note?: string;          // not_found/failed 原因（≤500 字符）
  attempts: number;       // 累计尝试次数（审计；手动重试递增）
  attemptedAt: string;    // 最近尝试 ISO
  resolvedAt?: string;    // 成功 ISO
  bytes?: number;
}
// SourceItem.fullText?: SourceFullTextProvenance（optional，老数据 lazy 兼容）
```

`attachFile(projectId, sourceId, { fileName, content, originalName })`：
- 条目必须存在；**已有 fileName → 幂等跳过**（返回 `{source, attached:false}`，
  不抛错——后台尝试与手动重试的竞态语义）；
- 复用 add 的全部纪律：sanitizeFileName（非法建议名回退 `fulltext.pdf`）、
  非空、≤MAX_SOURCE_BYTES、sha256 contentHash；
- 写 `papers/<sourceId>-<安全名>`；条目更新：`fileName / originalName（=下载
  URL）/ bytes / contentHash / status=pending / sourceType=pdf（F-1）`；
- 不做跨条目 contentHash 判重（identity 判重发生在导入/promote 层，
  D-0033 语义；同内容异条目各自持有文件与删除语义独立）。

`setFullTextProvenance(projectId, sourceId, provenance)`：读-改-写索引
（与 applyMetadataMerge 同模式）。

### 3.6 SourceImportService.tryResolveFullText（编排）

```ts
async tryResolveFullText(projectId, sourceId): Promise<{
  outcome: "resolved" | "not_found" | "skipped_has_file" | "not_resolvable" | "failed";
  source: SourceItem;          // 总是返回最新条目
  note?: string;
}>
```

流程（单次调用 = 一轮**有界**尝试：每个 resolver 一次 resolve + 每个命中
URL 一次下载，总数 ≤ 链长 ≤3，无内层重试风暴）：
1. 条目存在性 + 已有文件 → `skipped_has_file`（幂等）；
2. `buildFullTextResolverChain(effectiveIdentity)` 空链 → 记
   `fullText={status:not_found, note:"无 DOI/arXiv 身份…"}` → `not_resolvable`；
3. 依序 resolve：`found` → `downloadPdf`（§3.4 护栏）→ 任一环节失败（网络 /
   非 PDF / 超限 / SSRF 拒绝）记 note 后**继续下一 resolver**；`not_found` /
   `error` 同样继续；
4. 全部落空 → `fullText={status:not_found|failed, attempts+1}` →
   `not_found`（有 resolver 报过 error 则 `failed`）；
5. 成功 → `sources.attachFile`（幂等守卫）→ `BuiltinPdfAnalyzer.analyzeFile`
   → `setAnalysis`（contentHash 防失效）→ `fullText={status:resolved,
   license, url, resolver, resolvedAt}` → `retrieval.rebuildSource`
   （`SourceNotIndexableError` 捕获记日志：扫描件等如实 skip，manifest 留痕，
   resolve 本身不算失败）→ `resolved`。

**错误分类**（新 BusinessErrorCode）：
- `FULLTEXT_NOT_RESOLVABLE`（422）：无 DOI/arXiv/openalex 身份；
- `FULLTEXT_DOWNLOAD_FAILED`（502）：护栏拦截 / 网络失败 / 非 PDF / 超限
  （手动端点直接抛；编排内部则记 provenance 落 `failed`）。

### 3.7 promote 挂接 + 手动端点

- `promoteCandidate` 成功路径尾部：`origin=AGENT_RETRIEVED` 的新条目 /
  metadata 合并命中条目 → fire-and-forget `tryResolveFullText(...).catch(log)`
  （**单次**，不阻塞 promote 响应；幂等守卫吸收并发 promote 竞态）。
  注入面：`SourceImportServiceOptions.fullText?: { resolvers; http; analyzer }`
  ——缺省不配置 = 行为与 M7.1 完全一致（测试既有用例零改动）。
- 手动重试/触发：`POST /api/projects/:id/sources/:sourceId/resolve-fulltext`
  → 同步执行 tryResolveFullText → `{ source, outcome, note? }`。
  服务对象：一切 metadata_only 条目（含 DOI_IMPORT / ARXIV_IMPORT /
  BIBTEX_IMPORT 用户导入，不只 AGENT_RETRIEVED——通用断点修复）。
- PromoteResult 响应 schema 不变（前端 M7.1c 零回归）；resolve 完成后前端
  经既有 sources 列表刷新看到状态迁移（UI 增强留 M7.2 后续，见 §8）。

### 3.8 检索接线（N-3 收口）

成功 attach 后主动 `retrieval.rebuildSource(projectId, sourceId)`：
- 正常：chunks 落盘 + manifest indexed → `retrieve_library` 立即可检索；
- `SourceNotIndexableError`：捕获 + 日志 + 保留 manifest skipped 记录
  （reason=full_text_unavailable / parse_failed 如实）——resolve 成功 ≠
  可索引，不互相伪装；
- 即便不主动调，F-2 签名刷新保证下次检索自愈——主动调只是时机提前。
  RetrievalService / SourceChunker / ChunkStore 本体零改动。

### 3.9 装配（serviceStack.ts）

```ts
// email 链：PAPERTEAM_OPENALEX_MAILTO ?? CITATION_CONTACT_EMAIL
const fullTextEmail = searchConfig.openalexMailto;
const fullTextResolvers = buildDefaultFullTextResolvers({
  http: providerHttp,                       // 与 search providers 同一实例
  ...(fullTextEmail !== undefined ? { email: fullTextEmail } : {}),  // 无 → 不注册 unpaywall
});
sourceImport = new SourceImportService({ ..., fullText: { resolvers: fullTextResolvers, http: providerHttp }, retrieval? });
```

（retrieval 实例构造顺序在 sourceImport 之后——fullText 包内以 getter/惰性
引用注入，避免装配顺序环；实现时以最小侵入为准。）

### 3.10 明确不做（红线重申，均出自 SCOPE_FREEZE §M7.2 + §5）

- ❌ 不做爬虫兜底 / landing page 解析（Web 候选无 DOI/arXiv → 永远
  metadata_only，定位不是缺陷）；
- ❌ chunker / 检索 / Evidence 三段核验 / Workflow / Runtime 零改动；
- ❌ ProviderHttpClient 之外不引入新 HTTP 基建（fetchBytes 是它自己的方法）；
- ❌ 不做自动后台重试循环（每 promote 单次；重试=用户手动端点，语义确定）；
- ❌ 不把 abstract/snippet 升格为全文（chunker 红线不动）；
- ❌ 不新增 Agent / 不动 research.json schema / 不动 PromoteResult schema。

## 4. 数据流

### 4.1 成功路径（有 OA 全文）

```text
promote(C001) ──► SourceStore：S003 metadata_only（origin=AGENT_RETRIEVED）
   └─(后台, fire-and-forget)─► tryResolveFullText(P, S003)
        identity.doi=10.x/yyy
        ├─ UnpaywallResolver.resolve → found(url_for_pdf, license=cc-by)
        ├─ downloadPdf：SSRF 校验 → https 下载(≤20MB, 逐跳校验) → %PDF- 魔数 ✓
        ├─ SourceStore.attachFile：papers/S003-fulltext.pdf + contentHash
        │    + status=pending + sourceType=pdf（F-1）
        ├─ BuiltinPdfAnalyzer → setAnalysis(contentHash) → status=available
        ├─ setFullTextProvenance：{resolved, unpaywall, url, cc-by, resolvedAt}
        └─ retrieval.rebuildSource → chunks/S003.jsonl（chunkId=S003:SECxx:…）
S003 现在可被 retrieve_library 检索 → Researcher propose_evidence(S003, chunkId, quote)
→ 三段核验（零改动）→ EvidenceRecord(verified, fulltext, direct/partial)
→ EvidenceSelectionService formal → Writer / Reviewer / Quality Gate
追溯链：verified ← chunk(S003) ← library(S003) ← promote(C001) ← discovery ✅
```

### 4.2 无 OA（如实，不报错不阻塞）

```text
tryResolveFullText → [unpaywall:not_found, openalex-oa:not_found, arxiv:—(无id)]
→ fullText={not_found, attempts:1, attemptedAt} → S003 保持 metadata_only
→ 用户仍可手动上传（M7.1b 既有 link 编排路径不受影响）
```

### 4.3 失败（确定性重试语义）

```text
Unpaywall found 但下载 403/非 PDF/超 20MB → 记 note → 续试 openalex-oa →
全部失败 → fullText={failed, note:"unpaywall:…; openalex-oa:…", attempts:1}
→ S003 保持 metadata_only → 用户 POST /resolve-fulltext 手动重试（attempts 递增，无自动循环）
```

## 8. 风险与开放问题

| # | 项 | 处置 |
|---|---|---|
| R-1 | 出版社 OA 直链常反爬（403 / cookie 墙） | 下载失败如实记 failed + arXiv 兜底顺序；不做伪装 UA / 不做爬虫（红线） |
| R-2 | SSRF：resolver API 被污染返回内网 URL | §3.4 逐跳校验（https + 私网字面量 + 端口）；不做 DNS 解析级校验（记录为已知边界——URL 来源限于 Unpaywall/OpenAlex/arXiv 官方 API 响应） |
| R-3 | 后台 resolve 与用户 PATCH 的 index.json 读-改-写竞态 | 与既有 setAnalysis/applyMetadataMerge 同暴露面（单进程 + 快速写回）；attachFile 幂等守卫吸收重复触发；全店序列化属既有技术债，不在本里程碑扩 |
| R-4 | Unpaywall email 未配置 | resolver 不注册（日志如实）；OpenAlex/arXiv 路径不受影响——配置缺失降级而非失败（D-0033 optional 纪律） |
| R-5 | 开放：手动上传「补挂到既有条目」HTTP 端点（N-1 的人工路径根除） | 本里程碑不做（冻结范围外）；attachFile 原语已就位，后续端点化成本极小 |

| R-7 | 开放：OA 全文与正式版不一致（preprint vs published） | 链序（正式版 OA 优先）+ provenance 如实记录 resolver/url/version 来源；语义裁决不做 |
