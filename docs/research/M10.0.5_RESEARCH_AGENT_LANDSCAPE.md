## 1. Executive Summary

一句话定位：**PaperTeam 是当前市场上唯一把「证据纪律 + 修订安全」做成确定性机制的
Evidence-grounded Scientific Research Agent——检索与报告生成已由通用大厂商品化，
但「已有论文 × 新实验 × 新文献 × 审稿意见 → 可验证修订稿」这条返修链路在 2026-09
的市场上是空白，而 PaperTeam 在这条链路上的存量机制（external instructions / 修订
计划状态机 / fact-citation preservation / evidence supply）恰好是全部竞品中最深的。**

三个核心判断（详见 §5-§9）：

1. **不要与通用 Agent 拼搜索**【官方+推测】：ChatGPT/Gemini Deep Research 的迭代式
   检索、1M 上下文、细粒度引用已把「找到资料并写成报告」商品化；开源侧 GPT
   Researcher（29.6k★，约 $0.4/次）也已覆盖通用 web 研究。PaperTeam 的差异化不在
   检索纵深，在检索之后的信息处理（quote 逐字核验 / metadata 权威裁决 / 证据-论断
   对齐 / 修订后复核），这一层至今没有任何竞品产品化。
2. **返修场景是已验证的市场空白**【官方】：科研五强（Elicit / Consensus / SciSpace /
   ResearchRabbit / Semantic Scholar）全部没有「上传论文 + reviewer comments → 返修」
   功能；最接近的 Paperpal Agents（2026-09-07 官方博客）也只做到「以证据为上下文
   逐条处理审稿意见」的对话式辅助，无确定性修订安全、无编译验证闭环。而 PaperTeam
   的 `existing_paper_improvement` 工作流 + external instructions 机制已真实跑过 26 页
   中文论文的完整返修 A/B【代码事实】。
3. **机会的兑现成本主要是「接线」而非「新建」**【代码事实】：代码审计确认
   PDF/LaTeX/reviewer comments 三个用户资料入口已存在且经 E2E 验证，缺的是①实验
   数据一等登记（中等难度）、②improvement 工作流与 M8/M9 证据研究链的接通（接线
   级）、③跨 run 研究记忆（保持 POST_M8 的条件启动结论）。

## 2. 调研发现：三类竞品格局

### 2.1 通用 AI Agent（A 类）

#### Claude Code（Anthropic）【官方】

- **形态**：多 surface 引擎（CLI / VS Code / JetBrains / 桌面 / Web / 移动端 /
  Slack / GitHub Actions），版本约 2.1.282；Opus 5.5 已成默认 Opus（1M context）。
- **Web Search**：内置 WebSearch/WebFetch（可按域授权）；官方未披露搜索 provider
  【第三方】称 Brave Search API（未获官方背书）。无引用机械核验层。
- **Research Planning**：Plan mode（EnterPlanMode/ExitPlanMode）、TodoWrite、
  Workflows 动态编排多子 agent。
- **Tool Usage**：48 个内置工具；Read 支持 **PDF 视觉整读**（≤10 页整读、>10 页
  按 20 页/段分页）与图片视觉读取；MCP 全面支持（managed MCP + tool search）。
- **Long Context**：默认 200K，Fable/Sonnet 5/Opus 4.6+ 支持 1M；auto-compaction
  + `/compact` + `/rewind`。
- **Citation**：WebSearch/WebFetch 返回来源链接，agent 自行引用，**无自动引用
  验证**——引用质量完全依赖模型行为。
- **Knowledge Management**：CLAUDE.md 多层 + `.claude/rules/` + auto memory
  （MEMORY.md 自动积累）+ Projects（公测：持续会话协调并行云线程）。
- **Agent Workflow**：子 agent（自定义 `.claude/agents/*.md`）+ Agent Teams
  （跨会话消息）+ worktrees 隔离 + Routines 云端定时任务。
- **定价**【第三方】：Pro $20/月、Max $100/$200/月；API 约 $10/M 输入。

#### ChatGPT Deep Research（OpenAI）【官方】

- **2026-02-10 起底座换 GPT-5.2**（此前 o3/o4-mini）；新增 apps 连接器、特定站点
  检索限定、实时进度跟踪与中途追问。
- **Research Planning**：**可编辑研究计划**（运行前审查修改）+ 运行中随时打断——
  这是与 PaperTeam M8 计划批准断点同型的交互，属行业标配。
- **Web Search**：公网 + 上传文件 + 站点白名单 + 认证数据服务（只读 apps）。
- **Long Context**：未公布具体窗口；学术计划参与者获更大上下文【第三方】。
- **Citation**：报告含 citations/source links + Sources used 区 + **activity
  history（研究过程可审计）**；导出 Markdown/**Word**/PDF。
- **Knowledge Management**：Projects（每项目文件上限 Free 5 / Plus 25 / Pro 40，
  25GB/用户）+ 跨会话记忆。
- **硬限制**：512MB/文件、2M token/文本文件；**非 Enterprise 计划 PDF 仅做文本
  抽取（丢弃嵌入图片）**——公式图表理解受损。
- **2026-07-29 学术计划**：$2.5 亿承诺、10 万科研人员免费前沿访问（GPT-5.6 家族），
  明确包含 expanded deep research、75+ 生命科学 skills、Zotero/LaTeX 连接器。
- **定价**【第三方】：Free 约 5 次/月，Plus 有用户反馈 7-10 次触顶（2026 信用点
  制约 ~50 点/次）；API o3 版 $10/$40 每百万 token。

#### Gemini Deep Research（Google）【官方】

- **2025-12-11 重构**：Gemini 3 Pro 推理核，HLE 46.4%（当时 SOTA）、
  DeepSearchQA 66.1%（基准已开源）、BrowseComp 59.2%；与 OpenAI GPT-5.2 同日发布。
- **Web Search**：迭代式缺口驱动重搜（自行构造查询→读结果→找缺口→再搜）；
  【第三方】社区反馈偶有只读摘要不读全文。
- **Long Context**：Gemini 3 Pro **1M token**（全产品线最彻底）；app 端 Free 32K /
  Pro·Ultra 1M。
- **Citation**：**detailed granular citations**（细粒度引用）+ 规模化多步 RL for
  search 降幻觉（SimpleQA Verified 72.1%）。
- **Knowledge Management**：上传文件 + Gems；**NotebookLM 已更名 Gemini Notebook**
  （2026-07-16）：源库（50 万词/源）+ 行内引用 + Source Attribution（整 artifact
  来源溯源）+ 每 notebook 附带云计算机（原生代码执行）【第三方】Free 约 50 源 /
  Pro 约 300。
- **Tool Usage**：统一综合上传文档（PDF/CSV）+ File Search + 网络检索；**MCP 支持
  仍在路线图未交付**。
- **定价**：算力制限额（每 5 小时刷新至周上限）；Deep Research 全层级可用但消耗大。

#### 对 PaperTeam 的含义【推测】

- 三家的「计划-执行-报告」形态印证 PaperTeam M8 受控循环的交互方向正确；但三家的
  引用均为「来源链接」级（最细到 Gemini 的行内细粒度引用），**没有一家做逐字引文
  核验或引用与证据的机械对账**——PaperTeam 的三段核验仍是独有层。
- 三家都在强化「用户私有语料 + 检索」的融合（Workspace 连接器 / Projects 文件 /
  Gemini Notebook 源库）——「用户资料进研究流」是行业共同演进方向，PaperTeam 的
  file-first workspace 结构同型，缺的是资料类型的覆盖（实验数据/图片）。
- ChatGPT 学术计划与 Gemini Notebook 值得持续跟踪：前者可能改变科研用户的默认
  工具预期，后者是「多文档溯源改写」最强环境但产出止步于报告/Docs、不成稿。

关键观察【官方+推测】：

1. **五强全部不做手稿写作闭环**（Elicit/Consensus 明确「不做手稿」；SciSpace 有
   AI Writer 但无证据纪律），**全部不做返修**。它们的「review」一律指文献综述
   （literature review），不是同行评审返修（peer review revision）。
2. 2026 年的共同动向是 **agent 化 + API/MCP 开放**（Elicit API+MCP、Consensus API
   自助开放、SciSpace Agent Gallery）——科研数据与检索能力的商品化在加速，进一步
   压低「自建检索」的价值，抬高「检索后处理」的相对价值。
3. Elicit 的列式抽取（96% 准确率评测）是 PaperTeam 证据抽取最接近的竞品形态，但
   其粒度是「字段级答案 + 篇级溯源」，不是 PaperTeam 的「quote 逐字 + chunk 锚点 +
   三段核验」——前者适合综述建表，后者适合写作与修订时的可审计引用。

  而非绑定单一平台。
- Sessions 抽象明确「session=会话历史，不是长期记忆」。

#### MCP 生态【官方+第三方】

- 最新 spec 2026-07-28（无状态化、Tasks 长任务、Skills over MCP、MCP Apps）；
  2025-12 捐给 Linux Foundation 旗下 Agentic AI Foundation；官方 Registry 已上线；
  生态约 2 万 server【第三方】。
- **学术 MCP server 已相当拥挤**（35+【第三方】）：Ai2 官方 S2 MCP、
  crossref-mcp-server、paper-search-mcp、bibliography-mcp（文献校验+BibTeX）等。
  但【代码事实+推测】OpenAlex 的 arXiv-DOI 错配（M9.7.3 已实证）是**数据源级
  问题，任何基于 OpenAlex 的 MCP server 都会继承**——权威源交叉验证不能外包给
  MCP，这正是 PaperTeam 自建 resolver 层的理由。
- 对 PaperTeam 的含义【推测】：D-0033「内部零 MCP」决策在 2026 年依然可辩护
  （进程内 TS interface 类型安全 > 跨进程协议层），且 langgraph-supervisor 归档
  反向印证了 D-0009「少量角色 Agent + 强 Tool」红线。**可留意但不跟进**。

#### 开源 Deep Research 复刻与评估基准

- GPT Researcher（29.6k★，$0.4/次）/ STORM（31.5k★，维护明显放缓）/ Local Deep
  Research（8.9k★）——**全部面向通用 web 研究，学术 evidence-grounded 细分
  （结构化引用、需求-证据对齐、可核验性）是空档**【官方+推测】。
- **DeepResearch Bench**（arXiv:2506.11763）：100 个 PhD 级任务，双维度评估 =
  RACE（自适应准则 LLM-judge）+ **有效引用数/引用准确率**——与 PaperTeam M10.0

- GAIA→Gaia2（Meta+HF）：基准范式从静态问答转向交互式环境（1,120 动态场景）。
- AI Scientist-v2（Sakana）端到端自动科研系统论文 2026 年登上 Nature——全自动
  科研叙事在学界获得可见度，但其路线（无 HITL、无证据核验）与 PaperTeam 的受控
  路线是不同产品类目【官方】。

## 3. 重点场景：Existing Paper Improvement（任务二）

### 3.1 市场现状：空白确认

目标场景链路：**旧论文（PDF/LaTeX）+ 新实验数据 + 新增文献 + reviewer/导师意见
→ 分析问题 → Revision Plan → 修改论文 → Review → 新版论文（+ response letter）**。

调研结论【官方】：

1. **科研五强（Elicit/Consensus/SciSpace/ResearchRabbit/S2）全部无此功能**（各官网
   功能面逐一核查的否定性结论）。最接近的只有非产品化变通：SciSpace Chat with PDF
   对「论文 PDF + 审稿意见 PDF」做通用问答。
2. **最接近的商业产品是 Paperpal（Cactus/Editage）**：2026-09-07 官方博客宣称
   Paperpal Agents 能「结合支撑证据逐条处理审稿意见」，配套 Chat with PDF、投稿
   就绪度检查、引用幻觉检查。**能力边界**：官方未宣称自动生成 response letter
   或自动改稿；无确定性修订安全（改得对不对由模型自己说了算）、无编译验证闭环、
   无证据 quote 锚定。定价 Prime 约 $12-19/月【第三方】。
3. **相邻工具各占一角，无人闭环**：Curie（AJE，$11.25/月）「逐条回复审稿人」由
   人工服务承接（$289/次）；Writefull Revise 只做语言修改（带 Track Changes）；
   Writefull Cite 只查引用风格。出版社侧不仅没有工具，主流政策**禁止将在审稿件
   上传至生成式 AI**（Editage 2026-08 点名 SN/Wiley）——这对 PaperTeam 的
   本地单机部署形态（数据不出机器）反而是匹配点【官方+推测】。
4. **开源侧零散生长**：以 LaTeX 模板为主（klb2/review-response-template 140★ 等）；
   自动化工具 rejoinderoo 仅 28★（表格→回复信）；新兴 Claude Code 技能形态
   （Meet-Reviewer-2 44★ 模拟审稿团、AER-Skills 52★ 经济学 R&R 辅助）；中文生态
   有小众网页工具 ReviewReply（拆卡片+跟踪+导出草稿）。**均非成熟产品**。
5. **通用 Agent 中 Claude Code 对该场景支持度最高**【官方+推测】：本地全文件系统
   + PDF 视觉读 + Bash 跑 xelatex/bibtex 重编译验证 + git diff 天然修订跟踪——
   能力齐但**全部停留在「能力」层面**：无产品化工作流、无质量门禁、无事实保持
   裁决、无引用冻结，修订正确性依赖使用者自己监督。ChatGPT DR（报告/回复信起草
   强，PDF 非企业版丢图片、不能本地编译）与 Gemini DR（Notebook 溯源强，产出止步
   报告/Docs）次之。

### 3.2 六问核查：PaperTeam 自身答卷【代码事实】

| 问题 | PaperTeam 现状 | 证据 |
| --- | --- | --- |
| 1. 支持上传已有论文？ | **是（三入口）** | `POST /projects/import-pdf`（File First 建项+回滚）、`import-paper(format=pdf/latex)`（ZIP 防 Zip Slip + best-effort 基线编译）、文献库 sources 上传（PDF/BibTeX/DOI/arXiv/URL 五路径）。PDF 确定性重建 outline/sections/references.bib（M4.8）。26 页真实中文论文全链验证过（M5.6） |
| 2. 理解实验数据？ | **部分（最大缺口）** | CSV 可上传可检索（按文本 chunk），但无表格语义解析、无「用户实验事实」一等登记——数字无法成为 factPreservation 可授权的修改依据。`verificationLevel=user_confirmed` 档位已预留但通道是纯手填 |
| 3. 支持 Evidence grounding？ | **是（管线级最强，但 improvement 流未接）** | 三段核验（quote 逐字 NFKC→metadata 权威→语义 judge）+ chunkId 内容 hash 自校验锚点 + 候选-转正状态机。**但 `existing_paper_improvement` 工作流是 M4/M5 时代形态，未接入 M8 研究循环与 M9 证据链** |
| 4. 支持 reviewer feedback？ | **是（存量最深）** | external-instructions：逐字保存、`priority=mandatory`（先于内部审稿派发）、确定性状态机（handled=报告 applied 且文件真实变化且 gate 复核通过；conflict=与实验事实冲突时保留依据不篡改）、`%%%PT-OUTCOMES%%%` 执行报告防泄漏。M9.10 三案例 E2E：诱导性意见（要求把 901.5ms 改成 800）被拒并如实报告 CONFLICT |
| 5. 支持 revision loop？ | **是（市场独有深度）** | RevisionPlanItem 七态状态机（planned→applied→validated/rejected/needs_review/approved）+ RevisionProtocolError 结构化协议断言 + 四类确定性复核（fact/citation preservation、claim strength、evidence re-validation）+ 收敛判定（PASS/IMPROVED/CONVERGED/REGRESSION）+ 预算与 HITL |
| 6. 保留修改依据？ | **是** | 不可变修订快照（revisions/rev-{n}/ + 内容指纹）+ revision-validation-r{n}.json（rejectedItems 按四类归因）+ 事实变化 A/B/C/D 分类 + 引用冻结清单（M9.10 E2E：无据删引用 baseline 7/7 → PaperTeam 0/7）+ iteration-history 收敛史 |

结论：**六问中五问已 affirmative，且深度全部超过市场现有产品；唯一实质缺口是
第 2 问（实验数据）与第 3 问的后半句（improvement 流与证据链的接线）**——两者
都是「接线/投影层」量级的工程，不是新架构。

## 4. Web Search 能力分析（任务三）

### 4.1 Claude Code Web Search vs PaperTeam Search Pipeline 七维对比

| 维度 | Claude Code【官方】 | PaperTeam【代码事实】 | 判定 |

### 4.2 回答：继续加强 Search，还是重点放在 Search 之后？

**结论：不继续加强 Search。重点放在 Search 之后的信息处理，且这一判断在 2026 年
比在 M7.1d 时点更强**【推测，依据如下】。

理由：

1. **检索能力已高度商品化且在加速**【官方】：三大厂迭代式检索 + 1M 上下文；学术
   MCP server 35+；Elicit/Consensus API 全开。任何自建检索投入的边际差异化都在
   缩小。GPT Researcher（29.6k★，$0.4/次）证明「通用 deep research 开源复刻」
   也已饱和。
2. **PaperTeam 检索层现状已被真实使用验证够用**【代码事实】：M7.1b 真实公网三场景
   38 次工具调用 0 错误；M8 真实模型验收两轮循环 15+3 queries；M9.3 全文 12/12。
   POST_M8 对检索层的唯一保留项（dense embedding 跨语言）维持条件触发结论不变。
3. **检索之后的信息处理是唯一无人做的层**【官方+推测】：竞品的「证据」止步于
   来源链接（最细到 Gemini 行内细粒度引用），无逐字核验、无候选-转正、无证据-
   需求对齐、无修订后复核。PaperTeam 在这一层的每个机制都有 E2E 实证（M6.9 零
   泄漏、M9.8 需求对齐 12/12 linkage 100%、M9.10 引用删除 7→0）。
4. **M9.9 已经是正确方向的开始**【代码事实】：evidence supply 决策闭环把「检索」
   置于「证据需求缺口」的下游——这是从「搜索驱动」到「需求驱动」的重心转移，
   应延续而非回头。

**维持的边界**（与 POST_M8 一致）：不建 Vector DB / 不建 reranker / 不引入内部
MCP；dense embedding 仅在真实项目命中跨语言检索失败时按既有
`EmbeddingProvider` 抽象接 HTTP vendor（估 ~200 行）。

## 6. Current PaperTeam Strength（已超过普通 Agent 的能力）

以下每条均为【代码事实】，附可举证的验证记录：

1. **证据纪律是类型级不变量，且有跨模型实证**：Retrieved ≠ Candidate ≠
   Literature ≠ Verified Evidence 四层分离写入 Store 与工具权限（工具层零
   EvidenceStore 写路径三重钉死）；verified 写入唯一入口经三段核验（前两段零
   LLM）。M6.9 五模型族 live 评估：无库自报 25/25 捏造 vs 管线零泄漏。**没有
   任何竞品有等价机制**【官方调研对照】。
2. **修订安全 =「LLM 改稿后由确定性代码裁决改得对不对」**：Fact Preservation
   （表格数值/公式/方向性结论，授权只认计划点名或证据含新值，A/B/C/D 分类）+
   Citation Preservation + 引用冻结清单 + Claim Strength 升级检测 + Evidence
   Re-validation。M9.10 E2E：污染修订被 build.draft 确定性阻止；无据删引用
   0/7（baseline 7/7）。
3. **External instructions 机制正中返修场景要害**：reviewer/导师意见逐字保存、
   mandatory 最高优先、conflict 语义（与实验事实冲突时拒绝执行并如实报告）、
   跨轮 instructionId 跟踪、执行报告防泄漏。这是「处理审稿意见」这件事在市场
   上最深的机制化实现——Paperpal Agents 2026-09 的官方叙事（以证据回应审稿
   意见）验证了方向，但其实现无任何确定性裁决层。
4. **确定性 bibliography 与引用全链可追溯**：SourceIdentity→key（同输入重算
   一致）→渲染（byte identical）→`\cite` 裁剪同步→任一引用可回溯 bib key→
   EvidenceRecord→chunkId→原文（M9.5 验收抽查通过）。
5. **受控研究循环（M8）**：计划→批准→执行→覆盖→缺口→HITL→派生的状态机 +
   崩溃恢复纯按磁盘事实重算 + 证据需求对齐（M9.8/M9.9：requirements 进计划、
   supply 优先、缺口供给决策闭环）。交互形态与 ChatGPT DR 的可编辑计划同型，
   但多出覆盖度分析与证据供给决策两层。
6. **LaTeX 全链与中文工程**：导入（ZIP/PDF 重建）→ 分节写作 → xelatex+bibtex
   显式编排 → Draft/Final 冻结产物；中文论文（26 页）真实 A/B 验证。开源 DR
   项目全部止步于 Markdown 报告，无一产出 LaTeX 论文。

## 7. Current Weakness（问题 → 影响 → 解决方向）

按对「返修主打场景」的阻塞度排序。前三条直接阻塞 B 方向兑现。

### W-1 实验数据无一等登记

- **问题**【代码事实】：CSV 上传后仅按文本 chunk（`SourceChunker.ts` 自注
  「csv：文件即全文」）；无表格结构化解析、无「用户实验事实」登记面。
  `verificationLevel=user_confirmed` 档位已预留，但通道是 `POST /evidence` 纯手填。
- **影响**：返修场景四要素之一「新实验」无法成为可授权的事实来源——用户的新
  数据进不了 factPreservation 的授权链（授权依据只认计划点名或 Evidence 文本
  含新值），修订时新数字要么不被允许写入，要么走手填证据无 provenance。
- **解决方向**：Personal Research Workspace 的数据投影层——「用户数据文件 →
  结构化事实清单 → user_confirmed evidence（带 file:row provenance）」，复用
  既有 EvidenceRequirement / evidence_supply / user_confirmed 语义，不触碰
  Retrieved≠Verified 不变量（难度评估见 §8）。

### W-2 improvement 工作流与 M8/M9 证据链断链

- **问题**【代码事实】：`existing_paper_improvement` 是 M4/M5 时代形态（导入→
  重建→理解→审稿→改进计划→修订），当时的文献补充靠 Researcher 单轮调研的
  bibliography；M8 受控研究循环、M9 证据核验/需求对齐/供给闭环均未接入该工作流。
- **影响**：返修场景要素「新增文献」走的是 legacy 路径——补充文献无计划、无
  覆盖度评估、无 evidence grounding，引用核验只有 metadata 层（旧 citation
  verify），拿不到 M9 链的 verified evidence 支撑。产品最强管线与主打场景没有
  相通。
- **解决方向**：接线级工程——improvement 流的 research 阶段替换为 M8 计划执行
  + 证据供给形态（复用 `hitl.evidence_supply`），修订计划的 relatedEvidenceIds
  自然获得 verified 证据来源。

### W-3 无跨 run 研究记忆

- **问题**【代码事实】：全仓跨 run/跨项目长期记忆零实现（D-0013「workspace 是
  事实源」的刻意选择）；唯一持久化是项目内 8 目录落盘。
- **影响**：第二个研究项目无法复用第一个项目的文献库/证据/缺口结论；同一课题
  的返修项目要重建文献池；「课题组级知识资产」叙事无法成立。
- **解决方向**：维持 POST_M8 的条件启动结论（M11+，以真实多项目使用为前提）；
  2026 年竞品对照（Claude Code auto memory / Gemini Notebook 共享 Library /
  Elixir 共享 Library）确认该能力已是行业标配预期，条件成熟后优先级应上调。

### W-4 token/费用不落盘

- **问题**【代码事实】：per-run usage 仅内存 200 条环 + stdout 一行日志，重启
  即失（M10.0 审计 G1）；StageRecord 无 usage 字段。
- **影响**：成本不可事后审计；M10.1 评估只能用差分/日志解析绕行（已设计）。
- **解决方向**：M10.1 先按 G1 绕行方案实现；产品侧 stage 级 usage 持久化（POST_M8
  原案）作为 M10.1 附带项或 M11 小项择机落地。

### W-5 图片/表格视觉理解缺失

- **问题**【代码事实】：图片条目 chunking 显式跳过（`full_text_unavailable`，
  注释自认「视觉解析属后续能力」）；Writer 宏包契约禁 tikz；无图片进稿管线。
- **影响**：返修场景「新图表」（用户新实验的图）无法进入稿件；已有论文中的
  图被修订时无法核对图文一致。
- **解决方向**：分两档——表格数据理解（CSV/图表数字）并入 W-1 的投影层（中
  难度）；图片视觉理解与生成维持 DO NOT BUILD NOW（多模态依赖 + 新锚点语义，
  中-高难度，POST_M8 结论维持）。

### W-6 跨语言语义检索不命中

- **问题**【代码事实】：生产 lexical-only（dense 无 vendor），中文问题查英文
  文献无词重叠时不命中（benchmark 如实记录）。
- **影响**：中文研究定位的项目检索召回受损。
- **解决方向**：条件项不变——真实项目命中该失败时按 `EmbeddingProvider` 抽象
  接 HTTP vendor；仍无 Vector DB。

### W-7 无 DOCX 支持

- **问题**【代码事实】：LaTeX 单一格式链（无 Word 读写）。
- **影响**：部分期刊返修在 Word 生态（track changes）；ChatGPT DR 反而支持 Word
  导出。属于目标用户边界问题而非能力缺陷。
- **解决方向**：登记为 limitation；目标叙事锚定 LaTeX 生态（CS/工程学科），DOCX
  不立项（除非真实用户反馈成为主矛盾）。

## 8. Implementation Feasibility Analysis（任务五）

基于代码只读审计（所有结论附文件坐标）。总判断：**扩展用户资料导入与返修场景
激活都是「既有架构内的接线与投影」量级，无需新 Runtime/新 Agent/新存储引擎，
不触碰 M6 冻结的分层不变量**。

### 8.1 Evidence Store 当前能力（已验证）

- 数据结构：`EvidenceRecord`（claim/quote≤2000/sourceRef/location.chunk 锚点/
  verificationStatus 六态/supportStrength 四级/usedBy 追踪），`evidence/
  evidence.jsonl` 纯文件（追加写 + 原子重写 + 每项目写队列）。锚点 chunkId 内嵌
  内容 hash——内容变化旧 id 自动失效，回取自校验。
- 分级与治理：候选-转正状态机（终态唯一入口 markResolved）；verified 写入唯一
  入口 appendBatch；writer 强制 formalOnly 视图（verified+锚点，构造边界强制，
  Agent 传参不可放宽）；formal 池上限 20。
- 证据-需求关联：ResearchPlan.requirements（er-N，topic/claimType/priority/
  status open|waived）+ requirementCoverage 派生视图（covered=verified 或
  promoted 命中）+ 候选 requirementId 服务端回写不可伪造。
- 用户数据语义预留：`verificationLevel=user_confirmed` 档位已存在，`POST
  /evidence`（createdBy=user）与 `POST /evidence/:id/verify`（人工确认）通道
  已通——W-1 的投影层有现成挂点。

### 8.2 Revision Loop 当前能力（已验证）

- 编排：`definitions.ts` 共享后段（citation.verify→review.run→quality.gate→
  失败→revision.plan 确定性派发→revision.revise→复核→≤maxRounds）。
- 协议加固（M9.10）：RevisionProtocolError 六类结构化错误 + 计划 schema 构建期
  断言（坏计划不落盘）+ 条目七态非法流转确定性拒绝。
- 引用冻结清单：修订 prompt 确定性提取 key 显式列出 + 四条硬规则；确定性拦截链
  完整（unauthorized removal→rejected→HITL）。
- 事实保持：不可变修订快照为事实源；A/B/C/D 分类 + 数值等价归一消 false
  positive；无法判定保守 FAIL。
- 迭代控制：预算（默认 2 轮 + HITL revise_more ≤3）+ overflow/stalled/validation
  三种 HITL + rejected 条目可回 planned 重派发。

### 8.3 Project 数据结构（已验证）

file-first 八目录（project.json/manuscript/sources/evidence/reviews/build/
workflow/research + artifacts），无数据库；三类工作流 kind（idea_to_paper/
existing_paper_review/existing_paper_improvement）；HITL 八断点齐备，其中
`hitl.evidence_supply` 已带「补充检索/上传论文/waived」三动作——W-1/W-2 的产品
停靠点现成。

### 8.4 用户资料导入难度判断表

| 用户资料 | 现状 | 难度 | 依赖 | 风险 |
| --- | --- | --- | --- | --- |
| 已有论文 PDF | 三入口已存在，M5.6/M9.10 验证 | **低**（已存在） | pymupdf（可选，缺失则降级） | 扫描件提取质量差（如实报告 poor 不伪造）；50MB 上限 |
| LaTeX source | ZIP 导入+基线编译+回滚已存在 | **低**（已存在） | xelatex/bibtex（best-effort 不阻塞） | 原工程不能编译时如实记录；无 DOCX |
| 实验 CSV/表格 | 可上传可检索，无语义登记 | **中** | 无新硬依赖 | ①用户数据进 factPreservation 授权链需 provenance 保证（file:row 锚点）；②user_confirmed 的「verified」语义需单独分级（档位已预留）；③CSV 编码/20MB 上限 |
| 图片 | 仅存储展示，chunking 跳过 | **中-高** | 多模态分析器（能力依赖模型与沙箱授权，代码自认 capability-gap）+ 稿件资产管线 | 图片作为 evidence 违反「文本 quote 逐字校验」范式，需新锚点语义 |
| Reviewer comments | external-instructions 完整机制 | **低**（已存在） | 无 | 纯文本通道；PDF 版审稿意见需先解析再转录（可用现有 PDF 链路） |

### 8.5 风险汇总（实现前须正面处理的三件事）

1. **用户数据的证据语义边界**：用户登记的实验事实是 user_confirmed 而非机械
   verified——必须保持与 grounded_verified 的分级隔离（现有 EvidenceUsageClass
   已支持），防止「用户手填」洗白成「已核验」。factPreservation 消费
   evidenceTexts 时应只把 user_confirmed 证据用于「用户自己数据的数值」的授权，
   不用于文献事实。
2. **既有论文的 baseline 事实基线**：返修链的 factPreservation 以导入重建的
   修订快照 rev-1 为基线——PDF 重建是文本级（不含原版式/图），基线登记时须
   让用户确认关键数值表（否则 W-1 的授权链建立在机器重建文本上）。
3. **成本与预算**：M9.7.1 实测全管线 $3.48/35-45min；improvement + 研究循环 +
   证据链的合并工作流会更长——M10.1 的成本采集（G1 绕行）应先行，否则新场景
   无法被成本评估。

## 9. Recommended Roadmap（任务四/五）

### 9.1 六个候选方向的优先级判定

| 方向 | 判定 | 依据 |
| --- | --- | --- |
| **B. Existing Paper Revision** | **最高（M10.3 主打）** | 市场空白已验证（§3.1 五强皆无，Paperpal 无确定性裁决）；PaperTeam 存量机制最深（六问五 yes）；差异化叙事最锐（「可验证的返修」vs「AI 帮你回信」） |
| **A. Personal Research Workspace** | **高（M10.2，B 的前置）** | 是行业共同演进方向（三家通用 Agent 均在强化私有语料融合）；PaperTeam 大半已有（file-first+上传通道），实际增量集中在实验数据登记（W-1，中难度）；没有它 B 场景缺一要素 |
| **C. Research Memory** | **中（M11 条件启动）** | 唯一被竞品全面超越的行（§5）；但价值以真实多项目使用为前提（POST_M8 论证维持）；M10.2/M10.3 落地后自然产生第二个项目，届时条件成熟 |
| **D. Figure/Table Agent** | **低（拆开处理）** | 表格数据理解并入 W-1 投影层（服务于实验数据，中难度）；figure 视觉理解与生成维持 DO NOT BUILD NOW（多模态依赖+新锚点语义+Writer 宏包契约）；「Agent 化」本身违反 D-0009 |
| **E. Search Optimization** | **不做（维持现状）** | §4.2 结论：检索已商品化，自建投入边际差异化缩小；四学术源+SearXNG 已被真实使用验证；唯一条件项 dense embedding（跨语言触发） |
| **F. Multi Agent Collaboration** | **拒绝** | D-0009 红线（少量角色 Agent+强 Tool）三次验证未破例；2026 市场信号反向印证（langgraph-supervisor 官方归档、open_deep_research 归档、OpenAI 官方批评模型无关框架）——重型多 agent 编排在退潮，「图+工具调用+subagent」是共识 |

### 9.2 M10.1-M11 建议

**M10.1 — Evaluation Framework Implementation（维持已冻结设计，不改）**

- 内容：按 M10.0 五份设计文档实现（三臂 L-C-P 基准/驱动器/统一核验器/任务集/
  盲评通道），P0 = 模型平价冒烟（Claude Code 指向 GLM 网关 anthropic 兼容端点，
  M10.0 审计已确认通道可行但未冒烟）。
- 为什么它仍然第一：①设计已冻结、投入沉没成本低；②**B 方向的主张（「我们的
  返修比通用 Agent 可信」）只有三臂对比数据才能对外讲**——没有 Arm C（Claude
  Code）数据，差异化停在自述；③G1 成本采集绕行是新场景成本评估的前置。
- 可选附带项（小）：stage 级 usage 持久化（W-4 产品侧），若实现成本低可并入。

**M10.2 — Personal Research Workspace（数据侧）**

- Goal：用户研究资料成为一等公民——重点是实验数据：CSV/表格 → 结构化事实清单
  → user_confirmed evidence（file:row provenance）→ 进 factPreservation 授权链。
- 范围建议：①数据资产登记面（表格结构化解析 + 关键数值用户确认 = baseline 事实
  基线，同时解决 §8.5-R2）；②evidence_supply 扩展「上传数据」动作；③user_
  confirmed 与 grounded_verified 的分级隔离护栏（§8.5-R1）。
- 明确不做：图片视觉理解（中-高难度，维持后续）、DOCX、跨项目资料共享（属 M11
  记忆范畴）。

**M10.3 — Existing Paper Revision 全链路激活（主打场景）**

- Goal：打通「旧论文 + 新实验（M10.2）+ 新增文献 + 审稿意见 → 分析 → Revision
  Plan → 修改 → Review → 新版论文」的完整产品路径。
- 范围建议：①W-2 接线——improvement 工作流的 research 阶段替换为 M8 计划执行+
  M9.9 证据供给形态；②新增文献经锚定证据路径进修订依据（relatedEvidenceIds）；
 ③response letter 产物——external instructions 的 handled/conflict 状态机
  （PT-OUTCOMES）天然是一份 response letter 骨架，落盘为正式产物（每条意见：
  意见原文/applied-conflict/修改位置/依据证据）——这是市场空白里最轻的可兑现
  物；④E2E 验收：一篇真实旧论文 + 新数据 + 意见跑完整链，报告如实记录。
- 依赖：M10.2（实验数据要素）；M10.1 不阻塞但提供对比数据。

**M11 — Research Memory + Revision 场景收口（条件启动）**

- Research Memory：M10.3 后若出现第二个真实项目，按「记忆是 Derived Context 不是
  第二事实源」约束（D-0013）实现跨 run 研究状态沉淀（coverage 历史/gap 决策/
  文献池复用入口）。
- Revision 收口：真实用户验证（至少 1-2 个真实返修案例全链走完 + M10.1 口径的
  效率/成本对比数据）；视反馈决定 DOCX/图片等边界项是否升级。
- 条件项池：dense embedding（跨语言触发）、图片表格理解、bibliography-mcp 类
  外部能力对接评估。

### 9.3 与既有路线决议的关系

- POST_M8 的 M10（Observability）/M11（Evaluation）编号已被 M10.0（Evaluation
  Framework Design）实际占用——本报告按现状编号（M10.1=评估实现），Observability
  收敛为 M10.1 附带项/M11 小项（G1 绕行优先）。
- DO NOT BUILD 清单（Vector DB / Python 服务 / 内部 MCP / 自动路由 / reranker /
  Knowledge Graph / 无人值守自主循环）全部维持——2026 年市场调研未出现推翻
  任一条的新证据；langgraph-supervisor 归档反而加固了「少量 Agent+强 Tool」。
- 红线不变：零新增 Agent 角色；Retrieved≠Candidate≠Literature≠Verified 不变量
  不触碰；用户自供数据的 verified 语义单独分级。

## 10. 结论

1. PaperTeam 的护城河在「检索之后」——证据三段核验、修订四类复核、确定性
   bibliography、external instructions 状态机，四件都没有竞品等价物【官方调研
   对照 + 代码事实】。
2. 返修场景（B）是 2026-09 已验证的市场空白，PaperTeam 六问中五问已 affirmative，
   兑现成本 = W-1 数据投影（中）+ W-2 接线（接线级）+ M10.1 对比数据（已在排期）
   【代码事实+推测】。
3. 建议路线：M10.1 评估实现（维持）→ M10.2 Personal Research Workspace 数据侧 →
   M10.3 Existing Paper Revision 激活 → M11 Research Memory（条件）+ 收口。
4. 明确不做：Search 加强（E）、多 Agent 协作（F）、figure 生成、Vector DB、
   内部 MCP、DOCX（登记 limitation）。
