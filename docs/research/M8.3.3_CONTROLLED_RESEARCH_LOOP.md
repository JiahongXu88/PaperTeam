# M8.3.3 — Controlled Research Loop Foundation 实施报告

- 日期：2026-09-20
- 状态：已完成（实现 + 测试 + 文档；backend / frontend 全量测试、build、typecheck 通过）
- 范围：Human-in-the-loop 受控研究循环的地基——Coverage 缺口升级为显式研究对象
  （ResearchGap），经用户确认（accept）后可派生下一轮计划，并预注册循环边界
  （Loop Policy）。**不是无人值守 Deep Research**：M8.3.3 不自动执行任何循环步骤
  （无 while loop、无调度器；分析、确认、派生、批准、执行全部显式触发）。
- 冻结规则遵守声明：**不新增 Agent**（无 Planner / Coverage / Research Loop
  Agent）、**不修改 Runtime / Workflow Orchestrator**（新服务不进
  workflowServices）、**不引入 RAG / Vector DB / MCP / 新 Provider / CLI**、
  **Evidence 链路原样**（Gap 是分析结果不是 Evidence；accept / reject / derive
  不触碰 EvidenceStore / CandidateStore / SourceStore）。

## 1. 目标

M8.3.2 交付了只读覆盖分析 + 缺口建议，但「下一轮搜什么」仍是一次性建议——
没有确认环节、没有可追溯的决策记录、没有循环边界。M8.3.3 建立受控循环：

```
Coverage（覆盖分析，M8.3.2）
   ↓
Research Gap（缺口成为显式对象：gapId / severity / status=proposed）
   ↓
Human Approval（用户 Accept / Reject——循环的真实断点）
   ↓
Next Plan（从 accepted 缺口派生 draft，复用 M8.3.1 derive）
   ↓
Human Approval（用户批准计划，M8.2 approve）
   ↓
Next Execution（用户执行计划，M8.2 execute）
```

每一环都由用户显式触发；系统只负责给出可决策的结构化状态。

## 2. Research Loop 架构

```
ResearchCoverageService（M8.3.2，只读）
        │  coverage.gaps: ResearchGap[]（确定性 gapId，status=proposed）
        ▼
ResearchGapService（M8.3.3，新增）                research.json 顶层
        │  list      → 覆盖派生 + 决策覆盖          gaps?: ResearchGap[]
        │  accept    → proposed → accepted ────────▶（决策快照落盘）
        │  reject    → proposed → rejected ────────▶（决策快照落盘）
        │  derive    → accepted 缺口 ─┐
        ▼                             │
ResearchPlanIterationService（M8.3.1，复用，不新建第二套 Plan 创建逻辑）
        │  derive(source=缺口来源计划, 缺口默认值 + 用户改写)
        ▼
新 draft ResearchPlan（iterationNumber+1 / parentPlanId / 自动激活）

researchLoopPolicy.ts（M8.3.3，新增）
        loopPolicy?: ResearchLoopPolicy（research.json 顶层；只保存不执行）
```

分层不变量：

- **Coverage 只读纪律不变**：分析仍是即时重算的派生视图，不落盘（M8.3.2 决策
  原样）；缺口清单 GET /research/gaps 同为「派生 + 决策覆盖」，proposed 状态
  永不落盘——落盘的只有用户决策快照（accepted / rejected），杜绝状态双写漂移。
- **单一派生逻辑**：从缺口派生下一轮 100% 复用 `planIteration.derive`
  （M8.3.1）：状态校验（done 才可派生）、iterationNumber=链内最大+1、
  parentPlanId、检索重置 planned、自动激活、写盘——缺口侧只构造默认输入
  （questions 来自缺口、queries 来自 suggestedQueries），用户改写优先。
- **单一写入口**：gaps 决策与 loopPolicy 经 `writeResearchLoopState`
  （ResearcherService，与 writeResearchPlanChain 同风格）写回 research.json；
  research() / 论文理解重跑不覆盖这两个字段（merge strategy：用户可控状态一律
  保留，与 M8.3.1 计划链同纪律）。
- **旧计划永不被改写**：derive 只追加新轮次；来源计划保持 done 原样。

## 3. ResearchGap 模型（`backend/src/agents/researchGap.ts`）

```jsonc
{
  "gapId": "gap-3f9c2a1b8d7e",   // 确定性：sha256(planId + 问题/残差方向) 前 12 位
  "planId": "rp-…",              // 产生该缺口的计划（= 分析时活动计划）
  "question": "遮挡场景身份保持",  // 关联研究问题（残差方向缺口无此字段）
  "description": "计划中没有任何与该问题相关的检索（…）",
  "severity": "high",            // low | medium | high（确定性规则，见下）
  "suggestedQueries": ["遮挡场景身份保持"],
  "status": "proposed",          // proposed | accepted | rejected
  "createdAt": "…",              // = 覆盖报告 analyzedAt
  "decidedAt": "…"               // 用户决策时间（proposed 省略）
}
```

**severity 确定性规则**（无 LLM，从覆盖判定字段直接导出）：

| 来源 | severity | 依据 |
| --- | --- | --- |
| missing 且无关联检索（relatedQueryCount=0） | high | 计划完全没有该方向 |
| missing 但有相关检索未带回结果 | medium | 有方向无产出 |
| partial（有结果无证据/入库文献） | low | 有结果，缺支撑层 |
| report.literaturePlan 残差方向 | medium | 调研方声明的检索后残差 |

**gapId 稳定性**：同一计划同一问题/方向的缺口跨多次分析得到同一 id——用户
决策才能可靠挂回。覆盖来源消失（问题转 covered）时缺口从派生视图自然消失，
决策记录休眠（不删除；方向再次出现时自动恢复显示，休眠缺口不可操作 → 404）。

**持久化决策**：research.json 顶层 `gaps` 字段只存 accepted / rejected 快照
（决策记录语义：以落盘时内容为准），硬帽 100 条（超限丢最旧）；读取宽容
（形状非法 / proposed 条目按不存在处理）。Coverage API 兼容性：
`coverage.gaps` 由 M8.3.2 的 `{description, relatedQuestion, suggestedQueries}`
升级为 ResearchGap[]——**纯增量扩展**（原三字段语义分别由 description /
question / suggestedQueries 承载，relatedQuestion 更名为 question），
GET/POST coverage 端点形状与只读语义不变。

## 4. HITL 流程（Gap Acceptance Flow）

状态机：`proposed → accepted | rejected`。

| 动作 | 语义 | 边界 |
| --- | --- | --- |
| Coverage Analyzer | 只能产生 proposed（buildResearchGaps 结构性保证，永不自动 accepted） | 不写盘 |
| POST …/gaps/:gapId/accept | proposed → accepted，落决策快照 | 幂等（重复 accept 不写盘）；已 rejected → 409 GAP_INVALID_STATE（决策不翻转） |
| POST …/gaps/:gapId/reject | proposed → rejected，落决策快照 | 幂等；已 accepted → 409 |
| POST …/gaps/:gapId/derive | **只对 accepted 缺口开放**（Human Approval 是派生门槛，不是记录性装饰） | proposed / rejected → 409；来源计划非 done → 409 PLAN_INVALID_STATE（透传 M8.3.1）；未知 gapId → 404 |

派生默认值（用户改写优先，`{questions?, queries?}` 请求体与 M8.3.1 derive
同契约——不接受 queryId / status，新计划检索全部从 planned 起步）：

- questions = 缺口关联问题（`[gap.question]`）；残差缺口无问题 → 整拷来源计划
  问题（M8.3.1 derive 缺省语义）；
- queries = suggestedQueries（kind=academic，rationale 登记「来自研究缺口
  {gapId}：…」的溯源说明）。

## 5. API（符合既有 httpServer 风格）

| 方法 | 路径 | 语义 |
| --- | --- | --- |
| GET | `/api/projects/:id/research/gaps` | 当前活动计划缺口清单（覆盖派生 + 决策覆盖）；无 artifact / 无计划 → `{planId: null, gaps: []}` 空态 |
| POST | `/api/projects/:id/research/gaps/:gapId/accept` | 接受缺口（proposed → accepted）；200 `{gap}`；幂等 / 409 / 404 |
| POST | `/api/projects/:id/research/gaps/:gapId/reject` | 拒绝缺口（proposed → rejected）；同上边界 |
| POST | `/api/projects/:id/research/gaps/:gapId/derive` | 从 accepted 缺口派生下一轮；200 `{plan}`（draft、自动激活）；409 / 404 / 400 |
| GET | `/api/projects/:id/research/loop-policy` | 循环策略（无落盘值 → 默认 `{maxIterations:5, maxQueriesPerIteration:20, stopConditions:[no_new_coverage, budget_exceeded, iteration_limit]}`；无 artifact 也是默认值空态） |
| PUT | `/api/projects/:id/research/loop-policy` | 校验后保存到 research.json `loopPolicy`（maxIterations 1-20 / maxQueriesPerIteration 1-100 整数；stopConditions 已知枚举非空子集去重）；无 artifact → 404 |

错误口径：项目不存在 → 404 PROJECT_NOT_FOUND；方法不允许 → 405；
新错误码 `GAP_INVALID_STATE`（409）。服务装配：`serviceStack.gaps`
（ResearchGapService，依赖 ProjectStore + ResearchCoverageService +
ResearchPlanIterationService）。

### Loop Policy（第五部分：只保存规则，不实现执行）

```jsonc
{
  "maxIterations": 5,             // 单迭代线索最大计划轮数（1-20）
  "maxQueriesPerIteration": 20,   // 单轮检索预算（1-100）
  "stopConditions": ["no_new_coverage", "budget_exceeded", "iteration_limit"]
}
```

M8.3.3 的任何代码路径都**不读取**策略做控制流——它是给未来 M8.4
「受控多轮检索循环」预注册的边界（Self Review §5：不做无人值守长循环，
未来自动化也必须在服务层、按此预算与停止条件有界执行）。

### UI（DiscoveryPanel「Research Gaps」区域，第六部分）

覆盖分析区块保留问题三态与汇总（M8.3.2），其缺口列表与「按缺口派生」
按钮**上移重构**为本区块（受控循环要求确认在派生之前）：

- 每条缺口：标题（问题/残差描述）+ 严重度徽标（高/中/低）+ 状态徽标
  （待确认/已接受/已拒绝）+ 建议检索 + gapId + 决策时间；
- Actions：待确认 → 接受 / 拒绝；已接受 → 「由此派生下一轮计划」
  （活动计划非 done 时禁用，与后端 409 同口径）；已拒绝 → 仅审计展示；
- 派生调用 `POST /research/gaps/:gapId/derive`，成功后计划链 / 缺口清单
  一起失效重取（新 draft 出现在 Research Plan 区块，仍需批准才会执行）。

## 7. 未来自动化方向（M8.4+ 前置建议）

1. **受控多轮执行器（M8.4）**：在服务层实现有界循环编排——
   `execute(plan done) → analyze coverage → gaps（仅 accepted）→ derive →
   approve 断点留给用户`。第一步只自动到 derive 为止：approve / execute
   的 HITL 断点不撤（M7 Self Review §5：不做无人值守长循环）。
2. **预算与停止条件落地**：Loop Policy 的三个停止条件届时接入执行器——
   `iteration_limit`（链内轮数 ≥ maxIterations）、`budget_exceeded`
   （单轮 executed 检索数 ≥ maxQueriesPerIteration）、`no_new_coverage`
   （相邻两轮 covered 计数无增量；executionHistory 已带 planId 可按轮归因）。
3. **covered 判定收紧**：循环场景建议把 covered 从「任意 evidence」收紧为
   「verified evidence 或 promoted literature」（尊重 Verified Evidence
   顶层语义，M8.3.2 报告 §7.2 遗留项）。
4. **语义归因（可选）**：token 匹配的跨语言 / 同义改写局限仍在；若引入，
   复用 Researcher 通道做「标注层」叠加在确定性报告之上（可关闭、LLM
   不可用回落本版规则），不新增 Coverage Agent。
5. **决策记录审计视图**：休眠 / 历史决策目前只在 research.json；如需要
   「本次研究共确认过哪些方向」的审计面，可加只读 GET
   `/research/gaps/decisions`（不新增状态源，只是落盘数据的投影）。
