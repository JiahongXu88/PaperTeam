## 1. 起始问题（M10.3 PARTIAL 的两个缺口）

### G1：累计 Fact Preservation 漏洞（漂移「洗白」）

M10.3 真实 E2E 中，rev-2 的整文件修订重写了 λ_smooth 超参段：原文「λ_smooth 较小（0.25--0.5）时 MOTA 与 IDF1 影响不大……」被改写为以 67.3/67.1/71.5/71.0 四个无授权对比数字重新解释协议。Fact Preservation 在 gate r2（pairwise rev-1→rev-2）**正确检测到**；问题在于后续轮次 Writer 把 rev-2 当作既有稿件，rev-3…rev-10 不再触碰该段——每轮 pairwise（previous → current）都 clean，**最终稿相对冻结基线的累计漂移从未被任何 gate 规则呈现**，随基线滞留至终稿（Draft 以 gate FAILED-on-record 产出）。

### G2：Quality Gate / Feasibility 对 Existing Paper Revision 的收口问题

最终 gate（r10）：unsupported critical claims 9 / blocking 4 / critical 2 + major 9 / academicScore 79（阈值 80）/ feasibility **INSUFFICIENT**（8 项缺失需求）→ Final 被阻断。审计发现两类**错误适用**：

1. 9 条 UNSUPPORTED claim 中 **8 条是冻结原稿的既有声明**（摘要的 BDD100K / RDK X3 部署 / 基线对比 / 数据集事实 / RTX 4090 环境）——返修任务不引入也不改写它们，却被按「新 claim」要求重证；
2. feasibility 的 8 项缺失需求几乎全部是「从零完成全部研究阶段」标准（BDD100K 完整训练、四基线重跑、MRG-DTM 独立消融、板端部署完成、多种子方差、SOTA 实测……）——对「在已有论文和现有实验基础上可靠修订」的任务语境不适用（其中修订相关的 HARM 数值项实际有 user_confirmed 作者证据可覆盖）。

## 2. G1 root cause（代码级）

1. `computeFactPreservation` 只比较**相邻修订**（previous vs current）；「历史违规 + 本轮未触碰」在 pairwise 口径下不可见；
2. **pairwise 授权的漂洗漏洞**：revision.plan 为 gate 违规生成 `fact_preserve` 条目，其 problem 文本包含「before → after」片段；`buildAuthorization` 把 planned 条目文本作为通用授权（`plan_value_correction` 对称匹配 before/after 双值）——**「要求恢复它的计划」反而授权了「保留违规值」**；
3. 无确定性恢复通道：Writer 对「读起来合理」的未授权改写不会自行恢复（M10.3 实测 4 轮未恢复），系统只有「请求 Writer 改回」这一条低收敛路径。

## 3. Cumulative Fact Preservation 设计（G1 修复）

```
Frozen Baseline（导入 rev-1）
        + Approved ImprovementPlanItems（fact-authorizations.json，append-only）
        + Evidence authorized values
        ↓
Expected Fact State → vs Current Manuscript → CumulativeFactValidation
```

- **新增 `backend/src/quality/cumulativeFactPreservation.ts`**：
  - `computeCumulativeFactPreservation(deps, projectId, reviewedRevision, { existingPaper })` —— 复用 `evaluateFactPreservation` 的全套确定性提取 / 授权匹配（表格 / 正文数字 / 公式 / 方向 / 协议 / 占位），previous = 冻结基线快照，current = 被审阅修订；
  - **unresolvedViolations 由 Frozen → Current 得出**（不是 Previous → Current）；任何历史未授权漂移跨轮保持 unresolved（carry-forward），只有两条出路：(A) 当前稿恢复冻结基线值；(B) 已批准计划 / Evidence 授权新值；
  - `resolvedViolations`：与历史各轮 gate 产物中登记过的违规指纹对比（violationKey = file|reason|before|after 的稳定哈希）——「曾违规、现已恢复 / 获授权」进入审计轨迹；
  - 冻结基线判定 `findFrozenBaselineRevision`：existing_paper 工作流 = 最早修订（M10.3 真实项目实测导入链路首个修订由 review.snapshot 提交，reason 不一定为 baseline）；idea_to_paper = 只认显式 reason=baseline（首稿是 Writer 输出，不构成冻结导入稿，累计口径中性 null）。
- **授权台账 `research/fact-authorizations.json`（append-only）**：`hitl.plan_confirm approve` 时把改进计划条目（action / rationale / expectedFactChanges / relatedEvidenceIds / instructionId）固化登记——后续 run 覆盖 `improvement-plan.json` 也不丢失已授予的授权；按 itemId+文本指纹幂等去重。**累计授权只认台账 + Evidence**；`reviews/revision-plan` 的 fact_preserve 条目（恢复指令）绝不进入累计授权——否则漂移会被「要求恢复它的计划」洗白。
- **Gate 规则 `cumulative_fact_preservation`**（`gates.ts`）：`quality.gate` 计算并落盘（gate 产物 `cumulativeFactPreservation` 字段）；Final 必须通过（FinalizeService 消费 gate.passed，天然阻断）；Draft 不阻断但**必须显式可见**——`build.draft` 发 `fact_preservation.cumulative_unresolved` 域事件并在 stage 结果携带 unresolved 计数，Revision Trace 报告专章呈现（任务 §7：不能隐藏）。

## 4. Carry-forward 规则（确定性测试锁定，任务 §10 Cases A–D）

| Case | 场景 | 判定 |
|---|---|---|
| A | rev1→rev2 引入未授权值 | cumulative unresolved ≥ 1（ok=false） |
| B | rev2→rev3 不再触碰该段 | pairwise clean **但** cumulative 违规仍在 → gate Final FAIL |
| C | 后续恢复冻结值 | cumulative ok + resolvedViolations 记录历史违规 |
| D | 授权台账（expectedFactChanges / 条目文本） | 合法变更 → authorizedChanges ≥ 1，无违规 |

另加「台账持久性」测试：improvement-plan.json 被后续 run 覆盖后授权不丢失。

## 5. Restore / Authorization 规则（确定性恢复，任务 §8-§9）

- **`backend/src/quality/factRestore.ts`**：`planFactRestore`（段落级恢复规划，纯函数）+ `applyFactRestore` + `restoreValueDelta`（恢复连带数值增删清单）。克制边界：
  - 只做**段落级整段替换**（空行分块）：定位 = 违规数值锚点在当前稿**唯一**含该值的段落 + 冻结稿同文件最佳相似段落（词面 Jaccard ≥ 0.30 且领先次佳 ≥ 0.08；changed 类还要求冻结段含旧值——恢复方向正确性）；
  - LaTeX 转义（`26.1\%`）先剥离反斜杠再匹配；
  - **引用守卫**：当前段落含冻结段没有的 `\cite` → 不恢复（恢复不能连带删引用）；
  - 锚点歧义 / 定位失败 → 不恢复，保持 gate FAIL + 交 Writer / 用户；
  - 不做 diff patch engine / 模糊文本猜测 / LLM restore。
- **新 stage `revision.restore_facts`**（确定性，无 LLM）：消费最新 gate 的累计违规 → 规划恢复 → 写回段落 → 提交 `reason=revision.restore_facts` 的不可变修订 → 已解决违规的 fact_preserve 条目两步流转 planned→applied→**validated**（resolution=deterministic_restore）→ 发 `fact_restore.applied` 域事件。**同时把恢复的连带数值增删并入同文件条目的 factRestore**（恢复动作删除漂移值 / 加回原值，pairwise 下一轮按 removal/addition 计，须授权——否则恢复被误报）。
- **plan() 路由**：revision.plan 结果携带 `restorableFacts` 计数（同一确定性计算）；`restorable > 0` 且本轮未恢复过 → 先走 restore（恢复产生新修订 → 尾部整段重走复审）；恢复后剩余 planned 条目照常派发 Writer（兜底）——任何违规都保证有执行者。
- **pairwise 漂洗修复**（`factPreservation.ts` `buildAuthorization`）：
  - fact_preserve 条目**整体移出**通用 planTexts（其 before→after 文本不再构成 plan_value_correction 授权）；
  - 新增 `factRestore` 通道（条目可选字段 `restoreValues` / `removeValues`，由违规的 classification 确定性提取）：只授权**恢复方向**——改回旧值 / 加回被删原值 / 删除无依据新增值（basis=planned_fact_restore）；
  - 恢复授权在条目生命周期内持续有效（validated 后仍授权——否则恢复自身的变更在下一轮 pairwise 失去授权；rejected/skipped 除外）。
- **λ_smooth 本轮裁决（任务 §9）**：无新 Evidence 明确授权时默认最保守方案——确定性恢复冻结原文；不使用 67.3/67.1/71.5/71.0 重新解释该段（除非系统能从 manuscript/structured data 建立明确 provenance + 用户确认授权 + 计划 expectedFactChanges——本轮未建立）。

## 6. G2：unsupported claims 分类 + Quality Gap → Evidence Requirement（任务 §12-§15）

- **新增 `backend/src/review/claimGapAudit.ts`**（确定性，无 LLM）：review.run（existing_paper 流程）对每条 UNSUPPORTED/CONTRADICTED claim 归层，落盘 `reviews/claim-gap-audit-r{round}.json`（机器可读）：
  - `excluded_pre_existing`（E）：claim 数值**全部**存在于冻结基线（或无数字 claim 与基线段落词面重合 ≥ 0.35）→ 原论文既有内容，返修语境不重证（作者裁决）；
  - `excluded_author_data`（A）：claim 数值由 user_confirmed 作者实验证据（jsonPath 溯源）覆盖 → 作者自己的实验结果无需外部文献重证（携带 evidenceIds）；
  - `revision_introduced`：其余 → 修订引入的无支撑 claim，仍按原规则阻断（B/C/D 出路：已有证据关联（claim repair directives 既有机制）/ targeted supply / weaken——找不到可靠证据则降强度，不生成不存在引用；weakening 由 weakenedClaim 语义与 claim_strength_guard 把关）。
- **issue 归因**：fact / evidence_gap 类 critical/major/blocking issue 若可归因到被排除 claim（章节匹配 + 描述词面重合 ≥ 0.2 或逐字包含），不计入 Final 阻断口径——否则修订循环会反复派发作者级问题直到 stalled（M10.3 实测行为）。
- **Gate 规则 4/5/6 消费归层**（`claimGapAudit` 输入）：unsupported critical claims / blocking / open critical+major 只对**修订引入**口径计数；被排除项在 rule detail 与审计产物逐条留档（含依据），不隐藏。
- **revision.plan 消费**：归因排除的 issue 仍入计划（留档）但 status=skipped 不派发（note 注明返修语境不适用 + 作者裁决）。
- **Gap-driven research**（任务 §14）：本轮 rerun 的检索仍由改进目标研究计划驱动（批准后执行）；最终 gate 暴露的修订引入缺口走 claim repair / weaken / 作者裁决——不重跑整篇论文的泛搜索。

## 7. G2：Feasibility Task-aware Applicability（任务 §16-§18）

- `FeasibilityService`（assessKind=existing_paper）：
  - **Prompt 纪律**：明示返修任务语境——永远 required（不能 N/A）：修订内容 factual correctness / 修订引入论断 evidence support / 引用完整性 / 修订新增 claim 可行性 / 修订引入的 research gaps；默认 not_applicable（除非修订声称完成）：从零写作级的完整研究阶段（基线重跑 / 完整数据集训练 / 板端部署完成 / 多种子方差 / SOTA 实测——原论文既有实验体系的完备性由作者在新投稿语境裁决）；level 与适用性必须一致（全部 not_applicable 不得 LOW/INSUFFICIENT）；
  - **Schema**：`criterionApplicability[{criterion, applicability: required|not_applicable, reason}]` 逐条覆盖 missingRequirements / requiredExperiments / researchGaps；
  - **确定性校验**：列出差距却无适用性 → 拒绝（重试）；not_applicable 无非空 reason → 拒绝（不能为过 Gate 自动 N/A）；LOW/INSUFFICIENT 但全部差距 not_applicable → 自相矛盾拒绝。
- Gate `target_feasibility` 规则：**判定口径不变**（level 仍由评估器诚实给出，不因 N/A 条目自动放行）；detail 呈现 required / not_applicable 计数；逐条理由见 feasibility.json 与 Revision Trace。
- Revision Trace（`revisionResponse.ts`）新增三节：四、Cumulative Fact Preservation（结论 + 授权来源 + 未解决明细 + 已解决审计）；五、Claim Gap Audit（归层表 + 依据）；六、Feasibility（适用性表）。
