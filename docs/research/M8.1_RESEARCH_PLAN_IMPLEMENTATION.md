# M8.1 — Research Plan 一等产物实施报告

- 日期：2026-09-20
- 状态：已完成（实现 + 测试 + 文档；backend 1362 / frontend 214 测试全绿）
- 范围：将 ResearchPlan 提升为 research artifact 的一等字段，配套 Researcher 输出契约、
  读写 API 与 Discovery UI 展示/编辑。**不新增 Agent、不改 Runtime、不改 Workflow
  Orchestrator、不引入 RAG/Vector DB/新 Provider/MCP/CLI**（M8 架构冻结规则全部遵守）。

## 1. 目标

M8 的方向是把 PaperTeam 从 Search Agent 演进为 Deep Research Agent。M8.1 先落
「Research Plan 一等产物」：让检索从一次性的即时动作，变成有计划（研究问题 +
检索词及理由）、可查看、可编辑、可追溯的一等对象。具体目标：

1. ResearchPlan 领域模型（类型完整、默认状态、可序列化）；
2. research.json 从 ResearchReport 升级为 Research Artifact（`{ plan?, report }`），
   向后兼容（旧 artifact 无 plan 仍可读，所有既有消费者不受影响）；
3. Researcher Agent 输出升级：Prompt 明确区分「plan 用于指导检索（检索前制定）」与
   「report 用于总结研究结果（检索后综合）」，输出 schema 可校验（宽容解析）；
4. Research Plan API：GET / PUT `/api/projects/:id/research/plan`（参数校验、错误
   处理与既有 API 风格一致）；
5. Discovery UI 增加 Research Plan 展示（Topic / Questions / Queries + 理由），
   支持查看 / 编辑 / 保存；
6. 测试：backend schema / API / backward compatibility，frontend UI 测试。

## 2. 架构设计

### 2.1 冻结规则的落实

| 冻结规则 | 落实方式 |
| --- | --- |
| 不新增 Agent（无 Planner Agent） | `ResearchPlan` 是 `ResearcherService` 的内部能力：plan 由 Researcher 在同一次调研任务中产出（Prompt 要求 0「先计划后调研」），无独立 Runtime 任务 |
| 不修改 Runtime | 零 Runtime 改动；plan 走 Researcher 既有 `runAgent` 输出的 JSON 字段 |
| 不修改 Workflow Orchestrator | plan 不进 Workflow：stage / checkpoint / DoD 零变化（`research.idea` 的 DoD 仍只检查 report.researchGaps），plan 只是 artifact 的可选字段 |
| 不引入 RAG / Vector DB / 新 Provider / MCP / CLI | 全部复用既有装配；plan 不触碰任何检索 Provider |
| Retrieved ≠ Candidate ≠ Literature ≠ Verified Evidence 不变量 | plan 只是检索**意图声明**：不写任何持久化结果、不进 CandidateStore / SourceStore / EvidenceStore。`resultCount` 是执行侧回填字段，编辑 API 明确不接受 |

### 2.2 模块拓扑（全部为既有模块内的小步增量）

```
backend/src/agents/researchPlan.ts     ← 新增（唯一新文件，纯领域模块：类型+解析+校验+合并）
backend/src/agents/ResearcherService.ts ← 修改（artifact 类型 + prompt + research() 接线 + updateResearchPlan）
backend/src/httpServer.ts               ← 修改（research 资源块内新增 /plan 路由）
frontend/src/types/researchPlan.ts      ← 新增（视图类型，镜像后端）
frontend/src/api/researchPlan.ts        ← 新增（GET/PUT 客户端）
frontend/src/hooks/queries.ts           ← 修改（queryKeys.researchPlan + 两个 hooks）
frontend/src/components/project/DiscoveryPanel.tsx ← 修改（新增 ResearchPlanSection）
frontend/src/pages/ProjectPage.tsx      ← 修改（传 topic prop）
```

关键决策：

- **宽容解析（tolerant parse）**：`parseResearchPlan` 对 Agent 输出按条校验、
  非法条目丢弃（与 `readBibliography` 同风格）；无 plan / 空 plan → `undefined`，
  artifact 省略 plan 字段。这保证旧输出契约（scripted runtime、历史项目）零破坏，
  也是「输出 schema 可校验」的实现方式——校验发生在解析层，不炸整次调研。
- **ID 与时间戳由后端生成**：模型 / 客户端均不指定 `planId`（`rp-` + 12 位随机
  十六进制，与项目 id 同风格）与 `queryId`（`q-<n>`，1 起，编辑往返不漂移）。
- **整体替换 + 受限编辑**：PUT 的 `queries` 为整体替换语义；同 `queryId` 条目
  继承既有 `status`（缺省时）与 `resultCount`（执行状态不被编辑面冲掉），
  新条目分配不冲突 id。`plan.status` 流转（draft→approved→…）不在本里程碑
  编辑面范围内。
- **编辑即初始化**：旧 artifact（无 plan）收到 PUT 时初始化 draft 空计划起步；
  无 artifact 则 NOT_FOUND（先运行调研）。

## 3. 数据结构

### 3.1 ResearchPlan（backend/src/agents/researchPlan.ts，前端 types/researchPlan.ts 镜像）

```ts
type ResearchPlanStatus = "draft" | "approved" | "executing" | "done";
type ResearchQueryKind  = "academic" | "web";
type ResearchQueryStatus = "planned" | "executed" | "skipped";

interface ResearchPlanQuery {
  queryId: string;            // q-<n>，后端生成
  query: string;              // 检索词（非空）
  kind: ResearchQueryKind;
  rationale?: string;         // 为什么需要这条检索
  expectedCoverage?: string;  // 期望覆盖的文献 / 信息面
  status: ResearchQueryStatus; // 默认 planned
  resultCount?: number;       // 执行回填（编辑 API 不接受）
}

interface ResearchPlan {
  planId: string;             // rp-<12hex>，后端生成
  status: ResearchPlanStatus; // 产出即 draft
  questions: string[];        // 研究问题（指导检索）
  queries: ResearchPlanQuery[];
  createdAt: string;          // ISO
  updatedAt: string;
}
```

硬帽：questions ≤ 30、queries ≤ 30（Agent 解析与 PUT 校验同口径）。

### 3.2 Research Artifact（research/research.json）

```
{ generatedAt, taskId, plan?, report, evidence, bibliography }
                                 ^^^^ M8.1 新增可选字段
```

- 旧字段全部保留：`report.researchQuestions`、`report.literaturePlan` 及
  evidence / bibliography 契约不变；
- 既有消费者零改动即兼容：`definitions.ts`（research.idea DoD / feasibility /
  writer digest）、`FeasibilityService`、`scriptedRuntime` 均只读 `report.*`；
- existing-paper 流程的附加字段（`weaknesses` / `kind`）在 PUT 写回时原样保留
  （整对象读-改-写）。

### 3.3 Researcher 输出契约（Prompt）

JSON schema 新增首位字段 `plan`（questions + queries[query/kind/rationale/
expectedCoverage]）；要求 0 明确概念区分：

> plan 是检索计划（ResearchPlan）——在检索前制定，列出研究问题与你打算执行的
> 检索词及理由，用于指导本次检索；其余字段（domainOverview 到 bibliography）是
> 调研报告（ResearchReport）——在检索完成后综合研究结果得出。两者不要混淆。

并锚定 `plan.questions` 与 `report.researchQuestions` 的职责差异（指导检索 vs
调研后结论）。

## 4. API

### GET /api/projects/:id/research/plan

- 200 `{ plan: ResearchPlan | null }`——无 research.json 或旧 artifact 无 plan 时
  `plan: null`（空态而非错误）；项目不存在 → 404 PROJECT_NOT_FOUND。

### PUT /api/projects/:id/research/plan

- 请求体（questions / queries 至少其一，整体替换语义）：

```json
{
  "questions": ["问题 1"],
  "queries": [
    { "queryId": "q-1", "query": "检索词", "kind": "academic",
      "rationale": "理由", "status": "planned" }
  ]
}
```

- 200 `{ plan }`；参数校验失败 → 400 INVALID_REQUEST（空请求体 / 非数组 / 空
  query / 非法 kind / 非法 status / 超条数硬帽，错误信息带字段位置）；
- 无 research.json → 404 NOT_FOUND（先运行调研）；非 GET/PUT → 405
  （Allow: GET, PUT）。
- 不变式：`resultCount` 与 `plan.status` 不在编辑面——前者同 id 继承，后者保持
  不变（状态流转属执行侧）。

## 5. UI（DiscoveryPanel · ResearchPlanSection）

位于 Discovery 页首（计划指导下方检索的动线）：

- **查看**：Topic（项目标题，ProjectPage 传入）、Questions（有序列表）、Queries
  （检索词 + 学术/Web 徽标 + 状态徽标 + 「理由：…」+「期望覆盖：…」+ 执行结果数）、
  plan 状态与 updatedAt / planId；
- **编辑**：问题每行一条（textarea）；检索行内联编辑检索词 / 方式（学术·Web）/
  状态（计划中·已执行·已跳过）/ 理由，支持添加 / 删除行；空检索词本地校验拦截；
- **保存**：PUT 受限字段 → 失效重取；取消则丢弃编辑态；
- **空态**：无 plan 时引导「运行从想法到论文工作流的调研阶段」。

不做复杂视觉设计——全部复用既有 panel / source-row / chip / field 样式。

## 7. 未来 M8.2 扩展方向

按依赖排序的建议（对齐 M8_ROADMAP_PROPOSAL 的 M8.3/8.4 主线）：

1. **执行回填（P0）**：检索执行侧（用户在 Discovery 点检索 / Agent 会话内
   search_papers）按 query 精确匹配回填 `status: executed` + `resultCount`；
   plan.status 随之流转（draft → executing → done）。本里程碑已预留：resultCount
   编辑面只读继承、queryId 稳定。
2. **计划-执行对账（P1）**：UI 展示「计划 vs 实际」覆盖矩阵（哪些 planned query
   未执行、executed query 的候选产出量），支撑 roadmap 中「单轮覆盖是否足够」的
   数据 gate 判断。
3. **多轮迭代计划（P1）**：调研 rerun 时对既有 plan 做合并（用户编辑优先 /
   Agent 增量补充）而非整 artifact 覆盖丢失用户编辑（当前已知限制：research()
   整体重写 research.json 会覆盖手工 plan 编辑）。
4. **plan.status 状态机 + 批准流（P2）**：draft → approved 的显式 HITL 动作与
   API（PUT 当前刻意不动 plan.status）。
5. **expectedCoverage 度量（P2）**：把「期望覆盖面」与 literaturePlan 残差、
   候选 promote 率关联，形成检索质量漏斗观测（衔接 M8.1-roadmap 的
   Discovery Observability）。
