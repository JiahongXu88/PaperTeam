# M8.3.2 — Research Coverage Analyzer 实施报告

- 日期：2026-09-20
- 状态：已完成（实现 + 测试 + 文档；backend / frontend 全量测试、build、typecheck 通过）
- 范围：对**当前活动 Research Plan**（M8.3.1 计划链中 `activePlanId` 指向的条目）做
  覆盖分析——研究问题是否被覆盖（covered / partial / missing）、哪些方向仍存在
  缺口、下一轮计划应该关注什么。**只做 Analysis + Recommendation**，不是
  Controlled Research Loop。**不新增 Agent、不改 Runtime、不改 Workflow
  Orchestrator、不引入 RAG / Vector DB / MCP / 新 Provider**（M8 架构冻结规则
  全部遵守；Evidence 链路原样）。

## 1. 目标

M8.2 执行完计划、M8.3.1 能派生下一轮之后，缺一个「下一轮应该搜什么」的判断依据。
Coverage Analyzer 回答三个问题：

1. 研究问题是否被覆盖？
2. 哪些方向仍存在缺口？
3. 下一轮 Research Plan 应该关注什么？

定位纪律：分析**只读取已有状态**，不修改 plan / executionHistory /
EvidenceStore / CandidateStore；缺口只生成**建议**（suggestedQueries），
不自动 derive / approve / execute——派生仍走 M8.3.1 的显式 derive API（用户点击）。

## 2. Coverage 模型

`ResearchCoverage`（`backend/src/agents/researchCoverage.ts`）——结构化状态优先，
**不做评分系统**（`overall` 只有三态计数与一句话摘要，无 score）：

```jsonc
{
  "planId": "rp-…",              // 被分析的计划 = 活动计划（M8.3.1 计划链）
  "planStatus": "done",
  "iterationNumber": 2,
  "analyzedAt": "…",
  "questions": [
    {
      "question": "Transformer MOT 实时部署",
      "origin": "plan",            // plan（计划问题）| report（报告结论问题，去重补充）
      "coverage": "partial",       // covered | partial | missing
      "relatedQueryCount": 2,      // token 关联的计划检索数
      "executedQueryCount": 1,     // 关联检索中已执行且带回结果的条数
      "resultCount": 25,           // Search Result 总数（≠候选≠文献≠证据）
      "evidenceCount": 0,          // 关联 EvidenceStore 条目数
      "promotedCount": 0,          // 关联已入库文献数（accepted 且已 promote）
      "gap": "…"                   // 非 covered 时的缺口描述
    }
  ],
  "overall": { "questionCount": 3, "covered": 1, "partial": 1, "missing": 1,
               "summary": "研究问题 3 个：covered 1 · partial 1 · missing 1；缺口 N 项" },
  "gaps": [
    { "description": "…", "relatedQuestion": "…", "suggestedQueries": ["…"] },
    { "description": "调研报告登记的残差文献方向：…", "suggestedQueries": ["…"] } // literaturePlan 残差，无 relatedQuestion
  ]
}
```

分析的问题集合 = 活动计划 `plan.questions`（先计划后检索的意图侧）+
`report.researchQuestions`（调研报告结论侧；与前者精确去重后补充，`origin`
标注来源）。判定输入另含 `plan.queries`（status / resultCount）、
`executionHistory`（M8.2 执行记录）、`report.literaturePlan`（调研方声明的
检索后残差方向）。

**持久化决策：不落盘。** Coverage 是确定性派生视图（deterministic
projection），GET / POST 均即时重算——不在 research.json 上新增字段，避免
报告与源数据双写漂移，也天然满足「分析不修改任何状态」。

## 3. 分析规则（第一版：确定性纯函数，不依赖 LLM）

### 3.1 关联规则（问题 ↔ 检索 / 证据 / 文献）

`isTextRelated(question, text)`：双方 token 集交集非空即关联。token =
拉丁词（`[a-z0-9]+` 且 ≥3 字符，滤掉 a/of/42 类噪声）+ CJK 连续段二元组
（bigram；单字段退化为该字）。

匹配面：
- 检索条目：`query.query` 与 `query.expectedCoverage`（期望覆盖声明命中也算）；
- 证据条目：`claim + source.title`（EvidenceStore.list 只读）；
- 已入库文献：`candidate.query + candidate.title`（CandidateStore 中
  `accepted` 且有 `promotedSourceId` 的条目，只读）。

已知局限（如实呈现，不伪造关联）：纯中文问题 vs 纯英文检索词判不关联 →
落入 missing / 缺口；语义级归因（同义改写、跨语言）留给 M8.3.3 的
Researcher 通道（复用已有角色，不新增 Agent）。

### 3.2 三态判定（`assessQuestionCoverage`，规则全序）

```
1. 无关联检索                          → missing（计划检索不覆盖该问题）
2. 有关联检索，但无「已执行且带回结果」  → missing（有 query，resultCount=0）
3. 有带回结果的检索
   ├─ 存在关联 evidence 或 promoted literature → covered
   └─ 否则                                     → partial（结果有了，支撑没有）
```

三层如实分层，不混写：`resultCount` 是 **Search Result** 计数，
`evidenceCount` 是 **EvidenceStore** 条目数（任意核验状态，如实计数），
`promotedCount` 是**已入库文献**数——Search Result ≠ Candidate ≠ Literature
≠ Verified Evidence 链路语义原样。

### 3.3 executionHistory 合并（`mergeQueryFacts`）

- `executed`：plan `status=executed` **或**执行历史存在该 queryId 的
  `executed` 记录（失败重试后 plan 回到 planned 的场景以历史为准）；
- `resultCount`：plan 回填优先（M8.2 执行层写回），缺失时从历史累加
  （M8.1 旧 artifact 手工标记 executed 无 resultCount 的兼容路径）。
  历史不按 planId 过滤（旧记录无该字段；派生轮 queryId 重新分配，跨轮
  同号属预期——下一轮本就承接同一研究线）。

### 3.4 缺口建议（`buildCoverageGaps`，只建议不执行）

- 每个 missing / partial 问题一条缺口，`suggestedQueries = [问题原文]`
  （确定性 v1：语义化改写留给 Researcher 通道）；
- `report.literaturePlan` 每个残差方向直通一条缺口（原文即建议检索）；
- 上限 30 条（`MAX_COVERAGE_GAPS`）。

## 4. API（符合既有 httpServer 风格）

| 方法 | 路径 | 语义 |
| --- | --- | --- |
| GET | `/api/projects/:id/research/coverage` | 当前活动计划覆盖（即时重算）；无 artifact / 无计划 → `{ coverage: null }` 空态（与 GET /research/plan 的 `plan:null` 一致） |
| POST | `/api/projects/:id/research/coverage/analyze` | 执行分析（同一规则）；无 artifact / 无计划 → 404 `NOT_FOUND`（与 derive / execute 同口径） |

错误口径：项目不存在 → 404 `PROJECT_NOT_FOUND`；方法不允许 → 405。
服务装配：`serviceStack.coverage`（`ResearchCoverageService`，依赖
ProjectStore + EvidenceStore + CandidateStore，全部只读）。

## 5. UI（DiscoveryPanel 新增 Coverage Analysis 区域）

位置：Research Plan 区块之后、检索区之前；简单展示，不重设 UI：

- **分析覆盖**按钮（POST analyze；GET 派生视图自动加载，展示最近结果）；
- Research Coverage 列表：问题 + 三态徽标（已覆盖 / 部分覆盖 / 未覆盖）+
  来源徽标（计划问题 / 报告问题）+ 计数行（关联检索 / 已执行 / 结果 /
  证据 / 已入库）+ 行内缺口描述；
- Gaps 列表：缺口描述 + 建议检索；无缺口时明示「全部研究问题均已覆盖」；
- **按缺口派生下一轮**按钮：缺口建议检索（去重、上限 30）作为下一轮
  检索词，**调用既有 derive API**（`POST /research/plan/:planId/derive`，
  questions 整拷当前计划）——不新增第二套 Plan 创建逻辑；活动计划非
  done 时禁用（derive 侧 409 同源约束）；派生后仍是 draft，需用户编辑、
  批准才会执行（不自动执行）。

## 7. M8.3.3 Controlled Research Loop 扩展建议

M8.3.2 交付的是**只读分析 + 显式建议**；M8.3.3 若做受控研究循环，建议按
以下边界推进（均不违反 M8 冻结规则为前提）：

1. **语义归因替换匹配器**：token 匹配是 v1 的确定性底线，跨语言 / 同义
   改写的归因误差会直接传导为假 missing。M8.3.3 可把「问题 ↔ 检索 /
   证据」的归因交给**既有 Researcher 通道**（复用 ResearcherService /
   Runtime，不新增 Coverage Agent），但语义归因结果应作为**标注层**叠加
   在确定性报告之上，且可关闭（LLM 不可用时回落本版规则）。
2. **covered 判定的核验分层**：当前 evidenceCount 计任意核验状态；循环
   场景下建议把 covered 收紧为「verified evidence 或 promoted
   literature」（尊重 Verified Evidence 顶层语义），unverified 只计线索。
3. **受控循环的 HITL 断点**：自动「analyze → derive(缺口检索) → 用户
   批准 → execute」的循环必须在 derive 后保留显式批准（approve）断点；
   每轮预算（query 数 / provider 调用次数）与终止条件（如连续 N 轮无新
   covered）应预注册，防止无限派生。
4. **执行历史按轮归因**：executionHistory 已带 planId（M8.3.1）；循环
   多轮后可按轮统计覆盖增量（本轮新增 covered 数），作为终止条件的输入。
5. **不引入新存储**：覆盖报告继续即时重算；如循环需要历史对比，存
   「轮次摘要」而非全量报告，且写入仍走 research.json 单一写入口
   （writeResearchPlanChain 风格），避免双写漂移。
