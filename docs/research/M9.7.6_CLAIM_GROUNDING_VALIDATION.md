## 3. Duplicate Normalization Design

### 语义判定（先审计后设计）

transitions 是**按 id 分组的最终状态声明（declaration semantics）**，不是有序状态
变化：三个调用点（revise 派发 / validate 终态回写 / HITL 用户决策）全部从 item
当前状态出发做批式落定；apply 本体按 id 建 Map 单遍应用（顺序无关）；状态机不允许
`applied → applied`——把重复声明当顺序变化反而制造非法流转。

### 三类处理（M9.7.5 实测重复全部是情况 A）

| 情况 | 判定 | 处理 |
| --- | --- | --- |
| A. 完全相同重复（同 id 同 `to`；targetChanged 可不同） | 幂等重述（同声明派发到多目标） | collapse；applied 元数据合并：targetChanged OR、appliedRevision max、appliedAt 首个 |
| B. 同 id 不同 `to` 但构成合法前向路径（如 applied → validated） | 顺序 replay | 终态生效；沿途 applied 元数据随终态落盘（防御未来调用方；现有调用点不产生） |
| C. 同 id 矛盾且无合法路径（如 applied + skipped 并列） | 无法归一 | **结构化拒绝**（`存在无法归一的重复声明` + 逐 id 声明序列），走既有 repair / retry；绝不静默 last-wins |

不变量：未知 id 仍拒绝；单条非法流转仍拒绝（`不是合法流转`）；**原子性保持**
（任何拒绝都不部分应用——同批合法条目不会被写入）；`normalization` 诊断
（duplicateIds / originalSequences / originalCount / normalizedCount）随
`ApplyTransitionsResult` 返回，可恢复重复不构成 workflow fatal。

### 源头修复（双保险）

派发循环在 push 前按 id 合并 `dispatchedItems`（targetChanged OR）——重复不再
产生；normalizer 兜底任何其他调用方（含 plan id 撞号场景）。

## 6. Unsupported → Evidence-aware Revision

`revision.revise` stage（与计划派发同源 round）：

1. 加载该轮 claim-grounding 报告；对每个修订 target 取 section 匹配（与派发同一
   `sectionMatches` 口径）的 UNSUPPORTED / CONTRADICTED claims。
2. `buildClaimRepairDirectives`：候选 evidence 从项目证据库解析（解析不到的候选
   如实丢弃——SUPPORT 只允许 verified evidence）；**无候选的 claim 照样派发**
   （WEAKEN / REMOVE 路径）。
3. `reviseSection` prompt 注入 **Unsupported Claim Repair** 块：论断原文 + verdict
   + 候选 Verified Evidence（claim / 引文 / cite key）+ 三动作规则：
   SUPPORT（证据确实支撑 → 用该证据重写并 `\cite{key}`，范围/数值/限定词以证据
   为准）/ WEAKEN（部分支撑 → 降强度只保留被支撑部分）/ REMOVE（无证据 → 删除
   具体论断，保留无争议背景）；无候选 → 只允许 WEAKEN / REMOVE；红线：不得为此
   新增数字、年份、实验结果、bibliography key 或未经核验的具体事实。
   DEFER 未启用（现有系统无 request-more-evidence / HITL 语义，不为本阶段新增）。
4. **正文隔离**（§5）：Evidence ID 是 Agent Harness 内部 grounding contract，
   prompt 明文禁止正文出现 `[E###]` / `[c-###]` 标记；manuscript 只见 `\cite{...}`。
5. 既有红线叠加不替代：M9.7.2 A/B citation partition 保留；Fact / Citation
   Preservation（M5.6）与 revision.validate 复核照常。

Writer claim discipline（§4）：evidence 行新增 source identity（`src: title (year)`）；
写作与修订 prompt 注入事实性论断强度纪律（数字/年份/性能结论/方法能力/实验结果/
贡献描述/比较性事实——证据 claim 说什么写什么，不升级不外推；无证据 → 弱化为
背景 / 标注不确定 / 删除；禁止凭记忆补具体事实）。Writer 判断强度的依据即：
先在 Evidence 行里找能支撑该 claim 的证据 claim——有则受其范围约束，部分有则
降强度，无则删除。

## 10. Failure Cases（重大失败与 Root Cause）

1. **outline.plan 结构化失败 ×2 run ×2 attempts（阻断 smoke，非本阶段 claim
   grounding 缺陷）**。根因链（离线复现实锤，含抓到错误提取的原始输出）：
   GLM 在 abstract 字符串里输出**未转义 ASCII 双引号**（`提出"规划—工具—反思—
   记忆—协作"耦合分析框架`）→ 外层 JSON 非法 → `extractJsonObject` 的平衡扫描
   回退**静默命中内层最后一个 section 子对象**（title=结论、无 sections 字段）→
   伪装成「sections 必须是至少 3 项的数组」校验错（掩盖真实 parse 问题）→
   transient 重试同 prompt 同漂移 → 2/2 → run failed。修复：`planOutline` 增加
   ≤2 次 error-feedback 修复（M9.7.4 Reviewer repair 同构；修复 prompt 显式给出
   转义规则），模型层失败不进修复循环，耗尽如实抛错。遗留观察：extractJsonObject
   的「外层失败回退内层对象」行为对其他调用方仍是隐患（本次未改动，避免扩大
   爆炸面；已在此登记）。
2. **r3 修订试图改年份（2025→2024）**：Fact Preservation 复核确定性拦截
  （5 items rejected + blocked → HITL）。这是红线机制正常工作的实录，不是机制
   失败；也说明 revision prompt 的「年份不得新增/修改」约束在真实模型下仍会被
   试探，确定性复核层是必要兜底。
3. **绑定率 23% 的构成**：S+P=36 条 claim 中仅 9 条带 evidenceId 且 formal——
   Fact Reviewer 对多数 SUPPORTED claim 不输出 evidenceId（判定端行为），绑定率
   的上半段（claim→evidence 映射的产出）受 Reviewer 输出习惯限制，不是本阶段
   代码能单方面提高的。如实登记为 Remaining Limitation。
