## 0. 摘要

本报告对 6 个开源项目做了源码级静态分析（clone 到
`D:\Projects\PaperTeam-M6-Research`，浅克隆、只读、未运行），并对 PaperTeam
backend 做了 M6 视角的只读盘点。核心结论：

1. **PaperTeam 已有 AcademicSearchProvider 的 70% 雏形**（`ScholarlyResolver` +
   4 connector + 确定性打分 + 缓存/重试/telemetry），真正缺的是「关键词相关性
   检索语义、跨源融合去重、全文获取、sources 库 chunk 管线」四件事——M6 的
   正确姿势是**在既有边界内扩 seam，而不是引入任何外部框架**。
2. **没有任何一个被分析项目值得作为运行时依赖引入**：三个 MCP 项目证明的是
   接口/可靠性模式（正反两面），agent-search 证明的是算法片段（TS 移植百行级），
   SearXNG 以独立服务形态承担 Web Search 聚合。全部结论 = 借设计，不借代码
   （零第三方源码进入 PaperTeam）。
3. **Web Search 与 Academic Search 必须分开抽象**（原则 3 成立）：SearXNG 的
   engine 聚合是「通用网页检索」形态，学术源是「结构化元数据检索」形态，强行
   统一成万能 SearchProvider 会在归一化/去重/健康语义上互相污染（paper-search-mcp
   的 4 套字段并存即为反面实证）。
4. **中国大陆可用性是「多源 + 降级」问题而不是「选一个可靠源」问题**：架构上
   以 Provider Health 模型（healthy/degraded/rate_limited/unavailable）+
   DOI 优先的跨源同一性判定保证任意单源失效不阻断主流程。

### 2.2 缺口（M6 要补的）

1. **真关键词检索**：`ScholarlyResolver.search()` 把关键词当「标题」送
   `pickFromSearch` 相似度门控（strong 0.92 / medium 0.8+一作+年份），非标题形
   查询候选全被 tier=reject 丢弃 → 基本返回空；无相关性排序、无分页、无
   year/venue 过滤；search 路径只挂 crossref+openalex。
2. **跨源融合**：无「多 provider 结果 → 同一论文合并为单一 canonical 记录 +
   多源 ID 映射」的输出（`sameWork` 在但未用于融合输出）。
3. **全文获取**：无 OA/PDF 解析与下载（paper-search skill 明确排除；
   `AGENT_RETRIEVED` 无人写入）。
4. **sources 库无 chunk/索引**：`parsed/<id>.json` 只有 2000 字符 textPreview；
   chunk 管线仅服务 Final PDF。
5. **共享 HTTP 基建缺失**：`fetchJson` 在 `scholarly.ts` 与
   `citation/metadataProviders.ts` 有两份重复实现；无统一超时/退避/限流/熔断。
6. **无 Web Search 能力**（本任务主对象）。
7. Researcher 为单发 JSON prompt（`agents/ResearcherService.ts`），不引导工具
   调用；检索结果不落 SourceStore、`ResearchReport` 无检索结果字段。

### 2.3 架构红线（不因引入 Search/RAG 而破坏）

Authoritative State ≠ Derived Context ≠ Runtime Context（D-0013）；文件优先、
不提前引入数据库（ARCHITECTURE §5）；Agent 不持 shell、不直接外呼
（scholarlyTools 模式）；WorkflowOrchestrator 确定性编排（D-0008）；出口
Agent 输出必须落盘过校验才进状态机（§4.3）。

## 3. SearXNG

**版本**：f725cc7（master，含 360search/sogou/quark/chinaso 等中国引擎与新版
`result_types`/`network` 模块）。**License**：AGPL-3.0-or-later（LICENSE 全文；
`searx/` 下 365 文件带 SPDX 头）。**形态**：单进程 Flask WSGI「元搜索引擎」。

### 3.1 Architecture

```text
HTTP (Flask)                searx/webapp.py      /search /stats /config /healthz
   │
请求解析 / 引擎选择          searx/webadapter.py  get_search_query_from_webapp()
   │
搜索编排（每引擎一 OS 线程）  searx/search/__init__.py  Search / SearchWithPlugins
   ├─ 引擎处理器             searx/search/processors/*  OnlineProcessor 等 5 种
   │    ├─ 引擎模块          searx/engines/<name>.py   request()/response() 协议
   │    └─ HTTP 客户端       searx/network/*   curl_cffi AsyncSession（独占
   │                         asyncio 线程，TLS 指纹伪装 impersonate="chrome"）
   ↓
结果容器（归并/去重/打分）    searx/results.py    ResultContainer
   ↓
结果类型系统                 searx/result_types/*  Result/MainResult/Paper（msgspec）
```

关键点：HTTP 客户端是 **curl_cffi**（非 httpx/requests，模拟浏览器 TLS 指纹）；
所有出站请求由单一 daemon asyncio 线程统一执行，引擎工作线程经
`asyncio.run_coroutine_threadsafe` 提交（`searx/network/__init__.py: request()`）。

### 3.2 引擎抽象与注册

- 引擎模块协议：`request(query, params)` 改写请求 + `response(resp)` 返回
  `list[dict]`（→LegacyResult）或类型化 `EngineResults`（如 arxiv 返回
  `searx/result_types/paper.py: Paper`，含 doi/authors/journal/pdf_url）。
- 引擎声明字段（`searx/enginelib/__init__.py: Engine`）：paging / time_range_support
  / language_support / shortcut / categories / timeout / weight / tokens /
  send_accept_language_header / disabled / inactive 等。
- 注册：`searx/engines/__init__.py: load_engine()/load_engines()/register_engine()`
  从 `settings.yml` 的 `engines:` 列表（251 引擎模块/约 340 配置项）加载，产出
  全局 `engines/categories/engine_shortcuts` 表；处理器注册于
  `searx/search/processors/__init__.py: PROCESSORS`。

### 3.3 一次 `GET /search?q=…&format=json` 的完整调用链

1. `webapp.py: pre_request()`（@app.before_request）：合并 GET+POST 参数；limiter
   开启时 `searx/limiter.py: filter_request()` 先行（`/healthz` 豁免）。
2. `webapp.py: search()`：**`format` 不在 `settings['search']['formats']` → 403
   （默认只有 html——JSON 必须显式开启）**；`q` 空 → 400。
3. `webadapter.py: get_search_query_from_webapp()`：`parse_pageno/parse_time_range
   （仅 day/week/month/year）/parse_safesearch/parse_timeout/parse_lang`；引擎选择
   `parse_generic()`（categories= 逗号分隔 / engines= 显式 / `!bang` 语法，
   `searx/query.py: RawTextQuery`）；`validate_engineref_list()` 剔除未知引擎；
   产出 `searx/search/models.py: SearchQuery`。
4. `SearchWithPlugins.search()` → 插件 pre_search → `Search.search()` →
   `search_standard()`。
5. `Search._get_requests()`：每个 EngineRef 取 processor（init 失败静默跳过；
   被挂起引擎跳过并标记 suspended）；`OnlineProcessor.get_params()` 丢弃不支持
   的组合（如 pageno>1 且 engine.paging=False）；**总超时 actual_timeout =
   max(各引擎 timeout)，与 `outgoing.max_request_timeout`、用户 timeout_limit
   取 min**。
6. `search_multiple_requests()`：**每引擎一个原生 threading.Thread**，主线程按
   剩余时间 join；超时置 `th._timeout=True` 并 `add_unresponsive_engine(name,
   'timeout')`——线程不杀，迟到结果由容器丢弃。
7. `OnlineProcessor.search()` → `_search_basic()`：`engine.request()` →
   `searx/network/__init__.py: request()`（curl_cffi）→
   `searx/network/raise_for_httperror.py: raise_for_httperror()`（402/403→
   AccessDenied；429→TooManyRequests；Cloudflare 挑战页→CAPTCHA 异常挂起 15 天）
   → `engine.response(resp)`。
8. `searx/results.py: ResultContainer.extend()`（RLock）：先规范化（
   `_normalize_url_fields`：补 scheme、IDN 解码；`_normalize_text_fields`：标题
   截 200 / 内容截 1200 字符、内容==标题则清空），再分流 answers/suggestions/
   corrections/infoboxes，主结果进 `_merge_main_result()`。
9. **去重**：`MainResult.__hash__`（`searx/result_types/_base.py`）=
   `hash(template | netloc | path | params | query | fragment | img_src)`
   （**忽略 scheme**）；命中则 `merge_two_main_results()`：取更长 title/content、
   `engines` 集合并集、http→https 升级、名次 append 到 `positions`。
10. **打分** `results.py: calculate_score()`（`ResultContainer.close()` 统一执行）：
    `weight = Π(来源引擎 weight) × len(positions)`；`score = Σ_positions
    weight/名次`——**带引擎权重的倒数排名融合（类 RRF），公式极简可解释**。
11. 排序 `get_ordered_results()`：score 降序 + 按 `category:template` 分组穿插
    （纯 UI 目的）。
12. 输出 `webutils.py: get_json_response()`；`post_request()` 写 Server-Timing
    响应头（每引擎耗时）。

### 3.4 JSON API 精确 schema（`webutils.py:161`）

```jsonc
{
  "query": "…",
  "results": [ /* get_ordered_results() 每项 .as_dict()：
      url, title, content, engine, engines[](命中引擎全集), parsed_url, template,
      publishedDate, score, positions[], category, priority, …（引擎可附加字段，
      如 arxiv 的 doi/authors/journal/pdf_url） */ ],
  "answers": [], "corrections": [], "infoboxes": [], "suggestions": [],
  "unresponsive_engines": [ "engine: 错误文案(timeout/CAPTCHA/…)" ]
}
```

请求参数全集：`q(必填), format, categories, engines, category_*, language,
pageno, time_range, safesearch, timeout_limit`。无总命中数、无 cursor（分页=
透传 pageno，不少引擎不支持翻页）。

### 3.5 错误 / 超时 / 熔断模型

- 分层超时：每引擎 `engine.timeout`（继承 `outgoing.request_timeout=3.0`）；
  请求级 actual_timeout = max(引擎 timeouts) 再与全局/用户上限取 min；HTTP 层
  扣除线程已耗时间。
- **单引擎失败绝不拖垮请求**：异常分类捕获（ssl/Timeout/RequestException/
  CAPTCHA/429/AccessDenied），`ResultContainer.add_unresponsive_engine()` 记名，
  其余引擎照常返回，HTTP 仍 200；解析类异常只计数不挂起。
- **引擎自动挂起（熔断）**：`abstract.py: SuspendedStatus` + `searx/exceptions.py`
  异常类型自带挂起时长（`settings.yml: search.suspended_times`：403=180s、
  429=180s、CAPTCHA=3600s、**Cloudflare=1296000s(15天)**；其他网络错误
  ban_time_on_fail=5s 上限 120s）；挂起状态以 **Network 对象为键**（共享同一
  network: 的引擎组一处被封全家挂起）且进程内存（多 worker 不共享）。
- **无重试、无结果缓存**（仅引擎 cookie 的 sqlite EngineCache）；对上游容错
  完全靠多引擎冗余 + 挂起换源。

### 4.3 搜索链（SearXNG → normalize → dedup → rerank）

- **请求**（`SearXNGEngine.search`，search.py:729-759）：`GET {SEARXNG_URL}/search`
  参数 `q, format=json, pageno, engines, time_range, categories, language,
  safesearch`；15s 超时。默认引擎 `doubao,github,wikipedia,stackoverflow`
  （:113，中文生态取向）。
- **归一化**：映射为 `SearchResult` dataclass（:572）；
  `clean_url`（:238）清 URL 污染（Bing `/ck/a?u=` base64 重定向解包等）。
- **URL 去重**（`canonical_url`，:261-280）：scheme/netloc 小写、去 `www.`、
  path 去尾斜杠、**剔除 utm_*/fbclid/gclid/yclid/mc_cid/mc_eid 追踪参数**，以
  canonical key 精确匹配 first-wins；在引擎内 / 扇出合并 / research 候选池
  四处复用。无域名级/模糊去重。
- **重排**（`result_rank_score`，:507-565）：纯启发式——引擎分 + 标题命中×1.8 +

  +0.6 + rapidfuzz 近形补分。无 LLM/cross-encoder 重排（flashrank 注释未接）。

### 4.4 抽取链（fallback 顺序 / SSRF / 预算）

- 方法链（`ContentExtractor.extract`，:1106-1135）：auto = trafilatura（若装）→
  **Jina Reader（`https://r.jina.ai/{url}`，第三方免费服务）** → requests+bs4
  （readability-lxml 可选→main/article 启发式→正则兜底，截断 100KB）；deep=True
  前置 crawl4ai（JS 渲染）。每方法结果须过 `text_quality_ok`（≥120 字 + CSS
  密度启发式，:283）+ `_clean_text`（只删 ≤80 字符样板短行——cookie 横幅/登录/
  版权，长正文永不删，:303-330）否则试下一方法。
- **SSRF 防护（质量高，有测试）**：`url_is_safe`（:178-204）拒非 http(s)、私网/
  环回/链路本地（含云元数据 169.254.169.254）/保留段、内部主机名；可选 DNS 全
  解析防 rebinding；**`safe_get`（:212-224）禁自动重定向、每一跳 Location 重新
  过 `url_is_safe`，MAX_REDIRECTS=4**——堵 302→内网绕过；`test_search.py:203-247`
  有专项测试。⚠️ Jina 分支把目标 URL 送第三方（信息外泄面 + 免费限流）。
- 预算护栏：`batch_extract`（:1286-1323）12 URL / 并发 8 / 20s 软上限、超时降级
  占位；深抓（:1414-1418）depth≤6、pages≤120、每级 40、45s 时间预算、累计
  8MB。无礼貌延时/每主机限速。

### 4.5 RAG 与引用（与 README 宣称的差距）

无 embedding、无固定 chunking；「chunk」实为 `_relevant_excerpt`（:1966-2001）
词频计分 + 正则加分的贪心装填（ask 6000 字/源）。引用保证为 **prompt 级**（无
后验校验 [n] 是否存在），但有两点工程补救：①每源带 280 字符 excerpt 可追溯；
②**web_research 的参考文献清单由代码按全局编号拼装**（`_assemble`，:2623，
注释明确「参考来源不靠 LLM 生成」）。**README 宣称 "chunk-level citations"
（README.md:23）与代码不符**——实际是源级编号 + prompt 约束。

### 4.6 Tavily API / MCP / 可靠性

Tavily 兼容层仅 `POST /tavily/search` 一个端点（server.py:217-256；`search_depth`
收了但忽略）；无鉴权（靠 127.0.0.1 绑定）。MCP 工具 schema 由 FastMCP 从签名
生成，stdio/HTTP 双传输。可靠性：有全局超时、多级 fallback、SQLite WAL 缓存
（TTL 3600s，**空结果不缓存** :3136）；**无任何 retry/backoff、无限速、无熔断**
（全仓 grep 证实）；HTTP 服务无鉴权无限流。

### 4.7 耦合评估

物理上单文件巨石，但逻辑分层清晰（数据模型→缓存→引擎层→抽取层→生成层→编排
层→门面），构造注入。**搜索+抽取可完全脱离 RAG 使用**（web_search/extract/
map/crawl 不触碰 LLM 客户端）；反向不行（RAG 依赖搜索+抽取）。

### 4.8 Good ideas / Bad fit

**值得借**：`canonical_url` 去重规范；`safe_get` 逐跳重定向 SSRF 校验；

truncated_reason）；**参考文献代码拼装**；snippet 兜底分级；空结果不缓存。

| 机制 | 实现（symbol） | 评价 |
|---|---|---|

| Retry-After | `_parse_retry_after()` :165-196 | **教科书级**：RFC 9110 双格式（delay-seconds / HTTP-date 过去时→0）；`math.isfinite()` 拒 nan/inf；畸形回退默认值；有专项测试 |
| 429/502/503 | `_execute_request_with_retry()` :199-285 | 可重试集 {429,502,503}+超时+传输错误；Retry-After 优先于退避；**等待 30s 硬帽**（有突变测试钉死）；⚠️ 500 不重试（与 502/503 不对称） |
| 退避 | `backoff(n)` :215-218 | 1s×2^n + uniform(0,0.5) 加性抖动；MAX_RETRIES=3；常量不可配置 |
| 超时 | `get_client()` :96 | httpx Timeout(30, connect=10) + keepalive 池；无总 deadline（最坏 4×30s+3×30s≈3.5 分钟） |
| 类型化错误 | `errors.py` 六类层级（base 携 status_code；RateLimitError 额外带 retry_after）+ `handle_error()` 可操作化消息（429 无 key → 附免费申请 key 的 URL） | ✓；但 MCP 边界 `ToolError(str(e))` 抹平类型 |
| 缓存 | `cache.py` 进程内 dict，TTL 300s / 容量 200 / oldest-first | 只缓存实体详情；非 LRU、无 stale-on-error、无 singleflight |
| 安全 | `_enforce_trusted_api_origin()`（httpx event_hook：强制 HTTPS+精确 host+443，防重定向泄漏 x-api-key） | ✓ 值得复刻 |
| **熔断** | — | **无**：S2 宕机时每个调用独立走满 4 次尝试才报错 |

`server_status()` 工具区分「api_reachable+rate_limited（可达但被限）」与
「api_reachable=false（不可达）」——**限流 ≠ 宕机的区分**值得进 Provider Health。

### 7.2 分层裁定（共享基建 vs Provider 特有）

**进共享 Provider HTTP Infrastructure**：类型化错误层级；重试引擎（可重试集 +
指数退避 + 抖动 + Retry-After 优先 + 等待硬帽）；超时/连接池常量 + 共享
client；有界 TTL 缓存（淘汰策略由 provider 注入）；并发串行原语（**但数值
由 provider 配置、sleep 移出临界区**）；受信 origin 钩子；结构化重试日志 +
「限流 vs 宕机」区分。

**进 SemanticScholarProvider 特有**：速率档位与切档逻辑；base URL / x-api-key /
env 解析；字段集裁剪；S2 ID 格式校验；哪些端点缓存。

**PaperTeam 需超越处**：熔断器（连续 5xx 开路+半开探测）；每请求总 deadline；
退避不持锁；统一 5xx 策略（500 也重试）；LRU + serve-stale-on-error；
singleflight；结构化错误 payload（code/retryAfter JSON 而非纯文本）。

- 429 专用 axios 拦截器（`openalex-client.ts:111-130`）：读 Retry-After（缺省

  纯本地状态报告（cache size / 配置），不外呼。
- 无客户端限速器（只靠 mailto + 缓存 + 429 被动重试）；无类型化错误层级。

## 10. 中国大陆可用性分析

### 10.1 分析目标

**不是**保证某个境外 API 永远可达，而是架构上保证：任一 provider 不可用时
系统仍能工作（降级而非失败）。这与 SearXNG 的核心设计（多 engine 聚合 +
失败引擎不拖垮请求）同构。

### 10.2 各源可用性画像（源码/端点事实）

| 源 | 域名/端点 | 大陆可用性 | 失效模式 |
|---|---|---|---|
| SearXNG（自部署） | localhost HTTP | 本机可控 | engine 层失效（上游被 CAPTCHA/限流）→ 该 engine 结果缺失，聚合继续 |
| SearXNG: Bing | HTML+XPath；`base_url` 可覆盖为 cn.bing.com | △ 时好时坏 | CAPTCHA / DOM 改版；无 paging |
| SearXNG: Baidu | **JSON 接口（tn=json）** | ✓ 可达但脆弱 | CAPTCHA → 挂起 1h；私有 JSON 布局变更 |
| SearXNG: DuckDuckGo | html.duckduckgo.com POST（无 JS 端点） | ✗ 大陆基本不可达 | DNS/连接失败 |
| SearXNG: Brave | HTML+XPath（默认启用；付费 API 版 inactive） | △ | CAPTCHA / 配额 |
| OpenAlex | api.openalex.org | △（时通时断，无 CDN 大陆节点保证） | 超时/5xx → UNRESOLVED |
| Crossref | api.crossref.org | △ | 超时 → UNRESOLVED |
| Semantic Scholar | api.semanticscholar.org | △△（较不稳定） | 429/503 高发 → UNRESOLVED |
| arXiv | export.arxiv.org | △ | 超时 → UNRESOLVED |
| AMiner | datacenter.aminer.cn | ✓✓ 境内托管 | 限流 40306 / 余额 403（HTTP 200 信封） |

关键事实：SearXNG 的 `unresponsive_engines` 会把失败 engine 名单随响应返回
（SearXNG JSON API 字段）——**Web Search 的 health 模型可以 partially 委托给
SearXNG 自己上报**，PaperTeam 只需聚合观测。

### 10.3 Provider Health 模型（冻结）

每个 provider（Web 与 Academic 同一模型）维护本地状态机：

```text
healthy     正常服务（近期调用成功率 ≥ 阈值）
degraded    可用但质量下降（部分失败 / 超时率高 / SearXNG unresponsive_engines
            非空 / AMiner 免费层限流）——继续用，结果带 degraded 标记
rate_limited 明确被限流（429 / Retry-After / AMiner 40306）——冷却期内不派发，
            冷却时长 = Retry-After（有界）否则指数退避
unavailable 连续失败（DNS/连接/5xx ≥ N 次，N≥3）——熔断开路，半开探测恢复；
            Discovery 聚合自动绕开
```

设计约束（源自分析结论）：
- 状态由**共享 Provider HTTP 基建**维护（不是每个 provider 各写一份）——
  s2-mcp 的教训是状态散在模块级常量里不可配置；openalex-mcp 的教训是完全没有。
- **限流 ≠ 宕机**必须区分（借 s2-mcp `server_status()` 的二分：rate_limited
  时 api_reachable=true）——冷却恢复策略完全不同（定时唤醒 vs 半开探测）。
- Discovery 层（多源聚合）在每个源 unavailable 时**继续返回其余源结果**（借
  SearXNG「engine 失败不拖垮请求」+ paper-search-mcp「故障按 provider 天然
  隔离」的结构直觉）。
- 全源 unavailable 时的最终语义：Web Search → 结构化错误（可重试）；Academic
  Discovery → AMiner（境内）若可用则兜底，否则 UNRESOLVED 风格错误——
  **不伪造空结果**（D-0023 纪律在 search 侧的延续：error ≠ not_found ≠ 空集）。

### 10.4 Google 边界（原则 2）

本架构中 Google 不是任何环节的依赖：SearXNG engine 列表不含 Google 也可工作
（Bing/Baidu/Brave/…）；学术链路（OpenAlex/Crossref/S2/arXiv/AMiner）无 Google
组件。未来若加 Google engine，只是 SearXNG 配置项，不是代码依赖。

## 11. 15 个架构问题的回答（证据索引）

> 每条答案的证据指向本报告对应小节；正式决策与接口草案见 ADR。

**Q1 PaperTeam Web Search 是否应采用 SearXNG？——是。**
SearXNG 是被分析对象中唯一同时具备多引擎聚合/结果归一/URL 去重/失败引擎隔离/
分类与时间过滤/JSON API 的 Web Search 底座（§3），且以独立服务形态与 AGPL
隔离（Q2）。自建等价聚合层的成本（每引擎一个 scraper + 反 CAPTCHA 维护）已被
agent-search 的 WebFallbackEngine 证明不可持续（§4.8）。

**Q2 部署形态：externally configured service 为主 + Docker service 为部署推荐，
不做 bundled subprocess。**
理由（§3 + §4.7）：①Python/AGPL 双重隔离需求——进程内或子进程都会引入
AGPL-3.0 衍生作品问题与 Python 运行时依赖，而 HTTP 调用是干净的进程边界；
②PaperTeam 已有 compose 双容器形态，SearXNG 作为第三 service 是自然扩展；
③开发机上 SearXNG 是 optional 依赖（无它时 Web Search degraded，学术主链路
完全不受影响）；④不 bundling 意味着用户可指向任何已有 SearXNG 实例。

**Q3 Windows `npm run dev` 如何管理 SearXNG？——设计：不管理，只配置。**
`PAPERTEAM_SEARXNG_URL` env（缺省 `http://127.0.0.1:8888`）；启动时 readiness
探测（借鉴 openalex-mcp `checkConnectivity` 的一次性探测模式），不可达 →
Web Search 标记 unavailable（§10.3 模型），`/ready` 不因此降级（Search 是
optional 能力）。dev 文档提供 `docker run searxng/searxng` 一行启动指引 +
`settings.yml` 最小配置样例（engines 白名单 + limiter + json format 开启）。
**不自动拉起容器**（Windows Docker 不保证存在；保持 dev 启动器零新依赖）。

**Q4 WebSearchProvider 最小接口**（TS 草案见 ADR §接口）：
`search(query, opts?): Promise<WebSearchResult[]>` + `health()`。不做
engine 级透传（SearXNG 的 categories/engines 作为 opts 透传是唯一例外，因为
聚合本身是 SearXNG 职责）；不做 RAG、不做抽取（Q12）。

**Q5 AcademicSearchProvider 最小接口**：
`search(query, opts?): Promise<AcademicSearchResult[]>`（真关键词检索语义，
非现状的查证形）+ `health()`。`lookup`（核验语义）留在既有
ScholarlyResolver——**检索与核验两个接口分开**（§5.4 的教训：9 个工具混在
一起没有抽象；PaperTeam 已有正确的核验链路，缺的是检索）。

**Q6 角色分工：OpenAlex = default/primary；AMiner = China secondary +
enrichment；S2 = enrichment（引用数/TLDR/arXiv 关联）+ fallback；arXiv =
preprint + fulltext；（Crossref 见 Q7）。**
证据：AMiner 无前向引用/无精确引用数/免费层无摘要/计费成本悬崖 → 不能
primary（§6.3）；OpenAlex 免费额度最大（10 万次/天）+ 摘要重建 + `cites:`
filter → primary（§8.3）；S2 的 429/503 高发 + 1rps 限制 → 不做 default
（§7.1）。

**Q7 Crossref = MetadataResolver（核验链路），不是 discovery primary。**
既有 `CrossrefProvider.lookup()` 已服务引用核验（DOI 权威注册库），检索排序
质量弱（relevance 一般、无引用数概念）——保持现状，检索聚合里作为 fallback
源参与即可。

**Q8 Unpaywall = FullTextResolver 层。**
证据（§5.3）：它是「给定 DOI → OA PDF URL」的解析服务，无检索能力；paper-search-mcp
也把它放在 search 工具之外单独成工具。归入 FullTextResolver（与 arXiv PDF /
OA URL / 用户上传并列），绝不进 AcademicSearchProvider。

**Q9 跨源同一论文判定——分层键，全部确定性**：
①DOI（小写归一，剥 `https://doi.org/` 前缀）精确相等 → 同一；②arXiv ID
（去版本号 `v\d+$`）相等 → 同一；③PMID 相等；④标题归一化（`titleQueryVariants`
的断词/连字符归一）+ 年份（±1）+ 第一作者姓 strong tier（0.92）→ 同一
（复用 `candidateScoring.sameWork`）；⑤预印本-正式版合并**偏正式版**（借
AMiner `paper_set.py` 的 PREPRINT_MARKERS 模式）。输出 `SourceIdentity`
（canonical DOI/IDs + per-provider ID map + 归一标题指纹）。

**Q10 canonical domain model**（见 ADR 接口草案）：`WebSearchResult`
（query→URL/snippet/title/engine/score）、`AcademicSearchResult`（=
CanonicalPaperRecord 的检索投影 + relevance 来源信息）、`CandidateSource`
（候选：identity + 来源 provider + 检索上下文 + 状态 pending_review/accepted/
rejected）、`SourceIdentity`（Q9 的输出）。既有 `SourceItem`（入库后）与
`EvidenceRecord`（证据）不变。

**Q11 retry/rate-limit/circuit breaker 放共享 Provider HTTP Infrastructure。**
证据：s2-mcp 的分层裁定（§7.2）——重试引擎/类型化错误/超时/缓存/熔断全部是
跨 provider 通用件，速率档位/base URL/鉴权是 provider 特有；PaperTeam 现状
两份 `fetchJson` 重复实现（§2.2-5）正是缺这层的症状。M6.3 落地
`ProviderHttpClient`（详情见 ADR）。

**Q12 网页正文抓取 = 独立 ContentFetcher 接口，不属于 SearchProvider。**
证据（§4.3/§4.4）：抽取是「URL → 干净正文」的独立关注点（方法链 + 质检 +
SSRF + 预算四件套），与「query → URL 列表」正交；SearXNG 返回的 snippet
对 discovery 级候选通常已够用。v1 实现 PDF-first：学术场景优先走 FullTextResolver
的 PDF（pymupdf 管线现成），HTML 抽取 v1 用「requests + 确定性清洗（借
`text_quality_ok`/`_clean_text` 启发式）」最小实现，JS 渲染不做（crawl4ai/
playwright 不引入——agent-search 已证明其重量与脆弱性）。

**Q13 RAG 与 Web Search 不在同一模块。**
它们共享的只有 ProviderHttpClient 与 health 模型。Web Search 服务 discovery
（Researcher 找候选），RetrievalService 服务「项目文献库内的受控检索」
（Writer/Reviewer/Citation 的上下文供给）。合并会造成 agent-search 式的单
巨石（§4.7 的耦合虽可控但单文件 3534 行是教训）。

**Q14 第一版不需要 Vector DB——也不需要任何数据库进程。**
证据与理由：①规模——single-user、每项目文献库预期几十篇（PRD §6.1 项目级
隔离，无跨项目库）× 每 chunk ~2000 字符 ≈ 数千 chunk，内存索引毫秒级；②
D-0013/ARCHITECTURE §5 的「文件优先、不提前引入数据库」决策未被真实需求
推翻；③被分析项目同样没有一个用外部向量库（agent-search 无 embedding；
s2/openalex-mcp 用进程内 Map）；④Index 是 Derived State（原则 7）——chunk
文件（JSONL）持久化在项目 workspace，**lexical 索引进程内构建、可全量重建**，
dense embedding 可选（EmbeddingProvider 抽象，向量存 chunk 记录旁）。未来
若出现跨项目/万篇级需求，再评估 SQLite FTS5→专用引擎，届时只是
RetrievalIndex 接口换实现。第一版检索 = lexical（BM25 风格打分）+ 可选 dense
（余弦）+ RRF 融合 + metadata filter；**reranker 不做**（语料小、上下文预算
有限时收益存疑，且引入新模型依赖）。

**Q15 MCP 在 PaperTeam 的位置：内部零 MCP，外部远期可选。**
证据：PaperTeam 已有自己的 Agent Runtime（Pi in-process）+ customTools 注入
机制（scholarlyTools 先例），内部工具调用走 TS interface + `defineTool` 是
零开销路径；被分析的 4 个 MCP 项目全部是「给外部 Agent 客户端暴露能力」的
形态，其价值在 PaperTeam 内部由既有接口层承接。MCP 未来唯一有价值的位置：
**把 PaperTeam 的检索/核验能力暴露给用户的其他 Agent 工具**（如 Claude
Desktop 查询某项目的文献库）——这是产品边界问题而非架构问题，defer 到有
真实需求时单独立项。**不因分析对象用了 MCP 就 MCP 化内部一切**。

## 12. M6.4 RAG 初步架构（设计冻结，本轮不实现）

```text
Document Parser（PDF=pymupdf 管线（复用 paper/ 既有实现）；HTML=ContentFetcher）
   ↓
Section-aware Chunker（复用 sectionChunking 模式：TOC/标题→sections；
   ~1800/2600 字符；不跨 section；**新增 per-chunk contentHash**）
   ↓
Chunk Store（项目级 sources/chunks/<sourceId>.jsonl——Authoritative 的
   Derived 落盘；chunk 记录含 paper/section/page/contentHash 绑定）
   ↓
Index（Derived、可删可重建）
   ├─ Lexical（进程内倒排 + BM25 风格打分；启动/首次访问项目时惰性构建）
   └─ Dense（可选；EmbeddingProvider 产出，向量存 chunk 记录旁的旁车文件）
   ↓
Hybrid Retrieval（lexical + dense 并行 → RRF 融合）
   ↓
metadata filtering（sourceId/sourceRole/year/has DOI…）
   ↓
Context Budget Packing（复用 ReviewContextBuilder 的分项截断模式；
   检索结果进 Agent 上下文前打包：chunk + 出处 + 截断标记）
   ↓
Agent（Researcher/Writer/Reviewer/Citation 经 customTools 消费）
```

关键设计点：
- **chunk ID 稳定性**：`<sourceId>:<chunkSeq>`（C0001 风格延续）；contentHash
  决定内容身份——source 重解析后逐 chunk 比对 hash，未变 chunk 的 embedding/
  缓存不失效（**局部 invalidation**）；变了的追加式替换（chunk 记录带
  contentHash，索引按 hash 去重重建）。
- **source 更新失效**：SourceStore.setAnalysis 已有「替换即清 derived」模式
  （PaperIngestService.clearDerived 先例）；chunk 重建是确定性管线，可从
  checkpoint 幂等重放。
- **embedding provider 抽象**：`embed(texts: string[]): Promise<Float32Array[]>`
  ——后端可换（Pi 模型 provider 的 embedding API / OpenAI 兼容 / 本地）；
  无 provider 时 Dense 层整体关闭（lexical-only 降级可用）。
- **Index rebuild**：删除项目 `sources/chunks/` + 索引目录即回零；重建 =
  遍历 sources → 解析 → chunk → 索引，确定性无 LLM。

## 13. Evidence 边界：完整数据流（M6 最重要边界，与 ADR 联动）

```text
SearchResult            provider 返回（Web 或 Academic）
   │ 创建：SearchService（进程内对象，未持久化）
   │ authoritative：否
   ▼
CandidateSource          进入项目「候选文献」清单（project workspace 落盘）
   │ 创建：ResearchDiscoveryService
   │ 持久化：是（sources/candidates.json）
   │ verification：无（候选≠可信；PRD §6.4「先作为候选文献」）
   ▼
SourceDocument           用户/Researcher 确认后入库（SourceStore.add，
   │                     origin=AGENT_RETRIEVED / USER_ADDED）
   │ 创建：LiteratureLibraryService（M6.2）
   │ 持久化：是（sources/papers + index.json）
   │ verification：文献级状态（解析/元数据核验），仍非内容可信
   ▼
SourceChunk              解析 + chunk 管线产物（chunk 绑 paper/section/page/
   │                     contentHash）
   │ 创建：chunker（确定性，无 LLM）
   │ 持久化：是（sources/chunks/<sourceId>.jsonl）
   ▼
RetrievedChunk           RetrievalService 检索命中（带 score 与 query 上下文）
   │ 创建：RetrievalService（进程内，不持久化——重检索确定性可复现）
   ▼
EvidenceCandidate        Researcher 从 RetrievedChunk 提出的候选证据：
   │                     claim + quote（必须逐字来自 chunk 文本——确定性校验）
   │ 创建：Researcher（Agent），落 EvidenceStore 时 verificationStatus=
   │       unverified（既有行为不变）
   │ 持久化：是（evidence/evidence.jsonl）
   ▼
Verification             两条确定性通道 + 一条 LLM 通道（D-0023 延续）：
   │  ① quote 逐字匹配 chunk（fulltext 级）→ verified/level=fulltext
   │  ② 既有 ScholarlyResolver 元数据核验（metadata/abstract 级）
   │  ③ LLM judge 只见真实证据（引文逐字校验，沿用 semanticVerifier 模式）
   ▼
EvidenceStore            verificationStatus 由核验管道推进（unverified →
                         verified/plausible/mismatch/unverifiable）
```

**红线**（对应原则 1）：搜索 snippet 中的句子**永远不能**直接成为
`verificationStatus=verified` 的 Evidence——snippet 未经全文核验，最多支撑
`plausible`（level=metadata/abstract）；LLM 不得「根据检索摘要生成事实」绕过
EvidenceCandidate 的 quote 校验直接写 EvidenceStore（Researcher 现有
`createdBy=researcher, status=unverified` 的入库行为是合规下界，M6.5 只往上
加核验通道）。

## 14. 结论

六个项目对 PaperTeam 的全部价值 = **模式与算法**（SearXNG 的服务形态与聚合
纪律、agent-search 的去重/重排/SSRF/预算护栏/代码拼参考文献、s2-mcp 的
Retry-After 与错误分层、openalex-mcp 的薄原语+厚编排与 v1 最小集、AMiner 的
三方去重与信封穿透、paper-search-mcp 的反面统一性教训），**零运行时依赖**。
PaperTeam 的正确路径是：在既有 ScholarlyResolver/SourceStore/EvidenceStore/
chunk 管线边界内扩 seam（见 ADR 实施顺序 M6.2→M6.5）。
