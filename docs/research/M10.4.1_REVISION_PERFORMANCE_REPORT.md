### 1.1 瓶颈的逐 span 定位（本里程碑新增分析）

按 stage 的模型调用与 token（run-trace.json 实测）：

| stage | 调用 | latency | inTok | outTok | 成本 |
|---|---|---|---|---|---|
| review.run（3 轮 × 3 路） | 42 | 1,223s | 249,686 | 111,053 | $1.09 |
| **revision.apply** | 5 | **684s** | 105,703 | **79,534** | $0.58 |
| **plan.improvement** | 8 | **494s** | 71,676 | **42,863** | $0.37 |
| **revision.revise** | 2 | **461s** | 92,180 | **54,015** | $0.44 |
| research.propose | 6 | 194s | 57,781 | 20,996 | $0.22 |
| 其余（import/assessment/…） | 16 | 523s | — | — | $0.23 |

三个 Writer 类 stage 合计 **1,639s（48% of busy）/ 176K output tokens / $1.39**。逐 turn 下钻：

- **revision.apply（704s，单 agent 任务）**：turn 1 = 459s、in 37K / **out 46K**、stop=toolUse——wholeFile 契约下 Writer 把整篇 main.tex（77.7KB ≈ 40K tokens）生成在消息里，随后一个 `read` 工具调用让该输出作废；turn 5 = 224s、**out 33K** 再次生成整文件。**同一文件生成了两遍（79.5K out）**。
- **revision.revise（469s）**：同构——27K + 27K 两遍整文件。
- **plan.improvement（523s，8 turns）**：计划 JSON 重复生成 3 遍（17.6K → 10.6K → 10.2K：先出草稿再探索再重出）。
- **review.run**：42 调用 0 次修复性重跑；聚合 / gate / validate / claimGapAudit / claimGrounding 全部确定性零 LLM。

**当时的推断**：延迟 ≈ 输出 token 量（≈100 tok/s 生成速率主导）；「整文件×2」的输出浪费是最大可削减项 → 分节输出应可减半。**这个推断在真实模型上被证伪（见 §3）。**

## 2. 两轮优化方案与实测

### 2.1 Option 1：逐节单独派发（per-section dispatch）——已回退

**设计**：确定性 `texSectionSplit`（顶层 `\section` 切块 + round-trip 逐字节等价合并 + 节级引用匹配器：词边界标题命中 / 子节归属 / 全文引用保守超集）；单文件项目目标从「1 个整文件」变为「导言区（按需）+ 各节块」，Writer 每节一次调用、只输入本节内容、输出节片段；计划条目新增 `sectionTitle` 锚点（确定性校验）；合并写回保留块尾空行（fact restore 按空行分段——首版丢空行曾把相邻节并段导致 restore 误删节，已修复）。

**实测（run 1，真实案例完整跑通）**：

| stage | 基线 | Option 1 | 变化 |
|---|---|---|---|
| revision.apply | 704s / 79.5K out | **1,598s / 145K out**（5 节任务） | **+127% / +82%** |
| revision.revise | 469s / 54K out | 682s | +45% |
| plan.improvement | 523.5s | 358s（第 2 次尝试；第 1 次尝试遇 provider 挂起 900s 0-turn 超时，环境噪声） | −31% |
| **总 wall** | 3,139s | 6,109s | **+95%** |

**归因（agent.task 逐 turn）**：每节任务里 Writer 用 grep/read（合计 25 次工具调用）补偿被剥离的跨节上下文（核对其他节的表格 / 表述），且每节「草稿 → 核查 → 重出」+ 中间轮分析文本——5 任务中间输出 ≈ **100K tokens**；同会话累积又推高后续任务输入（末任务 in=36K vs 首任务 8K）。**输入瘦身（P0）反向放大了探索行为与中间输出。**

正确性：run 终态 completed（draft），**G1 累计事实漂移 = 0 / 引用删除 = 0 / LaTeX 构建 PASS / 全部红线断言 PASS**（比 M10.4.0 基线 run 的 3 项内容级 FAIL 还干净）；2 项 FAIL 为作者级内容 gate（claim-gap revisionIntroduced=3、academic 68<80——与基线 run 同类）。

### 2.2 Option 2：单次调用的分节补丁（single-call section patch）——已回退

**设计**：针对 Option 1 的归因反转为**保留整文件输入**（全局视野完整、消除工具探索动机）、只压缩输出契约——一次 Writer 调用，输出受影响节的补丁块（每块前置 `%%%PT-SECTION:<标题>%%%` 标记），确定性解析（标题归一化 / 未知重复拒绝 / 花括号 / 骨架 / `\end{document}` 对称校验；无标记但完整文档形态时整文件回退交付，gate 继续裁决）后按块拼回，未修订节逐字保留。安全规则与 reviseSection 逐字同源。

**实测（run 2）**：

| stage | 基线 | Option 2 |
|---|---|---|
| 前置链（import→review→assessment→research→ground） | ≈1,830s | ≈1,820s（各 stage 均接近基线） |
| plan.improvement | 523.5s | 513.5s（≈持平；run 1 的 −31% 未复现——run 间方差大于该指令收益） |
| revision.apply | 704s / 79.5K out | **尝试 1：852s / 90.3K out（单 turn）→ 解析失败；尝试 2：224s / 29.2K → 同一错误 → run failed** |

失败形态：两次尝试均 `分节补丁导言区包含了 \section 内容`——模型系统性地把（近乎）整篇修订稿放在「摘要与导言」标记下，不按节拆分标记。尝试 1 单 turn 无工具调用输出 90K tokens（> 整篇 ≈40K 的 2 倍）：**即便解析成功，输出量与基线整文件×2 同量级，无收益**。

### 2.3 P2（review 合并）：数据证明为 no-op，未动

42 次 review 调用 0 次修复性重跑；三路（fact/academic/style）并发是既有设计。合并三路或缩减复审覆盖面都会改变 review 产物 → 改变 academic_score / claim-gap 等 gate 输入（Quality Gate 语义，禁区）。两轮实现均未触碰 review 链路。

## 3. 结论：为什么负结果

**核心事实：GLM-5.3 在该修订任务上的生成长度是内生的，对 prompt 级输出契约不敏感。**三种契约形态下的输出量：整文件×2（基线 79.5K）、逐节×2+分析（Option 1 145K）、单 turn 全量+冗余（Option 2 90K）——没有一个低于基线；显式压缩契约反而引入 **100% 首试解析失败**（2/2 次）。plan.improvement 的「先核查后一次输出」指令收益（−31%）也小于 run 间方差，不可复现。

其次，本轮计划的 20 条条目覆盖 6 个锚点中的 5 个（摘要×3 / 引言×2 / 方法×4 / 实验×10 / 结论×1 / 全局×1）——「只输出受影响节」的理论上限就接近整篇，分节输出的期望收益天然有限；而 run 间环境噪声（provider 挂起 900s、未触达 stage 合计 ±1,100s 波动）大于任何可实现的节省。

**判定：无性能明显提升 → 按任务纪律不提交实现。** 两轮代码全部回退（工作树 clean，backend 全量回归在回退后复验通过）。

## 6. 后续可行杠杆（均超出本任务禁区，需单独立项）

1. **模型侧（最直接）**：修订轮换用更小 / 更快模型（如 glm-5.3-air 级）。瓶颈是 338K output tokens 的生成速率与总量，换模型是唯一直接作用于两者的手段；config 级可配，不需改运行时。
2. **运行时侧**：agent loop 内「工具轮文本预算」（toolUse 结尾的中间轮限制正文长度）——基线 46K 草稿作废、Option 1 的 100K 中间文本、Option 2 的 90K 单 turn 冗余都是同一行为模式，prompt 约束已证明无效，需运行时强制（属 Pi runtime 行为变更，需按「不重写 Agent Runtime」边界单独评估）。
3. **A3 派发覆盖缺口**（「方法·xxx」类 finding 从不派发）：正确性修复，值得单独立项（会使更多 finding 真正进入修订，工作量增加但覆盖更完整；与性能目标正交）。
4. **provider 挂起**（run 1 的 900s 0-turn 超时）：值得在 runtime 层加 streaming 心跳 / 请求级超时（观测已就位：M10.4.0 trace 可直接量化此类事件）。
