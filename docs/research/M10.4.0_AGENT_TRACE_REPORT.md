## 1. 代码审计：关键执行节点

审计范围：Agent Runtime / ModelRuntime / Revision Loop / Review Pipeline / Evidence Pipeline / Tool execution。

| 层 | 关键文件 | 执行节点 | 审计结论（trace 前） |
|---|---|---|---|
| Agent Runtime 契约 | `src/runtime/types.ts` | `startAgent/runAgent` → AgentTask 终态 | 已有 run 级 usage 汇总（`AgentRunUsage`）与 `queueDurationMs/executionDurationMs` 计时；**无逐 turn / 逐工具 latency** |
| Runtime 实现 | `src/runtime/PiRuntimeAdapter.ts` | per-session FIFO 排队 → 全局 permit → `session.prompt` 执行 → 终态归因 | 事件转发器已订阅全部 Pi 事件（message/tool/agent_end），但只映射子集进业务事件流；`auto_retry_*` / `compaction_*` 会话级事件**未被任何观测面消费** |

| Evidence Pipeline | `research.plan→execute→evidence_supply→propose→evidence.ground` | LLM 计划 → 检索执行 → propose → 三段核验 | 检索结果有快照；**LLM 调用与检索 wall time 不可分** |
| Tool execution | Pi 会话内工具（read/bash/…）+ 角色自定义工具（`scholarlyTools` / `retrieve_library` / evidence 工具面） | `tool_execution_start/end`（toolCallId 配对） | 只进有界事件缓冲（供 SSE）；**无聚合统计** |

**结论**：token / 成本在 run 级已有（M5.2/M5.6），**latency 维度全链路缺失**——这正是单次 60min 运行无法归因瓶颈的原因。

## 2. 设计与实现

### 2.1 新增模块（`backend/src/observability/`）

- **`trace.ts`**：进程内 tracer。OTel 兼容 span（`traceId/spanId/parentSpanId/name/kind/startMs/endMs/durationMs/status/attributes/events`）；`RunTraceSession` 按 `(projectId, runId)` 聚合（span 上限 50,000 + 会话注册表上限 8，超限如实丢弃计数）；`TaskTraceRecorder` 消费 Pi 事件。
- **`traceReport.ts`**：纯函数 `buildPerformanceReport(doc)` → markdown。

### 2.2 采集面（三类 span）

| span | 父 span | 关键属性 |
|---|---|---|
| `stage:<stageId>` | —（根） | stage.id / attempt / phase / 失败分类 |
| `agent.task` | stage span | task.id / agent.id / role / model.label / 状态 / queue+execution 时长 / usage / retry 计数 / compaction 计数 |
| `model.turn` | agent.task | provider / model / **latency（message_start→message_end 实测）** / in·out·cache tokens / stopReason / estimatedCost |
| `tool.call` | agent.task | tool.name / **latency（toolCallId 配对）** / isError |
| `hitl-payload:<stageId>` | — | HITL payload 构造耗时（可能读服务/调模型） |

重试捕获：`auto_retry_start/end`（provider 请求失败重试，失败请求的 model span 以 error 收口）+ `agent_end.willRetry`（agent 步级重试）+ `compaction_start/end`（上下文压缩，内含 LLM 调用）——三者此前均无观测面。

### 2.3 归属机制（不碰业务代码的关键）

orchestrator 在 stage 执行期间进入 `AsyncLocalStorage` trace scope；**PiRuntimeAdapter 在 `startAgent` 入口（首个 await 前）捕获该 scope**，后台链与事件转发一律用捕获值——不依赖事件触发点的动态 async 上下文（Pi 会话持久 listener 可能落在会话创建时的上下文）。业务服务（Writer/Reviewer/Researcher…共 25 处 `runAgent` 调用点）**零改动**。

### 2.4 落盘（每次 run 两个文件）

`projects/<projectId>/workflow/runs/<runId>/run-trace.json`（全量 span，原子写）+ `performance-report.md`。刷新时机：stage 完成/失败、HITL awaiting、run 终态（completed/failed/cancelled）。报告含：总时长（wall / busy 并集 / HITL 空隙）、stage 时间线（critical path + 段间空隙）、最慢 stage Top12、phase 汇总（import/research/evidence/revision/review/gate/build 前缀聚合）、模型调用（次数/median/p95/max/latency 总量/tokens/成本/按模型/按 stage）、工具调用（次数/失败/最慢 Top20）、Agent 任务汇总。**写盘失败只记日志，绝不影响 workflow 行为**。

### 2.5 审计中发现的既有缺陷（本里程碑顺带修复）

**`resume()` 与旧执行循环的竞态死锁**（orchestrator）：`awaiting_input` 在 `persistThenCommit` 内 `apply(handle.state)` 时即对 `GET /api/runs` 可见，而旧循环要到 emit/checkpoint 完成后才退出并清空 `handle.loop`；该窗口内的 resume 会让 `startLoop` 因 `loop !== null` 静默 no-op → run 永远停在 running。基线窗口 <1ms（仅一次事件追加），繁忙轮询客户端可稳定命中（本里程碑 trace 落盘把窗口拉宽到一次 fsync 量级后由测试暴露）。修复：与 `cancel()` 同口径，resume 在 startLoop 前先 `await handle.loop` 收敛（`WorkflowOrchestrator.ts` resume()，regression 由既有 HTTP e2e 测试锁定——修复前 existingPaper e2e 必现挂起，修复后 3.8s 通过）。

### 2.6 显式边界（不采集）

- run 外的模型调用（启动期 Skill 摘要、Settings test、**workflow 启动前的 vision 分析**）不入 run trace——无 run 归属；vision 自带 usage 落盘（vision.json）与 E2E 遥测。
- 进程崩溃时未落盘的 span 丢失（stage 边界增量落盘已把窗口压到单 stage 内）；stageHistory 仍可事后重建 stage 级时间线。

### 4.3 模型调用分布（首次可观测）

- **按 stage**：review.run 42 次 / 合计 latency 1,223s（三路并发——单次 review 的 wall 贡献 ≈313s）；revision.apply 5 次 / 684s；plan.improvement 8 次 / 494s；revision.revise 2 次 / 461s；research.propose 6 次 / 194s。
- **单次分布**：median 4.5s（review 逐节短调用）× **p95 223.7s、max 458.7s**（revision/整文件改造与 plan 长调用）——长尾完全由 Writer 类整稿任务贡献。
- **工具**：最慢 lookup_paper（14 次 / 36.7s / avg 2.6s）——学术元数据 HTTP 查询；业务内检索工具（retrieve_library/evidence_query/get_chunk 合计 98 次）全部 <1.5s 合计。

**瓶颈结论**：latency 100% 由模型生成长尾主导（79 次调用中 top-5 长调用 >200s 即占 >1,600s）；HITL 等待、工具、检索、LaTeX 编译、gate 全部合计 <90s。任何「把 60min 降下来」的优化都必须作用于**模型调用的次数×长度**（如 revision 循环的整文件重写策略、review 的逐节 fan-out 粒度），而不是基础设施。

### 4.4 论文内容级 gate（非系统工程项，如实记录）

本轮 3 项驱动断言 FAIL 与 M10.3.1 的 PARTIAL 同类：`cumulative_fact_preservation` 1 项未授权数值新增（Writer 在讨论节新增「0–2s 检索相似度变化 −0.014~…」——守卫正确阻断 Final、Draft 产出）；`claim-gap-audit` revisionIntroduced=9（M10.3.1 为 2，模型非确定性导致的同类波动，均待作者裁决）；`academic_score_threshold` 68<80（作者级，与 M10.3.1 相同）。**trace 改动不触达任何上述路径**（§5 红线审计）；本轮产物为 draft 级，M10.3.1 已归档的修订产物不受影响。trace 工件已另存 `D:\PaperTeamData\M10.4-outputs\`（run-trace.json SHA 817730f0… / performance-report.md / m1031-real-summary.json / e2e-console.log）。

## 6. 后续建议（不在本里程碑执行）

1. 接 OTLP exporter：span 形状已兼容，可按 §4 实测决定是否值得引入 collector。
2. 以 §4 baseline 为对照，候选优化点（均需单独立项 + 预注册评估，不动 gate）：
   - **revision.apply / revision.revise 的整文件长调用**（5+2 次调用 / 1,145s，单次 max 458.7s）——评估分节改造或增量 diff 策略；
   - **review.run 的逐节 fan-out 粒度**（42 次调用，median 4.5s 但串行节多）——评估批量审阅 prompt；
   - **plan.improvement**（8 次 / 494s）——评估计划输入瘦身（本轮 input 627K tokens、cacheRead 2.18M 的主要来源是逐 turn 全上下文重放，缓存命中率是成本主杠杆）。
3. trace 落盘可加开关（当前默认开启；单 run 落盘量级：294 spans ≈ 165KB，每 stage 边界原子重写 ×2 文件，fsync 开销 <1%）。
