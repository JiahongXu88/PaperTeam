## 1. Problem from M9.7.7

M9.7.7（SUPPORT 路径 A/B，docs/research/M9.7.7_CLAIM_GROUNDING_SUPPORT_AB_EVALUATION.md）结论：Claim Grounding 的 SUPPORT 转换 0/5，判定 NOT_SUPPORTED。机制各环节（候选检索 / 派发 / Writer 纪律 / 无害性）正常工作：

- matcher 找到候选 5/5（词面 ≥2 命中），但「词面相邻 ≠ 语义支撑」——Top 候选均不支撑 claim 原义；
- Writer 5/5 正确拒绝强配（全部 WEAKEN）——不是服从性失败；
- citation 链路完整（合法 \cite 的 claim 仍可判 U——citation-backed ≠ claim-supported）。

真正缺的是：**写作开始前，系统不知道「未来稿件需要什么证据」**。证据供给（Researcher 的锚定提案）由「检索到了什么相关 chunk」驱动，与写作自然产生的 claim 分布脱节；真正语义正确的材料（如 S006 综述全文内容、CAMEL 全文内容）根本不在 verified 池里。以及第二问题：WEAKEN 后的泛指性存在断言仍被判 UNSUPPORTED，U 永不收敛（两臂三轮 gate 全因 unsupported_critical FAIL）。

## 2. Root cause

**证据池构成与 claim 分布的语义错配（供给侧），而非判定侧或写作侧缺陷。**

- 判定侧（Fact Reviewer + claim grounding）：verdict 语义正确，错误只会来自强配；
- 写作侧（Writer）：拒绝无证据支撑的强论断是正确行为；
- 供给侧（Researcher → evidence.ground）：提案由检索面驱动，没有「成稿需要哪类论断」的先行声明，导致池子里长出的是「检索碰巧命中的 chunk」，而写作需要的「机制刻画 / 系统比较」支撑面无人负责供给。

修复方向因此是**前置规划**：在检索前显式声明证据需求（Evidence Requirement），让需求驱动检索词生成，并让覆盖分析能回答「每条需求是否已有证据供给」——即本里程碑。

### Phase 0 三问逐答

**Q1：Evidence Requirement 自然落在哪里？**
落在 `ResearchPlan`。它位于 `questions`（想回答什么）与 `queries`（怎么检索）之间，正是第三种计划成分：「未来正文的哪些论断需要证据支撑」。ResearchPlan 已具备需求所需要的全部生命周期设施：检索前制定（instruction 0「先计划后调研」）、宽容解析、HITL 编辑、派生、落盘单一写入口、重跑不覆盖。

**Q2：能否作为 ResearchPlan 的扩展？**
能，且这是唯一不产生平行状态的位置：新增可选字段 `plan.requirements: EvidenceRequirement[]`——旧 artifact 无该字段仍可读（与 M8.1 引入 plan 字段同兼容策略）；编辑/派生/落盘全部复用既有入口；Coverage Analyzer 在读侧派生需求覆盖，不在 research.json 上新增持久化覆盖状态（与 M8.3.2「Coverage 是派生视图」纪律一致）。

**Q3：如何避免变成又一个独立状态机？**
- 需求的「覆盖状态」**永不持久化**：covered/partial/missing 由 Coverage Analyzer 随源数据即时重算（既有纪律的延伸）；
- 存储模型上唯一可变字段是 `status: open | waived`，且**只有用户 PUT 能置 waived**（Agent 输出强制归一为 open）——waived = 「明知无此证据仍继续」的诚实弃权记录，不是自动流转的状态；
- 无新 Service、无新 Agent、无新 runtime：解析进 researchPlan.ts，聚合进 ResearchCoverageService，全部纯函数 + 既有只读装配层。

## 4. Design decision

### 4.1 Evidence Requirement 模型（Phase 1，最小化）

```ts
type EvidenceClaimType = "definition" | "mechanism" | "comparison" | "benchmark" | "limitation" | "background";
type ExpectedEvidenceType = "survey" | "original_paper" | "benchmark_paper" | "system_paper";
type EvidenceRequirementStatus = "open" | "waived";

interface EvidenceRequirement {
  requirementId: string;          // er-<n>，plan 内唯一（与 queryId 同分配策略）
  topic: string;                  // 未来正文需要支撑的主题（如「MemGPT 的记忆管理机制」）
  claimType: EvidenceClaimType;   // 论断类型
  expectedEvidenceType: ExpectedEvidenceType;
  relatedSection?: string;        // 预计落点章节（提示性，不与 outline 强绑定）
  priority: "high" | "medium" | "low";   // 缺省 medium
  status: EvidenceRequirementStatus;     // Agent 产出恒为 open；waived 仅用户显式
  note?: string;                  // 为什么需要 / 为什么弃权
}
```

上限 `MAX_PLAN_REQUIREMENTS = 12`（稿件规模量级，与 queries≤30 同防御口径）。解析宽容：topic 非空 + 两个枚举合法才收；priority 非法回退 medium；status 一律重置 open。

### 4.2 Researcher 集成（Phase 2）

- `buildResearchPrompt` 的 plan JSON 契约在 `queries` **之前**新增 `requirements` 块（生成顺序即思考顺序）；
- instruction 0 增补「需求先行」：requirements 是站在未来正文立场、先于检索制定的**预写证据需求**；每条 high/medium 需求必须映射至少一条主题相关检索词；**检索无法满足时不凑数**——如实写入 researchGaps / literaturePlan，绝不编造证据或自行降级需求；
- 需求→检索的影响是 prompt 层驱动 + 事后确定性核验：`requirementCoverage` 用与问题覆盖同一 token 关联规则（isTextRelated）计算每条需求的关联检索数——「需要 agent memory 机制证据」却没有 memory 相关检索词时如实显示 missing，不自动改写用户计划。

### 4.3 覆盖对齐（Phase 3）

`ResearchCoverage` 新增顶层 `requirementCoverage: RequirementCoverageEntry[]`（与 questions/gaps 平行），条目：

```ts
interface RequirementCoverageEntry {
  requirementId: string;
  topic: string;
  claimType: EvidenceClaimType;
  expectedEvidenceType: ExpectedEvidenceType;
  priority: "high" | "medium" | "low";
  coverage: "covered" | "partial" | "missing";
  relatedQueryCount: number;   // token 关联的计划检索数
  executedQueryCount: number;
  evidenceCount: number;       // 关联 verified 证据数
  promotedCount: number;       // 关联已入库文献数
  missingReason?: string;      // 非 covered 时的确定性缺口描述
}
```

判定规则与问题覆盖同骨架，但**全序以供给为准**（Phase 5 实测修正，见 §6.2）：无关联检索 → missing；存在关联 verified 证据或 promoted 文献 → covered；仅未核验证据 → partial；有关联检索但零结果 → missing；有结果但无任何证据 → partial。需求 ↔ 证据/文献匹配要求 **≥2 个内容词命中**（剔除孤立单字 CJK 功能词；与 claimGrounding CLAIM_REPAIR_MIN_MATCHED_TERMS 同哲学——宁可判缺不强配）。问题覆盖（questions）口径不变。`status=waived` 的需求不参与判定，只计入 overall 的 waived 计数。overall 新增 `requirements: {analyzed, covered, partial, missing, waived}`（加性字段，既有字段与语义不变）。GET/POST /research/coverage 响应自动携带（序列化透传，无端点改动）。

### 4.4 弱化终态语义审计（Phase 4）

**现状审计**：Writer 侧 WEAKEN 语义已存在（CLAIM_DISCIPLINE_LINES「只写被支撑的那部分，其余弱化为背景性描述」+ Repair 三动作）；但 Reviewer fact 模式判据是「无已核验证据支撑的关键论断必须是 UNSUPPORTED 并生成 critical/major issue」，**没有「可接受的弱化形态」概念**——M9.7.7 两臂实测弱化后的泛指性存在断言（「MemGPT 的记忆管理机制…」带合法 citation）在 r2/r3 仍判 U（新指纹、同语义），U 因此无法收敛，gate 无法 PASS。

**最小语义（何时弱化可接受）**：弱化可接受的唯一形态是**泛指性背景叙述**，必须同时满足：

1. 不含数字（数值 / 年份 / 百分比 / 版本号——含模型名内嵌数字，取保守侧）；
2. 不含比较方向或程度词（优于 / 超过 / 提升 / 降低 / outperform / better…）；
3. 不含性能 / 基准结果语义（准确率 / 性能 / F1 / 吞吐 / 延迟 / accuracy…）;
4. 不含对具体系统 / 方法的能力归因（提出 / 首次实现 / 证明了 / proposed / introduced…）。

违反任一 → WEAKEN 不能作为终态，出口只有两个：**SUPPORT（补证据——正是 Phase 1-3 供给路线的用武之地）或 REMOVE**。明确不放宽：M9.7.7 的 MemGPT/CAMEL/AutoGen 泛指句属于第 4 条（具体归因），在这些语义下**仍然不可接受**——它们的正解是证据供给（把对应全文纳入 verified 池），不是放行。

**落地形态**：确定性分类器 `assessWeakenedClaim`（review/weakenedClaim.ts，marker 级启发式，与 claimStrength.ts 同诚实边界——宁可漏报不制造误报）。本轮只提供工具与审计口径，**不接 Quality Gate、不改 Reviewer 判据**（硬约束；接线是下一里程碑的显式决策）。

### 4.5 明确不做（约束遵守）

不新增 Agent / Vector DB / Embedding / 知识图谱 / 新数据库 / 新检索 Provider / 新 runtime / MCP / Python 服务；不改 Quality Gate；不改 Writer/Reviewer prompt 的既有纪律；不动 Claim Grounding 机制。

**预注册假设判定：**

- **H1（prompt 依从）成立**：B 臂计划自然产出 12 条需求，high/medium linkage 100%，检索词逐需求显式对应（CAMEL→q-2、MetaGPT→q-3、MemGPT→q-4、Gorilla→q-5、AutoGen→q-6……），rationale 逐条声明「对应系统 X 的机制刻画」。需求没有停在数据里——它真实重塑了检索计划。
- **H2（诚实缺口）成立**：语料只有 3 篇全文，CAMEL / MetaGPT / 架构综述三条需求在**写作开始前**即被 requirementCoverage 标记 partial（供给不足）；该标记与写作后实际发生的 unsupported 面（CAMEL/MetaGPT/MemGPT/AutoGen 泛指句，与 A 臂未覆盖引用 li2023camel/patil2024gorilla 同构）精确对应——M9.7.7 的根因（池构成 vs claim 分布错配）在 B 臂变成了**写作前可见**的缺口清单。
- **H3（unsupported 数值）不设方向性结论（如实报告）**：B 的 U+C 实例（3/4/5/6/9）高于 A（2/1/0/1），claim 总量也更高（31 vs 24）；单 run 噪声（M9.7.7 §14 已登记 claim 习惯的 run 间随机性）+ B 写作覆盖了更多系统的具体机制断言，不构成 treatment 因果结论。M9.8 的目标是「写作前知道需要什么证据」，不是降低 U——后者依赖证据获取（promote / 全文），本轮协议在两臂对称地不做。

**Phase 5 实测暴露并修复的两处规则缺陷**（修复已入产品 + 测试回归）：

1. **执行回填前置 bug**：初版全序以「已执行且带回结果」为 covered 前置——但标准流程中检索由 Agent 工具执行，plan.queries 永远停留 planned（执行回填只在显式计划执行 API 后存在），需求会**永远 missing**。修正为供给优先（证据是供给的落地信号）。
2. **泛化词误判 covered**：孤立单字功能词（「与」）与泛化学术词（「机制」）单命中会把无全文系统的需求误判 covered（实测 CAMEL 需求被 ReAct 证据「覆盖」4 条——恰是 M9.7.7 根因的漏报）。修正为 ≥2 内容词命中（剔除孤立单字 CJK）。修正后 CAMEL/MetaGPT 正确回落 partial，但仍有 3 处主题相邻泄漏（er-8 MemGPT / er-9 Gorilla / er-10 AutoGen 各凭 1 条主题相关证据判 covered）——**在此停止 matcher 迭代**（M9.7.7 教训：参数调优不解决池问题，且单数据集上继续调阈值是过拟合）。

## 7. Limitations

1. **N=1 单 run 对照，无因果力**：分叉点在 research.idea 本身，无法共享 pre-state fork；run 间随机性（检索时序、写作习惯、FACT_PRESERVATION 失败）与 treatment 混叠。所有对比数字是方向观测，不是效应估计。
2. **token 匹配的固有精度边界**：需求 ↔ 证据匹配是内容词 ≥2 命中的确定性规则——纯中文需求主题 vs 纯英文证据文本判不关联（与问题覆盖同局限），主题相邻会泄漏（er-8/9/10 凭 1 条主题相关证据判 covered）。语义级匹配需要 embedding（架构红线外），当前口径宁可保留 3 处已登记泄漏也不引入语义服务。
3. **需求覆盖的时间口径混合**：交叉表用**终态** requirementCoverage 对照**各轮** U/C 实例——轮次间证据池在增长（3→10），早期轮的缺口比终态视图更大，88.9% 命中率是保守口径（若按轮当时池算只会更高）。
4. **两臂均未通过 build.draft**（FACT_PRESERVATION 对称失败，基线行为）：「写作完成后的最终稿指标」本轮不可观测；FACT_PRESERVATION_FAILED 本身是一个值得独立跟进的基线问题（Writer 修订 3→4 / 6→7 未授权事实改写在同种子上 4/4 复现）。
5. **需求只在首轮计划生成**：research 重跑保留既有计划链（用户修改优先），需求不随重跑刷新——新增系统断言需经编辑计划或派生路径，这是有意的（防隐式改写用户计划），但也意味着需求清单不是自动演化的。
6. **Researcher 成本上升**：需求驱动检索使 researcher 阶段成本 ~3.6×（$0.65→$2.35，12 条系统级检索词 + 更多工具调用）。换来的是可审计的对齐视图；对成本敏感场景可在 prompt 层收窄（如只对 high 需求强制映射）。
7. **Phase 4 语义未接线**：assessWeakenedClaim 只是工具与口径，未进 Reviewer 判据 / gate——U 不收敛问题（M9.7.7 §15-2b）在本轮没有产品级变化。

## 8. Next step

1. **把 requirementCoverage 接进 evidence-supply HITL**（最小闭环）：hitl.evidence_supply 的 payload 呈现「partial/missing 需求 + 对应 pending 候选的 token 关联」，让用户的 promote 决策直接对着缺口清单——这是 M9.7.7 方向 a（claim-surface-targeted evidence supply）的产品落点，且零新机制（全部既有部件）。
2. **弱化终态接线决策**（M9.7.7 方向 b）：把 assessWeakenedClaim 接入 Reviewer fact 判据（泛指形态不再强制 UNSUPPORTED）或 gate 口径（WEAKEN 后可接受的 claim 不计入 unsupported_critical）——需要作者决策放行边界，本轮已备好工具与回归用例（含 M9.7.7 实例形态）。
3. **FACT_PRESERVATION_FAILED 基线问题**：同种子 4/4 复现（两臂各 2 次），Writer 在修订轮未授权改写实验事实——建议单独立项诊断（与 M9.8 无关但阻塞 build 完成度观测）。
4. **matcher 停止迭代**的复核点：若 1 落地后供给闭环跑通，重新评估 3 处主题相邻泄漏是否仍造成误导（有真实 promote 数据后再看，不在空数据上调阈值）。
