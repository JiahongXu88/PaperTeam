## 0. Executive Summary

1. **M7.1 不是「从零接入」而是「接线收口」**。Search 基础设施（4 学术
   Provider + SearXNG + 融合 + 候选 + 转正 + 证据管线）在 M6 已全部交付且
   架构正确；本轮独立复核确认 M7.1_WEB_SEARCH_DESIGN.md §1 资产清单与
   源码一致，无返工项。
2. **四个断点全部为接线问题，非结构问题**：P-A（Researcher prompt 不引导
   检索工具）/ P-B（Agent 无候选保存工具）/ P-C（前端零消费）/ P-D
   （FullTextResolver 未实现，归 M7.2）。M7.1 修复前三个。
3. **不需要新增 Agent**。`search_papers()` / `search_web()` 已挂载到
   researcher 角色会话（`index.ts` roleCustomTools），差距只在任务 prompt
   与保存工具——保持 Researcher Agent + Tools 架构（§1.2）。
4. **CandidateSource → Literature Item 的提升链路后端已完整实现**
   （`promoteCandidate` 幂等 + HTTP `POST /sources/candidates/:id/promote`），
   无需新 API / 新 service / 新 adapter（§1.4）。
5. **本轮复核新发现三处边界**（既有文档未单列，§2.2）：① 无「向
   metadata-only 条目补挂全文文件」的 API——手动上传全文会产生独立
   SourceItem，需经 `linkSources` 建版本关系，否则 M7.1 验收的追溯链会断；
   ② promote 不做 ScholarlyResolver enrich；③ search provider API key 无
   运行时 settings 配置面（仅环境变量）。
6. **最大风险**（§7）：P-A 修复是概率性措施（prompt 引导 ≠ 模型必然调用
   工具），而 M7.1 验收底线是真实项目端到端磁盘证据——两者叠加使验收
   达成存在不确定性；缓解靠 §6 测试方案分层兜底。

### 1.1 SearchService 现状 —— ✅ 满足 M7 需求，缺口不在本层

**目录位置**：`backend/src/search/`（11 文件，全部完整实现，无 stub）。

**核心接口**（`search/types.ts`，文件头明示纪律：Web 与 Academic 数据形状
不同，不合并为万能 SearchProvider；provider raw payload 不泄漏上层；
search（发现）≠ lookup（核验））：

```ts
export interface AcademicSearchProvider {
  readonly name: string;   // "openalex" | "semantic-scholar" | "arxiv" | "aminer"
  search(query: string, opts?: SearchOptions): Promise<AcademicSearchResult[]>;
  healthSnapshot(): ProviderHealthSnapshot;
}
export interface WebSearchProvider { /* 同形，name: "searxng" */ }
export interface SearchOptions {
  limit?: number; yearFrom?: number; yearTo?: number;
  openAccessOnly?: boolean; language?: string; signal?: AbortSignal;

```

**Provider 抽象与实现状态**：

| Provider | 文件 | 状态 | 角色 / 鉴权 |
|---|---|---|---|
| OpenAlex | `openalexProvider.ts` | ✅ 完整 | primary；无 key，mailto 礼貌池（`PAPERTEAM_OPENALEX_MAILTO`，回退 `CITATION_CONTACT_EMAIL`） |
| Semantic Scholar | `semanticScholarProvider.ts` | ✅ 完整 | fallback + enrichment；可选 `x-api-key`，匿名可调（限流由共享 HTTP 层冷却） |
| arXiv | `arxivProvider.ts` | ✅ 完整 | preprint；Atom XML 轻量正则解析，无 XML 框架依赖 |
| AMiner | `aminerProvider.ts` | ✅ 完整 | China secondary；仅免费端点，有 key 才注册；HTTP-200 信封错误穿透 |

**编排层**（三层）：
- `AcademicSearchService`：有界并发 fan-out + partial success（单源失败只进
  diagnostics）；全失败抛 `SEARCH_ALL_PROVIDERS_FAILED`（D-0023）；
- `WebSearchService`：单 Web 源直调，未配置 → `SEARCH_PROVIDER_NOT_CONFIGURED`
  (503)，不阻塞启动、不影响学术链路；
- `ResearchDiscoveryService`（**discovery 对外唯一入口**）：`academicSearch`
  / `webSearch` 透传 + `saveAcademicCandidates` / `saveWebCandidates`
  （显式下标保存 → CandidateStore）+ `providerHealth()`。

**共享基建**：`providerHttp.ts`（517 行：超时 / 指数退避 + 抖动 /
Retry-After 双硬帽（请求内 5s + 冷却 60s）/ 熔断三态 / 健康四态，
「限流 ≠ 宕机」）+ `fusion.ts`（`identityKey` 分层去重 + 加权 RRF，K=60，
权重 openalex 1.0 / s2 0.9 / arxiv 0.8 / aminer 0.7 + 字段互补合并 +
确定性排序）。

**搜索结果数据结构**：
- 学术：`AcademicSearchResult = { identity: SourceIdentity, record: CanonicalPaperRecord, citationCount?, openAccess?, relevance: {provider, rank} }`，融合后为 `FusedAcademicResult`（`score` + `sources: [{provider, rank}]`）；
- Web：`WebSearchResult = { url(canonical), title, snippet, engines[], score, rank?, publishedDate?, provider }`；
- 诊断：`SearchDiagnostics.providers[]`（outcome 六态：ok / not_configured / skipped_cooldown / skipped_circuit_open / failed / degraded + latencyMs）。

**面向四目标的扩展性评估**：

| 目标 | 现状 |
|---|---|
| OpenAlex | ✅ 已实现（primary） |
| Semantic Scholar | ✅ 已实现（fallback + enrichment） |
| SearXNG | ✅ 已实现（optional Web 底座） |
| Crossref | **有意不实现 discovery provider**（D-0033：Crossref = MetadataResolver，存在于 `citation/scholarly.ts` 核验链第一环，不做 discovery 选手——裁判与选手分离，避免自证循环）。ADR §3 架构图该节点属文档张力，M7.2 时勘误（不改代码） |

新增 provider 的扩展点已被验证：实现双接口之一 + URL 构造与字段映射 +
serviceStack 条件注册（AMiner / SearXNG 即样例），共享 ProviderHttpClient

### 1.2 Researcher Agent —— ✅ 工具已挂载，缺 prompt 引导与保存能力

**实现位置**：
- Agent 服务：`backend/src/agents/ResearcherService.ts`（读项目元数据 →
  `buildResearchPrompt` → `runtime.runAgent` → `outputParsing` 确定性解析 →
  落盘 `research/research.json`）；
- Runtime：`backend/src/runtime/PiRuntimeAdapter.ts`（in-process
  `@earendil-works/pi-coding-agent`，implements `AgentRuntime` 契约 v2）；
  `scriptedRuntime.ts` 为测试专用 seam（不执行工具，浏览器级 E2E 用）；
- 角色配置：`runtime/pi/roleConfig.ts`——researcher 角色工具白名单
  `read/grep/find/ls`（只读，无 write/bash），systemPrompt 仅 3 行最小框架，
  任务指令由 prompt 内联。

**Tool calling 机制**（挂载链路，全部已就绪）：
`index.ts:152-190` 的 `roleCustomTools(role, projectId)` 回调 →
PiRuntimeAdapter 创建会话时并入 tools 白名单 + customTools（projectId 闭包，
项目隔离）。当前注入矩阵：

| 工具 | 来源 | 注入角色 |
|---|---|---|
| `search_papers` / `search_web` / `lookup_paper` | `skills/scholarlyTools.ts` | researcher + citation |
| `retrieve_library` | `retrieval/tools.ts` | researcher / writer / reviewer |
| `get_chunk` / `propose_evidence` / `evidence_query` | `evidence/tools.ts`（角色权限矩阵） | researcher 全三；reviewer/citation 读；writer 只读 formal |

**能否挂载 search_papers() / search_web()**：**已经挂载**（M6.3 完成）。
`search_papers` 走 `discovery.academicSearch()`（discovery 未装配时回退
resolver 标题检索兼容路径）；`search_web` 走 `discovery.webSearch()`，
未配置 SearXNG 时如实返回 `not_configured` 不抛错。

**断点所在**（源码确认）：`buildResearchPrompt`（`ResearcherService.ts:362-405`）
要求 1 写「调研基于项目文献库（下方提供）与**你的领域知识**」，通篇无
`search_papers` / `search_web` / `lookup_paper` 引导；`literaturePlan` 字段
语义为「调研后人工补检索的方向」且 grep 全仓无下游消费者。工具在白名单、
模型理论可见，但结构化任务约束使其在主链路（research.idea stage）事实上
不被使用。

**是否需要新增 Agent：不需要。** 结论 = **保持 Researcher Agent + Tools**。
理由（与 D-0009 / D-0041 冻结一致）：检索编排（provider 选择 / 融合 /
去重 / 降级）全是确定性服务层代码，无独立 LLM 决策面；query 生成是
Researcher 既有职责；新增角色只会制造第二个持有检索能力的会话面，违背
权限矩阵最小化。M7.1 的 Agent 侧改动只有两处：prompt 字符串（P-A）+
`save_candidates` 工具（P-B）。

### 1.3 CandidateSource 生命周期 —— ✅ 模型足够，零改动

**定义位置**：`backend/src/sources/CandidateStore.ts:29-52`。

```ts
export type CandidateStatus = "pending_review" | "accepted" | "rejected";
export type CandidateOrigin = "academic_search" | "web_search" | "manual";

export interface CandidateSource {
  candidateId: string;            // "C001" 递增
  identity: SourceIdentity;       // 与 SourceItem.identity 同构（判等基础）
  origin: CandidateOrigin;
  provider: string;               // 发现方（openalex / searxng / manual…）
  title?; authors?; year?; venue?; doi?; arxivId?; url?;
  snippetOrAbstract?: string;     // ≤3000
  query?: string;                 // 发现时检索词（provenance）
  status: CandidateStatus;
  promotedSourceId?: string;      // 转正回填指针（幂等重入依据）
  createdAt; updatedAt;
}
```

**存储**：单 JSON 文件 `<project>/sources/candidates.json`（`{items}` 原子
重写），与 authoritative 的 `sources/index.json` 分文件（候选 ≠ 正式文献，
D-0034）。

**生命周期**：`pending_review → accepted（markAccepted 回填 promotedSourceId）
| rejected（markRejected）`，两转移均幂等。判重只对 pending 按分层
`identityKey`（doi > arxiv > pmid > 标题指纹+年+一作 > url，精确相等非
相似度）；**rejected 不判重**——同一文献被拒后再次发现合法新建 pending
（设计正确）。同身份 pending 合并只补空缺（fillEmpty，信息只增不减）。

**对照设计目标**（Search Result → CandidateSource → User Review →
Literature Library → Evidence Pipeline）：现状已覆盖前三环；后两环见 §1.4。
**判定：模型足够，无需新增状态、无需修改存储结构。**

> ⚠️ 术语注意：代码中有**两条独立的 candidate 链路**，勿混淆——
> Discovery 链路的 `CandidateSource`（sources/candidates.json，转正目标
> SourceItem）与 Evidence 链路的 `EvidenceCandidate`（evidence/
> candidates.jsonl，转正目标 EvidenceRecord，要求 sourceId+chunkId 逐字
> quote 锚定）。M7.1 只动前者。

### 1.4 Literature Library 集成 —— ✅ 提升链路后端已完整实现

**已有三层**：`SourceStore`（authoritative 索引 `sources/index.json` +
papers/parsed 文件布局）、Literature Library 五入库路径
（`SourceImportService.importPdf / importDoi / importArxiv / importUrl /
importBibtex`）、`EvidenceStore`（evidence.jsonl，grounded 写入唯一入口
appendBatch）。

**CandidateSource → Literature Item 的实现：已经存在，无需新建。**

```text
Candidate(pending_review) → 用户 POST /api/projects/:id/sources/candidates/:cid/promote
  → SourceImportService.promoteCandidate（:301-337，幂等）
     ├─ 快路径：status=accepted 且 promotedSourceId 条目仍在 → 直接返回
     ├─ findByIdentity 库级判重：同身份已入库 → applyMetadataMerge 只补空缺
     └─ 新条目 → sources.addRecord：origin=AGENT_RETRIEVED，
        status=metadata_only（无全文），sourceType 按 identity 分层推导
  → CandidateStore.markAccepted(promotedSourceId) 回填指针
```

**回答「新 API / 新 service / 新 adapter？」：三者都不需要。** HTTP 层
（promote / reject / list / add / delete）与 service 层均已接线且幂等。
真正的缺口在消费侧（前端 P-C + Agent 工具 P-B），以及 promote 之后的
全文获取层（P-D，M7.2）。

**本轮复核发现的三个边界**（§2.2 详述）：
1. 手动上传全文走 `sources.add` 只按 contentHash 判重，产生**独立的新
   SourceItem**，不自动关联已 promote 的 metadata-only 条目——需再调
   `POST /sources/:id/link` 建版本关系；不存在「向既有条目补挂文件」的 API；
2. `promoteCandidate` 以 provenance=inferred 合并候选元数据，不调
   ScholarlyResolver enrich（对比 importDoi/importArxiv 有 enrich 路径）；
3. promote 不触发 retrieval rebuild（metadata_only 反正被 chunker skip，
   当前无意义；M7.2 FullTextResolver 落地后需在此接线）。

## 3. M7.1 目标设计

**目标**：修复 P-A / P-B / P-C，把 M6 冻结的能力组件接成真实闭环——

```text
User Research Question（项目 researchIdea）
  ↓ research.idea stage（P-A：prompt 接线）
Researcher Agent
  ↓ search_papers / search_web / lookup_paper（已挂载）
Search Tool（既有 scholarlyTools + ResearchDiscoveryService）
  ↓ save_candidates（P-B：会话内显式保存，服务端缓存按下标）
CandidateSource（既有 CandidateStore：pending_review，HITL 待审）
  ↓ 用户 promote（既有幂等链路；P-C：前端补 UI）
Literature Library（既有 SourceStore，metadata_only）
  ↓ 用户上传全文（既有路径，M7.1 阶段闭环依赖；M7.2 自动化）
Evidence Grounding（既有三段核验 → verified）→ Writer 消费
```

**范围（= 冻结文档 §4 四项，M7.1 全部增量）**：
1. Researcher prompt 接线（纯字符串，`ResearcherService.ts`）；
2. `save_candidates` 工具 + 服务端检索缓存（方案 B：LRU ≤5/query、
   TTL 10min、≤25 条/次、miss 结构化报错）；
3. 候选缓存护栏测试（`backend/test/search/`）;
4. 前端 Discovery & 候选管理 UI + e2e（零后端改动）。

**边界内不扩**：不改 workflow definitions（保存发生在 Agent 会话内，无新
stage）；不改 research.json 输出契约；不加自动 promote（转正永远 HITL）；
单轮调研（不做自动补检索循环）。

## 4. 数据流设计

### 4.1 检索与保存（P-A / P-B 修复后）

```text
research.idea stage
  └─ Researcher Agent（prompt 已接线）
       ├─ search_papers(query, {limit, yearFrom, yearTo})
       │    └─ ResearchDiscoveryService.academicSearch
       │         ├─ AcademicSearchService：OpenAlex(1.0)/S2(0.9)/arXiv(0.8)/AMiner(0.7)
       │         │   有界并发 fan-out + 共享 ProviderHttpClient（超时/退避/熔断/四态）
       │         ├─ fusion：identityKey 去重 + 加权 RRF + 字段互补
       │         └─ 返回 FusedAcademicResult[]（含 index）+ diagnostics
       │              └─【新】进程内检索缓存：Map<projectId, CachedSearch[]>
       │                  LRU ≤5/项目 · TTL 10min · 不落盘（重启即失）
       ├─ search_web(query)（SearXNG optional，not_configured 如实返回）
       └─ save_candidates(kind, query, resultIndexes)   ←【新工具】
            └─【新】saveCandidatesFromCache：命中缓存
              → 复用既有 saveAcademicCandidates / saveWebCandidates（单一写入路径）
              → CandidateStore.add（identityKey 判重，同身份 pending 合并补空）
              → sources/candidates.json（pending_review）
              miss（TTL 过期 / 被覆盖 / query 不一致）→ 结构化 SEARCH_CACHE_MISS
```

**关键纪律**：HTTP `saveAsCandidates` 与 Agent `save_candidates` 两个入口
**汇聚到同一个保存函数**——候选写入口径单一（与 EvidenceStore appendBatch
单点同构）；元数据只能来自 provider 真实返回（按值回传方案已因幻觉风险
被拒），Agent 无法伪造 DOI/标题入库。

### 4.2 审核转正与全文（P-C 修复后；全文手动路径含 N-1 编排）

```text
sources/candidates.json（pending_review）
  └─ 前端候选面板（新）→ 用户逐条审阅
       ├─ reject → POST /sources/candidates/:cid/reject（幂等；可再次发现）
       └─ promote（选 sourceRole）→ POST /sources/candidates/:cid/promote
            → SourceImportService.promoteCandidate（幂等）
            → SourceStore：origin=AGENT_RETRIEVED，status=metadata_only
                 ├─ 用户上传全文 PDF（既有 POST /sources）
                 │    → 新 SourceItem（contentHash 判重）
                 │    →【N-1 编排】前端自动 POST /sources/:newId/link
                 │       targetSourceId=promoted 条目（版本关系，追溯链闭合）
                 ├─ chunker（绝不索引 abstract；metadata_only 一律 skipped）
                 └─ M7.2：tryResolveFullText 自动获取 OA 全文（不在 M7.1）
  ↓ 有全文后
ChunkStore（sources/chunks/*.jsonl）→ retrieve_library 可检索
  → Researcher propose_evidence（sourceId + chunkId + 逐字 quote）
  → evidence.ground 三段核验 → EvidenceStore(verified)
  → EvidenceSelectionService(formal) → Writer / Reviewer / Quality Gate
```

**红线（数据流层面）**：discovery 链路无 EvidenceStore 写路径；snippet /
abstract 永不进 chunk；候选必经用户 promote；检索默认零持久化（缓存是
进程内 derived，不落盘）。

## 5. API 设计建议

### 5.1 HTTP API：M7.1 零新增、零修改

后端 API 面已完整，M7.1b 前端直接消费：

| 禁止项 | M7.1 方案是否触碰 | 依据 |
|---|---|---|
| ❌ 新 Agent | 否——Agent 侧仅 prompt 字符串 + 1 工具，仍为 Researcher + Tools | D-0009 / D-0041；§1.2 论证 |
| ❌ Runtime Rewrite | 否——工具经既有 roleCustomTools 通道注入，PiRuntimeAdapter 零改动 | 挂载链路已验证（index.ts:152-190） |
| ❌ Workflow Rewrite | 否——definitions.ts 零改动，保存发生在 Agent 会话内，无新 stage | 冻结文档 §5-3 |
| ❌ Vector Database | 否——检索栈 BM25+可选 dense+RRR hybrid 不动，候选/judged 数据仍是文件优先 | D-0036 / D-0013 |
| ❌ 新 RAG 框架 | 否——FullTextResolver（M7.2）只给既有 chunker 喂全文 | D-0041 |

### 7.2 风险清单

| # | 风险 | 等级 | 缓解 |
|---|---|---|---|
| 1 | **P-A 修复是概率性措施**：prompt 引导 ≠ 模型必然调用工具；不同模型工具调用倾向差异大，research.idea 可能仍不检索 → 验收底线 1（真实端到端）不稳 | **高（最大风险）** | 分层验收：护栏测试（确定性）先行；真实项目验收多模型实测；prompt 迭代空间预留（要求 1 措辞可调）；验收判据以磁盘证据为准，不放松 |
| 2 | N-1 追溯断链：手动上传全文产生独立 SourceItem，若前端不编排 link，验收的「source 追溯到 discovery 候选」断裂 | 高 | M7.1b 前端编排上传后自动 `link`（既有 API，零后端改动）；e2e 覆盖该路径 |
| 3 | save_candidates 滥存 / 缓存 miss 重试循环 / research.idea 时延上升 | 中 | ≤25 硬帽 + prompt ≤20 指引 + identityKey 合并兜底；miss 结构化指引（先 search 再 save）；时延提示 + fan-out 有界并发 |
| 4 | prompt 改动软化 Evidence 红线（P-A 修复误伤要求 3） | 中 | 要求 3 一字不动为验收项；红线回归测试（snippet 永不进 chunk / 工具零 EvidenceStore 写路径） |
| 5 | 外部 provider 在部署环境的可达性 / 限流（S2 429 高发；OpenAlex/S2/arXiv 大陆网络波动）影响真实项目验收 | 中 | ProviderHttpClient 四态健康 + partial 常态化如实呈现；live smoke 分离；验收可择时重试 |
| 6 | 前端范围蔓延（独立页面 / 新 store / SSE 推送等过度设计） | 低 | 严格限定 tab 内面板 + 既有组件复用；本 §6 Phase 4 清单为界 |

### 7.3 最大风险结论

**M7.1 最大风险 = P-A 修复的不确定性 × 验收的真实性要求。** 四个改动项中
三个（工具 / 缓存 / 前端）是确定性工程，唯有 prompt→行为是概率映射；而
M7.1 验收底线第一条要求真实项目端到端出现 verified evidence。若模型在
真实会话中不调工具，后端接线全部正确也无法闭环。缓解优先级：先以护栏
测试锁定确定性部分 → 真实项目小样本多模型实测 → 依实测调 prompt 措辞
（不扩范围）→ 若多轮仍不触发，升级为 DECISIONS.md 议题（如工具结果预注入
会话的确定性方案），**不得**以放宽验收标准或自动 promote 的方式「达成」
验收。

### 7.4 开放问题（不在 M7.1 处理）

- 多轮自主调研（literaturePlan → 自动补检索）：待 M7.1 真实使用数据；
- 候选长期膨胀（candidates.json 无上限）：观察后考虑 rejected 自动归档；
- 补挂全文 API / promote enrich / search key 运行时配置面（N-1/N-2/N-3
  的后端形态）：随 M7.2 设计评估。
