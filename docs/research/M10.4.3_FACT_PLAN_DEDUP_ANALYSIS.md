# M10.4.3 — Fact Preserve Plan Deduplication：只读分析

日期：2026-10-02　阶段：Phase 1（只读分析，未改任何代码）

---

## 1. Problem Statement

M10.4.2 基准 7 次真实运行中 2 次（A1·attempt-2 all-strong / A2·attempt-1 flash-writer）死于同一故障点：

> Writer 在 ≥2 处做了**内容完全相同**的未授权事实修改 → Fact checker 产出多条同 `violationKey` 的 violation → `revisionPlan.ts` 的 `fact-preserve:<violationKey>` id 派生**无去重** → M9.10 构建期断言 `duplicate_item_id` 抛 `RevisionProtocolError` → `revision.plan` stage 失败 → 整个 revision run fail-closed。

该故障与模型档位无关（两档都触发）。本文档给出根因分析与修复方案设计；修复与重验证见同目录 `M10.4.3_FACT_PLAN_DEDUP_REPORT.md`。

## 2. 现场实证（M10.4.2 真实产物）

| 运行 | 产物 | 违规明细 | 重复形态 |
|---|---|---|---|
| A1·attempt-2（strong writer） | `M10.4.2-outputs/A1/quality-gate-final.json` → `cumulativeFactPreservation.unresolvedViolations` | 2 条 finding，key `49742c0c9bd329e8` ×2；file=main.tex，reason=`prose_number`，before=`\includegraphics[width=0.75\linewidth]{figs/fig_pr_bdd100k.pdf}`，after=""（删除） | 同一 `\includegraphics` 行（含数值 0.75）在稿内出现 ≥2 处，被同时删除 → 两条 finding 的 (file, reason, before, after) 四元组**逐字节相同** |
| A2·attempt-1（flash writer） | `M10.4.2-outputs/A2-attempt1/reviews/quality-gate-r2.json` → 同字段 | 5 条 finding（4 个 distinct key），key `d56951de40b0b6c0` ×2；reason=`added_number`，before=""，after=同一新增段落行快照 | 同一新增行内 ≥2 个新数值 token 各产生一条 finding，`after` 都是**同一行的快照**（`lineOf(current, at)`），四元组相同 |

两个案例覆盖了 changed/removed 与 added 两个方向——**任何**「同内容漂移在多处发生」的形态都会命中。

## 3. 代码链路分析

### 3.1 fact-preserve item 生成（`backend/src/review/revisionPlan.ts:333-370`）

```ts
for (const regression of input.factRegressions ?? []) {
  items.push({
    id:
      regression.violationKey !== undefined
        ? `fact-preserve:${regression.violationKey}`        // ← 直接拼 key，无任何去重
        : `fact-preserve:${regression.file}:${findingCount(items, regression.file) + 1}`,  // ← fallback 反而有计数去重
    ...
```

矛盾点一目了然：**无 violationKey 的 fallback 路径**用 `findingCount`（同文件已入列条目计数）做了逐条递增；**有 violationKey 的主路径**（M10.3.1 引入）却假设 key 天然唯一，直接拼接。主路径恰恰是 existing-paper 工作流（真实返修场景）的必经路径。

### 3.2 violationKey 的定义来源（`backend/src/quality/cumulativeFactPreservation.ts:180-185`）

```ts
export function cumulativeViolationKey(finding: FactFinding): string {
  return createHash("sha256")
    .update(`${finding.file}|${finding.reason}|${finding.before}|${finding.after}`)
    .digest("hex")
    .slice(0, 16);
}
```

- **内容指纹，不是出现位置指纹**：key 只由 (file, reason, before, after) 四元组决定。`section`、`classification`（真正的数值 token）、行号都不参与。
- 这是**有意设计**：key 的用途是「跨轮跟踪同一漂移（文本不变则指纹不变）」——`resolvedViolations` / `collectHistoricalViolationKeys`（`:318-341`）全部按 key 寻址、天然集合语义。key 的多重性（同一内容漂移出现 N 次）在这个用途下是良性的。
- 产生重复的机制（`factPreservation.ts` 扫描循环）：
  - `added_number`（`:1196-1211`）：每个未配对新数值 token 一条 finding，`after = lineOf(current, at)`——同行多 token 或同内容行多处出现 → 同四元组；
  - `prose_number`（`:1138-1191`）：每个缺失/替换 token 一条 finding，`before` 为整行快照——同内容行多处同向漂移 → 同四元组。
- 汇聚点（`cumulativeFactPreservation.ts:282-289`）：6 个桶（changed/removed/added/directional/formula/placeholder）**直接 concat 后逐条 map 加 key，不做任何按 key 去重**——gate 的职责是如实报告全部出现，这一层不该去重。

### 3.3 duplicate id 检测位置（fail-closed 断言）

| 位置 | 时机 | 行为 |
|---|---|---|
| `revisionItemStatus.ts:119-144` `validateRevisionPlanShape` | M9.10 计划 schema 断言 | 扫描 items 计数 id，count>1 → `duplicate_item_id` violation |
| `revisionPlan.ts:434-441` `buildRevisionPlan` 尾部 | **构建期**（本 bug 的爆点） | shapeViolations 非空 → 抛 `RevisionProtocolError("duplicate_item_id")`，不落盘 |
| `revisionItemStatus.ts:349-358` `applyRevisionItemTransitions` | 流转期 / 读回期 | 双通道防御：落盘读回的坏计划同样拒绝 |

即：断言本身是 M9.10 Phase 1 的正确设计，爆点在**派生器违反了自己承诺的 id 唯一性不变量**。

### 3.4 M9.7.6 sectionMatches 重复 id：共同模式确认

commit `14cdcf2`（M9.7.6 P0，真实 m975 产物复现）：finding 的 section 字段引用多个目标（`X.tex（并见 Y.tex））`经 `ref.includes(stem)` 模糊匹配多个 revision target → 派发循环**每 target 压一次同一 plan item id** → `applyRevisionItemTransitions` 拒绝重复 id → run 确定性死亡。

共同模式（两案完全同构）：

> **确定性派生器按「finding × 目标/出现次数」扇出条目，而 id 只按 finding 内容寻址** —— id 承诺唯一性与派发扇出的多重性矛盾；下游断言（M9.7.6 转移协议 / M9.10 schema）正确地 fail-closed。

M9.7.6 的修法是「源头合并（dispatchedItems 按 id 合并）+ 转移归一化（幂等重述折叠）」。本案与之互补：gate 侧必须保留全部出现（3.2），所以**不能在源头合并 finding**，只能在派生 id 时为「同一 key 的第 N 次出现」提供确定性区分。

## 4. Root Cause（结论）

1. **直接根因**：`buildRevisionPlan` 的 fact-preserve 主路径把 `violationKey` 直接当条目 id，无出现次数消歧；`violationKey` 是内容指纹（有意设计），同一内容漂移多处发生时必然产生重复 id。
2. **设计缺口**：M10.3.1 引入 violationKey 路径时，未沿袭 fallback 路径已有的 `findingCount` 计数去重模式；M9.10 构建期断言正确地把该缺口暴露为确定性失败（而非静默坏计划）。
3. **模型无关性解释**：触发条件是「Writer 在多处做同内容漂移」——任何档位模型的同质化改写（如统一删同一图、统一加同一段）都会命中，与能力档位无关。

## 5. 为什么 fail-closed 是正确行为（不改动断言）

- 同 id 双条目会让 M9.10/M6.7 条目状态机的 byId 匹配产生未定义行为：同一 id 可能同时收到 `applied→validated` 与 `applied→rejected` 的矛盾转移序列，`revision_items_resolved`（Quality Gate 终局门）按 id 计数也会被重复污染。
- 计划是 Writer 派发与 HITL 呈现的**权威输入**；带重复 id 的计划若静默落盘，等价于让「漂移恢复指令」的执行追踪不可信——比阻断一次 run 严重得多。
- M9.7.6 已确立同类问题「在源头修派生、断言保持 fail-closed」的处置口径。本修复沿用：**断言一行不动**。

## 6. 修复层选择（为什么不放别处）

| 候选层 | 判定 | 理由 |
|---|---|---|
| ① 改 `cumulativeViolationKey` 公式（加入位置/行号/classification） | ❌ | 破坏跨轮 carry-forward：历史轮 gate 产物里的 key 用旧公式计算，新公式下 `resolvedViolations` / `collectHistoricalViolationKeys` 全部失配——已解决违规会被误报为新增。且该文件属 Fact Gate 红线。 |
| ② gate 侧按 key 去重 unresolvedViolations | ❌ | gate 的职责是如实报告**全部出现次数**（5 条 finding 报 5 条）；按 key 折叠会让「同漂移出现 N 次」在审计产物里不可见。亦属红线。 |
| ③ `buildCumulativeFactRegressions`（definitions.ts）合并同 key regression | ❌ | 丢失出现次数信息；且合并规则（保留哪条 detail/factRestore）引入新的语义裁决，无必要。 |
| ④ **`buildRevisionPlan` 派生 id 加出现序号（本案采用）** | ✅ | 最小改动：同一 violationKey 的第 N 次出现 → `fact-preserve:<violationKey>:<N>`（0 基）。纯函数、无随机/时间源、同输入同输出；沿用 fallback 路径已被验证的「计数消歧」模式；不触碰任何 gate 文件。 |

**受影响的唯一 id 格式消费者**：`definitions.ts:2325-2328`（restore stage 回写 validated 时按 `item.id.slice("fact-preserve:".length)` 反解 key）。violationKey 是 16 位 hex（不含冒号），改为取 id 前缀后第一段（`.split(":")[0]`）即可同时兼容新旧格式与 fallback 格式。其余全部消费点（factPreservation 授权过滤、restore factRestore 并入、派发、HITL）均按 `kind`/`section` 匹配，与 id 格式无关（grep 全仓核实）。

**key 级闭环语义说明**：restore span 按 key 解决违规（`resolves: [violationKey]`），同 key 的 N 个条目会在恢复成功时**全部**回写 validated。这与全系统「key = 漂移身份」的寻址一致；若某次出现的段落实际未恢复，下一轮 gate 基于快照重算会重新派发——计划状态不是授权来源（`cumulativeFactPreservation.ts:270-272` 明确 fact_preserve 条目绝不进入累计授权），不存在洗白路径。

## 7. 对既有 Fact Gate 语义的影响评估

- **零语义改动**：`factPreservation.ts` / `cumulativeFactPreservation.ts` / `citationPreservation.ts` 等全部 gate 文件不动；violationKey 公式不动；授权匹配不动（`factPreservation.ts:411/429` 按 `kind`/`factRestore`/problem 文本过滤，与 id 无关）。
- **产物兼容**：落盘计划为逐轮文件（`revision-plan-r{round}.json`），旧计划的裸 `fact-preserve:<key>` id 只被 restore 回写读取（新解析规则向后兼容）；无跨轮 id 追踪依赖。
- **可观察变化**（预期内）：同 key 多出现时计划条目数从「run 死亡」变为「N 条同 key 条目」；`summary.planned` 相应增加。

## 8. 残余同类风险登记（不在本案范围，无观测失败）

- `findingFingerprint`（`category|section|description` 哈希）在两条不同 issue 文本完全相同时同样碰撞——reviewer 实际产出未见；若未来出现，M9.10 断言会同样 fail-closed 暴露。
- `citation-missing:{key}:{file}` 在 `files` 数组含重复路径时会碰撞——上游 `citationMissingTargets` 为确定性扫描，未见重复。
- 两者均维持「断言暴露 → 源头修」口径，不预先修复。
