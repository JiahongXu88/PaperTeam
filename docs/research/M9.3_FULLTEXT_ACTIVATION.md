# M9.3 Academic FullText Activation

> 2026-09-22 完成态报告。前置：M8 COMPLETE、M9.1 PASS（`19b9ac4`）、M9.2 PASS
> （`0f48018`）。本阶段目标：让已经进入 Literature Library 的学术文献真正
> 获得可供后续 Parse / Chunk / Evidence 使用的全文——**激活** M7.2 已有的
> FullTextResolver，不重新设计全文系统。

## 1. Existing FullText Architecture Audit（静态审计结论）

以 main `0f48018` 源码为准（不引用旧报告）：

**Resolver 层**（`backend/src/search/fullText.ts`，M7.2 交付）：
- 三实现：`UnpaywallResolver`（DOI → `best_oa_location.url_for_pdf`；需 email
  配置，未配置不注册）、`OpenAlexOaResolver`（DOI/openalexId →
  `best_oa_location.pdf_url`；ADR 名 `oa-url`）、`ArxivPdfResolver`
  （arxivId → 确定性 PDF URL，无 API）；
- 链选择（`applicableFullTextResolvers`）：有 doi → `[unpaywall, oa-url]`，
  仅 openalexId → `[oa-url]`，有 arxivId 追加 `[arxiv]`；**URL-only 身份 →
  空链**（Web 候选定位，天然不可自动解析）；
- 下载（`downloadPdf`）：`ProviderHttpClient.fetchBytes` + SSRF 逐跳护栏
  （仅 https / 无 userinfo / 443 / 拒内网字面量）+ 重定向 ≤5 跳逐跳校验 +
  ≤20MB 大小帽 + `%PDF-` 魔数校验；error ≠ not_found（404=not_found，
  网络/限流=error）。

**编排层**（`SourceImportService.tryResolveFullText`，M7.2）：
- 单轮有界尝试：每 resolver 一次 resolve + 每命中 URL 一次下载，无内层重试
  风暴；结局是数据不是异常：`resolved / not_found / failed /
  skipped_has_file / not_resolvable` 五个 outcome；
- 成功路径与 PDF 上传同构：`attachFile`（同 sourceId 原地挂载，chunk 锚点链
  闭合）→ `BuiltinPdfAnalyzer` → `setAnalysis`（contentHash 防失效）→
  `onFullTextAttached`（检索重建钩子）→ provenance 落盘；
- **promote 已有自动契约**：`promoteCandidate` 对 metadata_only 条目
  fire-and-forget 单次尝试（M7.2 已如此，本阶段保持不动）。

**持久化状态**（`SourceItem.fullText?: SourceFullTextProvenance`）：
- 持久 status 只有三个：`resolved / not_found / failed`；
- `not_resolvable` 是**调用结局**（持久化时折叠为 not_found + 说明性 note）；
- 第五个 outcome `skipped_has_file` 是幂等跳过，不落新状态；
- 全字段 optional——老数据 lazy 兼容（本阶段零 migration）。

**检索层**（M6.4）：`onFullTextAttached → retrieval.rebuildSource`（生产装配
serviceStack 注入）+ retrieval 本身 lazy 自愈（`librarySignature =
sourceId:contentHash:updatedAt`，`loadProject` 对 stale/缺失 chunk 重新生成）。

**审计发现的缺口**（= 本阶段工作面）：
1. **无批量入口**：只有单篇 HTTP 端点
   `POST /sources/:sid/resolve-fulltext`（M7.2）；
2. **无手动补挂入口**：`SourceStore.attachFile` 原语已就位但未接任何路由；
3. **前端零可见**：`SourceItemView` 无 fullText 字段，SourcesPanel 无状态列
   / 按钮（API_CONTRACT §1.2 标注「前端 UI 后续按需」）；
4. **并发写隐患**（实施中暴露）：SourceStore 全部读-改-写无串行化——单篇
   时代无并发写方，批量并发下 index.json lost update（详见 §5）；
5. **BuiltinPdfAnalyzer 正则回溯缺陷**（实施中暴露，M6.2 预存）：真实论文
   PDF 大内容流上灾难性回溯，单流 30s+ 同步阻塞事件循环（详见 §8）。

## 2. Why Activation Was Needed（原先为什么 metadata_only）

M7.2 交付了完整的 resolver → download → attach → analyze → rebuild 链，
但只有两个触发面：promote 后台单发 + 单篇 HTTP 端点（无 UI）。用户视角：
- promote 后的文献大多停在 metadata_only（后台尝试失败 / Web 候选不可解析
  时无从知晓，也无重试入口）；
- 文献库 UI 完全不呈现全文状态，用户无法回答「这篇文献有没有全文」；
- 无批量补全：几十篇文献逐篇 curl 不现实；
- 自动解析失败（付费墙 / 无 OA / 网络失败）后没有人工兜底路径。

即：能力存在、产品不通。M9.3 = 产品接线 + 状态可见 + 批量控制 + 人工
fallback，零第二套存储 / 解析 / 检索。

## 3. Academic-Only Scope

M9.2 已启用 General Web Search，但 M9.3 **只处理学术文献全文**：
- Web Candidate / Web Source（url-only 身份）在 resolver 链选择层天然落空链
  → `not_resolvable`，单篇端点 422、批量计入 notResolvable 桶；
- **SearXNG URL 永远不会被 FullTextResolver 当论文 URL 下载**（resolve 的
  输入是 SourceIdentity，不是任意 URL；下载 URL 只来自
  Unpaywall/OpenAlex/arXiv 官方 API 响应，且受 SSRF 逐跳护栏约束）；
- 不做网页正文抓取 / Readability / browser automation——Web Result 保持
  URL + snippet + provenance，是否进 Web Evidence Pipeline 属后续单独设计；
- 手动 PDF 上传是唯一的人工全文路径（声明「这个文件属于这篇文献」，
  不做内容真伪判断）。

## 4. Resolve Flow（单篇 / 批量端点）

**单篇**（M7.2 已有，本阶段前端接线）：
`POST /api/projects/:id/sources/:sid/resolve-fulltext` →
`tryResolveFullText` → 200 `{source, outcome, note?}`；不可解析身份 →
422 `FULLTEXT_NOT_RESOLVABLE`（重试无意义的确定性失败）。

**批量**（M9.3 新增）：
`POST /api/projects/:id/sources/resolve-fulltext`，body `{sourceIds: string[]}`
（非空数组，逐条形如 S001，单次 ≤50 条；服务层去重保序 + 前置存在性校验，
不存在的条目整体 400 INVALID_REQUEST，不做半批静默）→
`SourceImportService.resolveFullTextBatch`：
- **有界并发**：`mapWithConcurrency`（`util/concurrency.ts`，与 Review 调度 /
  PaperMap 摘要共用的项目唯一并发原语），limit =
  `PAPERTEAM_FULLTEXT_BATCH_CONCURRENCY`（默认 3，1–8，
  `readIntWithFallback` 无效回退不拒启）——每条是「resolver 链 + 下载」的
  真实外呼，与 reviewConcurrency 同档的礼貌约束；
- **partial success**：单条结局是数据不是异常；成功项保留，失败项不回滚
  任何人（worker 的 catch 只兜「执行中条目被删」等极端竞态，按 failed 单条
  落账）；
- 响应：`{summary: {total, resolved, notFound, failed, notResolvable,
  skipped}, results: [{sourceId, outcome, source?, note?}]}`（results 按输入
  顺序，summary 各桶之和 === total）；
- 同步返回（与 `/research/plan/execute` 等长操作同 HTTP 模型；不为全文单独
  引入 Job Queue / SSE）。

**幂等**：已有全文的条目 `skipped_has_file`（attachFile 幂等守卫），不重复
下载、不覆盖有效文件；无 force refresh（上游变化后由用户对单条重试，
attempts 递增留审计）。

## 5. Batch Flow 的存储正确性（并发写串行化）

批量并发暴露的预存隐患：SourceStore 的 addRecord / update /
applyMetadataMerge / setAnalysis / attachFile / setFullTextProvenance /
remove 全部是「list → 修改 → saveIndex」读-改-写，无串行化时并发调用互相
用旧快照覆盖（实测：批量 mixed 场景 ok 项的 attachFile 被 S2 的 provenance
写覆盖 → fileName 丢失）。

修复：SourceStore 引入**项目级写队列**（`enqueue` promise 链，与
CandidateStore M6.2 同款同纪律；前序失败不阻塞后继，操作自身错误原样返回
调用方），全部读-改-写原语在队列内执行。回归锚：fullTextBatch.test.ts
「SourceStore 并发写不丢更新」五路并发混合原语，全部落盘共存。

## 6. Manual PDF Fallback（手动上传补挂）

`POST /api/projects/:id/sources/:sid/fulltext`，body
`{fileName, contentBase64}`（与既有上传端点同 base64-in-JSON 模型，
`MAX_SOURCE_UPLOAD_BODY_BYTES` 上限）→
`SourceImportService.attachManualFullText`：
1. 条目已有文件 → `{outcome: "skipped_has_file"}`（幂等，不覆盖）；
2. **`%PDF-` 魔数校验**（与 downloadPdf 同纪律——扩展名合法但内容不是
   PDF 的文件在此拦下，拒绝时不落任何文件）；
3. `SourceStore.attachFile`（复用全部既有纪律：PDF-only 文件名白名单 /
   ≤20MB / 非空 / 安全文件名拒绝路径穿越）；
4. `BuiltinPdfAnalyzer` → `setAnalysis`（失败不回滚挂载，如实 pending）；
5. provenance：`{status: "resolved", resolver: "manual-upload", bytes,
   resolvedAt, attempts: 沿用}` —— resolver 字段的保留值，全文来源可审计
   （覆盖此前的 failed/not_found 记录；attempts 保留 resolver 尝试轨迹不
   伪造）；
6. `onFullTextAttached` → 检索重建（FullTextSupport 未装配时同样可用——
   分析走 BuiltinPdfAnalyzer，检索由 lazy 自愈兜底）。

**边界（§11 详述）**：上传只声明文件归属，不创建 Evidence、不标 Verified、
不判断 Citation 正确性。

## 7. FullText States（UI 呈现口径）

前端以「后端 fullText provenance + fileName」为唯一事实源推导（不虚构状态）：

| UI 状态 | 推导条件 | 语义 |
| --- | --- | --- |
| 全文已获取 | `fileName` 存在 或 `fullText.status=resolved` | 文件已挂载（chip title 带 provenance：来源 resolver / URL / license / 尝试次数） |
| 全文未获取 | 无 fullText 记录 且 有学术身份（DOI/arXiv/OpenAlex） | metadata-only 未尝试，可获取 |
| 无开放全文 | `fullText.status=not_found` 且 有学术身份 | resolver 链明确无 OA（重试无意义，除非上游变化） |
| 获取失败 | `fullText.status=failed` | 系统性失败（网络 / 下载护栏 / 非 PDF），可重试 |
| 不可自动获取 | 无学术身份（如 Web 候选 url-only） | resolver 链空——提示手动上传 PDF |

「有学术身份」的判定读 backend 全量序列化的 `identity`（前端 DTO 只取
doi/arxivId/openalexId 最小子集）+ metadata 兜底。解析状态（仅元数据 /
待解析 / 已就绪 / 部分解析 / 解析失败）继续由既有 `status` chip 呈现，
与全文状态列正交。

## 8. Parse / Chunk Integration（及一个预存缺陷修复）

**激活链验证**：全文 resolved / 手动挂载后——
- 分析：attach 路径内联触发（同上传端点语义），contentHash 防失效；
- chunk：生产装配 `onFullTextAttached → retrieval.rebuildSource`（eager）；
  且 retrieval lazy 自愈（librarySignature 变化 → loadProject 重建）——
  eager 失败（如扫描件 SourceNotIndexable）如实记录，下次检索自愈；
- 未改成强 eager：lazy 路径（首次检索时建立）同样成立（域测试覆盖）。

**预存缺陷修复（M6.2 → M9.3 暴露）**：`BuiltinPdfAnalyzer` 的 TJ 数组正则
`/\[((?:\\.|[^\]])*)\]\s*TJ/g` 中 `(?:\\.|[^\]]*)` 两分支都能匹配反斜杠 →
歧义交替引发灾难性回溯。真实论文 PDF（attention.pdf 流 #21）实测**单流
33s 同步阻塞事件循环**——上传该 PDF 或对其全文 attach 时后端整体挂起。
修复：字符类排除反斜杠（`[^\]\\]`，`\` 只由 `\\.` 分支消费），线性化后
同流 **2ms**。回归锚：SourceStore.test「高反斜杠密度的大内容流不触发
灾难性回溯」。此为既有 Parser 系缺陷修复（任务纪律允许的「明确阻塞 +
先报告」情形），非新增 Parser。

## 9. Security（全部复用既有护栏）

自动路径（M7.2 全量保留）：SSRF 逐跳护栏（仅 https / 无 userinfo /
443 / 拒 localhost·私网·保留 IP 字面量）+ 重定向 ≤5 跳每跳重校验 +
content-length 预检与流式截断（≤20MB）+ `%PDF-` 魔数（landing page /
付费墙 HTML 确定性拦截）+ resolver 超时 10s / 下载超时 60s。

手动路径（M9.3 新增面，全部落在既有原语上）：
- 大小上限：attachFile ≤ `MAX_SOURCE_BYTES`（20MB）+ HTTP 层
  `MAX_SOURCE_UPLOAD_BODY_BYTES`（base64 膨胀后上限）双帽；
- 类型：只接受 `.pdf`（sanitizeFileName 白名单）+ 内容 `%PDF-` 魔数双重
  校验；
- 路径穿越：不信任用户文件名（sanitizeFileName 拒绝路径分隔符 / 特殊
  字符；实际存储名 `<sourceId>-<安全名>`）；
- project scope / ownership：projectId 存在性 + sourceId 项目内解析
  （跨项目条目 404）；批量端点前置存在性校验。

## 10. Provenance

成功获取全文后可回答「这个全文来自哪里」（不新增 provenance graph）：
- 自动：`fullText.{resolver, url（最终下载地址）, license, bytes, resolvedAt,
  attempts}`（M7.2 字段，license 原样透传不解释）；
- 手动：`fullText.{resolver: "manual-upload", bytes, resolvedAt}` +
  条目的 fileName/originalName；
- 失败审计：`fullText.{status, note（≤500 字符）, attempts, attemptedAt}`。

## 11. Evidence Boundary（红线）

全文操作（单篇 / 批量 / 手动上传）**不** create Evidence / verify Evidence /
mark Evidence grounded。完成 M9.3 后的合法状态：Literature + FullText +
Chunks，**Verified Evidence = 0**。测试（域级 + HTTP 级）与 live smoke 均
断言 evidence 列表为空。Retrieved ≠ Candidate ≠ Literature ≠ Verified
Evidence 四层不变量全程保持；chunk → Evidence Proposal → Verification 属
M9.4。

## 14. Known Limitations

1. **arXiv 大文件下载超时**：本机到 arxiv.org 带宽 ~11–16KB/s，2MB 级论文
   （如 1706.03762）超过下载层 60s 硬超时（M7.2 产品常量，本阶段不为
   smoke 放宽）→ 表现为 failed（可手动重试 / 手动上传）。live smoke 选用
   ~110KB 小论文在时限内完成全链。
2. **Unpaywall email 未配置则不注册**（PAPERTEAM_OPENALEX_MAILTO /
   CITATION_CONTACT_EMAIL 缺省时 OpenAlex/arXiv 路径可用，DOI→Unpaywall
   唯一入口的文献不可达）——optional 降级纪律，非缺陷。
3. **并发上传同内容判重竞态**（预存，未变差）：SourceStore.add 的
   contentHash 判重在写队列外预读，极端并发下可能双建；M9.3 未触碰该路径。
4. **手动上传不校验内容与元数据一致性**：用户挂错文件系统不设防（声明式
   归属，符合 §11 边界；真伪判断属 Evidence 核验层）。
5. **批量同步返回**：几十条慢网络下 HTTP 请求可能数分钟（有界并发 3 ×
   每条 ≤5 resolver 调用 + 下载）；与 plan/execute 同模型，前端呈 pending
   态。进度流（X/N 实时）需要 SSE/Jobs，本阶段明确不做。
6. **not_found 持久化折叠**：not_resolvable 以 not_found + note 存储，
   UI 靠身份推导区分（openalexId-only 且无 DOI/arXiv 的极端条目在 identity
   序列化齐全时不误判；仅 metadata 缺身份字段的老条目可能显示「全文未
   获取」而非「不可自动获取」——点击获取后收到 422 如实纠正）。

## 15. M9.4 Transition（下一阶段建议）

M9.3 交付后，文献库已具备「有全文 → 有 chunk」的真实底座。**M9.4
Anchored Evidence Activation**（Roadmap Step 4）：Researcher 在文献库有全文
时优先 retrieve_library → get_chunk → propose_evidence 锚定路径（工具面
与三段核验管道零新增，prompt / 流程接线 + 真实验证 evidence.ground 非
no-op）。M9.3 的验收产物直接是 M9.4 的输入：fullText 状态列让「哪些文献
