## 1. Existing Evidence Architecture Audit（静态审计结论）

以 main `f6c7432` 源码为准（不引用旧报告）。审计范围：`backend/src/evidence/`
（EvidenceStore / candidates / EvidenceGroundingService / chunkAccess /
quoteVerification / evidenceJudge / EvidenceSelectionService / tools）、
ResearcherService / WriterService / ReviewerService、workflow definitions、
researchCoverage、frontend EvidencePanel、HTTP API、全部既有测试。

- **候选域模型**（`evidence/candidates.ts`）：`EvidenceCandidate
  { candidateId(EC001+), projectId, sourceId, chunkId, claim, quote, summary?,
  status: pending|verified|rejected|mismatch|unverifiable, proposedBy,
  statusReason?, metadataOutcome?, judgeVerdict?, judgeReason?, evidenceId?,
  createdAt }`，存储 `evidence/candidates.jsonl`，状态转换唯一入口
  `markResolved`（终态不可再变；unverifiable 可 retry；verified 必带 evidenceId）。
- **提案契约**：`sourceId + chunkId + claim(≤4000) + quote(≤2000，归一化后
  ≥6 字符) + summary? + proposedBy`；chunkId 必须匹配
  `<sourceId>:<sectionId>:<序号>:<hash10>` 且前缀 == sourceId，且 chunk 必须
  经 ChunkAccess 真实可回取——**无效锚点在提案期拒绝**（INVALID_CHUNK_ID /
  CHUNK_NOT_FOUND / SOURCE_NOT_FOUND）。
- **propose_evidence 调用方**：仅 researcher 角色（`evidenceToolsForRole` 权限
  矩阵）与 ResearcherService JSON 锚定路径，两者收敛到
  `EvidenceGroundingService.propose` 单一入口；完全同文（chunkId+claim+quote）
  的 pending 候选去重复用。
- **retrieve_library 返回**：packed 检索上下文 + 每段 `[SRC:x CHUNK:y
  SECTION:z PAGE:n]` 引用标记 + score/channels；明示 "not verified evidence"。
- **get_chunk 返回**：chunkId/sourceId/sectionId/section/page/ordinal/全文
  text/charCount/tokenCount/contentHash + 来源元数据；chunkId 内嵌内容 hash，
  内容变化即旧 id 失效（天然自校验）。
- **三段核验顺序**（`EvidenceGroundingService.ground`）：
  Stage 1 quote 逐字校验（确定性：NFKC + 去零宽/软连字符 U+00AD/U+200B-D/
  U+FEFF + 空白折叠 + 小写子串；失败 → mismatch 终态，**LLM 禁止参与**）→
  Stage 2 metadata 核验（ScholarlyResolver 确定性外呼；mismatch → mismatch，
  not_found/unresolved 如实记录不阻塞，D-0023）→ Stage 3 语义 judge（唯一
  LLM 阶段，复用 citation 角色 scope `citation/evidence/<candidateId>`；
  unsupported → rejected；insufficient_evidence → unverifiable 不伪造裁决；
  judge 声称的 keyQuote 伪造即剥离）。
- **转正写路径红线**：grounded EvidenceStore 写入只发生在
  EvidenceGroundingService（appendBatch）；工具层只持有只读投影
  （EvidenceReadAccess，类型层面无写方法）；任何角色都没有 write_evidence
  工具；候选状态只经 markResolved。verified 记录字段：
  `verificationStatus=verified, verificationLevel=fulltext,
  supportStrength=direct|partial, verificationMethod=evidence-grounding/v1
  quote=exact metadata=<outcome> judge=<verdict>, location.chunk=chunkId`。
- **Writer 消费面**：所有写作路径（outline.plan / writing.sections /
  revision.revise）经 `EvidenceSelectionService.selectForWriting` 只取 formal
  （verified + sourceId + chunk 锚点三件套）；writer 的 evidence_query 是
  构造边界强制的 formalOnly 视图（运行期参数不可放宽）。legacy unverified
  自 M6.6 起排除（分类 `legacy_unverified`）。
- **HTTP 面**：`GET /evidence`、`POST /evidence`（人工登记，createdBy=user）、
  `GET /evidence/candidates`、`POST /evidence/ground`（单条/批量核验触发）、
  `GET/POST /evidence/:id(/verify)`（人工确认 user_confirmed——既有 HITL
  通道，M9.4 不动不扩）。人工确认与机器 grounding 是两条独立语义，UI 分开标注。

## 2. Why Evidence Previously Stayed Legacy / Unverified

M8 真实验收中 `evidence.ground` pending=0 的根因链（源码 + 产物核实）：

1. **物理不可能**（主因）：M8 时代文献库几乎全部 metadata_only——没有
   FullText 就没有 chunk，retrieve_library 返回空，锚定无从谈起。M9.3 交付
   FullText 激活后此层已解除。
2. **无信号**：`buildSourceDigest` 只注入摘要预览，模型不知道哪些文献有
   全文可检索、retrieve_library 值得调用——真实模型默认走「摘要 + 检索
   元数据」捷径。
3. **指引散**：prompt 规则 4 提及 retrieve_library/get_chunk，但锚定工作流
   没有被组织成明确路径，也没有失败纪律（找不到支撑时的行为未定义）。
4. **非接线问题**：`research.idea → evidence.ground → research.feasibility`
   的 stage 顺序、candidates store 共享、groundPending 处理逻辑在 M6.5 起
   即正确——输入侧零锚定提案才是 no-op 的原因（有既有
   evidenceGroundStage E2E 佐证：预置锚定候选时 stage 正常转正）。

## 3. Anchored Evidence Path（本阶段激活实现）

目标链（全部既有组件，零新增）：

```
Research Question
  → retrieve_library（chunk 检索，CHUNK 标记）
  → get_chunk（逐字原文回取）
  → propose_evidence（claim + 逐字 quote + chunkId → pending 候选）
  → evidence.ground（quote 逐字 → metadata → 语义 judge）
  → Verified Evidence（formal，Writer 可消费）
```

实现改动（最小集，全部在既有文件）：

1. **`ResearcherService.buildSourceDigest`（M9.4 核心激活）**：每条文献标注
   全文可检索性——`全文：已入库（可检索锚定）`（status available/partial，
   即 chunk 已入库）或 `全文：未入库（仅元数据）`；digest 头部汇总
   「N 项已入库全文可检索锚定」；存在可检索全文时附锚定路径提示行。
   模型第一次能在 prompt 里看到「锚定值得做、对哪些文献可做」。
2. **`buildResearchPrompt` 要求 4 重写**（锚定证据路径）：条件化优先（文献
   库有可检索全文时，关键论断优先走 retrieve_library → get_chunk →
   propose_evidence / evidence JSON 锚定字段）；quote 纪律（逐字复制、不要
   改写、不要凭记忆生成）；去重纪律（propose_evidence 已提交的不在
   evidence 字段重复）；**无机械数量指标**（「是否提出证据由你的研究判断
   决定，不设数量指标」——不做「每问 N 条」的假工作量）；**失败纪律**
   （检索后仍无支撑 → 如实记为证据不足写入 researchGaps / literaturePlan，
   绝不编造 quote 或锚定不相关段落）；legacy 兜底不变（无法锚定的保持
   原格式未核验线索）。
3. **并发写竞态修复（真实 smoke 暴露的产品 bug）**：
   `EvidenceCandidateStore` 与 `EvidenceStore` 引入**项目级写队列**
   （promise 链串行化，与 M9.3 SourceStore 修复同纪律）。修复前：真实模型
   在同一回合并行调用 propose_evidence 时，append 的
   loadAll → maxExisting+1 → 追加写竞态写出多条同号候选（实测 Scenario A
   出现 EC001×6：6 行不同 claim 同 id），markResolved 只改首行、其余行
   **永久卡 pending**（幽灵行）。修复后并发提案 id 唯一、零幽灵行
   （回归测试 `anchoredPathActivation.test.ts`「并发提案回归」覆盖 8 路
   并行 propose + 4 路并行 evidence.append）。EvidenceStore 的
   append/appendBatch/updateVerification/markUsage 同步加队列（同构风险，
   researcher JSON 追加 / grounding 批量转正 / workflow markUsage 并发面）。
4. **Coverage 质量收紧**（§12 详述）。

## 4. Researcher Tool Behavior

真实运行观测（live smoke，GLM-5.3 via zai-coding-cn，见 §14）：Researcher
在同一会话内自然组织出 `search_papers → save_candidates → retrieve_library →
get_chunk → propose_evidence` 的工具序列（Scenario A 22 次调用 / Scenario B
20 次调用），工具面与 roleCustomTools 接线（index.ts / scripts 同源装配）
零改动——激活靠 digest 信号 + prompt 路径指引，不靠新增工具或 Planner。

## 5. Evidence Proposal Contract

以源码为准（§1 已列）。关键不变量：**Chunk retrieved ≠ Evidence Verified**——
propose 只产生 pending 候选；quote 必须真实来自对应 chunk（LLM 自造 quote
在 Stage 1 确定性拦截）；sourceId/chunkId/quote/claim 缺一或失配在提案期
结构化拒绝（不炸 Agent 会话）。幂等：同 chunkId+claim+quote 的 pending
候选去重复用；转正后重复 ground 幂等返回（不 append 第二条）。

## 6. Quote Verification（确定性，未改动）

`quoteVerification.ts` 原样保留：NFKC → 去零宽/软连字符 → 空白折叠 → 小写
的归一化子串匹配（MIN_NORMALIZED_QUOTE_LENGTH=6）。验收口径：正确 quote →
pass；归一化可容（大小写 / 跨行空白 / 软连字符，既有测试）；伪造 quote →
mismatch（本阶段新增「伪造 quote 在核验期被拒」端到端用例 + Browser
Acceptance EC002 对照候选实测 mismatch）。**未引入任何 LLM 判 quote**。

## 7. Metadata Verification（确定性外呼，未改动）

ScholarlyResolver（与 sourceImport / citationIntegrity 共享实例：缓存/限速/
telemetry 一体）。live smoke 实测：PLOS DOI 命中 `metadata=match`
（canonical 字段进转正记录）；离线部署（无 provider）→ unresolved 如实
记录不阻塞（D-0023，既有测试覆盖）。metadata mismatch → 终态 mismatch
（既有测试：同 DOI 不同标题）。

## 8. Semantic Verification（唯一 LLM 阶段，未改动）

`evidenceJudge.ts` prompt 只含 claim + quote + chunk 原文（+ 来源展示行仅
语境）；verdict ∈ supported / partially_supported / unsupported /
insufficient_evidence；keyQuote 伪造剥离。live smoke 实测三种裁决都出现
（supported → direct、partially_supported → partial）；Browser Acceptance
的 scripted judge 返回 supported。输入契约经审计确认无需调整。

## 9. Grounding State Machine（未改动，红线保持）

- 候选 → 正式证据的唯一转换入口：EvidenceGroundingService.ground /
  groundPending；`verified` 只能由 grounding 在转正时写入 markResolved。
- Researcher / Tool / Workflow / Agent 无任何 Verified 直写路径
  （evidenceTools「全部角色工具轮询后 evidence.jsonl 零写入」既有测试 +
  本阶段 §15 测试 11 再确认）。
- HTTP 不新增 bypass；既有 `POST /evidence/:id/verify` 是人工 user_confirmed
  语义（UI 按钮触发，与机器 grounding 通道分离），保持不动。
- 幂等：append 与 markResolved 之间中断 → 重跑先查同文 verified 记录复用
  （findGroundedRecord，既有测试）。

## 10. Writer Consumption（验证既有行为 + 补测试）

Writer formalOnly 语义不变：`selectForWriting` formal 池 = verified + 三件套
锚点；`evidence_query` writer 视图构造边界强制。本阶段补真实断言
（anchoredPathActivation §「ResearcherService JSON 锚定路径」）：同一项目
中 legacy unverified 与 grounded verified 并存时，writer 视图只见 grounded
（1 条），legacy 排除计数 =1；`selectForWriting` 同口径。老项目（纯 legacy）
formal 为空、ground no-op、记录可读（§17 兼容测试）。

## 11. Academic / Web Evidence Boundary

M9.4 锚定路径**只对学术文献 FullText 生效**（结构保证，非策略约定）：

- 锚定输入是 chunkId（`<sourceId>:<sectionId>:<序号>:<hash10>`）；chunk 只
  存在于「文献库条目 + 全文解析 + chunk 落盘」之后——url-only Web 候选
  天然无 chunk。
- 任意 URL 当锚点 → INVALID_CHUNK_ID（提案期结构拒绝）；web 来源伪造
  chunkId → CHUNK_NOT_FOUND（chunk 不存在）；两者都零候选入队
  （新增测试覆盖）。
- 工具面不存在「按 URL 抓正文 → evidence」的任何入口；SearXNG URL 永远
  不进 FullTextResolver（M9.3 §3 边界延续）。Web Evidence 是后续独立设计。

## 12. Coverage Decision（researchCoverage 收紧）

**源码事实**：M9.4 前 `assessQuestionCoverage` 的 covered 判定 = 有带回
结果的检索 &&（关联 Evidence **任意状态** || promoted literature）——即
**legacy unverified 证据单独可把问题推成 covered**。

**决策**：最小质量收紧——`evidenceTexts` 只含 `verificationStatus ===
"verified"` 记录（grounding 管道 / user_confirmed 产物）；其余
（unverified / plausible / mismatch / unverifiable / not_found）归入
`unverifiedEvidenceTexts`：关联命中时问题最多 **partial**（gap 文案明示
「尚无已核验（verified）证据或已入库文献支撑」）。promoted literature 仍
构成 covered（不变）。

**为什么不是 verified-only 一刀切**：covered 的另一支撑（promoted
literature）是「已入库候选」层级，Evidence 不变量分层计数本就允许它独立
支撑 covered（M8.3.2 设计）；收紧只针对「unverified 证据冒充 strong
coverage」这一处违反 Retrieved ≠ Verified 的判定，未动问题-检索关联规则、
gap 派生与 loop 判定骨架（`no_new_coverage` 等语义不变）。受影响测试三处
（researchCoverage / httpResearchCoverage / researchGap 的 covered 种子）
改为显式 `verificationStatus: "verified"`——与「用户看到 covered 即代表
有已核验支撑」的产品语义一致。

## 18. Known Limitations

1. **并发提案去重粒度**：写队列只保证 id 唯一与不丢更新；同文去重仍按
   chunkId+claim+quote 精确匹配——语义近似（同一论断不同措辞）的重复提案
   会各自入队（由语义 judge / Writer formal 限量兜底，不做 similarity
   clustering，M9.4 红线）。
2. **propose 无 HTTP 端点**（延续 M6.5 设计）：候选提案只来自 Agent 工具 /
   research JSON 路径；人工补录锚定候选需走 Agent 流程或直接操作数据
   （Browser Acceptance 的 fixture 预置即属测试准备，不构成产品入口）。
3. **scripted 栈无法走 UI 启动按钮**：scripted runtime 恒报 model.unknown
   （E2E 门控用例据此自动跳过），UI 生成按钮被产品门禁禁用——浏览器级
   UI 验收用真实模型栈完成；这是测试基建与产品门禁的固有交互，非缺陷。
4. **txt 手动上传在手动 analyze 前不进 researcher digest**：非 PDF 上传
   状态停在 pending（M6.2 设计），buildSourceDigest 的 usable 过滤排除
   pending——用户需经 SourcesPanel 的解析动作（或上传 PDF 走自动解析）。
   Browser Acceptance R2 轮实测确认；产品内已有手动 analyze 端点，M9.4
   不改此行为。
5. **live smoke 的 judge 与 researcher 同模型族**（same-model judge bias，
   M6.9 已知限制延续）；两场景论文主题单一（医学），跨领域泛化未测。
6. **Coverage 收紧只到 verified/promoted 二分**：`verified_missing_anchor`
   （verified 但缺锚点，如 user_confirmed 无 chunk）计入 verified 支撑
   covered——按「已核验」语义归队，未再细分（现有 classify 已有该层，
   coverage 未消费，属后续按需）。
7. **Researcher 行为非确定**：锚定提案数量随模型 / 文献 / 问题波动
   （本轮 8-9 条/场景、核验通过 7-9）；失败纪律（researchGaps 如实记录）
   已入 prompt，但无机械下限保证——这是刻意设计（任务红线：不设数量指标）。
8. **evidence-gate.spec 两处过期断言已修正**（§17）：该套件在 pristine
   HEAD 上即红（M6.6/M6.7 演进后未同步），提示「带环境门的 E2E 套件」
   需要在里程碑收口时纳入常规回归清单。
