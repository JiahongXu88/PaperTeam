# M8.2 — Research Plan Execution 实施报告

- 日期：2026-09-20
- 状态：已完成（实现 + 测试 + 文档；backend / frontend 全量测试、build、typecheck 通过）
- 范围：将 M8.1 的静态 ResearchPlan 升级为**可执行研究计划**——批准（draft →
  approved）后遍历 planned 检索逐一执行、回填状态与结果数、留存最小执行历史。
  **不新增 Agent、不改 Runtime、不改 Workflow Orchestrator、不引入 RAG/Vector
  DB/MCP/新 Provider/CLI**（M8 架构冻结规则全部遵守，基于 M8.1 冻结架构增量实现）。

## 1. 目标

M8.1 让检索有了「计划」（研究问题 + 检索词及理由），但计划只是静态意图。M8.2
补上执行层（Plan Execution Layer）：

1. **执行服务**：把 approved 计划中 status=planned 的检索逐一执行——复用
   ResearchDiscoveryService（academic / web 按 kind 分派），不复制任何 provider
   逻辑；
2. **执行历史**：最小执行记录挂在 research artifact 顶层的可选
   `executionHistory` 字段（不设计数据库），旧 research.json 完全兼容；
3. **状态机**：draft → approved → executing → done，批准是显式动作（绝不自动
   draft → approved），executing 禁止重复执行；
4. **API**：`POST /research/plan/execute`（+ 批准流 `POST /research/plan/approve`）；
5. **链路不变量**：执行只产生 Search Result 计数，不自动 promote、不写
   Literature、不产生 Evidence——保存候选 → promote → Evidence 仍由用户显式
   驱动（M7 设计原样）；
6. **UI**：DiscoveryPanel 的 Research Plan 区域增加状态展示与 Approve / Execute
   按钮，执行后展示每条 Query 的 Status 与 Results。

## 2. 架构设计

### 2.1 冻结规则的落实

| 冻结规则 | 落实方式 |
| --- | --- |
| 不新增 Agent（无 Planner / Research Execution Agent） | `ResearchPlanExecutionService` 是普通业务 Service：不调用 `Runtime.runAgent`，无 prompt、无 Agent 会话 |
| 不修改 Runtime | 零 Runtime 改动（AgentRuntime / PiRuntimeAdapter / tool injection 全部未触碰） |
| 不修改 Workflow Orchestrator | 不进 `workflowServices`、不加 stage：执行是用户经 HTTP 显式触发的同步动作，与 Workflow 生命周期正交 |
| 不引入 RAG / Vector DB / MCP / 新 Provider / CLI | 检索 100% 复用 `ResearchDiscoveryService`（OpenAlex / S2 / arXiv / AMiner / SearXNG 的 fan-out、融合、诊断一体复用；provider 装配零变化） |
| Search Result ≠ Candidate ≠ Literature ≠ Verified Evidence | 执行只回填计数：不写 CandidateStore / SourceStore / EvidenceStore；调 `academicSearch/webSearch` 时不传 projectId → 不写检索缓存（对 Discovery 侧零副作用）；保存候选仍是用户在检索结果中显式勾选的动作 |

实施前的架构检查结论：本任务全部为既有模块内的小步增量（新 Service 文件 +
serviceStack 装配行 + research 资源块路由 + artifact 可选字段），未出现需要
修改 Runtime / Workflow 核心 / 破坏 Evidence 链路的情形，无需停止报告。

### 2.2 模块拓扑

```
backend/src/agents/researchPlanExecution.ts     ← 新增（唯一新文件：执行记录类型 + 批准/执行服务）
backend/src/agents/ResearcherService.ts          ← 修改（ResearchArtifact 增可选 executionHistory 字段）
backend/src/errors.ts                            ← 修改（新错误码 PLAN_INVALID_STATE → 409）
backend/src/serviceStack.ts                      ← 修改（装配 planExecution，依赖 projects + discovery）

```

关键决策：

- **复用而非复制**：执行侧只有一处分派（`kind === "academic" ?
  discovery.academicSearch : discovery.webSearch`），provider / 融合 / 健康观测
  全部经既有编排层；后续 provider 演进对计划执行自动生效。
- **执行记录挂 artifact，不建存储**：`executionHistory` 是 research.json 顶层
  可选字段（与 M8.1 的 `plan?` 同风格）；条数硬帽 200（超限丢最旧）。
  已知限制：`research()` 重跑会整体重写 research.json，plan 编辑与执行历史
  一并被覆盖（M8.1 §7.3 已登记的多轮计划问题的子集，M8.3 收口）。
- **重复执行守卫双保险**：进程内 `Set<projectId>` 在 execute 入口同步
  check-and-add（事件循环上原子，并发请求第二个必 409）+ 磁盘 status=executing
  可见性。崩溃残留 executing 时按字面规则仍拒绝重复执行（409 信息附手工恢复
  指引：把 research.json 的 plan.status 改回 approved）。
- **失败语义**：单条检索失败（provider 未配置 / 全源失败等）→ 记 failed 条目
  （error 入 history）、该 query 保持 planned（修复后可重试）、继续执行其余；
  整轮结束 plan 照常流转 done，failedQueries 如实返回，不伪造成功。
- **零 planned query**：全部 executed / skipped 时执行直接流转 done、计数为 0
  （幂等重放安全）。

## 3. 执行流程

```
用户在 Discovery 点击「批准计划」          （draft → approved，显式 HITL）
        │
        ▼
POST /research/plan/execute   ── 404：无 artifact / 无 plan
        │                       409：非 approved（draft/executing/done）或并发重复
        ▼
plan.status → executing（落盘，可见性） + executionId = exec-<12hex>
        │
        ▼  逐条（顺序）遍历 queries 中 status=planned 的条目
academic ─→ ResearchDiscoveryService.academicSearch(query)   ┐
web      ─→ ResearchDiscoveryService.webSearch(query)        ┘ 既有 provider 链
        │
   成功：query.status=executed + resultCount=results.length；history 记 executed 条目
   失败：query 保持 planned；history 记 failed 条目（error 摘要）
        │
        ▼
plan.status → done；executionHistory 追加本轮条目（写回 research.json）
        │
        ▼
响应 { executionId, totalQueries, executedQueries, failedQueries, plan }
        │
        ▼
Search Result 只是返回值与计数 —— 用户仍在 Discovery 检索/候选区显式：
save candidate → promote literature → Evidence（M7 链路，不变）
```

## 4. 状态机

```
draft ──approve（显式）──▶ approved ──execute──▶ executing ──轮次完成──▶ done
  │                          │                      │
  └─ 只能编辑（执行→409）      └─ 允许执行             └─ 禁止重复执行（409）
```

| 状态 | 编辑（PUT /plan） | 批准（approve） | 执行（execute） |
| --- | --- | --- | --- |
| draft | ✅ | ✅ → approved | ❌ 409（提示先批准） |
| approved | ✅（M8.1 语义保持） | ❌ 409 | ✅ → executing → done |
| executing | ✅（见下） | ❌ 409 | ❌ 409（并发守卫 + 磁盘状态） |
| done | ✅（补充新 planned 检索后需重走批准流——当前无 done→approved 通道，M8.3 受控循环收口） | ❌ 409 | ❌ 409 |

- 绝不自动 draft → approved：唯一迁移入口是显式 `POST /plan/approve`。
- 执行中（executing）的编辑：后端沿用 M8.1 受限编辑语义未加新限制；执行是单次
  同步请求且前端在 pending 期间禁用编辑入口，多标签页并发编辑的窄窗口竞态是
  已知限制（最后写入者胜），M8.3 如需可加 executing 期写锁。

## 5. API

### POST /api/projects/:id/research/plan/approve

- 200 `{ plan }`（status=approved，updatedAt 刷新）
- 非 draft → 409 `PLAN_INVALID_STATE`；无 research.json / 无 plan → 404
  `NOT_FOUND`；非 POST → 405

### POST /api/projects/:id/research/plan/execute

```json
{
  "executionId": "exec-1a2b3c4d5e6f",
  "totalQueries": 3,
  "executedQueries": 2,
  "failedQueries": 1,
  "plan": { "status": "done", "...": "..." }
}
```

- `totalQueries` = plan 内全部 query 数（含既有 executed / skipped）；
  `executedQueries` / `failedQueries` 只计本轮 planned 条目；
- 状态不允许 → 409 `PLAN_INVALID_STATE`（draft / executing / done / 并发重复，
  错误信息区分四种情形，executing 附崩溃残留恢复指引）；plan 不存在 → 404
  `NOT_FOUND`（无 artifact / 旧 artifact 无 plan）；非 POST → 405；
- 单条检索失败不产生 HTTP 错误（进入 failedQueries + history）；执行期 IO 等
  意外错误按通用 INTERNAL_ERROR 如实返回。

### executionHistory（research.json 顶层可选字段）

```json
{
  "executionId": "exec-1a2b3c4d5e6f",
  "queryId": "q-1",
  "query": "transformer multi-object tracking survey",
  "kind": "academic",
  "timestamp": "2026-09-20T12:00:00.000Z",
  "status": "executed",
  "resultCount": 2
}
```

失败条目：`status: "failed"` + `error`（摘要，≤500 字符）、无 resultCount。
timestamp 即该 query 的 executedAt。旧 artifact（M8.1 及更早）无此字段照常
读取；`GET /research/plan` 契约不变（plan 视图含回填后的 query status /
resultCount）。

## 7. 未来 M8.3 Controlled Research Loop 扩展建议

按依赖排序：

1. **计划-执行-残差闭环（P0）**：执行完成后把 Search Result 与
   `expectedCoverage` 对账（本轮覆盖了哪些计划面、planned 残留多少），把
   `literaturePlan` 残差并入展示，形成「单轮检索是否足够」的数据 gate——
   这是 Controlled Loop 的判停依据。
2. **多轮计划迭代（P0）**：解决 `research()` 重跑覆盖 research.json 丢失 plan
   编辑与 executionHistory 的已知限制：调研 rerun 时对既有 plan 做合并
   （用户编辑优先 / Agent 增量补充），并给 done 计划提供「派生下一轮」动作
   （done → 新 draft，继承 executed 状态与残差），替代当前的死端。
3. **执行结果与候选链路的受控衔接（P1）**：当前执行刻意不保存任何候选。
   M8.3 可引入受控的「执行后批量提案」：按相关性阈值把 Search Result 预填为
   pending 候选（仍走 save_candidates 单一写入口径），用户一键审核——
   不越过 Search Result ≠ Candidate 红线（显式、可见、可拒绝）。
4. **执行历史观测（P2）**：暴露 `GET /research/plan/executions`（分页 history +
   每轮汇总），支撑 Discovery Observability（provider 健康与计划执行成功率）。
5. **Agent 会话内受控执行（P2）**：把执行能力包装为 Researcher 的
   `execute_plan` 工具（进会话工具注入而非新 Agent），让调研阶段按计划驱动
   检索——需先解决 3 的候选衔接与 1 的判停，否则只是把人工循环自动化为
   无人监督循环。
