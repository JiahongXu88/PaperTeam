## 0. Executive Summary

1. **Web Search 能力的服务层已全部存在**（M6.3 / D-0035）：SearXNG + 4 学术
   Provider、共享 ProviderHttpClient、融合去重、ResearchDiscoveryService、
   `search_papers` / `search_web` / `lookup_paper` 三个 Agent 工具、HTTP API、
   compose 部署、1545 行测试——全部交付且与 ADR 对齐（§1）。
2. **真正的缺口不在「有没有 Search」，而在「接没接进主链路」**。四个断点：
   - **P-A Prompt 断点**：Researcher 任务 prompt 不引导 search 工具，仍写
     「基于你的领域知识」——工具已注册但主链路（research.idea stage）事实上
     不使用（§2.1）；
   - **P-B 持久化断点**：Agent 检索结果无法保存为候选（工具零持久化红线），
     保存只能由用户手动经 HTTP `saveAsCandidates`（§2.2 / §4.3）；
   - **P-C UI 断点**：前端无 discovery 搜索界面、无候选管理界面，e2e 无场景
     （§2.3）；
   - **P-D 全文断点**：FullTextResolver 是 D-0033 六层唯一未实现层——候选
     转正后 `metadata_only`，chunker 明确跳过（`full_text_unavailable`，
     绝不把 abstract 当全文），因此 discovery 结果**没有任何路径能成为
     verified evidence**（§5.3）。
3. **磁盘实况**：现有 4 个真实项目的 `sources/` 下无 candidates.json、无
   index.json、`evidence/` 为空——M6.2–M6.5 的 discovery→library→evidence
   写路径**从未在真实数据上跑过**（仅测试覆盖）。M7.1 验收必须含真实项目
   端到端（§7.4）。
4. **不需要新 Agent**（§6）：与 D-0009 / D-0041 冻结一致，检索编排是确定性
   服务层代码，Agent 侧只是工具消费者。
5. **Crossref 维持 MetadataResolver 定位、不做 discovery**（§3.4）——实现
   正确，但 ADR §3 架构图与 §2-4 存在文档张力，建议勘误（不改代码）。

## 2. 五接入点现状评审（要求 1）

### 2.1 Researcher Agent —— ⚠️ 工具已接线，prompt 未引导（断点 P-A）

**事实链**（全部经源码确认）：

- 工具注册：`index.ts:152-161` 把 `createScholarlyTools(resolver, discovery)`
  注入 **researcher 与 citation** 两角色的 Pi 会话（roleCustomTools 回调，
  按 projectId 闭包构造）。researcher 最终工具全集 =
  `read/grep/find/ls`（roleConfig 白名单）+ `search_papers/search_web/
  lookup_paper` + `retrieve_library` + `get_chunk/propose_evidence/evidence_query`。
- 角色 system prompt（`runtime/pi/roleConfig.ts:39-43`）只有 3 行最小框架，
  未提及任何检索工具（设计如此：任务指令由 prompt 内联）。
- **任务 prompt（`agents/ResearcherService.ts:362-405` buildResearchPrompt）**
  ：要求 1 写「调研基于项目文献库（下方提供）与**你的领域知识**；不要编造
  不存在的论文」；要求 3 只引导 `retrieve_library` / `get_chunk` /
  `propose_evidence`——**通篇无 `search_papers` / `search_web` / `lookup_paper`**。
- `literaturePlan` 字段语义为「应补充检索的文献方向」——检索被定位成
  **调研之后的离线人工动作**；且 grep 全仓确认该字段无任何下游消费者
  （前端 / workflow 均不读）。
- Workflow 层（`workflow/definitions.ts`）完全不接触 discovery：
  `research.idea`（:2000）→ `evidence.ground`（:2040）→ `research.feasibility`
  的 stage 序列中无 discovery 调用；ResearcherService 也不直接调 discovery
  ——Agent 侧唯一入口就是 customTools。

**判定**：工具在白名单内、模型理论可见可调，但任务 prompt 的结构化约束
（「只输出 JSON」「基于文献库与领域知识」）+ 零引导 = 主链路上外部检索
事实上不会被使用；即便模型自发调用，检索结果也只能进 research.json 的
文本字段（未核验线索），与「凭记忆调研」的产出形态无差别。这正是
M6 FINAL_SUMMARY §4 遗留项「Researcher legacy 路径迁移」的具体形态。

### 2.2 Tools —— ✅ 工具面完整且红线正确；⚠️ 无保存能力（断点 P-B 前半）

`scholarlyTools.ts` 三个工具的边界纪律全部正确（文件头 :9-14）：

- 输出明示「candidate sources（非 verified evidence；**不自动入库**）」；
- `search_web` 对 not_configured / 失败**如实返回结构化 payload 不抛错**
  （:138-147，optional 语义，不打断 Agent）；
- `search_papers` 在最小栈（无 discovery 装配）时回退 resolver 查证形检索
  （:82-97，兼容路径）；
- limit 钳制 1–50（:187-192），abstract/snippet 截 500 字符控上下文预算。

**缺口**：检索结果的持久化入口只有 HTTP `saveAsCandidates`（用户手动），
Agent 工具面无对应能力（§4.3 设计补全）。这是 D-0035「检索默认零持久化
（显式 saveAsCandidates）」决策的**有意为之**——但该决策落地时只做了
HTTP 一个显式入口，Agent 会话内的显式入口缺失，导致 research 阶段的
检索产出与候选库完全脱节。

### 2.3 SourceStore / Literature Library —— ✅ 入库路径齐备；❌ 前端零消费（断点 P-C）

- 五种入库路径齐备：PDF 上传（既有）+ DOI / arXiv ID / URL / BibTeX
  （`SourceImportService.importXxx`，经 ScholarlyResolver 补全元数据）+
  检索候选转正（`promoteCandidate`）；
- `promoteCandidate` 幂等且库级判重：同身份已入库 → `applyMetadataMerge`
  只补空缺，不复制条目；新条目 origin=AGENT_RETRIEVED、无全文 →
  `status=metadata_only`；
- 候选删除保护 / Evidence 引用阻止删除（`SourceInUseError`）等安全边界在位。

**缺口**：`frontend/src/` grep 无 academic-search / web-search / discovery
任何引用；`SourcesPanel.tsx`（492 行）只有 origin 徽章映射（:44
「检索入库」），无候选清单、无 accept/reject、无搜索表单；e2e/tests/
无 discovery 场景。**HTTP API 已就绪但全产品无消费者**——这是 UI 层唯一
但完整的断点。

### 2.4 CandidateSource —— ✅ 数据模型与状态机正确；⚠️ 写入率=0

- 字段（`CandidateStore.ts:26-52`）：`candidateId`（C001 递增）、
  `identity`（SourceIdentity 同构判等）、`origin`
  （academic_search / web_search / manual）、`provider`、展示元数据、
  `query`（provenance）、`status`、`promotedSourceId`、时间戳；
- 状态机：`pending_review → accepted（promote 幂等回写 promotedSourceId）/
  rejected（幂等）`；**rejected 不参与判重**——同一文献再次发现是合法
  场景，会新建 pending 候选（设计正确）；
- 判重：`identityKey` 分层确定性键（doi > arxiv > pmid > 标题指纹+年份+
  一作 > url），精确相等非相似度；同身份 pending 候选合并只补空缺
  （`fillEmpty`，信息只增不减）；
- 写入点全量枚举：HTTP `saveAsCandidates`（academic/web）+ HTTP 手动添加
  （origin=manual）。**无 workflow 写入、无 Agent 工具写入**。

### 2.5 Evidence Pipeline —— ✅ 不变量三重钉死；⚠️ 对 discovery 结果「断头」（断点 P-D）

不变量 `SearchResult ≠ CandidateSource ≠ SourceDocument ≠ SourceChunk ≠
RetrievedChunk ≠ EvidenceCandidate ≠ Verified` 在 discovery 链路完整成立：

- researchDiscoveryService 文件头红线：「EvidenceStore 在本链路中不存在
  ——snippet 最高支撑 plausible 属 M6.5」；核验后 EvidenceRecord 的
  `verificationLevel=fulltext` 只能由「quote 逐字匹配 chunk」授予；
- chunk 管线红线：`SourceChunker.ts:75-90` 对 metadata_only / bibtex /
  image 一律 `skipped: full_text_unavailable`，**绝不把 abstract/snippet
  当全文索引**——正确，但直接导致下述断头；
- 写入路径单点化维持：EvidenceStore grounded 写入唯一入口
  `EvidenceGroundingService.appendBatch`（:366-369），工具零写路径；
  Researcher 的 evidence 双路径（`ResearcherService.ts:166` chunk 锚定 →
  grounding.propose；:191 无锚定 → legacy evidence.append 未核验线索）。

**断头问题（架构级，M7.1 必须正视）**：discovery 候选 promote 后是
`metadata_only` → 无全文 → 无 chunk → `retrieve_library` 检索不到 →
`propose_evidence` 无法锚定 → 三段核验无从发生。**当前 discovery 的
最终产出上限就是「候选线索 + abstract 级元数据」，对 verified evidence
池贡献恒为零。** 桥接层正是 D-0033 六层中的 FullTextResolver（§5.3）。

### 2.6 断点汇总

| 编号 | 断点 | 层 | 影响 | M7.1 处置 |
|---|---|---|---|---|
| P-A | Researcher prompt 不引导 search 工具 | Agent 任务层 | 主链路不用外部检索，仍凭记忆调研 | §4.5 prompt 升级设计 |
| P-B | Agent 工具无候选保存能力（显式入口只有 HTTP） | 工具层 | research 阶段检索产出不进候选库 | §4.3 save_candidates 设计 |
| P-C | 前端无 discovery UI / 候选管理 UI；e2e 无场景 | 前端 | HTTP API 零消费者，用户无法走完闭环 | §7.2 M7.1b |
| P-D | FullTextResolver 未实现（六层唯一缺层） | 服务层 | discovery 结果永远到不了 verified evidence | §5.3 设计 + §7.3 排期 |

另记：真实项目磁盘零写入（§0-3）——不是独立断点，而是 P-A+P-B+P-C
叠加的必然结果。

## 3. 四源接入方式评估（要求 2，基于 M6.1 ADR）

### 3.1 SearXNG（Web 底座）—— ✅ 接入方式完全符合 ADR，维持

| 维度 | ADR 要求（D-0033） | 实现现状 | 判定 |
|---|---|---|---|
| 形态 | 独立服务，HTTP 调用（`GET /search?format=json`），唯一 WebSearchProvider；**不做 bundled subprocess、不复制代码**（AGPL 边界） | `SearXNGProvider` 经 ProviderHttpClient 调 `baseUrl/search?format=json`；compose `research` profile 引官方镜像，自维护仅 settings.yml | ✅ |
| Optional 语义 | 不可用时 Web Search 降级 unavailable，其余能力不受影响 | 未配 URL → 不注册 → `WebSearchService.search` 抛结构化 `SEARCH_PROVIDER_NOT_CONFIGURED`(503)；启动零阻塞；`search_web` 工具侧如实返回 not_configured 不抛错 | ✅ |
| 大陆可用性 | engine 白名单 cn.bing + baidu，无 Google 依赖 | settings.yml 模板白名单 cn.bing + baidu；`unresponsive_engines` 非空 → markDegraded（结果带 degraded 事实，不当「互联网没有」） | ✅ |
| 常见错配 | JSON API 默认未启用 | HTTP 403 → 结构化提示「settings.yml search.formats 加 json」（provider 内特判 :56-65） | ✅ |

**M7.1 增量建议**：无架构改动；仅随 M7.1b 前端在「未配置 SearXNG」时给出
配置引导（指向 DEPLOYMENT §8），及 M7.1a prompt 中告知 Agent
`search_web` 可能不可用、学术链路不受影响。

### 3.2 OpenAlex（学术 primary）—— ✅ 维持

免费无 key、works search 真关键词语义（无相似度门控——与 legacy
resolver.search 的本质区别）、publication_year / is_oa 服务端 filter、
mailto 礼貌池（回退 CITATION_CONTACT_EMAIL）、倒排索引重建摘要、
单源 ≤25 条帽。**发现与核验双角色**：discovery primary 之外，也是
ScholarlyResolver 核验链（crossref → openalex → s2 → arxiv）第二环。
M7.1 无改动。

### 3.3 Semantic Scholar（enrichment / fallback）—— ✅ 维持

匿名可调 + 可选 x-api-key；429/503 高发风险由 ProviderHttpClient 统一
冷却（限流≠宕机），不进 provider 自判；融合权重 0.9 次于 OpenAlex——
与 ADR「不做 default」一致。citationCount / openAccessPdf 字段进融合
（引用数取保守最大）。M7.1 无改动。

### 3.4 Crossref —— ✅ 维持 MetadataResolver 定位、不做 discovery（附 ADR 勘误建议）

**现状**：Crossref 无 search provider（`backend/src/search/` 无
crossrefProvider）；其存在于 `citation/scholarly.ts:99-155`
（ScholarlyResolver 核验链第一环，DOI 精确匹配 + bibliographic 查询）。

**裁定**：实现正确，理由链——

1. ADR §2-4 明文：「Crossref = MetadataResolver（引用核验链路，既有职责
   不变，**不做 discovery primary**）」；其检索排序弱、无摘要（分析报告
   §5.4），discovery 收益边际；
2. discovery 侧 OpenAlex 本身覆盖 DOI 注册库的绝大部分文献（OpenAlex 数据
   源含 Crossref），再加 Crossref search provider 的融合增益 << 维护成本；
3. Crossref 的不可替代价值（DOI 权威元数据核验）已经在 Stage 2 metadata
   核验（EvidenceGroundingService）与 promote 元数据补全
   （ScholarlyResolver.resolve）中发挥——**它是 discovery 结果的「裁判」，
   不必同时当「选手」**；选手与裁判分离还避免了同一来源既喂候选又核验
   候选的自证循环。

**文档张力（建议勘误，不改代码）**：ADR §3 架构图画了
`CrossrefSearchProvider（fallback 参与）`，与 §2-4 决策文字冲突。建议在
M7.1 文档冻结时于 DECISIONS.md 追加一行勘误说明（或 M7.1 决策登记时
一并声明）：**以 §2-4 为准，Crossref 不实现 discovery provider；§3 图中
该节点删除**。若未来大陆以外主源全灭确需第五学术源，优先评估
CrossrefSearchProvider 的注册制扩展点（接口已留），而非现在实现。

### 3.5 附：arXiv / AMiner（评估范围外但同链路）

arXiv（preprint，Atom XML 轻量正则解析、无 XML 框架依赖、年份客户端过滤）
与 AMiner（China secondary，**仅免费端点** `/api/paper/search`，付费端点
URL 集被测试钉死不含；HTTP-200 信封错误经 envelope 钩子穿透——40306 →
rate_limited 冷却、其余 business_error 不重试不熔断）均与 ADR §4 角色
约束一致。无 key / 未配置时各自不注册，如实 not_configured。维持。

套术语与代码漂移）。**

### 4.2 现有分层设计评审（维持项）

- **Web 与 Academic 不合并**（不同数据形状：URL/snippet vs DOI/venue）——
  D-0033 §9 已拒绝万能 SearchProvider，维持；
- **归一化投影是唯一出口**：provider raw payload 不泄漏进
  ResearchDiscoveryService / CandidateStore / 工具输出（types.ts 纪律注释）；
- **search ≠ lookup**：`search_papers`（发现，无门控）与 `lookup_paper`
  （核验，ScholarlyResolver 相似度门控语义不变）双接口分离，维持；
- **聚合纪律**：单 provider 失败 → partial（diagnostics 记录）；全失败 →
  `SEARCH_ALL_PROVIDERS_FAILED`（error ≠ not_found ≠ 空集，D-0023 延续）；
  有界并发 fan-out（不用无上限 Promise.all）；
- **检索默认零持久化**（D-0035）：显式 `saveAsCandidates` 下标选择——
  M7.1 延续该语义，只增加 Agent 侧显式入口（下同）。

### 4.3 增量设计一：`save_candidates` 工具（补断点 P-B）

**目标**：让 Researcher 在会话内把检索结果显式存为 pending 候选——
**保存仍显式、候选仍待审、promotion 仍归用户（HITL）**，三条红线不动。

**候选方案对比**：

| 方案 | 形状 | 优点 | 缺点 | 裁定 |
|---|---|---|---|---|
| A 按值回传 | 工具参数携带完整结果对象（title/doi/…），服务端重建 identity 入库 | 无状态 | **Agent 回传字段无真实性校验——幻觉编造 DOI/标题可直接进候选库**；与 HTTP 下标语义分叉 | ❌ 拒绝 |
| **B 服务端检索缓存 + 下标**（推荐） | ResearchDiscoveryService 进程内 per-project 缓存最近检索结果；`save_candidates(kind, query, resultIndexes)` 命中缓存后**复用现有 saveAcademic/ WebCandidates(results, indexes)** | 元数据只能来自 provider 真实返回（防篡改）；与 HTTP `saveAsCandidates` 语义/实现完全同构；改动最小 | 需管理缓存生命周期 | ✅ 采纳 |

**方案 B 设计要点**：

```ts
// —— 设计草案（M7.1 只冻结形状，不实现）——
// search/researchDiscoveryService.ts 增量：
interface CachedSearch {
  kind: "academic" | "web";
  query: string;                 // 缓存键成分（须与保存时精确一致）
  results: unknown[];            // FusedAcademicResult[] | WebSearchResult[]
  cachedAt: number;
}
// 进程内 Map<projectId, CachedSearch[]>；LRU 每项目 ≤ 5 次检索；
// TTL 10 分钟；不落盘（Derived in-memory，重启即失——与「检索默认
// 零持久化」红线兼容：红线约束的是 candidates.json 落盘，非进程内存）。

async saveCandidatesFromCache(
  projectId: string,
  kind: "academic" | "web",
  query: string,
  resultIndexes: number[],       // ≤ 25/次（量护栏，防滥存）
): Promise<SavedCandidatesResult>;
// 命中：直接转发现有 saveAcademicCandidates / saveWebCandidates；
// 未命中（超 TTL / 被新检索覆盖 / query 不一致）：结构化错误
//   SEARCH_CACHE_MISS（提示先调用对应 search 工具再保存），
//   不静默降级、不伪造保存成功。
```

工具层（scholarlyTools.ts 增量，注入 researcher 角色；citation 不需要）：

```ts
defineTool({
  name: "save_candidates",       // 「把检索结果存为待审候选」
  description: "将 search_papers / search_web 返回结果中选中的条目（按 index）
    显式保存为项目候选文献（pending_review，origin=academic_search/web_search）。
    保存 ≠ 入库 ≠ 证据：候选需用户审核转正；本工具不写 EvidenceStore。
    query 必须与检索时完全一致（服务端按检索缓存定位结果）。",
  parameters: Type.Object({
    kind: Type.Union([Type.Literal("academic"), Type.Literal("web")]),
    query: Type.String(),
    resultIndexes: Type.Array(Type.Number()),   // 1-25 个
  }),
  // execute → discovery.saveCandidatesFromCache(projectId, …)
  // 失败（缓存 miss / 越界）如实返回结构化 payload，不抛错打断 Agent。
})
```

**为什么不改 workflow（遵守用户红线）**：保存动作发生在 Agent 会话内
（Agent 自主决定存哪些），不需要 WorkflowOrchestrator 新 stage——
`research.idea` 的 producedOutputs 已经包含「evidence 候选」语义，候选
落盘路径（candidates.json）与 stage 产物（research.json）本就是分离的
关注点，无需耦合。

### 4.4 增量设计二：检索结果引用稳定性

`search_papers` / `search_web` 工具输出已含 `index`（0 起）——维持不变，
成为 save_candidates 的引用键。约束：index 只在「同一 query 的最近一次
检索」内有效（缓存覆盖即失效），工具 description 明示，防 Agent 拿旧
index 保存错条目（缓存 miss 错误兜底）。

### 4.5 增量设计三：Researcher prompt 接线（补断点 P-A）

`buildResearchPrompt`（ResearcherService.ts:362-405）修改面（**只改字符串
内容，不改代码结构 / 输出契约 / Runtime**）：

1. 要求 1 重写：「调研优先使用 `search_papers` 检索外部学术文献、

2. 新增检索产出指引：「检索到的高相关文献，用 `save_candidates` 保存为

## 5. Search 结果进入三层的链路（要求 4）

### 5.1 → CandidateSource：现状 + M7.1 增量

```text
现状（HTTP 唯一入口）：
  用户 → POST /research/academic-search|web-search {query, saveAsCandidates:[i]}
       → ResearchDiscoveryService.saveAcademic/WebCandidates(results, indexes)
       → CandidateStore.add（identityKey 判重：同身份 pending 合并补空，
         rejected 不判重可复现）→ sources/candidates.json（pending_review）

M7.1 增量（Agent 入口，§4.3）：
  Researcher → search_papers / search_web（结果含 index，进程内缓存）
            → save_candidates(kind, query, indexes) → 同一保存函数 → 同一落盘
```

两个入口最终汇聚到**同一个** `saveAcademicCandidates` /
`saveWebCandidates`——单一写入路径纪律（与 EvidenceStore 的
appendBatch 单点同构），无第二套候选写入口径。

### 5.2 → Literature Library：promote 幂等链路 + FullTextResolver 挂接点

```text
Candidate(pending_review) → 用户 POST /candidates/:id/promote
  → SourceImportService.promoteCandidate（幂等）
     ├─ 库内同身份 → applyMetadataMerge 只补空缺（不复制条目）
     └─ 新条目 → sources.addRecord：origin=AGENT_RETRIEVED，status=metadata_only
  → CandidateStore.markAccepted(promotedSourceId)
```

**M7.1 设计决策：FullTextResolver 的挂接点在 promote 之后（而非
discovery 保存时）**，理由：获取全文是网络重操作（下载 PDF），不应在
「用户还没确认要这篇文献」时发生；promote 表达了确认意图。形状：

```ts
// —— 设计草案（排期 §7.3；接口形状即 ADR §12 冻结稿，无改动）——
interface FullTextResolver {
  readonly name: string;                     // "unpaywall" | "arxiv" | "oa-url"
  resolve(identity: SourceIdentity): Promise<
    | { kind: "found"; url: string; source: string; license?: string }
    | { kind: "not_found" }
    | { kind: "error"; note: string }>;
}
// 编排：SourceImportService 新增 tryResolveFullText(sourceId)——
// Unpaywall(DOI) → ArxivPdf(arxivId) → OaUrl(OpenAlex oa_url) 顺序，
// 任一 found → 下载字节流 → 走既有 importPdf 管线（contentHash 判重 +
// pdfAnalyzer.setAnalysis + chunk 签名自动刷新）；
// 全部 not_found / error → 保持 metadata_only，如实记录，不阻塞不报错。
```

**Web 候选（origin=web_search）的如实边界**：identity 通常只有 canonical
URL，无 DOI/arXiv → FullTextResolver 全部 not_found → 永远 metadata_only。
这不是缺陷而是定位：Web 检索产出的是**线索**（用户据此人工获取全文/
上传 PDF），PaperTeam 不做爬虫型兜底（D-0033 §9 拒绝项维持——脆弱、重、
维护成本高；agent-search WebFallback 教训）。

### 5.3 → Evidence Pipeline：不变量维持 + 断头修复路径

**不变量（全部维持，M7.1 不触碰）**：

- SearchResult 永不直接写 EvidenceStore（discovery 链路无 EvidenceStore
  引用——researchDiscoveryService 文件头红线）；
- snippet/abstract 最高支撑 plausible（abstract 级），`verificationLevel=
  fulltext` 只能由 quote 逐字匹配 chunk 授予；
- Evidence 唯一转正通道 = 三段核验（quote 逐字 / metadata 权威裁决 /
  judge 只见真实证据），grounded 写入唯一入口 appendBatch。

**断头修复后的完整通路**（P-D 修复 = discovery 结果对 evidence 池的
合法贡献路径）：

```text
search_papers → save_candidates → [用户 promote]
  → tryResolveFullText → PDF 入库(status: available)
  → chunker（section-aware，绝不索引 abstract）
  → retrieve_library 可检索
  → Researcher propose_evidence（chunk 锚定 + 逐字 quote）
  → evidence.ground stage 三段核验 → EvidenceStore(verified)
  → EvidenceSelectionService(formal=verified+sourceId+chunkId)
  → Writer / Reviewer / Quality Gate 消费
```

**M7.1 排期裁定**：FullTextResolver 是 P-D 的唯一桥，但它是**新增网络
下载面**（新 provider 族 + 二进制下载 + PDF 管线复用），工作量与风险
独立成章——建议**独立里程碑 M7.2**（§7.3），M7.1 只交付本节的挂接点
设计 + 接口冻结（形状已由 ADR §12 冻结，无需重开）。这样切分的另一个
理由：M7.1 的三断点（P-A/P-B/P-C）修复后，discovery→候选→转正→
**用户手动上传全文**→evidence 的链路已经完整可验收（手动上传是既有
路径），FullTextResolver 是把「手动」变「自动」的增强，不是闭环前提。

### 5.4 数据流总图（M7.1 后形态）

## 6. 是否需要新 Agent（要求 5）

**结论：不需要。用 Tool 解决，零新增 Agent。**

论证（五条，按重要性）：

1. **冻结决策一致**：D-0009（角色最小化）+ D-0041（M6 冻结重申「能力
   扩展走 Tool / Layer / Gate，不开新 Agent 角色；M6 全程零新增」）。
   M7.1 若为检索新开角色，等于在冻结后第一个里程碑就重开已验证决策。
2. **检索无独立决策面**：query 生成是 Researcher research 阶段的既有
   职责（ADR §10：「检索质量依赖 chunk 化质量与查询改写——Researcher
   负责 query 生成」）；检索编排在确定性服务层（ProviderHttpClient +
   fan-out + fusion），没有任何需要独立 LLM 角色承担的判断——provider
   选择、融合、去重、健康降级全部是确定性代码。
3. **「深度调研循环」（search→read→refine 迭代）不需要新角色**：该能力
   的载体是 Researcher 的 prompt + 工具集（search + retrieve + save +
   propose 本就在同一会话），属 §4.5 prompt 工程范畴。若未来迭代式调研
   需要更长会话，调 PAPERTEAM_PI_LONG_RUN_TIMEOUT_MS / 拆 stage 即可，
   都不是开新角色的理由。
4. **工具注入矩阵已覆盖**：search_papers/search_web/lookup_paper 已注入
   researcher + citation（核验语义本属 citation），retrieve_library 已
   注入 researcher/writer/reviewer——消费侧无空位。新增角色反而制造
   第二个持有检索能力的会话面，违背权限矩阵最小化。
5. **与 M6.6 架构审计结论一致**（AGENT_ARCHITECTURE_AUDIT）：Agent 可以
   *使用*证据但*不能定义*什么是证据——检索工具消费同样适用此纪律：
   Agent 可以发起检索与保存候选，但转正（promote）与证据化（ground）
   的判定权在用户与核验管道。新 Agent 在此纪律下没有任何独占职责可领。

同时确认用户红线：不改 Runtime（零改动——工具经既有 roleCustomTools
回调注入）、不改 Workflow（零新 stage、definitions.ts 不动）、不新增
Agent（§6 全节）。
