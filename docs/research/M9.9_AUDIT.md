目标：回答任务书 Phase 0 的四个问题——Evidence Supply HITL 现状、ResearchRequirement

## 1. Evidence Supply HITL 当前实现

### 1.1 链路总览（源码级）

```
research.idea stage execute（definitions.ts:2146-2158）
  └─ candidatePending = CandidateStore.list(projectId, "pending_review").length
     → 写入 stageResults["research.idea"].candidatePending（definitions.ts:2157）
planner（buildIdeaToPaperPlan 内每步，definitions.ts:2570-2572）
  └─ planEvidenceSupply(state)（definitions.ts:2426-2433，纯函数只看 state）：
     未呈现过（"hitl.evidence_supply" ∉ stageResults）且 candidatePending ≥ 3
     （EVIDENCE_SUPPLY_MIN_PENDING，definitions.ts:2387）→ 进入 hitl.evidence_supply
hitl.evidence_supply stage（definitions.ts:2389-2424）
  └─ hitl.payload(ctx)：异步构建业务上下文（见 1.2）
  └─ Orchestrator：status=awaiting_input → checkpoint（awaiting.stageId/prompt/
     options/payload 持久化，重启不丢）→ 前端经 run.awaiting 读取
用户决策（POST /api/runs/:runId/resume，action 严格校验）
  └─ continue → applyEvidenceSupplyDecision（definitions.ts:3278-3296）：
       stageResults["hitl.evidence_supply"] = { decision, pendingCandidatesAtDecision }
       → 继续 writing.sections
  └─ cancel → run 终结（已完成阶段保留；用户去文献发现页 Promote / 入库全文后重跑）
```

边界纪律（注释明示，definitions.ts:2380-2386）：只提示不自动晋升（promote 永远是
用户显式动作，D-0033/D-0035 红线）；不是 Quality Gate（continue/cancel 由用户决定，
无自动否决）；每 run 至多一次；无候选零打扰。

### 1.2 payload（当前形状）

`evidenceSupplyStage.hitl.payload`（definitions.ts:2404-2423）在暂停时构建一次并随
checkpoint 持久化：

```ts
{
  pendingCandidates: number,          // pending_review 候选数
  verifiedEvidenceRecords: number,    // selectForWriting().formal.length
  verifiedEvidenceSources: number,    // formal 去重 sourceId 数
  pendingSample: Array<{ title, year?, doi?, arxivId?, origin }>,  // 前 5 条样本
  action: string                      // 指路文案（Promote → 全文 → 重跑 / continue）
}
```

**没有任何 requirement / coverage 信息。**

### 1.3 API

- 读取：无独立端点——payload 随 run 视图返回（`GET /api/projects/:id/runs` →
  `run.awaiting.payload`，frontend/src/types/api.ts:154-159，`Record<string, unknown>`）。
- 提交：`POST /api/runs/:runId/resume`，body `HitlDecisionInput`；evidence_supply 只
  接受 `continue` / `cancel`（definitions.ts:3278-3296，其余抛 WORKFLOW_INVALID_STATE）。
- 覆盖分析（M9.9 要接入的数据源）已有独立端点：`GET /research/coverage`（即时重算）
  与 `POST /research/coverage/analyze`（httpServer.ts:1291-1302，同规则）。

### 1.4 UI

- `HitlPanel`（frontend/src/components/project/HitlPanel.tsx）是统一 HITL 壳：
  prompt 引用块 + 按 stageId 分发的 payload renderer + 严格按 options 渲染的按钮。
- **`HitlPayload` 的 switch（HitlPanel.tsx:444-461）没有 `hitl.evidence_supply`
  分支**——落 `default: return null`，即当前 payload（含 pendingSample）**完全不渲染**，
  用户只看到 prompt 文本 + 「以当前证据继续写作」（continue，HitlPanel.tsx:147-159）
  + 「取消任务」。
- stageId 已有中文标签与时间线注册（status.ts:328、424），无需新增注册项。

### 1.5 小结

HITL 通道（checkpoint / resume / options 校验 / UI 壳）全部现成；接入研究缺口只需
两处：payload 构建器加数据 + HitlPayload 加一个 renderer 分支。**不需要新端点、
不需要动 Orchestrator。**

## 2. ResearchRequirement 当前结构

### 2.1 存储位置

`research/research.json` 顶层 plan（活动计划兼容视图）→ `plan.requirements?:
EvidenceRequirement[]`（researchPlan.ts:107）。可选字段：旧 artifact 无该字段仍可读，
所有既有消费者不受影响（与 plan 字段本身的兼容策略一致）。计划链形态下每轮 plan
各自持有自己的 requirements 副本。

`EvidenceRequirement`（researchPlan.ts:59-72）：

```ts
{ requirementId /* er-<n>，plan 内唯一 */, topic, claimType /* 6 枚举 */,
  expectedEvidenceType /* 4 枚举 */, relatedSection?, priority /* high/medium/low */,
  status /* open | waived */, note? }
```

关键设计：**status 只有 open/waived 两种持久化状态**——覆盖状态（covered/partial/
missing）永不持久化，由 Coverage Analyzer 随源数据即时派生（researchPlan.ts:50-55
注释：「不造第二个状态机」）。waived 只能经用户编辑面（PUT）设置，Agent 产出一律
归一 open。

### 2.2 生命周期

| 事件 | 行为 | 位置 |
|---|---|---|
| 创建 | Researcher Agent 输出 → `parseEvidenceRequirements` 宽容解析（单条非法丢弃不炸整体；status 重置 open；≤12 条） | researchPlan.ts:283-320 |
| 用户编辑 | `PUT /research/plan`（httpServer.ts:1430）→ `parseResearchPlanUpdateInput` + `applyResearchPlanUpdate`：requirements **整体替换**，同 requirementId 原样收编（id 稳定），waived 只能经此路径写入 | researchPlan.ts:326-327、434-502、548-554 |
| 派生新计划 | `buildDerivedPlan` 整拷来源 requirements（waived 跨轮保留——「已显式弃权」语义跨轮才诚实） | researchPlan.ts:794-798 |
| research() 重跑 | `resolvePlanChainOnRerun`：已有链原样保留（用户修改优先），Agent 新产出 plan 不落盘 | researchPlan.ts:648-659 |

### 2.3 与 ResearchPlan 的关系

requirements 是 ResearchPlan 的可选子字段，**不是独立实体**——没有独立存储、独立 id
空间（er-\<n\> 只在 plan 内唯一）、独立生命周期。查询某项目的需求 = 读 artifact →
`readPlanChain` → 活动计划的 `requirements`。

## 3. Requirement Coverage 当前输出

### 3.1 数据来源与形状

`ResearchCoverageService`（researchCoverage.ts:568-682，只读装配层）：

```
research.json（plan.requirements + plan.queries + executionHistory）
+ EvidenceStore.list（verificationStatus === "verified" → evidenceTexts；
  其余 → unverifiedEvidenceTexts，最多支撑 partial，M9.4 收紧）
+ CandidateStore.list（status === "accepted" && promotedSourceId ≠ ∅ → literatureTexts）
→ analyzeCoverage（纯函数，researchCoverage.ts:424-522）
→ ResearchCoverage.requirementCoverage: RequirementCoverageEntry[]
```

`RequirementCoverageEntry`（researchCoverage.ts:307-324）——**任务书 Phase 1 要求的
payload 字段几乎一一对应**：

| 任务书要求 | RequirementCoverageEntry 字段 | 备注 |
|---|---|---|
| requirementId | requirementId | 同名 |
| topic | topic | 同名 |
| claimType | claimType | 同名 |
| evidenceType | expectedEvidenceType | 命名差异 |
| coverageStatus | coverage | 命名差异 |
| evidenceCount | evidenceCount | 同名（verified 关联证据数） |
| missingReason | missingReason | 同名（非 covered 时的缺口描述；covered 省略） |

另有 promotedCount / relatedQueryCount / executedQueryCount / priority（可按需投影）。

判定规则（assessRequirementCoverage，researchCoverage.ts:350-399）：供给优先全序 +
≥2 内容词命中（REQUIREMENT_MIN_MATCHED_TERMS=2，M9.8 Phase 5 实测修正——单命中
会把无全文系统误判 covered）。waived 需求不进入判定，只在 overall.requirements.waived
计数。

### 3.2 是否可以直接消费

**可以，但有一处接线缺口：**

- 服务已存在且在 serviceStack 单例装配（serviceStack.ts:413，`stack.coverage`）；
- HTTP 已暴露（GET /research/coverage 即时重算，null = 无 artifact/无计划空态）；
- 前端类型 `ResearchCoverageView`（frontend/src/types/researchPlan.ts:210-224）
  **未镜像 requirementCoverage 字段**，且 DiscoveryPanel CoverageSection（只渲染
  questions 与 gaps）不渲染需求覆盖——即 M9.8 的需求覆盖目前**只有后端与测试可见，
  用户在 UI 上完全看不到**（与任务书「当前发现」一致）；
- **`WorkflowServices`（definitions.ts:144-194）不含 `coverage`**——
  serviceStack.ts:589 的 workflowServices 装配也没传。evidenceSupplyStage 的 payload
  闭包只拿得到 services，故当前 payload 构建器无法直接调用 ResearchCoverageService。

### 3.3 消费语义注意点

coverage 是**派生视图**：HITL payload 在暂停时构建一次并随 checkpoint 持久化——
用户在 Discovery 页 Promote / 上传全文后，**已暂停 run 的 payload 不会自动刷新**
（重跑研究 / 新 run 才重算）。「Coverage 更新」环节天然由派生语义满足（源数据变 →
下次分析即变），不需要任何回写动作；但 UI 文案必须如实告知「快照时点」，避免用户
以为面板数字会实时跳动。

## 4. Candidate provenance：能否记录「来自哪个 research requirement」

### 4.1 现状

`CandidateSource`（CandidateStore.ts:38-61）的 provenance 字段：

- `query?`：发现该候选的检索词（M6.3 discovery provenance；manual 添加无）；
- `origin`：academic_search / web_search / manual；
- `provider`：openalex / searxng / manual / …。

写入路径：Researcher 的 `save_candidates` 工具（scholarlyTools.ts:36-，prompt 要求
「kind 与 query 必须和检索时完全一致」，ResearcherService.ts:595）→
`discovery.saveCandidatesFromCache` → `CandidateStore.add`（同身份 pending 候选合并
时 query 只填空缺，CandidateStore.ts:187）。

**没有 requirementId 字段，也没有任何 requirement 语义的间接标记。**

### 4.2 可行性分析（两条路线）

**路线 A：不加存储字段，展示时确定性派生（推荐）。**
需求 ↔ 候选的关联用 Coverage Analyzer 同款 token 匹配（≥2 内容词命中）即时计算。
- 优点：零模型变更、零迁移、与「覆盖状态永不持久化」的 M9.8 设计完全同构；
  候选由多个 query / 多轮发现，本就不存在单一「来源需求」，派生匹配如实反映多对多；
- 缺点：匹配是词面的（纯中文需求 vs 英文标题判不关联——M9.8 已知局限，需求驱动
  query 生成的对齐率 100% 缓解了这一点：需求 → query → 候选链路里 query 文本
  承载了语义桥）。

**路线 B：CandidateSource 加可选 `requirementIds?: string[]`。**
- 优点：精确；
- 缺点：需要动 AddCandidateInput / save_candidates 工具契约 / Researcher prompt
  / 合并语义（同身份候选来自不同需求轮次如何并集）——改动面 5+ 文件，且引入
  「Agent 声明的关联」与「派生关联」两套口径并存的漂移风险；候选身份的稳定性
  （merged 候选跨轮复用）会让历史 requirementId 悬挂（需求可被用户编辑删除）。

**判定：M9.9 取路线 A。** 本里程碑的闭环只需要「用户看到缺口 → 补给 → 覆盖刷新」，
不需要逐候选的精确归因；Phase 1 payload 的 evidenceCount/missingReason 已用派生
口径回答「该需求还差多少」。路线 B 若未来有逐候选归因的真实需求再立项。

## 5. 结论：当前架构是否支持最小改造

**支持，且是纯接线级改造。** 判定依据：

| 环节 | 现状 | 最小改造 |
|---|---|---|
| 数据（需求 + 覆盖判定） | 全部现成：plan.requirements + requirementCoverage（M9.8） | 零改动 |
| 覆盖计算服务 | ResearchCoverageService 单例已装配 | **加 1 个字段**：WorkflowServices 加 `coverage`，serviceStack.workflowServices 传入（复用，非新服务） |
| HITL payload | 构建器现成（闭包持 services） | 构建器内调 `coverage.get(projectId)`，投影 requirementCoverage → payload.requirements（命名按任务书：evidenceType / coverageStatus），null 容忍（旧项目无计划 → 空数组） |
| HITL 决策 | continue/cancel 通道现成（严格校验） | 按任务书后续阶段决定是否扩展决策语义（Search/Upload/Skip）；applyEvidenceSupplyDecision 已有 stageResults 落点可记录决策上下文 |
| UI | HitlPanel 统一壳 + 按 stageId 分发 renderer | **加 1 个 case**：`hitl.evidence_supply` 的缺口列表 renderer（现有 payload 连 renderer 都没有，正是要补的洞） |
| 前端类型 | awaiting.payload 本就是 Record<string, unknown> | renderer 内部做形状收敛（与 Feasibility/Outline payload renderer 同风格，不扩 api.ts 契约） |
| Search / Upload / Skip 动作 | 全部现成：Discovery 检索与 Promote（DiscoveryPanel）、上传全文（SourcesPanel useUploadSource → sourceImport → 全文管线）、PUT /research/plan 可设 waived（Skip 的显式语义） | 零新增动作端点 |
| Coverage 更新 | 派生视图语义天然满足（源数据变 → 下次分析/下轮 HITL 即变） | 零回写代码；UI 需如实标注快照时点 |

**不触发任何任务书禁令**：无新 Agent（payload 构建器是 stage 定义内的既有异步函数）、
无新 Runtime、无新 Workflow 状态机（hitl.evidence_supply stage 已注册，planner 边
不动）、无 Vector DB / KG / Embedding / MCP / 新 Search Provider / Python 服务。

**风险与如实声明**：
1. HITL payload 是暂停时快照（§3.3）——用户补给后需重跑研究才见新覆盖，文案必须写明；
2. 覆盖判定是词面匹配（§4.2 路线 A 缺点）——纯中文需求对英文证据判缺是已知保守
   偏向（宁可判缺不强配，M9.8 定的哲学，不在本里程碑翻案）；
3. `coverage.get` 在 evidence_supply 暂停时点多读三个 store（evidence.list /
   candidates.list 已是该 payload 构建器本来就读的，plan 读 artifact 也已发生）——
   实际新增成本≈一次 JSON 读 + 纯函数，无性能疑虑；
4. 旧项目（无 requirements）payload 多一个空数组字段，前端 renderer 空态不渲染，
   零打扰语义不变。

## 6. 建议的改造清单（供任务书后续 Phase 对照）

1. backend：`WorkflowServices` + `serviceStack.workflowServices` 接入 `coverage`
   （复用 ResearchCoverageService）；
2. backend：`evidenceSupplyStage.hitl.payload` 投影 `requirements[]`
   （requirementId / topic / claimType / evidenceType / coverageStatus /
   evidenceCount / missingReason[+ priority/promotedCount 可选]）+ 汇总计数；
3. frontend：`HitlPayload` 加 `hitl.evidence_supply` renderer（缺口列表 + 快照时点
   声明 + 指路文案对齐现有 action 字段）；
4. 测试：payload 投影单测（含 null 容忍 / waived 过滤 / 命名映射）+ renderer 收敛
   单测（沿用既有 HitlPanel 测试风格）。

决策语义扩展（Search/Upload/Skip 如何进入 decision 通道与 stageResults 留档）取决于
任务书后续 Phase 的完整规格——本审计不预设。
