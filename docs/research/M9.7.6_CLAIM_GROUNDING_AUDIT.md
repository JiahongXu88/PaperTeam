## 1.1 Revision Transition 链（完整链路与 duplicate root cause）

### 链路（源码级）

```
RevisionPlanItem（revisionPlan.ts buildRevisionPlan；status=planned）
  ↓ collectPlanDirectives（definitions.ts:3422；plan.items → RevisionDirective{match, item}）
  ↓ listRevisionTargets（definitions.ts:3707；outline sections + abstract + 被引用文件）
  ↓ revision.revise 循环（definitions.ts:785-859）：
      for each target: matchedDirectives = directives.filter(d => d.match(target) !== null)
                       matchedItems → dispatchedItems.push({id, targetChanged})   ← 逐 (target × item) push
  ↓ transitions 构造（definitions.ts:878-887，确定性；只保留 plan 中仍为 planned 的 id）
  ↓ applyRevisionItemTransitions（revisionItemStatus.ts:88；重复 id → throw）
  ↓ services.reviewArtifacts.savePlan
```

第二/三处调用：

- `revision.validate`（definitions.ts:1026-1035）：`evaluateRevisionValidation` 的
  `result.items` 直接 map 自 `plan.items.filter(status === "applied")`——**plan 内 id 唯一
  则这里唯一**。
- `hitl.revision_validation`（definitions.ts:1167-1173）：`plan.items.filter(...)` map——
  按构造唯一。

**关键事实：transitions 从不来自 Writer/LLM 输出。** M9.7.5 报告 §13-1 的根因假设
（"Writer revision 输出的 transitions 对同一 plan item 产生重复 id"）与源码不符——
transitions 是编排层从 `dispatchedItems` 确定性构造的；Writer 输出根本不包含 transition。
Writer 唯一的输出契约行是 `%%%PT-OUTCOMES%%%`（外部意见执行报告，走
`splitExternalOutcomes`，与 revision item 状态机无关）。

### A. 模型为什么有机会对同一 item id 输出多个 transition？

它没有机会（见上）。真实机制是**确定性编排的多目标匹配**：

1. Reviewer finding 的 `section` 字段经常一次引用多个章节，例如（m975 Arm A r1 实物）：
   - `f-841df05ccd04`：`sections/evaluation-failure.tex（并见 sections/reasoning-acting.tex）`
   - `f-ac47c8eceb97`：`sections/introduction.tex（贡献一）与 sections/framework.tex 末段`
2. `sectionMatches`（definitions.ts:3679）是模糊匹配，含 `ref.includes(stem)`：finding 的
   section 字符串里**提到**的任何章节 stem 都会命中该 target。
3. 于是同一 plan item 匹配 ≥2 个 revision target → 循环内被 push ≥2 次 →
   `dispatchedItems` 含重复 id → transitions 重复 → throw。

**已在 m975 真实产物上复现**（`e2e/.tmp/m975/a/projects/p-8b409718e123`，脚本
`e2e/.tmp/m976-audit-repro.mjs`，用当时 manuscript 结构 rev-2 的 10 个 section 重建 target 集）：

```
r1 f-841df05ccd04 section="sections/evaluation-failure.tex（并见 sections/reasoning-acting.tex）" → matches: reasoning-acting, evaluation-failure
r1 f-ac47c8eceb97 section="sections/introduction.tex（贡献一）与 sections/framework.tex 末段"    → matches: framework, introduction
r3 f-620cfaf97662 section="sections/introduction.tex（并涉及 …conclusion.tex、architecture…）"    → matches: introduction, conclusion（现 outline 下还有 architecture）
```

两次 run 的失败 stage 记录（`0010/0011-revision.revise-a*.json`）error 均为
`revision item transitions 包含重复 id`，与上述多目标匹配一一对应。r1（w-78d9c111035c）
与 r3（w-f241d004fa71）各触发一次，transient 2/2 耗尽（确定性输入 → 重试必然复现）→
workflow.failed。**根因实锤：编排层 section 模糊匹配导致同 item 多 target 派发。**

另一次级风险：plan.items 本身 id 撞号（`findingFingerprint = hash(category|section|description)`，
两个完全相同的 finding 会撞号；m975 三个 plan 实测唯一，但该路径未设防）会让
`revision.validate` 的 transitions 重复。

### B. 当前 output contract 是否明确禁止重复？

没有。`applyRevisionItemTransitions` 的 JSDoc 只说"非法流转抛错、不做部分应用"；
没有任何文档禁止重复 id；`RevisionItemTransition` 类型也无法表达"每 id 至多一条"。
 Writer 侧输出契约（PT-OUTCOMES）与 transition 无关，无从谈起禁止。

### C. 重复是完全相同重复还是同 id 不同状态？

**完全相同状态**（两条都是 `{id, to: "applied", reason: "dispatched"}`），差异仅在元数据
`targetChanged`（该 item 在不同 target 上的确定性 diff 结果，语义为"该 item 是否产生实际
文本变化"——item 级正确值应为 OR）。没有任何"同 id 不同 to"的真实案例；唯一构造出
不同 to 的路径是 plan id 撞号（validate 调用点），那属于上游数据缺陷。

### D. transitions 的语义是"按顺序执行的状态变化"还是"最终状态声明"？

**按 id 分组的最终状态声明（declaration semantics），不是有序 replay。** 证据：

1. 三个调用点全部是"从当前状态出发对本批条目的落定声明"：revise 点全部声明
   `planned → applied`；validate 点全部声明 `applied → 终态`；HITL 点全部声明
   `rejected/needs_review → approved/needs_review`。同一批内不存在"先 A 后 B"的排序
   语义——`applyRevisionItemTransitions` 本体就是按 id 建 Map 后对 plan.items 单遍应用
   （顺序无关，`byId` 覆盖即证）。
2. 状态机（REVISION_ITEM_TRANSITIONS）不允许 `applied → applied`——若把重复的
   applied 声明当"顺序状态变化"，第二步就是非法流转；而真实语义是同一声明的重述
   （同 item 派发到多个章节文件）。
3. 元数据 `targetChanged` 的 per-target 语义（该 item 在该文件上是否产生变化）只有
   merge（OR）一种自洽解释，任何"last wins"都会丢失信息。

结论：normalization 语义必须是——**同 id 分组；声明与（本批内已到达的）状态一致 →
幂等 collapse（applied 元数据 OR-merge）；不一致但构成合法前向路径 → 有序 replay 取终态
（防御未来调用方）；不构成合法路径 → 结构化拒绝（进既有 repair/retry），绝不静默 last-wins**。

## 1.2 Claim Grounding 当前能力（已有 Claim → Evidence 结构盘点）

已存在（必须复用，不得另建平行 store）：

| 能力 | 位置 | 现状 |
| --- | --- | --- |
| Fact Reviewer 逐 claim 核验 | `ReviewerService`（fact mode）→ `FactClaimCheck{section, claim, verdict, evidenceId?, note?}` | **已是 Claim→Evidence 单向绑定结构**；verdict ∈ SUPPORTED / PARTIALLY_SUPPORTED / UNSUPPORTED / CONTRADICTED |
| verdict 归一 | `normalizeFactVerdict`（别名收窄，语义不放宽） | 完备 |
| Evidence Record | `EvidenceRecord{id, claim, quote, source{sourceId,title,doi,year}, location.chunk, verificationStatus, supportStrength, verificationLevel}` | claim / quote / source / chunk 齐备——§4 概念形式的 E012 行所需字段全部存在 |
| formal 判定 | `EvidenceSelectionService.isFormalEvidence`（verified + sourceId + chunk 锚点） | 唯一事实源，工具层同源 |
| Evidence → bib key | `EvidenceSelectionService.matchBibliographyKey`（DOI → 归一 title+年）；`resolveEvidenceCitationKey` | Writer 引用与 coverage gate 同源 |
| Citation 覆盖（key 级） | `quality/evidenceCitationCoverage.ts`（cited key 是否有 formal evidence） | key 级，**不是 claim 级** |
| verdict 计数进 gate | `ReviewSummary.scores.factVerdicts` + `unsupportedCriticalClaims` → gate `unsupported_critical_claims_zero` | 只保留聚合计数 |
| claim 明细落盘 | `reviews/review-r{round}-fact.json`（ModeReviewResult.claims） | **聚合后明细即丢失**：ReviewSummary 不带 claims，无 loader；plan/revise 均读不到 |
| claim 强度复核（修订侧） | `quality/claimStrength.ts` + revisionValidation（escalation 检测） | 已有，语义不同（强度升级检测，非 claim→evidence 绑定） |

**结论：Claim → Evidence 的判定端已存在（FactClaimCheck.verdict + evidenceId），缺的是
（a）claim 级 id / 绑定有效性的确定性整理与落盘（ClaimGroundingReport），（b）UNSUPPORTED
claim → 候选 Verified Evidence 的检索注入（revision 输入），（c）Writer 写作期的 claim
强度纪律显式化。全部可在现有结构上加，无第二套 claim store。**

## 1.3 Writer 当前事实写作约束

写作/修订 prompt 中的 Evidence 呈现（`renderEvidenceLines`，buildSectionPrompt /
buildRevisePrompt / buildOutlinePrompt 共用）：

```
- [E001]（cite: vaswani2017attention）claim 前 150 字（引文："quote 前 120 字"）
```

即 Writer **已经**看到 Evidence ID / supported claim / exact quote / citation key；缺 source
identity（title/year）与逐条"该证据能支撑什么"的强度纪律。约束现状：

- 引用纪律（M9.7.2 A/B 组）：事实性论断引用必须取 A 组（evidence-backed key）——key 级。
- 写作规则 3（buildSectionPrompt）："论述必须优先基于 Verified Evidence Context……证据
  不足时显式弱化表述或标注"——存在但**泛化**，没有把"数字/年份/性能结论/方法能力/实验
  结果/贡献描述/比较性事实"这些 claim 类型与"证据 claim 说多少写多少"的强度对应关系写明。
- 修订规则（buildRevisePrompt 3-7）：实验事实冻结、负结果不美化、claim 强度/比较方向不
  互换、不得新增数字——修订侧红线已相当完备。
- Writer 可用 `evidence_query`（formalOnly 视图）主动查证据——运行期工具已具备。

模型目前如何知道"这条 Evidence 可以支撑什么事实"？**只靠 evidence 行里的 claim 字段**。
没有任何机制强制"写下的每个事实性 claim 对应某条 evidence claim"。

## 1.4 Unsupported → Revision 链（断点定位）

```
fact.claims[verdict=UNSUPPORTED] ──(Reviewer prompt 要求)──> issues[category=fact/evidence_gap]
        ↓ aggregateReviews（claims 计数后丢弃；issues 去重保留）
buildRevisionPlan(summary.issues) → finding 条目 {problem=description, instruction=默认
        "基于现有 Evidence 修正论述；证据不足的论断弱化或删除（不允许编造）",
        relatedEvidenceIds=[issue.evidenceRef?]（单条，且是 Reviewer 引用的"问题证据"）}
        ↓ collectPlanDirectives → reviseSection(prompt: 问题 + 泛化 Evidence 快照 ≤15 条)
```

断点确认（M9.7.5 "Evidence 涨、Unsupported 不降"的直接嫌疑）：

1. **revision 只收到"这个 claim unsupported"**：plan 条目 problem 是 finding 描述文本，
   claim 原文、verdict、review finding 与 claim 的对应关系全部丢失。
2. **没有收到"哪些 Verified Evidence 可能支撑它"**：revise prompt 的 Evidence Context 是
   `usableEvidence()` 的 formal 快照（direct 优先的固定排序，前 15 条），与该 claim 无任何
   相关性筛选；`evidence_query` 工具靠 Writer 自觉，无人保证查询。
3. unsupported claim 在 plan/revise 全链路无稳定 id，跨轮不可追踪。

## 修复与设计决定（依据本审计）

- **P0 normalization 语义**（§1.1-D 结论）：分组 collapse（幂等重述）+ 合法路径 replay +
  非法冲突结构化拒绝；`applied` 元数据 OR-merge targetChanged。同时在派发源头
  （definitions.ts dispatchedItems 构造）按 id 合并，消除重复的产生源。
- **P1 全部复用**：ClaimGroundingReport = Fact Reviewer claims 的确定性整理（复用
  verdict，不新增 LLM 判定）；claim id = `c-{sha256(section|claim)[0:12]}`（派生指纹，
  非存储）；候选证据 = tokenizeText（retrieval 同源 tokenizer）对 formal evidence
  claim+quote+title 的确定性词面评分，bounded Top-5，不足阈值返回空；经
  ReviewArtifactStore 落盘 `reviews/claim-grounding-r{round}.json`；revise prompt 注入
  Repair Context（SUPPORT/WEAKEN/REMOVE 三动作 + 红线）；正文只出现 \cite（Evidence ID
  不入 manuscript）。
