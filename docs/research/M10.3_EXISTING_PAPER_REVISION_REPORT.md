# M10.3 — Existing Paper Revision 全链路激活（实现报告）

日期：2026-09-30　基线：`main @ c4a7a1c`　状态：实现 + 确定性验证完成（真实论文 live E2E 见同目录 `M10.3_REAL_PAPER_E2E.md`）

---

## 1. 目标与边界

M10.3 不是重做论文修改 Agent，而是把既有能力真正接起来：

```
Existing Paper + User Experimental Data + Figures/Notebook + Literature + Reviewer/Author Instructions
  → Existing Paper Understanding
  → M8 Research Plan / Research Loop（requirement-driven）
  → M9 Evidence Supply / Verified Evidence
  → Revision Plan（A–G 七类输入）
  → Revision（整文件/分节修订）
  → Fact / Citation Preservation + Claim Strength + Evidence Re-validation
  → Review / Quality Gate
  → Revised Paper + Revision Trace Report
```

明确不做：Browser Tool、Research Memory、DOCX、新数据库、Vector DB、Knowledge Graph、新 Agent、MCP、多模型 ensemble、自动模型 router、新图生成、重跑算法实验、上板实验、自动决定投稿期刊、修改 `D:\paper`。

## 2. 审计结论（接线的起点）

三路并行审计（existing_paper_improvement 全链路 / M8+M9 研究证据链 / M10 ingestion+vision）确认：

1. `existing_paper_improvement` 前段止于 `analyzeExistingPaper`（论文理解），**没有任何 M8 计划链接入**——文献需求无处产生，检索不发生；
2. Fact Preservation 的授权通道（`evidenceTexts` = 全库证据文本 + `improvementPlanItems`）**已天然支持 user_confirmed 证据授权**（M10.1/M10.2 层已产出该层级的证据），但改进计划条目 schema 单薄（section/action/rationale/priority），无法携带证据关联与事实变更授权；
3. 外部意见状态机没有「导入前已落实」的表达（round-1 意见会被当 pending 强行再改）；
4. Existing-Paper 项目 `syncReferencesBib` 完全 no-op——新增 evidence-backed 引用永远进不了 bib（citation.verify 判 missing → Writer 被要求删除）；
5. **单文件 LaTeX 项目（真实案例形态）在 `revision.apply` 直接失败**：`listRevisionTargets` 无 sections 时无目标，且 Writer 全文件输出被「不得含 \documentclass」的 DoD 拒绝；`buildManuscriptDigest` 对单文件只取 2000 字符（审稿/理解近乎失明）；
6. 修订报告只有内部 PT-OUTCOMES 状态，没有正式产物投影。

## 3. 实现（最小接线，全部复用既有服务）

### 3.1 新增 stage（existing_paper_improvement 前段扩展）

```
import.parse → import.baseline_build
  → import.inventory   （新，确定性）MANIFEST 案例角色映射 → research/asset-inventory.json
  → import.baseline    （新，确定性）current manuscript 事实基线 → research/revision-baseline.json
  → import.understand  （digest 改进：单文件按 \section/\subsection 分块 ≤18×2600 字符）
  → citation.verify → review.run → assessment.target
  → research.plan       （新，LLM）文献缺口 → M8 ResearchPlan（requirements 驱动 queries；只规划不检索）
  → hitl.research_plan  （新 HITL；approve → planExecution.approve；revise 带反馈重规划 ≤3）
  → research.execute    （新）批准后执行检索（结果快照回填，不自动入库）+ coverage 分析
  → hitl.evidence_supply（条件出现；复用 idea 流程 stage，requiredInputs 参数化）
                        用户在此暂停期间：save-candidates → promote → resolve-fulltext → supply-query
  → research.propose    （新，LLM+工具）从文献库全文对 requirements 提出锚定证据候选
  → evidence.ground     （复用 idea 流程 stage）三段核验（quote 逐字 / metadata / 语义 judge）→ verified
  → plan.improvement    （输入扩展）→ hitl.plan_confirm → revision.apply → 共享后段
  → revision.report     （新，确定性）收尾投影 build/revision-response.md
```

`WorkflowServices` 新增 `planExecution` 依赖（serviceStack 注入）。planner 纪律不变：检索只在计划批准后执行（M8 HITL 红线）；候选 promote 永远是用户显式动作。

### 3.2 外部意见 `already_satisfied` 终态（M10.3 §14）

- `ExternalInstructionStatus` 新增 `already_satisfied`：登记性终态——不派发（`collectExternalDirectives` 过滤）、不被 gate 复核降级（`reverifyHandledInstructions` 只动 handled）、不被派发聚合翻转；
- `POST /external-instructions` 接受 `initialStatus: "already_satisfied"`（必须携带 `statusNote` 依据，防滥用为跳过通道）；
- `buildRevisionPlan`：该状态 → skipped 条目 + note「已在当前稿落实（导入登记）」。
- 用途：CEA 第一轮 5 条意见（投稿版已按 response 落实）以真实状态入库，不强行再改。

### 3.3 改进计划条目 schema 扩展（M10.3 §12）

`ImprovementPlanItem` 新增可选字段（Writer LLM 产出 + 确定性校验）：

- `instructionId`——必须存在于系统指令清单，否则剥离；
- `relatedEvidenceIds[]`——必须存在于证据库 id 清单；
- `expectedFactChanges[{before, after, basis?}]`——授权的事实数值变更。

计划输入扩展（`plan.improvement` prompt）：**A** 原稿冻结基线要点（revision-baseline digest）、**B/E** 分层证据摘要（verified 外部文献 ↔ user_confirmed 作者实验，prompt 中明示两层用途纪律）、需求覆盖视图、外部意见摘要（含状态）、作者修订目标（run prompt）。

Fact/Citation Preservation 的 `readImprovementPlanItems` 同步消费 `expectedFactChanges`（并入授权文本 → `plan_value_correction`）。

### 3.4 证据分层的保持（M10.3 §8 核心纪律）

- `user_confirmed`（verificationLevel）+ `unverified`（status）→ `isFormalEvidence` 恒 false → 永不进入 Writer/Reviewer formal 池（不冒充外部科学事实验证）；既有测试锁定该边界，本轮新增接线测试复验；
- 其数值授权只经 Fact Preservation 的 `evidenceTexts` / 计划点名通道——修改的必须仍是**作者自己的实验事实**；
- 外部科学论断仍只能由 grounded_verified（三段核验）证据支撑。

### 3.5 bib 追加式合并（append-only）

`syncReferencesBib` 对 existing-paper 项目不再纯 no-op：正文 `\cite` 了 bib 中不存在的 key 且该 key 在 canonical bibliography 中存在**且有 formal evidence 关联**（matchBibliographyKey 对 canonical 解析）→ 确定性渲染条目**追加**到实际解析的 bib 文件末尾。既有条目逐字节不动（测试锁定）；无证据支撑的新 key 不追加（citation.verify 报 missing → 引用纪律生效）。

### 3.6 单文件 LaTeX 项目支持（真实案例形态）

- `listRevisionTargets`：无大纲且无 sections 时 main.tex 成为唯一修订目标；
- Writer `reviseSection` 新增 `wholeFile` 契约：输出完整文件（含导言区），校验反向要求 `\documentclass` + `\begin{document}` 存在；prompt 内容不截断（截断 = 丢失逐字保留义务）；
- `buildManuscriptDigest` 单文件分块（审稿/论文理解恢复可见性）；
- `revision.apply` 派发改进计划条目时以伪 `RevisionPlanItem` 携带 `relatedEvidenceIds`/`instructionId` → Writer 注入「修改前依据」（itemEvidence 池含 user_confirmed 记录）。

### 3.7 资产清单与事实基线（确定性，无 LLM）

- `import/assetInventory.ts`：MANIFEST（M10.3 案例 schema：caseVersion + assets[{packagedPath, role}]）→ source 扁平文件名按 basename 唯一匹配角色；歧义 → `ambiguous`（不猜）；域视图 current/historicalBoard/historical/feedback——**PC final 与板端 C0 绝不混域**；
- `review/revisionBaseline.ts`：表格（label/caption/行）/ 正文数字多重集 / 公式片段 / 方向性结论句 / citation keys / 图引用 / 硬件 / 占位计数 + 内容指纹——修订前冻结事实的机器可读投影（冲突检测与报告输入）。

### 3.8 Revision Trace / Author Revision Report（M10.3 §15）

`review/revisionResponse.ts`（确定性投影，无 LLM）：外部意见逐条（原文引用块 + Status + Affected section + Change made（改进计划/修订条目）+ Evidence + Conflict/Unresolved reason）+ 修订计划条目汇总（含终态）+ Revision Validation 结果 → `build/revision-response.md`。报告头明示「是 Revision Trace，不是 Response Letter」；无据可写处如实标注。

### 3.9 digest 与收尾

- `revision.report` 在 existing-paper 流程收尾（Final 或 Draft 完成路径）执行一次；
- `WorkflowDomainEventType` 新增 `revision_report.created`。

### 3.10 整文件修订噪声归一（live E2E 驱动的两处保守加固）

真实 78KB 单文件论文的整文件重排暴露两类 Fact Preservation 假阳性，均只减少
违规计数（保守方向）、不吞掉真实漂移，并由既有 + 新增测试锁定：

1. **数字 run 内部断行**（`BDD1␊00K`，␊=换行）：prose 数字提取前仅当断行两侧都是数字时连接（词边界断行 `41.8␊after` 保持原样——LaTeX 中换行即空格，语义不同）；
2. **前导宏管道**（`\newcommand{\keywords}[1]{...}` 的参数个数）：从 prose 提取中剥离（LaTeX 管道，不是论文事实）；
3. **资产清单角色词表**：真实案例 MANIFEST 使用 `experiment_result`/`deployment_result`/`evaluation_report`/`reviewer_feedback_response` 等词表——域归类按别名集映射（PC current 与板端 historical 互斥红线不变）；上传时加前缀改名的文件按**唯一后缀命中**回退匹配（多命中维持 ambiguous 不猜）。

## 6. 已知边界

1. `wholeFile` 修订对超长单文件（78KB 真实论文）依赖模型长输出能力（GLM 5.3 maxTokens 131072 可容纳）；输出被截断时按既有重试/修复路径失败——不静默截断。
2. 追加 bib 只认可 canonical bibliography 中**有 formal evidence 关联**的 key——意图与「无据新增引用为 0」一致；纯背景性新引用仍走人工编辑 bib（不在本轮授权面内）。
3. `import.inventory` 的 basename 匹配在同名资产时判 ambiguous（如两个 `README.md`）——如实登记不猜测；E2E 驱动按 MANIFEST packagedPath 上传，角色来自事实边界。
4. assoc_metrics.json 含 Python 风格 `NaN`（原始实验数据事实）——ingestion 的 JSON parser 按标准 JSON 拒绝（结构化记录通道不可用，如实失败）；E2E 驱动读取侧容错。数据本身不改。
5. 整文件 Writer 修订（GLM 5.3，单轮 8-12 分钟）超出驱动脚本原 30 分钟轮询窗口——脚本已放宽至 90 分钟；run 状态全部落盘可恢复（live 实录以 restore + 新 run 续跑验证）。
6. Writer 对「已读起来合理」的未授权改写（如 λ_smooth 段重写）不会自行恢复——多轮修订把它当作既有内容保留。这是模型纪律边界，不是守卫缺口（gate 每轮都标记）；处置见真实 E2E 报告 G1（needs_user_confirmation）。
