## 3. 逐问回答

### 3.1 当前 sectionMatches / dispatch 的真实算法是什么？

`definitions.ts:5019-5044`，纯路径/stem/key 模糊匹配：

```ts
ref = sectionRef.trim().replaceAll("\\","/").toLowerCase()
if (target.key === "abstract") return isAbstractSectionRef(ref);        // 摘要互斥分支
if (isAbstractSectionRef(ref)) return false;                            // ← 摘要类引用对一切非摘要目标直接 false
path/fileName/stem/key 比较：
  ref===path || ref===fileName || ref===stem || ref===key ||
  ref.endsWith(`/${path}`) || path.endsWith(ref) ||
  ref.includes(stem) || key.includes(ref)
```

**没有任何 heading / 标题感知**。`isAbstractSectionRef` = 引用含「摘要」或 "abstract"（`[^)]` 不限位置）。

### 3.2 Reviewer finding 中「章节名称」是什么格式？

输出契约（`ReviewerService.ts:559`）明确允许三种：`"section": "sections/xxx.tex、abstract（摘要问题归这里）或章节名"` —— **「或章节名」是 prompt 契约的一部分**。真实产物中的形态（M10.4.2/M10.4.3 A1/A2 全部真实 run）：

| 形态 | 实例 |
|---|---|
| 摘要 | `abstract`、`abstract（摘要）及 结论` |
| digest 标签复述 | `main.tex · 引言（第一段）`、`main.tex·方法/轨迹稳定性自适应损失 与 总损失函数与训练策略` |
| 父·子 / 父/子 | `方法 · 总体框架 / YOLOv11 检测与身份特征分支 / 总损失函数与训练策略`、`实验与结果/数据集介绍` |
| 编号+标题 | `方法/3.6 轨迹稳定性自适应损失 与 3.7 总损失函数` |
| 跨节 | `摘要与方法节（跨节）`、`讨论与局限性 及 车载边缘设备部署实验` |

单文件 digest 的块标签本身就带 heading（`splitSingleFileDigest`：`[main.tex · <标题>]`）——模型被系统引导用 heading 指位，而 matcher 只认路径。**契约与实现脱节。**

### 3.3 LaTeX parser 是否已保存 section/subsection/heading/source range？

**没有。** 修订链路上不存在任何持久化的 heading 结构：

- `LatexImporter`：只做扩展名白名单 + 入口识别 + 原样落盘，零解析；
- `buildManuscriptDigest`/`splitSingleFileDigest`（definitions.ts:4640-4701）：每次 review 即席用正则 `\\(?:sub)*section\*?\{[^}]*\}` 切 digest 块——**`[^}]*` 不支持嵌套花括号**（真实论文 `\subsection{…MRG\mbox{-}DTM…}` 跨行标题会被截断），且结果不落盘、派发侧不可见；
- `ingestion/textAsset.ts` 的 `latexSection`（证据摄入子系统）：行级正则、同样不支持嵌套花括号，且属另一子系统不可复用；
- `ManuscriptService` 的 `Outline`（id/file/title）：**只有写作流（outline.json）存在**；existing-paper 导入项目无 outline（`loadOutline` → null）。

### 3.4 是否已存在可复用的 ParsedDocument / manuscript structure？

派发时刻唯一可靠的结构事实源是 **`RevisionTarget.currentLatex`**（`listRevisionTargets` 组装时读入的文件内容）。heading 匹配应 grounded 在它之上（匹配到的标题物理存在于被派发文件内，天然排除「错派发到不含该标题的文件」）。无需新建 ParsedDocument——最小做法是给 target 内容加一个确定性 heading 提取器（平衡花括号 + 归一化）。

### 3.5 为什么单文件 main.tex 场景尤其容易漏派发？

单文件项目（无 \input / 无 outline）的修订目标**只有一个**：`{key:"main.tex"}`，stem="main"。于是：

1. heading 式引用（`方法/3.6 …`）不含 "main" 字样 → 8 个谓词全 false → **条目永不进入任何 Writer prompt**（`issues.length===0` → 该目标 continue → 该轮 revise 只靠无章节外部意见兜底触发）；
2. 摘要类引用（`abstract`、`摘要…`）被 `isAbstractSectionRef` 早退 **false**——而单文件项目没有独立摘要目标，摘要物理上就在 main.tex 里 → abstract 类 finding 也全部滞留（r2 有 3 条 planned abstract 条目）；
3. 多文件项目里 heading 引用可以退化成路径匹配（digest 标签是路径），单文件项目的 digest 标签偏偏是 `main.tex · 标题`——标题才是区分度所在，而 matcher 不读标题。

反向问题（偶然命中）：`ref.includes(stem)` 把一切含 "main" 的引用（`tab:main_*` 等）都吸进唯一目标；多文件场景 `path.endsWith(ref)` / `key.includes(ref)` 同样存在过宽匹配。

### 3.6 当前是否存在 false negative / false positive？

- **false negative（真实、大量）**：r1 19 条 / r2 23 条 / r3 23 条 heading 式与摘要式引用从未派发（§1 回放）。这些 finding 被 Reviewer 找到、被计划记录（planned），然后永久滞留——correctness 缺陷。
- **false positive（结构性风险）**：`ref.includes(stem)` 的偶然命中（含 "main"/含其它文件 stem 的引用被吸入）；对单文件唯一目标而言「错文件」不存在，但多文件下 stem 子串会把引用吸进错误文件；`target.key.toLowerCase().includes(ref)` 对短引用同样过宽。

### 3.7 是否还有多文件 LaTeX 场景需要兼容？

两类多文件场景，现行路径匹配必须保持：

1. **写作流项目**（outline + sections/*.tex，main.tex 为确定性组装根绝不入目标）：digest 以路径标块，引用多为 `sections/xxx.tex` 或 outline key；摘要互斥（M4.7/M4.8）语义必须保持——`revisionLoop.test.ts:229` 锁定「`main.tex（摘要）` → abstract 目标、组装根绝不被修订」。
2. **多文件导入项目**（\input 链、无 outline）：目标 = 各非 main tex + 按指令追加的 pseudo-target；M9.7.6 已处理「一个引用命中多目标」的重复 id（dispatchedItems 同 id 合并、targetChanged 跨目标 OR）。

## 4. 修复方案（Phase 2 实现依据）

分层匹配，全部确定性（无模型、无 NLP 库）：

```
0. 空 / 哨兵引用（"(global)"、"(unknown)"、空串）→ 不匹配（维持）
1. 摘要互斥分支改造（grounded）：非摘要目标遇到摘要类引用时，
   不再一律 false，而是当且仅当该目标自身内容含摘要环境（\begin{abstract}/摘要标题）
   才匹配——单文件 main.tex（摘要物理在文件内）恢复派发；
   outline 项目组装根本就不入目标、章节文件无摘要环境 → 行为不变
2. 既有路径/stem/key 匹配：逐字保留（Case C / Case F）
3. 新增 heading 匹配层（grounded in target.currentLatex）：
   a. 提取 \section/\subsection/\subsubsection/\chapter/\paragraph（平衡花括号，
      支持嵌套 \mbox{-} 与跨行标题）
   b. 双侧归一化：\mbox{X}→X、其余命令删除、连接号统一、去空白、小写
   c. 引用切段（分隔符 / · > 、 与 及 和 等 + 剥离中文/英文括号注释 + 剥离前导编号）
   d. 先「段 == 标题」精确匹配（文档序），后「归一化标题 ⊆ 归一化引用」子串兜底（标题 ≥2 字）
4. ambiguous：同一标题物理存在于多个目标 → 全部 grounded 目标派发
   （M9.7.6 同 id 合并已防重复 id；派发覆盖诊断里显式计数 multiTarget，绝不静默）
5. 无法可靠匹配 → 维持 unmatched（不伪造、不广播到整篇）
```

原型验证（frozen paper.tex 35 个 heading + §1 的 23 条 r2 MISS 引用）：heading 层命中 21/23，剩余 2 条（`abstract`、`main.tex·摘要区…`）由 grounded 摘要分支覆盖——**MISS 集合 32/32（r1+r2 去重）全覆盖**；既有 OK 集合行为不变。故意不做的：**编号→标题映射**（reviewer 编号在真实产物中已观察到与 LaTeX 实际编号错位，按编号派发有错派风险；编号+标题并存时标题段已足够命中）。

授权侧（factPreservation / citationPreservation 的 `sectionRefMatchesFile`）与归因侧（revisionValidation 的 `itemTouchesFile`）是 file 级路径匹配：fact_preserve / improvement 条目的 section 是确定性文件路径（finding.file / planner 全部输出 "main.tex"），路径层已覆盖；**归因侧 `itemTouchesFile` 需同步加 grounded heading 匹配的可选内容参数**——否则 heading 引用条目被派发应用后，其违规归因会漏看该文件（修复引入的新盲区）。授权侧维持现状（heading 引用若进入授权通道会走 fail-closed 报违规 → restore 循环，方向安全）。

# 第二部分：Provider Stall（请求长时间无任何响应，白等数百秒）

## 5. 真实模型调用链

```
WorkflowOrchestrator（stage attempt 循环；BusinessError→classifyBusinessError→
  category "timeout" 按 stage.retryable/maxAttempts 重试 —— 既有 stage 级 retry）
→ 业务服务（WriterService / ReviewerService / …）→ runtime.runAgent / startAgent
→ PiRuntimeAdapter：
   init（懒初始化）→ session（会话获取）→ queue（per-session FIFO + 全局 permit）
   → runOnSession：attachEventForwarder + 武装【唯一一个执行期 timer】
     executionTimeoutMs = input.timeoutMs ?? 配置（长任务 = longRunTimeoutMs
     默认 1,800,000ms = 30min；通用缺省 300s）→ session.prompt(...)
→ Pi SDK（pi-agent-core runLoop）：
   agent_start / turn_start（本地）→ user prompt 回声 message_start/end（本地）
   → streamFunction（provider HTTP 流）→ provider 首个流事件才触发
     assistant message_start → message_update（thinking/text/toolcall delta 流）
     → message_end → 工具执行 → 下一轮 → agent_end（willRetry = Pi 级重试）
```

关键事实（pi-agent-core `agent-loop.js` 源码确认）：

- **assistant `message_start` 在 provider 返回的第一个流事件（`case "start"`）时才发出**——它就是「provider 活着」的第一信号；reasoning/thinking delta 走 `message_update`，同为有效 activity；
- user prompt 的 `message_start/message_end` 是**本地回声**（role=user），不是 provider activity——watchdog 必须按 `event.message.role === "assistant"` 区分（现有 `state.sawPiEvents` 不区分，不可复用）；
- `tool_execution_*` 是本地工具执行，不是 provider activity；
- Pi 自身的 auto-retry（`auto_retry_start` / `agent_end.willRetry`）**由 provider 错误事件触发**——挂起（0 事件）不产生错误事件，因此**不会**触发任何既有重试。

## 6. M10.4.1 的 900s 挂起定位在哪一层

可观测事实：plan.improvement 第 1 次尝试，请求发出后约 900s 无任何 model turn 输出（0-turn），最终由 WorkflowOrchestrator 的 stage 无进展 deadline（`DEFAULT_STAGE_TIMEOUT_MS` = 900s）abort。卡点在 provider 请求发出之后、任何 assistant 流事件之前——**provider 侧内部原因不可观测**（本分析只声明「provider request 长时间无 activity」，不虚构厂商内部归因）。结构上：从 `session.prompt` 到 provider 首个流事件之间，Runtime 只有整体 execution timer（长任务 30min）一道防线，stage deadline（15min）先行兜底——一次 0-activity 挂起白等 15~30 分钟，且 Pi 自身的 auto-retry 需要 provider 错误事件触发，挂起（0 事件）不会触发任何既有重试。

## 7. Watchdog 设计（Phase 4 实现依据）

**First Activity Watchdog**：`runOnSession` 武装 execution timer 的同时再武装一个 first-activity timer；事件转发器观测到**第一条 assistant 消息事件**（message_start/update/end 且 role=assistant）即解除。

| 需求 | 实现口径 |
|---|---|
| 长生成不误杀 | watchdog 只管「首条 activity 之前」；一旦解除，后续生成只受既有 executionTimeoutMs 约束（Writer 合法长生成 459s+ 不受影响） |
| reasoning 前置不误杀 | assistant `message_start` 在 provider 首个流事件即发（先于正文 token）；thinking delta 亦为 activity——「首条有效 activity」不是「首个可见文本 token」 |
| 用户 cancel 优先 | 复用 first-wins `abortInitiator`（timer 回调检查 `state.settled \|\| abortInitiator !== undefined`；cancelRun 同条链路） |
| 不重复 retry | watchdog 只 abort + 抛 `AgentTimeoutError(phase="first_activity")` → settle timed_out（errorCode=FIRST_ACTIVITY_TIMEOUT，沿用 `${PHASE}_TIMEOUT` 体系）→ 交既有 stage retry；不新增第二套 retry |
| 不泄漏 timer / close 清理 | 与 execution timer 同一 try/finally clearTimeout + unref；Runtime close 走 cancel/settle 路径自然清掉 |
| 可观测 | trace：agent.task span 记 `task.firstActivityMs`；model.turn span 记 `model.ttfbMs`（距上一 activity 的间隔）；watchdog 触发记 task.errorCode=FIRST_ACTIVITY_TIMEOUT + threshold/elapsed |

**默认值依据**：现有 run-trace.json 只有 span 级 start/end（model.turn 从 assistant message_start 起算），**不含 TTFB 数据**——按任务纪律「先新增 instrumentation，不要乱猜」：本次随 watchdog 落地 `task.firstActivityMs` / `model.ttfbMs` 采集，默认阈值取保守值 180,000ms（3 分钟，env `PAPERTEAM_PI_FIRST_ACTIVITY_TIMEOUT_MS`，0=关闭）。依据：message_start = provider 首个流块（TTFB），与生成长度无关（正常量级为秒级；M10.4.0 全部 79 次 model turn 均正常完成，最慢单 turn 459s 是完整生成而非 TTFB）；3 分钟 = 典型 TTFB 的 >60× 裕量，同时把 30min 白等压缩到 3min。真实 E2E（Phase 7）采集到的 firstActivityMs 分布将回填验证该默认值的裕量，如分布显示裕量不足再上调。

**边界（如实声明）**：watchdog 只覆盖「本 run 首个 provider 请求」的挂起；agent loop 中途（首 activity 之后）的下一轮请求挂起仍由整体 executionTimeoutMs 兜底（per-turn watchdog 会改变长生成的超时语义，超出本里程碑边界）。
