# M9.9 Evidence Supply Decision Integration

日期：2026-09-24 ｜ 基线：main @ 7c57f7c（M9.8 之后） ｜ 审计：[M9.9_AUDIT.md](M9.9_AUDIT.md)

## 1. M9.8 遗留问题

M9.8 交付了 EvidenceRequirement 模型（plan.requirements，预写证据需求）与
requirementCoverage 分析（Coverage Analyzer 的供给优先三态派生视图），并经 A/B
验证了「需求驱动检索词生成」（12 需求 100% high/medium linkage）与「未覆盖需求
预测 unsupported claim」（88.9% 命中）。

遗留断点：**这些信息只存在于内部数据**——

- requirementCoverage 只有后端与测试可见：前端 `ResearchCoverageView` 未镜像该
  字段，DiscoveryPanel 覆盖分析区只渲染 questions 与 gaps（审计 §3.2）；
- Evidence Supply HITL（M9.7.4）payload 只含候选/证据规模计数，无任何需求信息，
  且 `HitlPayload` 渲染器 switch 没有 `hitl.evidence_supply` 分支——该节点连
  既有 payload 都不渲染（审计 §1.4）；
- 用户因此无法在供给决策点上回答三个问题：缺什么类型的资料、为什么需要、
  如何补齐。

## 2. 为什么需要 Evidence Supply Integration

Evidence Supply HITL 是产品里唯一一个「用户面对证据缺口做供给决策」的停靠点
（研究完成、写作未开始）。缺口信息（M9.8）与决策点（M9.7.4）在数据上已经相邻，
在产品上却互不相见——用户看到的是「有 10 篇待审候选」，不是「成稿还缺 MetaGPT
机制与评测基准两类证据」。

M9.9 把两者接成闭环，全程复用既有组件，不加任何新架构：

```
ResearchPlan.requirements（M9.8）
  → requirementCoverage（Coverage Analyzer 派生，M9.8）
  → Evidence Supply HITL payload（本次接线）
  → 用户决策：补充检索（Search）/ 上传论文（Upload）/ 跳过（Skip）
  → Candidate（provenance 记录来源需求）→ FullText → Evidence
  → Coverage 更新（派生视图随源数据即时重算——无回写代码）
```

## 3. 架构设计

冻结规则全部遵守：无新 Agent / Runtime / Workflow 状态机 / Vector DB / KG /
Embedding / MCP / 新 Search Provider / Python 服务。`hitl.evidence_supply`
stage、planner 边（每 run 至多一次、候选 ≥3）、continue/cancel 决策契约全部不动。

### 3.1 数据流（全部只读派生 + 既有用户动作端点）

| 环节 | 复用组件 | M9.9 改动 |
|---|---|---|
| 缺口呈现 | ResearchCoverageService.get | WorkflowServices 接入 `coverage`（此前未传入 workflowServices，审计 §3.2 的唯一接线缺口） |
| payload | evidenceSupplyStage.hitl.payload | 投影 requirementCoverage → `requirements[]`（旧项目无计划 → 整节省略） |
| UI | HitlPanel 统一壳 | `HitlPayload` 增加 `hitl.evidence_supply` 分支 + 三动作 |
| Search | ResearchPlan query 生成 + 计划批准/执行 + 快照保存候选 | 新端点只做「追加查询进计划」，不执行 |
| Upload | SourceStore 上传 → PDF 分析 → retrieval | 仅前端导航（onOpenTab("sources")） |
| Skip | PUT /research/plan（M9.8 整体替换语义，waived 唯一入口） | 前端读活计划做 read-modify-write |
| Coverage 更新 | 派生视图语义 | 零代码——源数据变（promote/入库/证据）→ 下次分析即变 |

### 3.2 供给检索（Phase 3）的审计性设计

`POST /research/requirements/supply-query`（body: requirementId，可选 query/kind）
把一条供给查询**追加进活动计划**而不是旁路执行：

- 查询确定性派生：`topic + 证据形态提示词`（survey → " survey"、benchmark_paper
  → " benchmark"；主题原文不翻译不改写）；用户可在计划编辑面改写；
- 新查询 status=planned、`requirementId` linkage、rationale 记录
  「需求 er-N（主题）供给检索——当前覆盖 <status>」——requirementId + generated
  query + rationale 三要素全部落在 plan 里，随计划 UI / executionHistory 可审计；
- 服务端守卫（缺口驱动纪律）：covered 需求拒绝；waived 拒绝；同需求已有 planned
  供给检索拒绝（防重复点击堆叠）；executing/done 计划拒绝（done 走「派生下一轮」
  显式路径）；
- **不执行**：执行走既有「批准 → POST /research/plan/execute → resultSnapshot →
  显式勾选保存候选」链路——无隐藏搜索、无自动无限搜索。

### 3.3 候选 provenance（Phase 4，最小存储）

`CandidateSource` / `AddCandidateInput` 增加可选扁平字段 `requirementId?: string`
（与 query/origin/provider 同风格的 provenance 字段，不复制需求元数据、不改
CandidateStore 核心职责；旧数据兼容——可选字段）。写入唯一路径：从需求供给检索
的执行快照保存候选时，HTTP 层按 execution 条目的 (planId, queryId) 在计划链上
查回该查询的 requirementId，服务端记录（调用方不可按值伪造）。同身份合并时与
query 同策略：只填空缺。

> 与审计 §4.2 路线 A（纯派生、零存储）的取舍：任务书 Phase 4 明确要求候选可
> 记录来源需求。采用最小存储后，「检索了什么」在 plan、「搜到了什么并存了什么」
> 在 candidate.requirementId，两端口径同源（都来自供给查询），无第二套判定。

### 3.4 Evidence Boundary（不变式核查）

Search Result ≠ Candidate ≠ Literature ≠ Verified Evidence 链路原样：供给查询
追加只是计划意图；执行只回填 resultCount/快照；候选保存仍是用户显式勾选
（pending_review）；promote 仍是用户显式动作；waived 只能来自用户 PUT。工作流
零自动晋升（evidenceSupply.test.ts 既有断言不变且通过）。

## 4. 实现细节

**Backend**

- `agents/researchPlan.ts`：`ResearchPlanQuery.requirementId?`；编辑合并同 queryId
  继承 linkage（与 resultCount 同策略，PUT 输入不接受该字段——系统记录不可伪造）；
  `buildRequirementSupplyQuery` / `appendRequirementSupplyQuery` 纯函数（含全部
  守卫）。
- `agents/ResearcherService.ts`：`supplyRequirementQuery`（读 artifact → 活动计划
  追加 → 链中原位替换 → 写回；与 updateResearchPlan 同模式）。
- `workflow/definitions.ts`：`WorkflowServices.coverage`；payload 投影
  `requirements[]`（requirementId / topic / claimType / **evidenceType** /
  **coverageStatus** / evidenceCount / promotedCount / priority / missingReason）

- `serviceStack.ts`：workflowServices 传入既有单例 `coverage`。
- `httpServer.ts`：`POST /research/requirements/supply-query`（covered 守卫在 HTTP
  层基于 Coverage Analyzer 派生结果）；`/execution-results/save-candidates` 增加
  `requirementIdOfQuery` 只读查回并透传。
- `sources/CandidateStore.ts` + `search/researchDiscoveryService.ts`：
  requirementId 字段与快照保存透传。

**Frontend**

- `HitlPanel.tsx`：`hitl.evidence_supply` 渲染器（规模行 + 缺口清单：覆盖徽章 /
  claimType·证据形态·优先级 chip / 证据计数 / 缺口原因 / 快照时点声明）+ 三动作：
  补充检索（POST supply-query → 跳「文献发现」批准执行）、上传论文（跳「文献库」
  既有上传表单）、跳过该需求（读活计划 → PUT requirements 置 waived + note 留痕；
  快照过期即拒绝伪造弃权）。
- `WorkflowPanel.tsx`：OpenableTab 扩宽 discovery/sources；HitlPanel 传入 onOpenTab。
- api/queries/types：`supplyRequirementQuery` + `useSupplyRequirementQuery` +
  `ResearchPlanUpdateInput.requirements`（waive 复用 PUT 整体替换语义）。

## 6. 已知限制

1. **覆盖判定的词面性（继承 M9.8）**：≥2 内容词命中是保守口径；中文需求主题
   直进学术检索词的检索面朴素（er-3 的供给查询召回的 MobileAgent 与「SOP」
   词面相关、与 MetaGPT 语义不精确相关）——宁可检索面朴素，不虚构语义改写；
   用户可在计划编辑面改写检索词。
2. **promoted 驱动的 covered 部分自指**：供给检索保存的候选，其 query 字段即
   需求派生词——promote 后 topic 词面命中既来自标题也来自 query 本身。证据级
   covered（evidenceCount>0）不受影响（仍需 verified 证据）。
3. **resolve-fulltext 可能失败**：候选 promote 后全文解析依赖公开可得性
   （本轮 S003 失败、metadata_only 如实保留）；上传路径（Case B）不受影响。
4. **HITL payload 是暂停时快照**：用户在 Discovery 页补给后，已暂停 run 的
   payload 数字不自动刷新——重跑研究 / 下次停靠才重算（UI 已声明快照时点）。
5. **计划链写入互斥**：supply-query 与 PUT /research/plan 均走 writeResearchPlanChain
   的项目队列语义，但两跳之间用户手工 PUT 理论上可交错（单用户产品、决策点
   停靠期使用，风险可忽略）。
6. **run2 的证据增量归因**：+3 verified 证据来自 run2 的 ground（含 S004 上传
   文献），不逐条区分供给候选贡献（S003 无全文故无证据贡献）。

## 7. 下一阶段建议

1. **DiscoveryPanel 覆盖区镜像 requirementCoverage**：后端 GET /research/coverage
   已返回该字段，前端补一个与 CoverageQuestionRow 同风格的渲染行即可让缺口在
   非停靠期也可见（本里程碑按任务书范围只接 HITL 面）；
2. **供给检索词的语义增强（可选）**：当前确定性派生对中文主题朴素；若真实
   使用中召回质量不足，可评估「经 Researcher 会话改写检索词」——须保持显式、
   可审计、不自动执行；
3. **FACT_PRESERVATION 基线问题**（M9.8 遗留登记）：与 M9.9 无关但持续阻断
   idea_to_paper 完整走通（m98 Arm A / 本仓 build.draft 均受影响），建议独立
   立项；
4. **evidenceType 的 UI 语义细分**：缺口行已展示期望证据形态，后续可在 Discovery
   检索面板按 evidenceType 预设过滤（如 benchmark_paper 限定数据集类检索词）。
