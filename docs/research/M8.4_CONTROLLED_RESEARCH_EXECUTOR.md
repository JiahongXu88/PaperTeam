# M8.4 — Controlled Multi-round Research Executor 实施报告

- 日期：2026-09-21
- 状态：已完成（实现 + 测试 + 文档；backend / frontend 全量测试、build、typecheck 通过）
- 范围：把 M8.1（Research Plan）/ M8.2（Plan Execution）/ M8.3.1（Iteration）/
  M8.3.2（Coverage）/ M8.3.3（Research Gap + HITL + Loop Policy）编排成真正
  可运行的 **Controlled Research Loop**——一个带 HITL 断点、策略边界与崩溃
  恢复的状态机。**Loop 只负责状态编排**：检索 / 覆盖 / 缺口 / 派生逻辑全部
  委托既有服务，零复制。
- 冻结规则遵守声明：**不新增 Agent**（纯 Service + 纯函数）、**不修改 Runtime /
  Workflow Orchestrator**（不进 workflowServices）、**不引入 RAG / Vector DB /
  MCP / 新 Provider / CLI**、**Evidence 链路原样**（Loop 不触碰 EvidenceStore /
  CandidateStore / SourceStore；Retrieved ≠ Candidate ≠ Literature ≠ Verified
  Evidence 分层不混写）。

## 1. 目标

M8.3.3 交付了循环的全部构件（计划 / 执行 / 覆盖 / 缺口 / 决策 / 策略），但
构件之间靠用户手动串接——每一步都是独立 HTTP 调用，没有统一的循环状态、
轮次历史与策略执行。M8.4 补上编排层：

```
Research Plan（draft）
   ↓
Plan Approval HITL ────────────── 断点一：Loop 停等用户（POST /loop/plan/approve）
   ↓
Execute（委托 M8.2）
   ↓
Coverage（委托 M8.3.2）
   ↓
Loop Policy Evaluation（真实消费 ResearchLoopPolicy）
   ↓ 命中停止条件 / 无缺口
   completed ←──────────────────── 终态（stopReason 落盘）
   ↓ 继续
Research Gap（委托 M8.3.3 视图；用户经既有 accept / reject 决策）
   ↓
Human Decision ────────────────── 断点二：Loop 停等用户
   ↓
Derive Next Plan（委托 M8.3.3 gaps.derive → M8.3.1 单一派生）
   ↓
awaiting_plan_approval ────────── 断点三：派生后停等下一轮批准，绝不自动执行
   ↓（用户批准 → 下一轮）
```

## 2. Loop 架构（`backend/src/agents/researchLoop.ts`）

```
ResearchLoopService（M8.4，新增；纯状态编排层）
        │ start        → 校验 draft 计划 → awaiting_plan_approval
        │ approvePlan  → 策略硬校验 → 委托 M8.2 approve → 登记轮次
        │                → execute（委托 M8.2）→ coverage（委托 M8.3.2）
        │                → 策略判定 → awaiting_gap_decision | completed
        │ resume       → 按磁盘事实重算续跑点（崩溃恢复 / 重试）
        │ cancel       → 任何非终态 → cancelled
        │ deriveNextPlan → 委托 M8.3.3 gaps.derive → awaiting_plan_approval
        ▼
research.json 顶层 loop?: ResearchLoopState（状态机 + 轮次历史）
```

依赖注入只有三个既有服务的委托入口 + ProjectStore：

- `planExecution`（M8.2）：approve / execute——检索执行与状态回填的唯一路径；
- `coverage`（M8.3.2）：analyze——覆盖判定唯一路径；
- `gaps`（M8.3.3）：list / derive——缺口决策视图与派生唯一路径
  （**accept / reject 永不经 Loop**，用户直接走既有 API，Loop 只读结果）。

持久化挂 `research.json` 顶层可选 `loop` 字段（经 `writeResearchLoopState`
单一写入口；research() 重跑与 existing-paper 重跑原样保留——与 gaps /
loopPolicy 同纪律）。写侧每次先重读 artifact 再展开写回，其余字段不冲掉。

## 3. State Machine

| status | 语义 | 进入 | 退出 |
| --- | --- | --- | --- |
| `awaiting_plan_approval` | 停等用户批准活动 draft 计划 | start / deriveNextPlan | approvePlan（用户） |
| `running` | 轮次执行中（execute → coverage；磁盘可见性标记） | approvePlan / resume | 覆盖判定完成 / 错误 / cancel |
| `awaiting_gap_decision` | 轮次完成且策略允许继续；停等用户对缺口 accept/reject | 覆盖判定（缺口 > 0） | deriveNextPlan / cancel |
| `awaiting_retry` | 轮次被可恢复错误打断（BusinessError，如 executing 残留） | runRound catch | resume（重试）/ cancel |
| `failed` | 轮次被非业务异常打断 | runRound catch | resume / cancel |
| `completed` | 终态：策略停止或无缺口（stopReason 落盘） | 覆盖判定 | —（可重新 start） |
| `cancelled` | 终态：用户显式终止 | cancel | —（可重新 start） |

轮次历史（Round History）逐轮登记：`approvedAt` → `execution`（M8.2 真实
计数）→ `coverage`（M8.3.2 真实计数）→ `decided`（派生时点 accepted /
rejected 快照）→ `derivedPlanId`。

**崩溃恢复（resume）只依据磁盘事实重算**，不依赖进程内存：

| 磁盘事实（活动计划状态） | resume 行为 |
| --- | --- |
| done（执行已完成落盘） | 从 executionHistory 按 planId 回填执行快照（真实计数）→ 继续覆盖分析 |
| approved（批准后 / 上次中断前） | 重试执行 |
| executing（进程重启残留） | awaiting_retry + 修复提示（与 M8.2 的 409 提示同口径） |
| 被更高迭代号计划替换（用户手动派生） | 采纳为待批计划 → awaiting_plan_approval |
| 被切走（迭代号不高于本轮） | 409 指引（先 activate 回本轮计划或 cancel） |

另有批准崩溃窗口恢复：loop 在 awaiting_plan_approval 而计划已是 approved
（批准落盘、轮次未登记，或用户经既有 API 直接批准）→ resume 采纳并续跑
（策略硬校验照做）。

并发纪律：

- **进行中守卫**（同步 check-and-add）：轮次执行中并发 resume / 重复 approve
  → 409 LOOP_INVALID_STATE；
- **项目级写互斥**（promise 链）：所有 loop 字段落盘串行化，cancel 的
  标记+落盘与轮任务的检查+落盘严格串行（锁内检查取消标记，不丢更新）；
- cancel 不中断进行中的单条检索（已发生的检索是真实结果），轮任务在下一个
  落盘点停止推进与写盘。

## 4. HITL 边界（全部停等用户，绝不自动推进）

- **draft → approve 不自动**：approvePlan 是用户显式入口；Loop 自身永不在
  start / deriveNextPlan / resume 的常规路径中调用 approve（唯一例外是
  resume 的崩溃窗口恢复——**批准已经是磁盘事实**时采纳，不代批）；
- **accept / reject gap 不自动**：Loop 只读缺口决策视图（gaps.list），
  accept / reject 走既有 M8.3.3 API（DiscoveryPanel 既有按钮不变）；
- **derive 后不自动执行**：deriveNextPlan 落在 awaiting_plan_approval，
  下一轮批准仍是用户动作；
- **没有决策就没有下一轮**：零 accepted 缺口时 deriveNextPlan → 409
  （用户应继续决策，或 cancel 结束循环）。

## 5. Loop Policy（真实消费，M8.3.3 预注册边界的执行层）

| 策略字段 | 消费点 | 行为 |
| --- | --- | --- |
| `maxQueriesPerIteration` | 批准检查点硬校验 | planned 检索数超限 → 409 LOOP_POLICY_VIOLATION（计划保持 draft，不静默截断） |
| `maxTotalQueries`（**M8.4 最小扩展**，默认 100，上限 500） | 批准前：已消耗 + planned > 预算 → 409；轮后：消耗 ≥ 预算 → completed(`budget_exceeded`) | 消耗 = Σ 轮次 executed + failed（每条都是真实发生过的 provider 调用；**不估算、不伪造 token 成本**） |
| `maxIterations` | 轮后判定：计划链最大迭代号 ≥ 上限 → completed(`iteration_limit`)；deriveNextPlan 策略复检 | 以 iterationId 计划链的真实迭代号为准 |
| `no_new_coverage` | 轮后判定：本轮 covered ≤ 上轮（首轮豁免——首轮建立基线）→ completed(`no_new_coverage`) | 与上一轮 coverage 快照比较 |
| `stopConditions` | 声明式开关：未列出的条件不参与判定 | — |

结构完成（不受开关约束）：覆盖缺口为 0 → completed(`no_open_gaps`)——
没有可决策对象。

## 6. API（符合既有 httpServer 风格）

| 方法 / 路径 | 语义 |
| --- | --- |
| `GET  /api/projects/:id/research/loop` | 循环状态（未创建 → `{loop:null}` 空态） |
| `POST /api/projects/:id/research/loop/start` | draft 计划 → awaiting_plan_approval |
| `POST /api/projects/:id/research/loop/plan/approve` | HITL 批准 + 同步执行一轮（响应 200 携带落点状态：awaiting_gap_decision / completed / awaiting_retry / failed / cancelled） |
| `POST /api/projects/:id/research/loop/derive-next` | 请求体可选 `{gapId?, questions?, queries?}`（多 accepted 缺口须指定 gapId；questions / queries 透传 M8.3.3 改写入口）→ `{loop, plan}` |
| `POST /api/projects/:id/research/loop/resume` | 崩溃恢复 / 重试（无可恢复断点 → 409） |
| `POST /api/projects/:id/research/loop/cancel` | 任何非终态 → cancelled |

新错误码：`LOOP_INVALID_STATE`（409，状态机非法转移 / 并发守卫）、
`LOOP_POLICY_VIOLATION`（409，策略硬校验）。

前端零改动（Loop 是后端编排层；既有 DiscoveryPanel 的计划批准 / 执行 /
缺口决策按钮与 M8.4 API 兼容共存——缺口 accept 走既有 API，Loop 只读决策）。

## 8. 已知限制（如实登记，不顺手修）

1. **直连端点干预计划状态**：循环进行中用户经既有 `/research/plan/approve`、
   `/research/plan/execute` 直接操作活动计划，Loop 只在 resume 的
   approved/done 路径上部分对齐；其余形态（如直接执行完下一轮草案后停留在
   awaiting_plan_approval）需 cancel 重启。缓解：resume 按磁盘事实重算，
   常见崩溃窗口均可恢复。
2. **检索执行不可中断**：cancel 只阻止后续步骤与写盘，进行中的单条 provider
   调用自然完成（其结果已如实入 executionHistory / plan 回填）。
3. **轮次为同步 HTTP 执行**：一轮 = approvePlan 请求内完成 execute（真实
   检索，分钟级）+ coverage。与 M8.2 `/plan/execute` 的同步语义一致；未来
   如需后台化，state machine 与磁盘状态已就绪（running 是可见性标记）。
4. **research.json 单文件读-改-写**：Loop 的写互斥只覆盖 Loop 自身落盘；
   既有各服务（PUT plan / gaps 决策 / plan 链）与 Loop 并发写同一文件的
   窗口与 M8.3.3 相同（单用户节奏下无观察到的损坏；CandidateStore 的
   并发写坏 candidates.json 是登记在案的 P0，属 M8.5 / M9 范围）。
5. **真实验收已发现的五个问题不在本里程碑范围**（进入 M8.5 / M9）：
   CandidateStore 并发写坏 candidates.json、SearXNG 部署、Search Result →
   Candidate 自动衔接、FullText → Verified Evidence、Research Memory。
