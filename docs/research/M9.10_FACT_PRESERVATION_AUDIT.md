## 1. Revision 数据流全景

```
review.run（三路 Reviewer LLM：fact/academic/style）
  → ReviewAggregator.aggregateReviews（确定性去重：category|section|description）
  → ReviewSummary（reviews/summary-r{round}.json）
quality.gate（evaluateQualityGate：18 条确定性规则）
  → QualityGateResult（含 citationPreservation / factPreservation 投影）
revision.plan（buildRevisionPlan：确定性派生，无 LLM）
  → RevisionPlan（reviews/revision-plan-r{round}.json）★条目唯一事实源
revision.run（逐 target 派发 Writer.reviseSection）
  → Writer 重写章节 → 写回文件 → revisions.commit（不可变快照 rev-{n}）
  → applyRevisionItemTransitions：planned → applied（dispatched + 确定性 targetChanged）
revision.validate（evaluateRevisionValidation：四类确定性复核）
  → RevisionValidationResult（reviews/revision-validation-r{round}.json）
  → applyRevisionItemTransitions：applied → validated/rejected/needs_review
  → blocked（rejected>0 或 block 级 claim finding）→ hitl.revision_validation（approve/reject/needs_review）
citation.verify → review.run（r+1）→ quality.gate（r+1）
  → 仍未过 → revision.plan（r+1）→ revision.run ……（bounded by revisionBudget）
```

编排新鲜度（`planSharedTail`，definitions.ts:1846）：修订写入后必须先过 `revision.validate`
（`validateIdx < reviseIdx` 时优先派发），blocked 且用户未按 validationId 回答 → HITL；
之后 citation.verify → review.run → quality.gate 依次要求新于上游。

## 2. Schema 与状态机（现状）

### 2.1 RevisionPlanItem（revisionPlan.ts:78）

| 字段 | 说明 |
|---|---|
| `id` | 确定性指纹：`f-{sha256(category\|section\|description)[0:12]}`；`external:{instructionId}`；`citation-missing:{key}:{file}`；`citation-removed:{key}:{file}`；`fact-preserve:{file}:{n}`；`build-error:latest`；`gate:{rule}` |
| `kind` | external_instruction / review_finding / citation_missing / citation_removed / fact_preserve / build_error / gate_blocker |
| `status` | planned / skipped / applied / validated / rejected / needs_review / approved |
| `instruction` | 派发给 Writer 的修订指令文本（≈ ReviewIssue.suggestedAction，缺省按 category 模板） |
| `needsEvidence` | 证据不足类：只允许弱化/删除，不允许编造 |
| `riskLevel` | 确定性派生：fact/citation/external = high，major = medium，表达类 low |
| `relatedEvidenceIds` | finding.evidenceRef 或 bib key ↔ evidence 链接（evidenceLinks 注入） |
| `appliedRevision` / `targetChanged` | applied 元数据（验证对齐 / 不采信 Writer 自称） |

### 2.2 状态机（revisionItemStatus.ts:21）

```
planned ──→ applied ──→ validated（终态）
   │           ├─────→ rejected ──→ planned（重派发）/ approved / needs_review
   │           └─────→ needs_review ──→ validated / rejected / approved
   └──→ skipped（终态）
```
非法流转确定性抛错（原子性：不做部分应用）。

### 2.3 RevisionPlanItemTransition（id + to + reason + applied 元数据）

三个调用点（全部由**代码**构造，Writer/LLM 不直接产出 transition）：
1. `revision.run`（definitions.ts:945）：dispatchedItems → applied。M9.7.6 P0 已在派发侧去重（同 id 只记一次，targetChanged 跨目标 OR）。
2. `revision.validate`（definitions.ts:1092）：applied 条目 → validated/rejected/needs_review。
3. `hitl.revision_validation` 决策（definitions.ts:1230）：rejected/needs_review → approved/needs_review。

### 2.4 duplicate-id 现有防线（M9.7.6 P0）

`normalizeRevisionItemTransitions`（revisionItemStatus.ts:130）：
- 同 id 幂等重述 → collapse（applied 元数据合并：targetChanged OR / appliedRevision max / appliedAt 首）；
- 合法前向路径（planned→applied→validated 依序）→ replay，终态生效；
- 无法构成合法路径（如 applied 与 rejected 并列）→ `conflicts` → 抛错（进既有 repair/retry）；
- 诊断信息 `normalization`（duplicateIds / originalSequences / 计数）随结果返回。

**残余缺口（Phase 1 修复面）**：
- G1：抛错为普通 `Error`（字符串拼接），非结构化错误——stage 失败分类 / 修复循环拿不到机器可读的违规清单；
- G2：**计划本体**（plan.items 内部）无重复 id / 非法 status 的 schema 校验——聚合层去重保护了 finding 通道，但 `buildRevisionPlan` 的多通道合流（external + finding + citation + fact + build + gate）没有终态断言；一旦上游输入变化产生同 id 条目，会在 validate 阶段以「矛盾序列」形式晚爆；
- G3：**缺失 transition 无检测**——`revision.validate` 后计划中仍残留 `applied` 状态条目（复核漏判/编排跳步）时无任何断言，条目会无声悬置（gate 只消费 validation result，不看计划残留）。

### 2.5 RevisionValidationResult（revisionValidation.ts:61）

四类复核（纯确定性）：
1. **Fact Preservation**（复用 M5.6）→ 违规文件命中条目 rejected（`fact_preservation_violation`）；
2. **Citation Preservation**（复用 M5.6）→ `unexpectedRemoved` 命中文件条目 rejected（`citation_removal_unauthorized`）；
3. **Claim Strength**（M6.7）→ block 级 rejected / warning 级 needs_review（`claim_strength_escalation`）；
4. **Evidence Re-validation** → 关联证据失效 needs_review（`evidence_stale`）。

归因粒度 = 文件级（`itemTouchesFile`：路径/文件名/stem/包含；摘要归 main.tex）。

**缺口（Phase 4 修复面）**：条目结果只有 `reasonCodes/reasons`（人读句子），无 `category` 分类、
无结构化 `evidence`（before/after 片段）、无 rejectedItems 汇总——「rejected 16/24 为什么」
只能人工翻 gate detail 与 preservation summary 对照。HITL payload 只截 reasons[:3]。
前端 `HitlPanel` 对 `hitl.revision_validation` **无专属 renderer**（switch 落 default: null，只显示 prompt 文本）。

### 修订 prompt 的事实/引用约束（现状，WriterService.ts:899-917）

- 规则 2：受限修订不是重写，只改问题指向位置；
- 规则 3：实验事实默认冻结（数值/表格/协议/硬件/超参/公式），除非问题明确要求且给出新值依据；
- 规则 4：疑似数值错误未授权时保留原值；论断可弱化但事实不得占位化；
- 规则 5：负结果不得美化、方向不得反转；
- 规则 6：不得新增不存在的实验细节/数字/超参；冲突时报告不调和；

- CLAIM_DISCIPLINE_LINES：无证据的出口只有弱化/标注不确定/删除。

## 5. Q3 — Fact Preservation 当前检测什么（factPreservation.ts，纯事实列举）

对象：previous 快照（被审阅修订的前一修订）→ current 快照，仅 previous 已存在的文件参与（新章节文件不参与违规审查）。

| # | 检测 | reason 码 | 归类桶 |
|---|---|---|---|
| 1 | 表格同表同行同列数值变化 / 占位替换 | `table_cell` / `table_cell_placeholder` | changedFacts / placeholderRegressions |
| 2 | 整表 / 含数字整行消失 | `table_removed` / `table_row_removed` | removedFacts |
| 3 | 新增表 / 新增含数字行 | `table_added` / `table_row_added` | addedUnsupportedFacts |
| 4 | prose 数字多重集缺失（配对→值变更；未配对→删除） | `prose_number` | changedFacts / removedFacts |
| 5 | 事实型新增数字（%/带单位/量纲词后缀） | `added_number` | addedUnsupportedFacts |
| 6 | 超参/阈值赋值新增（name=value） | `hyperparameter_assignment` | addedUnsupportedFacts |
| 7 | 量纲后缀新增（71维/64路） | `added_number` | addedUnsupportedFacts |
| 8 | 数学片段多重集缺失/新增 | `formula_removed_or_changed` / `formula_added` | formulaChanges / addedUnsupportedFacts |
| 9 | 方向反转：负结果→优势 / 持平→优势 / 同指标方向对调 | `negative_to_advantage` / `parity_to_advantage` / `metric_direction_flip` | directionalChanges |
| 10 | 数据集划分表述对调（官方↔自定义） | `dataset_split_changed` | changedFacts |
| 11 | 硬件型号增删（白名单正则） | `hardware_removed` / `hardware_added` | removedFacts / addedUnsupportedFacts |
| 12 | 占位回归（待回填/TBD/TODO 增多） | `placeholder_*` | placeholderRegressions |

授权（只承认结构化依据，自由文本不构成依据）：
- 值变更：计划条目文本同时点名旧值与新值（`plan_value_correction`），或点名旧值且 Evidence 含新值（`plan_and_evidence`）；
- 值删除：needsEvidence 条目命中章节（`planned_evidence_removal`），或计划点名值+删除词（`planned_value_removal`）；
- 值新增：Evidence 或计划文本包含（`evidence` / `plan_value`）；
- 公式：计划文本含公式词（`planned_formula_change`）；方向：计划含结论方向词且命中章节（`planned_direction_change`）。

限额：每桶 cap 30；prose 循环上限 400。数字边界安全（47 不匹配 147/47.5）。

**数字 token 现状**（styleInvariants.extractNumericTokens + proseOf）：NUMBER_PATTERN 含千分位逗号与单位后缀；
proseOf 还原 `\%`、剥离 cite/ref/环境/命令名。**未归一**：全角数字（２０２２——根本不进 token）、
千分位写法差异（1,446 vs 1446）、小数尾零（45.90 vs 45.9）、全角/半角符号——这些是 false positive 的已知来源（Phase 3 修复面）。

诚实边界（代码注释自述）：保守必要条件守卫，不是语义等价证明；语义改写依赖 Reviewer 与人审。

## 6. Q4 — Citation Preservation 当前检测什么（citationPreservation.ts）

- 事实源：不可变修订快照；比较**实际被引用的 key 集合**（key 语义：同 key 引用次数变化不算删除）；
- 默认：previous 存在的 key 不得在 current 无依据消失；
- 有依据删除的四种 basis：
  1. `planned_citation_missing`（key 不在 bib，计划就是删它）；
  2. `planned_explicit_mention`（计划条目文本显式点名 `\cite{key}`）；
  3. `planned_evidence_removal`（needsEvidence 条目命中章节，且该 key 在 previous 的**全部**出现都落在这些章节内）；
  4. `improvement_plan_explicit_mention`（Existing-Paper 改进计划显式点名）；
- catastrophic：previous 有引用、current 一处不剩 → 只有显式点名的 key 才算有依据（章节级证据条目**不足以**解释全删）→ hard fail；
- 历史回归：previous/current 都 0 但基线修订有 → FAIL；
- 不可比较（无前序/快照缺失/revision.restore）→ null 中性规则，不伪造 PASS。

revisionValidation 附加：`citationDelta.added`（evidence-backed 判定，与 gate 覆盖同源）+ `removed`（authorized 标志）+ `uncoveredAddedKeys`。

## 7. Q5 — 为什么 GLM-5.3 会选择删除 citation

从 prompt、context、tool 能力三个层面分析（不评价设计，机制归因）：

### 7.1 Prompt 层：约束存在但存在可利用的解释空间
1. 规则 10 的例外子句「**除非某条问题明确要求删除该引用**」与 needsEvidence 类 instruction 的
   「证据不足的论断弱化或**删除**」（defaultInstruction/规则 2）叠加——当 Reviewer 报「该论断缺证据/
   需补引用」时，模型面临张力：「补证据」（受规则 6/9 约束，B 组不得新增、A 组可能没有覆盖该论断的
   证据）vs「弱化/删除」。在无法补证时，**删除整条论述（连带其 \cite）成为满足约束的最短路径**——
   M9.7.1 run2 的 7 个 key 正是这样消失的。
2. 规则 9b 把 B 组 key 标注为「无 verified evidence 支撑…证据不足时弱化或删除论断」——模型将 B 组引用
   视为合规负债，倾向在改写中静默丢弃（besta2024graph 等 7 key 多为该类）。
3. 「不得新增列表之外的 key」+「A 组才可支撑事实性论断」在没有合适 A 组证据时，把模型推向
   「去引用化」重写而非补引用。

### 7.2 Context 层：现有 key 集合不可见
- prompt **没有列出本章节现有引用 key 的冻结清单**；模型改写时必须从 12k 字符原文中自行记住每个
  \cite。受限修订（规则 2「只改问题指向位置」）对 GLM-5.3 的实际执行是**整节重写式**输出
  （M9.7.1 已观察：rev3/rev4 全文变化），重写过程中 key 遗漏是纯概率性丢失，无任何提示锚定。
- Writer 看不到 Citation Preservation 的判定结果（验证是事后确定性阶段），生成时无反馈回路。

### 7.3 Tool 层
- Writer 有 `evidence_query`（可查证据），但**没有引用级工具**（无「查询本节应保留 key」/「引用合法性
  预检」）；输出协议只有外部意见的 PT-OUTCOMES 行，无引用自报协议。
- M9.7.1 §11 归纳：GLM-5.3 协议遵循弱（PT-OUTCOMES 重复上报），对隐式清单（原文中的 cite）保持力
  弱于对显式清单（A/B 组白名单）——A/B 组 hallucinated=0 全零恰恰说明显式清单有效，
  而隐式「保留现有 key」失效。

**结论**：删除引用不是模型「违规越狱」，而是约束组合下的理性最短路径 + 隐式清单记忆丢失。
修复方向因此是 Phase 2 的两点：(a) 把「现有 key 集合」变成 prompt 里的**显式冻结清单**+硬规则
（预防）；(b) 确定性 validator 生成 `citation_removal_detected` 结构化拒绝（拦截——现状已具备
`citation_removal_unauthorized` 通道，需补结构化分类与报告）。
