# M8.3.1 — Research Iteration Foundation 实施报告

- 日期：2026-09-20
- 状态：已完成（实现 + 测试 + 文档；backend / frontend 全量测试、build、typecheck 通过）
- 范围：为 ResearchPlan 建立**迭代（Iteration）基础能力**——计划完成后可派生下一轮、
  可查看 / 切换历史迭代、research() 重跑不再覆盖用户计划与执行历史。
  **不新增 Agent、不改 Runtime、不改 Workflow Orchestrator、不引入 RAG/Vector
  DB/MCP/新 Provider/CLI**（M8 架构冻结规则全部遵守；Evidence 链路原样）。

## 1. 问题背景

M8.1/M8.2 后 ResearchPlan 的生命周期是单向单轮：

```
draft → approved → executing → done   （终态，无法继续）
```

两个已知缺口：

1. **无法演化**。真实科研不是一次搜索，而是「Research Question → Plan →
   Search → 发现知识缺口 → 调整研究方向 → 新 Plan → 继续搜索」的多轮循环。
   done 之后只能靠编辑旧计划加 planned 检索重走批准流，没有「下一轮」的概念，
   历史轮次的计划与执行状态也无法回看（M8.2 文档 §2.2 已登记，留给 M8.3）。
2. **重跑覆盖**。`research()` / 论文理解重跑会整体重写 research.json：用户编辑过
   的 plan（questions / queries）与 executionHistory 一并被 Agent 新输出冲掉
   （M8.2 文档「已知限制」同源问题）。

M8.3.1 一次收口两者：Iteration 是 **Research 数据模型能力**（research.json 的
计划链），不是新 Agent、不进 Workflow、不动 Evidence 链路。

### 1.1 冻结规则的落实

| 冻结规则 | 落实方式 |
| --- | --- |
| 不新增 Agent（无 Planner / Research Loop Agent） | `ResearchPlanIterationService` 是普通业务 Service（与 M8.2 执行层同风格）：不调用 `Runtime.runAgent`、无 prompt、无 Agent 会话；「发现缺口 → 派生」的判断主体是用户（HITL），不是 Agent |
| 不修改 Runtime | 零 Runtime 改动（AgentRuntime / PiRuntimeAdapter / tool injection 全部未触碰） |
| 不修改 Workflow 核心 | 不进 `workflowServices`、不加 stage：迭代是用户经 HTTP 显式触发的同步动作，与 Workflow 生命周期正交 |
| 不引入 RAG / Vector DB / MCP / 新 Provider / CLI | 只做 research.json 读改写；检索执行仍 100% 复用 M8.2 的 ResearchPlanExecutionService（其下是 ResearchDiscoveryService 既有编排），provider 装配零变化 |
| Search Result ≠ Candidate ≠ Literature ≠ Verified Evidence | 派生 / 激活 / 列出只搬移计划数据，不写 CandidateStore / SourceStore / EvidenceStore；Iteration 只管理研究计划生命周期，链路语义原样 |

实施前架构检查结论：全部为既有模块内的小步增量（一个新 Service 文件 + 领域
模型可选字段 + serviceStack 装配行 + research 资源块路由 + artifact 读写收口），
未出现需要修改 Runtime / Workflow 核心 / 破坏 Evidence 链路的情形，无需停止报告。

## 2. Iteration 模型

### 2.1 字段

`ResearchPlan`（M8.1 既有字段基础上）增加三个 iteration 字段：

```jsonc
{
  "planId": "rp-a1b2c3d4e5f6",     // 计划 id（不变；链内每轮新建）
  "iterationId": "it-0f1e2d3c4b5a", // 迭代线索 id：同一条派生链共享（首轮生成、派生继承）
  "parentPlanId": "rp-9f8e7d6c5b4a", // 派生来源（首轮计划无此字段）
  "iterationNumber": 2,             // 迭代号：首轮 = 1，派生轮 = 链内最大 + 1
  "status": "draft",                // draft | approved | executing | done（不变）
  "questions": ["..."],
  "queries": [ /* queryId / query / kind / rationale / expectedCoverage / status / resultCount? 不变 */ ],
  "createdAt": "...", "updatedAt": "..."
}
```

- `iterationId` 标识「同一次研究迭代过程」：派生链上所有 plan 共享（v1 生成、
  v2/v3 继承），为多研究线留出分组依据；当前单链场景下它只是廉价的前向字段。
- 旧 artifact（M8.1 / M8.2）没有这三个字段：**读取时归一化**——
  `iterationNumber=1`、`iterationId=planId`（稳定、无需迁移脚本），首次写回时固化。
- 语义：第一轮 `iterationNumber=1`、无 `parentPlanId`；从 v1 派生 v2 →
  `iterationNumber=2`、`parentPlanId=v1.planId`；从链内任意 done 计划（含中间轮）
  派生 → `iterationNumber=链内最大+1`（与来源无关，杜绝同号）。

### 2.2 Artifact 形态（任务四：plans + activePlanId）

research.json 顶层在 M8.1 `plan?` / M8.2 `executionHistory?` 基础上增加：

```jsonc
{
  "generatedAt": "...", "taskId": "...",
  "plan":  { /* 活动计划（兼容视图，始终 = plans 中 activePlanId 指向的条目） */ },
  "plans": [ /* 全部迭代轮次，iterationNumber 升序 */ ],
  "activePlanId": "rp-a1b2c3d4e5f6",
  "executionHistory": [ /* M8.2 执行历史；M8.3.1 起条目带 planId 归属 */ ],
  "report": { }, "evidence": [ ], "bibliography": [ ]
}
```

设计取舍（按「结合当前代码结构选择，不为抽象增加复杂度」）：

- **不废弃 `plan` 字段，而是保持它等于活动计划**。全部既有消费者
  （GET /research/plan、M8.2 执行层、M8.1/M8.2 测试、任何读 research.json 的
  外部脚本）零改动继续工作；`plan` / `plans` / `activePlanId` 三字段由**单一
  写入口** `writeResearchPlanChain` 一并产出（`planChainFields`），结构上保证
  不漂移。
- **读取归一化**：`readPlanChain` 优先读 `plans + activePlanId`（activePlanId
  缺失 / 指向不存在的 plan → 回落最新一轮，数据自愈）；否则回退旧形态单一
  `plan`（归一化为单轮链）；均无 → 空链。旧 research.json **不需要任何迁移**，
  首次被任一 M8.3.1 写入口触碰时自然升级为新形态。
- **活动计划（active plan）是唯一的操作对象**：编辑（PUT /plan）、批准
  （approve）、执行（execute）都作用于 activePlanId 指向的条目。切换入口是
  `activate`（显式）与 `derive`（新计划自动激活）；查看历史计划在 UI 层是
  只读视图切换，不改活动状态。
- 不引入「删除迭代」「并行多活动计划」等能力：链只增不改（旧计划永不被改写，
  除活动计划自身的编辑 / 状态流转），历史即审计。

## 3. Artifact Merge Strategy（任务三）

### 3.1 字段分类与规则

research.json 的字段按所有权分三类，`research()` / 论文理解重跑时按下表合并
（不再简单整体覆盖）：

| 类别 | 字段 | 重跑时 |
| --- | --- | --- |
| 生成侧（本次运行的产出） | `generatedAt`、`taskId`、`report`、`evidence`、`bibliography` | **新值替换**（刷新报告正是重跑的目的） |
| 用户可控（用户可经 PUT 编辑） | `plans`（含每轮的 questions / queries / rationale / expectedCoverage）、`activePlanId` | **原样保留**（用户修改优先） |
| 执行回填（M8.2 执行层写） | plan 内 status / resultCount、顶层 `executionHistory` | **原样保留**（执行记录是事实，不可被重跑抹掉） |

核心是纯函数 `resolvePlanChainOnRerun(existing, generated)`：

- 已有链（含旧 artifact 单轮链）→ 原样返回，**本轮 Agent 产出的 plan 不落盘**；
- 无链且 Agent 产出合法 plan → 以其初始化 iteration 1（M8.1 首跑语义保持）；
- 无链且无 plan → 空链（M8.1 旧输出契约兼容）。

「Agent 新 plan 不落盘」是有意选择：重跑的诉求通常是刷新报告（例如 HITL
反馈后重调研），若隐式改写计划链，用户编辑与执行历史又会回到被覆盖的老问题
——计划演化的入口收敛为**显式**的「编辑计划」与「派生新计划」。Agent 本轮
产出的 plan 仍在 `research()` 返回值（ResearcherResult.plan）中如实透出，用户
认可后可手工并入派生输入。这一取舍与 M8.3.2（Coverage Analyzer）的衔接见 §6。

### 3.2 一致性保证

- **单一写入口**：`writeResearchPlanChain`（ResearcherService 内）是唯一把计划
  链写回 research.json 的函数——`plan`（兼容视图）/ `plans` / `activePlanId`
  由 `planChainFields` 一次性产出；`updateResearchPlan`、approve / execute、
  derive / activate 全部经它写盘。`research()` / 论文理解重跑的整对象写入也
  改为先读旧链再合并（`...existing` 展开天然保留 existing-paper 附加字段如
  weaknesses / kind）。
- **执行历史不丢**：执行历史只在写入非空时落字段；读改写路径上 `...artifact`
  展开保证调用方没显式传历史时旧历史保留，不会被意外清空。
- **执行记录归属**：M8.3.1 起新执行条目带 `planId`（多轮迭代下可定位到具体
  计划）；旧条目无该字段，兼容读取。

## 4. API 与 UI

### 4.1 API（3 个新端点，均在既有 research 资源块内）

| 端点 | 语义 | 错误 |
| --- | --- | --- |
| `GET /api/projects/:id/research/plans` | `{plans: ResearchPlan[], activePlanId: string\|null}`（iterationNumber 升序）；无 artifact / 无计划 → 空态 | 项目不存在 404；非 GET 405 |
| `POST /api/projects/:id/research/plan/:planId/derive` | 从 **done** 计划派生下一轮：body 全可选（`{questions?, queries?}`，不接受 queryId / status）；新计划 draft、自动激活；旧计划不动 | 非 done 409 PLAN_INVALID_STATE；planId 不存在 / 无计划 / 无 artifact 404；body 非法 400；非 POST 405 |
| `POST /api/projects/:id/research/plan/:planId/activate` | 切换活动计划（幂等：目标已是活动 → 200 不写盘） | planId 不存在 / 无计划 / 无 artifact 404；非 POST 405 |

### 4.2 UI（DiscoveryPanel · ResearchPlan 区域，简单展示、不重设计）

- **迭代条**（≥2 轮时出现）：`v1 · 已完成` `v2 · 草稿（当前）`——当前活动计划
  带标记；点击历史条目 → 主区域切换为该轮内容（只读查看，不改变活动状态）；
- **查看历史计划**：历史视图下提示「正在查看历史计划 vN（非当前）」，附
  `设为当前`（activate）与 `回到当前计划`；编辑按钮在历史视图下禁用（编辑 /
  批准 / 执行只作用于当前活动计划）；
- **派生新计划**：当前活动计划 done 时出现按钮，点击即从活动计划整拷派生
  （API 支持携带新 questions / queries，UI 首版从简——派生后用既有编辑表单调整）；
  派生 / 激活失败如实呈现（不吞 409）。

## 6. 未来 M8.3.2 Coverage Analyzer 扩展（实施建议）

M8.3.2 的定位（M8 提案）：用检索结果对照 plan.questions / expectedCoverage 做
**覆盖分析**，把「发现知识缺口」从用户手工判断升级为有依据的提示。M8.3.1 已
为其备好地基，建议按以下顺序实施：

1. **数据已就绪，无需新存储**。覆盖分析的全部输入都在 artifact 里：
   `plans[].questions / queries[].expectedCoverage / status / resultCount` +
   `executionHistory[]`（带 planId 归属）。M8.3.2 第一步应实现
   `analyzeCoverage(projectId)`：对活动计划逐 query 对照 resultCount=0 /
   failed / skipped 与 expectedCoverage 文本，产出结构化的 coverage gaps
   （哪个问题没被哪条检索覆盖、哪条检索空转），**纯读函数 + 缓存在内存**，
   不新增持久化字段。
2. **派生建议 = derive 输入的预填**。Coverage Analyzer 的自然输出口是
   「基于缺口预填 derive 的 questions / queries」：M8.3.1 的 derive API 已接受
   `{questions, queries}` 覆盖输入，M8.3.2 只需一个「生成派生建议」端点或
   UI 预填，把 §3.1 中「Agent 新 plan 不落盘」的残余问题（用户手工并入）一并
   收口——建议作为 derive 的可选 body（如 `{fromCoverage: true}`）或独立
   `GET /research/plan/:planId/coverage` 供前端预填，二选一，不要两个都做。
3. **判定主体仍是 HITL**。覆盖分析是「提示」不是「动作」：Analyzer 不自动
   derive / activate / execute（与 M8.3.1 的显式生命周期一致）；缺口 → 建议 →
   用户确认派生。
4. **冻结规则延续**。Analyzer 同样是 Service + artifact 只读分析，不新增
   Agent、不进 Workflow；若需要 LLM 参与 expectedCoverage 语义比对，走既有
   Researcher Agent 的调研通道（作为 research() 的输入增强），而不是新建
   Analyzer Agent——若评审后认为必须独立 Agent，需先回到架构冻结规则重新报批。
5. **测试基线**。沿用本次的纯函数 + HTTP 两层模式（resolvePlanChainOnRerun
   的三分支测试是模板）；覆盖判定逻辑必须先写判定表测试再实现（M7.1a 预注册
   纪律）。
