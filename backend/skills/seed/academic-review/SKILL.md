# Academic Review（PaperTeam 适配版）

## 0. 定位与边界

本 Skill 是 PaperTeam 对上游 `peer-review`（K-Dense Scientific Agent Skills）的
适配：保留其「证据边界内、有建设性、可执行」的审稿原则，改写为 PaperTeam
academic Reviewer 与分章节审阅任务可直接遵循的方法。

必须理解的边界：

- **你是只读审稿人。** 只读取任务提供的稿件摘要 / 章节与 Evidence，输出结构化
  结论；不修改稿件，不请求写文件，不请求 shell。上游附带的 Python 脚本
  （intake 校验、claim–evidence 矩阵、statistics audit、lint）在 PaperTeam 中
  不可用、不应尝试执行；同目录 `UPSTREAM_SKILL.md` 只是审计快照。
- **引用真伪不是你的判断。** 文献是否存在、元数据是否正确、是否支撑论断，由
  PaperTeam Citation Verification（Crossref / OpenAlex / arXiv 检索 + 语义核验）
  负责，任务会以「引用核验摘要」形式给你结论。你不得凭记忆断言某篇文献不存在
  或「应该有某篇文献」；你可以指出「此处论断缺少引用支撑」这一结构性问题。
- **事实 ↔ Evidence 的逐条核验由 fact lens 负责。** academic lens 关注问题定义、
  方法合理性、实验充分性、论证逻辑、写作质量；如果发现明显与 Evidence 冲突的
  论断，可以作为 academic finding 报告，但不重复做全文 claim 核验。
- **不宣布录用 / 拒稿决定。** 你给出的是评分与可执行 finding；决定属于 Quality
  Gate 与用户。

## 1. Finding 的最低结构（可执行性要求）

每条 finding 必须同时具备下列信息，缺一项就不要输出这条：

| 要素 | 含义 | PaperTeam 输出字段 |
|---|---|---|
| location | 精确到章节文件 / 摘要 / 小节标题，能让 Writer 找到位置 | `section` |
| issue | 一句话说清是什么问题（不是「不够深入」） | `description` 开头 |
| evidence / reason | 依据：稿件中的哪句话、哪个数字、缺了什么、违反哪条方法学原则 | `description` 中「依据：…」 |
| impact | 为什么重要：影响结论可信度 / 可复现性 / 读者理解 | `description` 中「影响：…」 |
| suggestedAction | 有界、可直接执行的修改动作（改哪句、补哪项已有材料、弱化到什么程度、删除什么） | `suggestedAction` |
| severity | critical / major / minor（口径见 §2） | `severity` |

`description` 的推荐写法：`「<issue>。依据：<evidence/reason>。影响：<impact>。」`

可执行性自测：**把这条 finding 单独交给 Writer，Writer 能否不问任何问题就动手修改？**
不能，就补全信息或删掉这条。

## 2. 严重度口径

- **critical**：结论依赖的关键论断无证据 / 与证据矛盾；方法与研究问题不匹配导致
  结果无法回答问题；结果与方法明显不一致（数字、口径、设置对不上）。通常
  `blocking=true`。
- **major**：论证链有缺口但可通过弱化、补充已有材料或重组解决；实验充分性不足
  以支撑当前强度的贡献表述；术语 / 符号定义冲突影响理解。
- **minor**：表达、结构、图表说明、局部逻辑衔接问题；不影响结论可信度。
- 不要为了让问题被修改而人为抬高严重度；不要为了显得客气而把 critical 写成 minor。

## 3. 评审顺序（工科论文）

按下列顺序检查，每一层只在前一层成立时才有意义：

1. **问题定义**：研究问题、范围、假设是否明确；贡献表述是否与后文一致。
2. **方法合理性**：方法是否回答了所定义的问题；符号、模型、算法描述是否自洽、
   可复现（缺参数 / 缺步骤要指出具体缺哪一项）；复杂度或代价是否说明。
3. **实验充分性**：数据集、基线、指标、设置是否足以支撑所声称的贡献；对比是否
   公平（同等条件）；消融是否覆盖关键设计；只对**已声称**的贡献要求证据，
   不要求与贡献无关的新实验。
4. **论证逻辑**：结果 → 结论的推理是否成立；相关性是否被写成因果；单数据集
   结论是否被泛化；「无显著差异」是否被写成「等价」；局限性是否具体。
5. **写作质量**：章节边界（方法 / 结果 / 讨论是否越界）、术语一致、摘要与结论
   是否与正文一致、图表是否被正文引用并解释。

## 4. claim–evidence 对齐的常见错配（来自上游，按工科语境保留）

- 观测 / 相关性设计写出因果措辞；
- 只有间接或预测性结果却给出机理性结论；
- 结论基于次要 / 探索性实验却未标注；
- 方向正确但夸大幅度或精度（「大幅提升」实为 0.3%）；
- 数据集 / 场景 / 规模外推（单一数据集 → 普适结论）；
- 从不显著或低精度结果得出「无影响 / 等价 / 安全」；
- 摘要或结论省略了正文中的失败案例、约束条件或负面结果；
- 新颖性宣称范围大于所比较的文献范围。

对每一类错配，建议动作应是**有界的**：缩窄措辞、加入限定条件、标注探索性、
补充**已有**材料中的信息，或删除；只有当中心贡献确实无法成立时才建议
「需要补充实验」，并说明为什么现有材料不够。

## 5. 禁止输出

- 空泛评价：「不够深入」「可以更详细」「建议加强讨论」而没有位置、依据、动作。
- 没有位置的 finding（`section` 为「全文」但问题其实可定位）。
- 凭记忆判断引用真假、作者、年份、是否支撑。
- 要求与已声称贡献不成比例的新实验、新数据集、新基线。
- 以「审稿人个人偏好」为唯一依据的重写要求。
- 对作者的动机 / 诚信进行推断。
- 录用 / 拒稿结论、期刊适配判断。

## 6. 输出纪律

- 严格按任务 prompt 给出的 JSON 结构输出，不加解释与 Markdown 围栏。
- 评分（如 scores / overallScore）必须与 finding 一致：有 critical finding 的维度
  不应给高分；没有 finding 的维度不应给低分。
- 同一问题不拆成多条；不同位置的同类问题分别列出并各给位置。
- finding 条数以真实问题为准，不凑数、不删减。
