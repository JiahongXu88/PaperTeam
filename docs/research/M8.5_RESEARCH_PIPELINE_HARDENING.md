## 1. M8 真实验收暴露的问题（本报告修复对象）

| # | 级别 | 问题 | 验收报告出处 |
|---|------|------|--------------|
| 1 | **P0** | save_candidates 并发写损坏候选库：Researcher 在同一毫秒（15:37:17.098Z）发起 ≥4 次 save_candidates，`sources/candidates.json` 落盘为「完整文档 + 3 个残尾」的非法 JSON；此后 GET 静默空 / POST 500，候选链路对该项目阻断（规划 20 条候选仅 2 条落盘） | §4-1 |
| 2 | P1 | Search Result 可追溯性不足：计划执行的 140 条检索结果只留 `resultCount`，事后无法审计「q-1 那 10 条到底是什么」 | §4-4 |
| 3 | P1 | 真实 Web Search 环境验证不足：SearXNG 接线（配置 → provider → pipeline）缺少系统验证 | §4 全局 |
| 4 | P2 | Evidence / Artifact 链路审计不足：rerun 覆盖历史 / iteration 丢失 / loop state 丢失没有测试防线 | 验收 §6 |
| 5 | P3 | GET /sources/candidates 对损坏索引的口径与写路径不一致（读取侧掩盖损坏） | §4-7 |

**根因分析（P0，两层叠加）**：

1. **tmp 名毫秒粒度可碰撞**：`writeFileAtomic` 的 tmp 名
   `.<name>.<pid>-<Date.now()>.tmp` —— 同进程同一毫秒内的并发写共用同一 tmp
   路径，多个文件句柄（各自独立 offset）交织写同一文件 →「完整文档 + 残尾」；
2. **CandidateStore 无 per-project 串行化**：`add` / `markAccepted` /
   `markRejected` / `remove` 都是「读 list → 改 → save」的读-改-写，无互斥时
   并发调用互相覆盖（丢更新；读空列表的一方把 `{"items":[]}` 写回——
   这就是验收中「GET 静默返回空」的另一面：文件合法但数据被并发冲掉）。
   ProjectStore 有 `mutate()` 互斥，CandidateStore 没有。

## 2. CandidateStore 修复（P0）

`backend/src/sources/CandidateStore.ts` + `backend/src/util/atomic.ts` +
`backend/src/errors.ts`：

1. **项目级 promise 链互斥**（与 `ProjectStore.writeQueues` 同款）：所有
   读-改-写（`add` / `markAccepted` / `markRejected` / `remove`）经
   `enqueue(projectId, op)` 排队串行执行，后到者基于前者的落盘结果计算——
   同一项目任何时刻只有一个写操作在途；操作自身的错误原样返回调用方
   （前序失败不阻塞后继）。读取（`list` / `get`）不需要互斥：落盘是原子
   rename，读者要么看到旧文件要么看到新文件，不存在中间态。
2. **tmp 名加单调序号**：`.<name>.<pid>-<ts>-<seq>.tmp`（进程内 `tmpSequence`
   自增）——同一毫秒的并发写 tmp 路径必不相同。这是对**所有**
   `writeJsonAtomic` 使用方（project.json / checkpoint / evidence 等）的全局
   加固，不只候选库。
3. **原子写保持**：tmp → write + fsync + close → rename 原样（异常退出最多
   留下无害 tmp，目标文件永远是上一个完整版本——不存在「半个 JSON」的
   假成功）。
4. **崩溃残留 tmp 清理**：每次写成功后 best-effort 清理同目录
   `.<candidates.json>.<pid>-<ts>-<seq>.tmp` 残留（互斥保证此刻没有同文件
   在途写者，剩下的只能是历史进程异常退出残留；只匹配 candidates.json 自己
   的形态，不动其它文件）。
5. **旧 candidates.json 完全兼容**：`{items: [...]}` 形态、M6.2 旧条目
   （无 query / origin 字段）继续可读可追加；nextId 延续旧序号。

### 2.1 损坏读取的显式报错（P3 同步收口）

新增稳定错误码 `CANDIDATE_STORE_CORRUPTED`（HTTP 500）：

- 非法 JSON / 缺 items → 结构化错误，消息明确「**候选文献数据损坏……这不是
  『没有候选论文』**」，并给出恢复指引（检查 `candidates.json.corrupted-backup`
  类备份 / 手工修复）；
- 文件不存在仍是空列表（空 ≠ 损坏，两种事实不混淆）；
- 损坏期间**写入被拒绝且不覆盖现场**（修复前的 POST 不产生假成功）；
- HTTP 层（GET / POST /sources/candidates）与 Service 层同口径；前端
  DiscoveryPanel 候选区对 500 + 该错误码显示专用标题
  「候选数据损坏（不是没有候选论文）」（`utils/errors.ts` 将该码列入
  PREFER_SERVER_MESSAGE，优先展示后端的具体恢复指引）。

## 3. Search Result 可审计性（P1）

`backend/src/agents/researchPlanExecution.ts`——`PlanExecutionEntry` 两个新
**可选**字段（旧 artifact 无字段仍可读；自动 promote 仍然不做，Search
Result ≠ Candidate 边界不变）：

```ts
providers?: { provider, outcome, resultCount, latencyMs?, note? }[]
resultIdentifiers?: string[]   // doi:… / arxiv:… / url / title:…；封顶 50 条
```

- **providers**：diagnostics.providers 的最小投影——谁在何时参与了这条
  query、各自带回多少条、是否降级（不含 header / API key / 原始错误对象；
  整体失败原因仍在 `error` 字段）；
- **resultIdentifiers**：结果标识符投影（学术 DOI > arXiv > URL > 标题；
  Web = canonical URL），回答验收 §4-4 的「这次到底搜到了什么」——只是
  审计痕迹，不进任何 Store，不是候选；
- 暴露出口：`GET /api/projects/:id/research/execution-history`（只读视图，
  无 artifact → 空数组）+ DiscoveryPanel Research Plan 区的可折叠
  「执行审计」块（每条：时间 · 类型 · query · 结果数 / 失败原因 · 检索源
  摘要 · 标识留存悬停查看）。

## 4. Artifact 链路审计（P2）

对 `research/research.json` 的结论（测试防线见 §7）：**M8.1→M8.4 的数据
全链路可追，写路径互不覆盖**——

- 计划链（plans / activePlanId + plan 兼容视图）：`writeResearchPlanChain`
  单一写入口三字段同产；执行历史 / gaps 决策 / loopPolicy / loop 原样保留
  （`...artifact` 展开）；
- 循环状态：`writeResearchLoopState` 只覆盖传入字段，计划链与执行历史不丢；
- rerun（research() / existing-paper 重跑）：`resolvePlanChainOnRerun` +
  merge strategy 保持「用户可控与执行回填字段一律保留，只刷新报告侧」；
- 追溯链：Plan（链 + 状态）→ Execution（executionHistory，含 M8.5 审计
  字段）→ Coverage（派生视图按需重算，源数据 = 链 + 历史）→ Gap（gaps
  决策记录）→ Loop（loop 轮次历史：批准 / 执行快照 / 覆盖快照 / 决策 /
  derivedPlanId），一次落盘五层齐全。

## 5. Web Search 环境验证（P1）

**结论：未配置 → 明确失败；配置 → 全链接线可用。**

1. **未配置显式失败（不伪造成功）**：`WebSearchService` providers 为空 →
   结构化 `SEARCH_PROVIDER_NOT_CONFIGURED`（503）；计划执行中 web query
   如实 failed（error 入 executionHistory、条目保持 planned 可重试）——
   既有单测（searxng.test.ts #9）与 HTTP 测试（researchDiscovery.http.test.ts
   「web-search 未配置 → 503」）覆盖，本阶段全量回归通过。
2. **SearXNG JSON API 未启用（403）→ 结构化 provider_misconfigured**：
   既有 searxng.test.ts #5 覆盖。
3. **接线验证（本机无 Docker，离线可跑的真实 HTTP 假服务）**：新增
   `researchWebSearchPipeline.test.ts` —— 本地起 SearXNG-shape HTTP 服务
   （`GET /search?format=json` 最小真实形状），经 `searxngUrl` 生产装配路径
   注册 provider → 计划执行 kind=web 的 query 真实 HTTP 调用 →
   executionHistory 落 providers(searxng ok) + resultIdentifiers(canonical
   URL)。同轮 academic（openalex fake）并行可用——**academic + web 均可进入
   Research Pipeline 并留下审计痕迹**。
4. **真实 SearXNG 容器 smoke**：本机无 Docker（`docker: command not found`），
   无法启动 compose `--profile research` 的 searxng 服务——**环境限制，如实
   记录**（部署侧启动方式不变：`docker compose --profile research up -d` +

## 8. Known Limitations

1. **跨进程写互斥**：CandidateStore 互斥是**进程内**的（promise 链）。当前
   部署形态是单 backend 进程（compose 单容器），成立；若未来多进程共享同一
   projects 目录，需要文件锁（flock / lockfile）级别互斥——进 M9 评估。
2. **真实 SearXNG 容器 smoke 未执行**：本机无 Docker（§5.4）；已用离线假服务
   验证全链接线，容器级验证留给有 Docker 的部署环境。
3. **审计字段对旧 history 条目缺省**：providers / resultIdentifiers 只对
   M8.5 之后的执行回填；旧 executionHistory 条目无这两个字段（兼容读取，
   UI 相应省略）。
4. **resultIdentifiers 是投影不是全文**：回答「搜到了什么」（标识符级），
   不保存 snippet / metadata 快照——完整 Search Result 持久化是 M9 的
   Search Result → Candidate intelligent handoff 范畴。
5. **Agent 会话内检索（search_papers / search_web）不入 executionHistory**：
   审计范围是 Research Pipeline 的计划执行（M8 验收暴露的 140 条断层即来自
   此处）；Agent 交互式检索的审计依赖 save_candidates 的 provenance
   （query / provider 已落候选），无计划的裸检索不留痕——与「检索默认零
   持久化（D-0035）」红线一致。
6. **GET candidates 损坏时不自动恢复**：显式报错但不自动截断 / 恢复
   （验收报告对自建项目做过恢复性截断，那是验收者的数据操作；生产侧自动
   改写损坏文件有数据风险，保持人工修复指引）。

## 9. M9 Transition（本阶段明确不做）

以下进入 M9（来自 M8 Roadmap 与验收报告建议，本阶段零实现）：

- Search Result → Candidate intelligent handoff（智能补存）
- FullText extraction / Chunk storage（检索结果的全文链路）
- Evidence verification / Citation grounding（证据核验与引用落地）
- Research Memory（跨轮研究记忆）
- Novelty discovery（新颖性发现）

M8 至此收口：Research Plan → Approve → Execute → Coverage → Gap → Human
Decision → Derive → Multi-round Loop 的完整链路，加上本阶段的可靠性
（并发安全 / 损坏显式 / 审计可追）与验证（接线 / 边界 / 兼容），达到
「工程可长期运行」标准。
